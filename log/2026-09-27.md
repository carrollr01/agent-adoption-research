## Patterns

### 1. Catastrophe-event triggered multi-agent claims pipeline
**Source:** [Allianz Project Nemo](https://www.allianz.com/en/mediacenter/news/articles/251103-when-the-storm-clears-so-should-the-claim-queue.html) — Allianz Australia's first production agentic system, launched July 2025, now expanded; handles food spoilage claims under AUD$500 following storm events.
**Mechanism:** A severe weather event plus an inbound spoilage claim triggers the pipeline. A Planner agent orchestrates six specialists: Coverage (reads the policy system to confirm spoilage is included), Weather (queries meteorological data to verify a qualifying storm at the claimant's postcode/time), Fraud (pattern-checks against claim history), Payout (computes the recommended amount from policy limits), Audit (writes a reasoning trace), and Cyber (enforces data-access guardrails). Output writes to the claims system with a recommendation; a human adjuster approves. Replaces the manual first-pass triage that normally takes 3–5 days.
**Why agentic:** Each specialist reasons over a different system and hands state to the next; no fixed if-then flow decides which agent does what — Planner routes based on what the claim looks like once assembled.
**Generalizable core:** External event + inbound record → specialist agents assemble evidence from independent systems → orchestrator writes a recommendation → human approves.
**Deployability:** Enterprise-scale reference (real-time weather APIs, policy admin systems, fraud models). SMB-relevant version is much simpler: one orchestrator + 2–3 specialist tool calls against Google Workspace, a vertical SaaS, and one external feed. Weekend-to-week build on Claude API + a workflow runner (Zapier, n8n) once the specialist tools exist. Replaces the intake analyst / triage adjuster role. Caveat: the "seven agents" framing is architectural — most of what makes it work at Allianz's scale is the connective tissue to internal systems, not the model calls.

### 2. Upload-triggered RFP/proposal drafting
**Source:** [Field Aerospace n8n case study](https://n8n.io/case-studies/field-aerospace/) — mid-sized aircraft modification firm (Oklahoma City / Toronto / Cincinnati), primarily DoD and international defense customers. Cut proposal generation from ~2 weeks with 3–4 people to a 25-minute run; ~$22k/yr in labor savings.
**Mechanism:** A business user uploads a government solicitation (PDF) into an internal React web app. The upload fires an n8n webhook. The workflow parses the solicitation into structured sections (scope, requirements, evaluation criteria, compliance matrix), pulls matching prior-proposal language and technical specs from an internal knowledge base, and drafts a section-by-section response. Output lands as a draft document the business user reviews. Replaces the manual "read the RFP, chunk it, pattern-match past proposals, draft sections" work of a small proposal team.
**Why agentic:** The system decides per-section what compliance the RFP is asking for and which past-proposal sources to cite; it isn't a fill-in-the-template macro. Each section gets its own retrieval and drafting pass.
**Generalizable core:** Long structured document uploaded → agent decomposes it into required-response sections → retrieves matching internal artifacts per section → drafts a compliant response → human reviews.
**Deployability:** Self-hosted n8n plus a light React front end and a Node backend. Realistic week-to-month build for a firm that has good prior-proposal history. Replaces a proposal writer / capture manager for the first draft; humans still finalize. Scale caveat: quality depends heavily on the quality and structure of the prior-proposal corpus. A firm with 5 messy past proposals gets thin results.

### 3. Merchant back-office agent as the conversational alternative to a dashboard
**Source:** [Anthropic Claude Commerce Agents](https://github.com/anthropics/commerce-agents), open-sourced September 2, 2026. Reference blueprint runs on Claude API, Bedrock, Foundry, Vertex. Real-world tests at Shopify, Priceline, Visa, Mastercard, Accenture and others.
**Mechanism:** Two agents. Customer-facing agent handles catalog search, comparison, cart. The pattern worth noting here is the merchant-side back-office agent. Trigger is a merchant chat query ("what's underperforming this week?", "raise price on SKU-4412 by 8% across all channels", "which promos are cannibalizing full-price orders?"). The agent reads sales, inventory, and promo tables; runs the analysis; and — for write actions — proposes the change with the impact estimate and executes on approval. Writes go to the commerce platform's pricing/promo/inventory APIs. Replaces the merchandiser's daily loop through 4–5 dashboards plus a spreadsheet.
**Why agentic:** The merchant doesn't pick a chart — they ask a question, the agent decides which tables to pull, which comparison to run, and what to write back if authorized. Same conversation moves from analysis to action.
**Generalizable core:** Operator asks a natural-language question against operational data → agent picks the queries → returns analysis + proposed write → operator approves → agent writes back to the source of truth.
**Deployability:** Blueprint is open-source Apache 2.0; on the SMB end, the pattern is a Claude project with MCP connectors to the operator's vertical SaaS (Shopify, Square, ServiceTitan, Housecall Pro, Jobber, whatever the operator lives in) plus a write-through with human confirmation. Weekend build if the SaaS has a decent API; longer if you need to wrap a legacy one. Replaces the daily-report reader and the manual pricing/promo/inventory adjustment task. Caveat: write authority is the risky part — the reference implementation deliberately keeps payment and checkout out of scope for a reason.

### 4. Diagnostic-code triggered maintenance work order
**Source:** [Fleetrabbit agentic fleet ops writeup, 2026](https://fleetrabbit.com/blogs/post/agentic-ai-fleet-operations-autonomous-workflow-2026); pattern is corroborated in Locus's transportation management deployments (350+ enterprise fleets).
**Mechanism:** A diagnostic trouble code (DTC) fires from a truck's telematics unit. The agent reads the code and vehicle history, decides severity, creates a work order in the fleet management system, checks the shop schedule for the nearest depot, books an appointment, notifies the driver via SMS with the new stop, and orders the required part from the primary parts supplier (or an alternate if lead time is bad). Writes go to the FMS, the parts supplier's ordering API, and the driver messaging channel. Replaces the dispatcher's morning triage of overnight alerts plus the shop coordinator's parts-ordering phone calls.
**Why agentic:** Nothing about this is a passive alert. Between the code firing and the driver getting the SMS, the agent has read four systems, decided which shop, which slot, and which part, and executed writes into three.
**Generalizable core:** Sensor / device event → agent reads the affected record's history + current schedule + supplier availability → creates the work order → books the resource → notifies the human affected → orders inputs.
**Deployability:** For a small fleet (10–50 vehicles), realistic on Samsara / Motive telematics webhooks + Fleetio or a similar SMB FMS + Twilio + a parts supplier ordering API + Claude API for the reasoning step. Week-to-month build. Replaces a portion of the dispatcher and shop coordinator role. Caveat: many SMB shops don't have a real parts-ordering API — the "order the part" step falls back to a formatted email or Slack message, which is fine and still saves time.
