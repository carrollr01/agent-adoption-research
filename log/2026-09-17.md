# 2026-09-17 — Agent Pattern Scan

## TL;DR
Six patterns today, most interesting is playbook-driven contract triage: a codified team standard (indemnity fallbacks, IP language, cap positions) is loaded as retrieval context so the agent produces a redlined draft with a position, not a summary. Same skeleton (codified standard + inbound doc → marked-up doc back to the reviewer) generalises well beyond legal. The Ramp/Notion "fleet of small agents" approach and Uber's Slack SQL agent with a validated alias corpus round out the theme of the week: mechanism-level reliability is coming from the retrieval layer and the harness around the model, not the model itself.

## Patterns

### 1. Playbook-driven contract triage
**Source:** https://gc.ai/blog/ai-agents-for-lawyers — GC AI, running across 2,100+ in-house teams; named production users include Snyk, Columbia Sportswear, Eventbrite, Tipalti, Arc'teryx.
**Mechanism:** contract lands via intake email or CLM upload → agent loads the team's "playbook" (a structured markdown/YAML file of fallback positions on indemnity, IP assignment, DPA, term, liability caps, governing law) plus the incoming contract → produces a clause-by-clause comparison, drafts redlines, writes a per-clause rationale note → returns a Word doc with tracked changes and posts a Slack summary into the intake channel for the reviewing lawyer. Replaces the first-pass associate/paralegal review that used to precede negotiation.
**Why agentic:** it emits a redlined document taking a position, not a report describing risk. The playbook is the codified team standard the agent negotiates against.
**Generalizable core:** inbound document → compared against a codified team standard → marked-up document returned to the reviewer's queue.
**Deployability:** Claude API + a document parser (Unstructured, LlamaParse, Docling) + Word add-in or CLM webhook. Two to four weeks if the team already has a playbook, four to eight if you're building the playbook with them. The playbook-building is where the real work is, not the model wiring.

### 2. Monthly personalised-memo batch pipeline
**Source:** https://claude.com/customers/athena — Athena Intelligence with an AmLaw 100 firm; 400 monthly comp memos automated end-to-end.
**Mechanism:** month-end cron fires → agent pulls comp figures from the firm's spreadsheets (previously stitched by Excel macros), pulls partner precedent language from SharePoint → drafts each memo in the firm's template, personalises tone and rationale per recipient → writes finished PDFs into the correct secure SharePoint folders and pings a two-person verification queue. What used to be a two-to-three-day process by a comp analyst plus a paralegal QA now runs overnight up to the human sign-off gate.
**Why agentic:** it produces 400 signed-ready documents into a distribution folder each month, not an analytic. The batch structure and per-recipient personalisation are the point.
**Generalizable core:** scheduled batch → per-recipient data assembly → personalised document draft → drop into an existing review/distribution folder.
**Deployability:** Claude API + python-docx or Puppeteer PDF + SharePoint MCP or Graph API. Two to six weeks. Fails hard if the template drifts, so the client needs a locked template before you start. Replaces analyst-plus-paralegal work in any firm that produces personalised documents on a schedule (comp letters, renewal notices, board packages, quarterly investor updates).

### 3. Straight-through decisioning on multi-doc submissions
**Source:** https://insurance-edge.net/2026/09/03/sixfold-launches-ai-underwriter-for-life-health/ and https://ffnews.com/newsarticle/sixfold-and-inforce-launch-strategic-partnership-to-drive-ai-underwriting-transformation/ — Sixfold's life-and-health underwriter launched Sept 3, deployed with INFORCE.
**Mechanism:** new application evidence arrives in the carrier's intake (APS docs, lab results, MIB report, financials) → agent reads each doc, extracts structured risk factors, applies the carrier's own underwriting manual as retrieval context → emits a case-level decision object (accept / decline / request X / refer to human) with a written rationale → writes the decision into the underwriting workbench, and on straight-through cases initiates quote-and-bind against the policy admin system.
**Why agentic:** the output is a decision the system-of-record acts on, not a risk score for a human to interpret. The rulebook plus the write-back are what make it agentic rather than a triage classifier.
**Generalizable core:** multi-doc submission → codified rulebook + structured extraction → decision object written into the system-of-record.
**Deployability:** heavy for a two-person shop end-to-end (regulated intake, audit trails, adverse-action letters). The transferable skeleton is much cheaper: rulebook + extractor + decision writer. Realistic mid-market build is Claude or GPT + JSON-schema outputs + PDF parser + write-back webhook. One month plus a domain expert in the loop. Generalises to mortgage prequal, small-business lending intake, benefits eligibility, permit review.

### 4. Slack-native analyst agent with a validated alias corpus
**Source:** https://www.zenml.io/llmops-database/conversational-ai-data-agent-for-financial-analytics and https://blog.bytebytego.com/p/how-uber-built-a-conversational-ai — Uber Finance's "Finch."
**Mechanism:** analyst posts a plain-English question in a finance Slack channel (e.g. "What were GBs in US&C last quarter?") → a supervisor agent parses acronyms and business terms against an OpenSearch index of column-level aliases and definitions the finance team maintains → a SQL-writer sub-agent generates a query against the warehouse and executes it → the result is checked against a golden-query test set before responding → posts the answer plus the exact SQL back into the Slack thread. Replaces the "quick question for the data team" queue that used to eat analyst hours.
**Why agentic:** the destination is a live thread with an evaluated answer, and the alias index + golden-query harness are the reliability layer the model runs inside. It is text-in, action-out, not a BI chart.
**Generalizable core:** channel question → domain-jargon retrieval + schema retrieval → generated query → validated result posted back inline.
**Deployability:** a small-business version is a week with Claude API + Snowflake or Postgres MCP + a Slack bot + one YAML of internal aliases. The reliability lives in the alias corpus and eval set, not the model choice, so budget the build around the corpus, not the code. Replaces the internal-analytics support queue at any company where non-analysts keep asking data questions.

### 5. Fleet of small database-triggered agents inside the workspace tool
**Source:** https://www.notion.com/releases/2026-09-15 and https://matthiasfrank.de/en/notion-custom-agents-full-tutorial-use-cases-pricing-changes/ — Ramp runs 300+ Notion Custom Agents daily; three concrete flavours below.
**Mechanism:** rather than one big agent, Ramp built many small ones, each with one trigger, one system-of-record it reads from, one it writes to. Examples:
- Product Q&A Oracle: @-mention in a #product-questions Slack channel → RAG over Notion docs (PRDs, specs, changelogs) → posts an answer in-thread with source links. Replaces the on-call PMM watching the channel.
- Sales Feedback Categorizer: new row in a "customer feedback" Notion database (fed by Gong/HubSpot) → tags theme, matches against existing roadmap items, either appends to an existing feature request or opens a new one linked to the account. Replaces a product-ops triage step.
- Referral Bonus Roy: daily cron → pulls candidate accounts from the warehouse via MCP, checks eligibility rules, drafts the internal approval ticket, and on approval files the payout in the finance system. Replaces monthly manual reconciliation.
**Why agentic:** each one writes new records, opens tickets, or moves money in a different downstream system. The fleet shape is the interesting bit: many single-purpose agents beat one general one, and the workspace tool becomes the trigger and control plane.
**Generalizable core:** event on a database row or channel mention → domain retrieval → structured write to another system-of-record.
**Deployability:** buildable inside Notion Custom Agents plus MCPs for Slack, HubSpot, and the warehouse. Weekend build per read-only agent, two to three weeks for anything that writes to finance or payroll. This is the most reproducible customer-engagement template of the week: sell a "starter fleet" of six to ten small agents rather than one big project.

### 6. Charge-capture agent as the second half of an ambient scribe
**Source:** https://www.oracle.com/news/announcement/oracle-health-expands-clinical-ai-agent-with-coding-dictation-chart-review-2026-08-19/ — Oracle Health, deployed inside its EHR to customers on the ambient documentation product.
**Mechanism:** visit ends and the ambient recording is finalised → agent reads the transcript plus the visit's EHR context (chief complaint, prior notes, orders placed) → suggests CPT/HCPCS codes with per-code rationale grounded in the transcript → drops the suggestions into the clinician's charges review pane → on approval, writes to the billing queue. Variation on the ambient-scribe pattern already logged; the new angle is that this closes the loop into billing rather than stopping at the note.
**Why agentic:** the output is a billable code list that lands in a live billing queue, not a summary or a documentation aid. Different economic value (denied-claim reduction, revenue capture) and different buyer (RCM leadership) than a scribe pitch.
**Generalizable core:** event completion (call, visit, site inspection) → transcript + system context → structured code or line-item recommendation → written into the downstream financial system for human sign-off.
**Deployability:** the mid-market clinic version is Whisper + Claude + a rules-lookup table + a write to the PMS via a Practice Better / Jane / DrChrono API. Four to six weeks. Same skeleton applies to construction change orders (transcript of a site walk → line items in the change order system), field-service invoicing (visit recording → parts and labour lines in the FSM), and any professional-services timekeeping that today runs on end-of-day note reconstruction.
