# 2026-11-28 — Agent Pattern Scan

## TL;DR
Spotify's Honk is shipping ~1,000 merged PRs every 10 days by gating each attempt through a deterministic CI verifier before it ever opens a PR. The trigger-verify-handoff skeleton — change campaign → artifact edit → deterministic verifier → gated creation of the handoff — is distinct from any pattern logged so far, and the small-scale version (single-repo "upgrade every controller" or "add a test for every untested endpoint") is a realistic week build.

## Patterns

### 1. CI-gated continuous migration agent
**Source:** Spotify Engineering — 1,500+ PRs Later (Nov 2025), https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1 and the Claude customer page for Spotify, https://claude.com/customers/spotify — Spotify's Honk agent running across 20M+ lines of code; by QCon London 2026 reported at ~1,000 merged PRs every 10 days.
**Mechanism:** a migration campaign (e.g. "replace deprecated API X everywhere") is registered → agent reads affected files plus per-service build config → edits the code on a branch, calls a verification service that abstracts whatever CI the owning team uses → waits for green builds and iterates on failures → opens a PR only after full validation → safety-check layer auto-merges. Replaces the senior engineer who used to sweep a change across the fleet by hand over weeks.
**Why agentic:** the agent iterates against CI feedback per attempt and only produces the handoff (PR) once the verifier passes; a dashboard would report migration coverage, this one actually moves it.
**Generalizable core:** change campaign defined → agent edits artifacts in a system of record → calls a deterministic verifier → creates gated handoff only on pass.
**Deployability:** n8n or GitHub Actions + Claude Code + a thin verifier wrapping existing CI. Week build for a one-repo SMB version ("upgrade every Rails controller," "add a test for every endpoint missing one"). Scale caveat: Spotify's throughput leans on their Fleet Management infra; the pattern works at small scale but ROI compounds with repeat campaigns.
**Dedup note:** variation of 2026-05-09 "development agent team" — new angle: the handoff is gated by a separate verifier service, and the trigger is a campaign scope, not a ticket.

### 2. Self-maintaining observability agent
**Source:** Ramp Labs — Ramp Sheets Self-Maintaining, https://labs.ramp.com/research/ramp-sheets-self-maintaining/ — Ramp's internal Sheets product; agent writes its own Datadog monitors against feature-level telemetry.
**Mechanism:** a release or code change ships → agent reads recent Datadog telemetry (backend events, SSE queue depth, agent-activity signals) plus the deployed code's domain model → generates composite monitors (e.g. "fire when agent activity diverges from broadcasted event throughput") → writes the monitor config back to Datadog → tunes thresholds across re-runs. Replaces the on-call engineer's weekly chore of adding and retuning alerts for whatever just shipped.
**Why agentic:** the agent reasons about which combinations of signals mean a real failure for this feature and writes a composite monitor, rather than firing a static threshold on a dashboard panel.
**Generalizable core:** deploy event → agent reads telemetry patterns + domain context → writes alert/monitor config back to the observability platform → replaces SRE monitor curation.
**Deployability:** Datadog/New Relic/Grafana API + Claude API + GitHub webhook on deploy. Week build. Role augmented: SRE or senior engineer's monitor-hygiene time. Scale caveat: needs enough telemetry volume to correlate — thin SMB stacks won't have it, but any business with a transactional SaaS plus Sentry/Datadog will.

### 3. Document-arrival routing and extraction
**Source:** Agentech launches Dynamic AI Document Routing (Mar 2026), https://coverager.com/agentech-launches-dynamic-ai-document-routing-to-streamline-claims-and-eliminate-manual-triage/ — insurtech vendor positioned against carrier mailroom triage.
**Mechanism:** inbound document arrives (email attachment, fax-to-PDF, ACORD form, policyholder upload) → agent reads the document and extracts carrier, policy number, doc type, claim stage → classifies into the right downstream queue (first notice of loss, supplemental, estimate, subrogation) → writes extracted fields into the claims platform and attaches the original to the matched claim → notifies the correct adjuster. Replaces the mailroom/intake clerk who opened, labeled, and forwarded each document.
**Why agentic:** trigger is heterogeneous (any inbound doc in any format), classification is content-based not sender-based, and the action writes structured records into the system of record without a human preview step.
**Generalizable core:** inbound document → agent reads/classifies/extracts → routes to correct destination in system of record → replaces mailroom/triage role.
**Deployability:** Gmail/O365 inbound + S3 + Claude API + the vertical's system of record (Guidewire, HubSpot, Clio, Dentrix). Week build if the system of record has a decent API; month build with on-prem legacy. Role replaced: intake/mailroom clerk. Flag: vendor's "~80% automation" figure is not independently verified.

### 4. Inbound-email screening with CRM-aware reply
**Source:** Lindy case study — Tiddle, https://lindy.ai/case-study/tiddle-transformed-their-influencer-agency — small influencer agency; CEO reports 40–60 hours/week saved on inbound email handling.
**Mechanism:** new message hits Gmail → agent reads the message plus the sender's prior history in HubSpot → classifies as qualified lead vs. not → if qualified, drafts a personalized reply pulling partnership info and relevant case studies, or asks for the two or three specific missing fields it needs → sends (or queues for human approval) → updates the HubSpot record with status, intent summary, and extracted fields. Replaces the inbox-screener role, usually a junior staffer or part-time VA.
**Why agentic:** the reply is conditioned on the CRM state of this specific sender, not a form response. Different senders get different replies, and the CRM is updated on every exchange.
**Generalizable core:** inbound email → agent reads message + CRM/history → categorizes and drafts reply conditioned on prior relationship → writes back to CRM and sends → replaces inbox screener.
**Deployability:** Lindy, or Gmail + Claude API + HubSpot/Attio/Pipedrive. Day-to-weekend build for a solo-operator version; week build with approval queues and CRM write-back for an agency. Role replaced: inbox screener / junior AE. SMB-scale confirmed.
**Dedup note:** adjacent to 2026-05-01 "creator recruitment negotiation" and 2026-05-07 "sales opportunity agent," but the trigger class (every inbound email, not scheduled outbound) and the replaced task (screening + conditional reply + CRM sync) are different enough to log.
