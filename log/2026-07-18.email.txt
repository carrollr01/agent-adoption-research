## Patterns

### 1. Insurance remittance ingested from bank rails, posted directly into on-prem practice-management software
Source: https://sacra.com/c/lassie/ and https://www.unite.ai/lassie-raises-35m-series-a-to-build-ai-agents-that-handle-medical-practice-administration/ — Lassie ($35M Series A, June 2026, a16z-led), running in 700+ US medical and dental practices across 49 states; reports handling ~250,000 hours of labor per year that would otherwise be done by front/back-office staff.
Mechanism: Insurer deposits EFT into the practice's bank account → local Windows agent bridges on-prem EHR (Dentrix, Eaglesoft, Open Dental) to Lassie's cloud → Lassie pulls remittance/ERA data and matches deposit to bank-side transaction via Plaid/MX → for each line, matches to the correct payer, patient, and claim, applies the practice's contractual adjustment logic → posts the payment and adjustment directly into the practice-management system in real time → when records align it runs untouched; when they don't (underpayment, mismatched EFT, ambiguous write-off), it flags a specific exception for staff review with the reconciled context attached.
Why agentic: The system doesn't display a reconciliation view for a human to work through — it does the reconciliation, decides whether to post or escalate, and only surfaces the residual. The bridge from bank feed → payer data → contract logic → EHR write is executed end to end without a human keying anything.
Generalizable core: External payment/event enters via a bank or partner feed → agent joins it against internal contract/entity data → executes the resulting write in the system of record → escalates only the tail of unmatched cases with the full match context prepared.
Deployability: Stack is a lightweight desktop agent (bridging legacy on-prem software) + cloud ingestion + Plaid/MX + payer connectors. Cross-industry translation is likely a month-plus build per new EHR/PMS target — the value lives in the domain-specific matching and adjustment logic, not the LLM. Replaces a payment-poster / A/R clerk role, not a task. Scale caveat: needs volume to justify the payer/PMS integration work; single-location shops probably don't hit ROI on a custom build, but the pattern generalizes to any SMB category with structured inbound payments (property management, franchise ops, storage) where domain adapters already exist.

### 2. Human-labeled GitHub issue triggers a sandboxed agent that reproduces the bug and attaches a failing test
Source: https://www.metabase.com/blog/reprobot-github-issue-triage-agent and https://news.ycombinator.com/item?id=47767829 — Metabase's OSS engineering team runs it against their public backlog.
Mechanism: Engineer applies the `.Run Repro-Bot` label to a GitHub issue → GitHub Action fires → agent parses the issue description, extracts the reported reproduction steps → provisions an ephemeral, sandboxed test environment → writes scripts, configures databases, runs the Metabase app, attempts the reproduction → on success, comments back on the issue with the stack trace, exact environment state, a minimal reproducible example, and a committed failing test the eventual fixer can run against.
Why agentic: The agent is not classifying or summarizing an issue for a human to then act on; it stands up infrastructure, executes multi-step code, and produces an artifact (the failing test) that becomes the developer's starting point. The human's contribution collapses to one label click and later reading the reproduction result.
Generalizable core: Human-in-the-loop label/tag → agent spins up an ephemeral environment matching the described state → executes the described steps → writes a verified artifact back into the source system for the next human step. The label gate is deliberate: it's the injection-attack firewall for any pattern where untrusted text (public issues, customer emails, form submissions) can otherwise auto-drive code execution.
Deployability: Stack is GitHub Actions + a container/sandbox runtime (Firecracker, gVisor, or a plain disposable Docker) + Claude/GPT for the reasoning loop + a code-execution tool. A weekend build for a single app; the sandbox and reproducibility rig are the real work, not the LLM. Replaces the first 20–60 minutes an engineer normally spends verifying that a bug report actually reproduces. Scale caveat: assumes issues include enough detail to reproduce at all — the pattern is a filter that surfaces reproducible bugs faster, not a magic wand for vague reports.

### 3. Operators forward an email to a tenant inbox; agent extracts structured ERP actions for one-click approval
Source: https://github.com/open-mercato/open-mercato/blob/main/.ai/specs/implemented/SPEC-037-2026-02-15-inbox-ops-agent.md — implemented spec in an open-source ERP project; the same pattern shows up in commercial products (Lindy welcome-flow trigger, Agently cross-app routing), but the spec has the mechanism written out in the clear.
Mechanism: Operator forwards an email (customer PO, shipment update, supplier note, meeting recap) to a per-tenant address like `ops-acme@inbox.openmercato.com` → email provider webhook (HMAC-verified, 5-min replay window) fires an `email.received` event → worker cleans the thread (strips quoted replies/signatures), matches participants against CRM by exact/fuzzy lookup, fetches relevant catalog products for price validation → LLM call (Vercel AI SDK `generateObject` with XML-delimited content to resist prompt injection) returns a Zod-validated structured proposal: summary, participants, up to eight typed actions (`create_order`, `create_quote`, `update_shipment`, `create_contact`, `log_activity`, `draft_reply`, etc.), flagged discrepancies, per-action confidence → operator sees a two-panel review page (email thread + action cards) and accepts/edits/rejects individually or batch-approves → on approve, permission-checked mutations execute in the ERP under optimistic locking, with proposal/action IDs written into entity metadata for a bidirectional audit trail.
Why agentic: The agent isn't summarizing the email or drafting a reply — it proposes concrete state changes in the ERP (create this sales order for these SKUs at this price, update this shipment's tracking) that ship straight to the target system once approved. A dashboard here would show emails and let a human key data; this ships the data.
Generalizable core: Freeform inbound in any channel → LLM extracts a typed, schema-validated action set with confidence and discrepancies → human review UI is one screen per event with per-action accept/edit/reject → approved actions execute in the system of record with a linked audit trail. Works for any team that currently reads messages and keys them into a CRM/ERP/ticketing tool.
Deployability: Stack is any inbound-webhook email provider (Postmark, SendGrid, Cloudflare Email) + a worker queue + Claude/GPT via a structured-output SDK + the target system's write API. Week-to-month build depending on how many action types and how strict the audit requirements. Replaces the fraction of an ops/AR/CS role that consists of reading a thread and typing its contents into an internal tool. Composes cleanly with the label-gated agent pattern (#2) — the "forward the email in" gesture is the same injection-attack firewall the label click is.

### 4. Per-question-type autonomy ladder: same review-response agent runs supervised on new topics and agentic on trusted ones
Source: https://www.akia.com/blog/ai-for-hotels — hotel messaging platform used by operators for guest reviews and inbound messaging; documents the supervised-vs-agentic mode split as an operator-facing configuration.
Mechanism: Guest posts a review (Google/Booking.com/TripAdvisor/Expedia) or sends a message with a keyword/pattern match → agent classifies the question type (breakfast hours, late checkout, WiFi, complaint about noise, etc.) → in supervised mode for that type, the agent drafts a response and holds it for staff approval; in agentic mode, it replies directly → the operator's config per property records which question types are agentic and which are supervised → as the operator watches supervised responses land correctly for a given type, they promote that type from supervised to agentic; a bad reply demotes the type back to supervised. Low-score reviews also trigger real-time alerts so staff can attempt recovery before a bad review posts publicly.
Why agentic: The interesting part isn't the draft; it's that the autonomy boundary is per-question-type and moves over time based on observed accuracy. The system is deciding, per message, whether it may act on its own or must escalate — a runtime routing decision, not a fixed rule.
Generalizable core: Classify each inbound event into a topic → look up the current autonomy level for that topic in a config → act autonomously or route to human accordingly → observed outcomes push the topic up or down the autonomy ladder. Applicable anywhere a human currently reviews every LLM output "just in case" — CS reply drafts, expense approvals, PR review comments, contract redlines.
Deployability: Stack is any messaging/reviews API (Google Business Profile, Booking.com, etc.) + a small classifier + an LLM for the reply + a topic-level config table + an observability loop that records staff overrides. Week-scale build; the harder part is the classifier taxonomy and the discipline of actually reviewing supervised-mode outputs before promoting a topic. Replaces the "junior team member drafts, senior reviews everything" pattern that keeps most LLM-in-the-loop rollouts stuck at 100% human review forever. Scale caveat: only works if there's enough volume per topic to see whether the agentic replies are actually landing — very long-tail topics stay supervised indefinitely.
