# 2026-11-06 — Agent Pattern Scan

## TL;DR
Five concrete patterns, all pulled from vendor case studies with mechanism-level detail. Most useful today: Supermetrics' conversational marketing agent, which replaces the usual "ads dashboard" with a prompt interface that both reads live data and writes changes back to Google Ads, Meta, TikTok, LinkedIn, and Snapchat behind an approval gate. Direct anti-dashboard proof point.

## Patterns

### 1. Slack-alert-triggered engineering triage that opens PRs
**Source:** [Carvana — Claude Tag](https://claude.com/customers/carvana) — used-car retailer, "half a dozen teams" running it; retail-science alerts fell 56% after root causes were addressed.
**Mechanism:** Production monitoring alert lands in a team's Slack channel → agent reads the alert + channel history + ownership map + related tickets + build history + source code + logs (including a baseline from the hour before each release) → posts a root-cause analysis in the team's preferred format, tags the owning engineer, and where useful opens a pull request (e.g. adding logging when existing logs can't explain a deployment) → PR gates on human merge. A sibling scheduled trigger fires hourly against CI pipeline and feature-flag status and starts fixes for stale flags. Replaces the engineer's manual alert triage, log-diff-after-release, and the two homegrown Slackbots the team previously maintained.
**Why agentic:** Not a passive incident page. It reconstructs the pre-incident log baseline on its own, picks a format per team, revises its own conclusions when evidence contradicts them, stands down when the cause is an upstream outage, and writes code where that's the right answer.
**Generalizable core:** inbound monitoring/channel event → agent pulls ownership + prior-state baseline + code → drafts explanation and, if warranted, a code change → humans gate the merge.
**Deployability:** Claude Tag in Slack + Claude Code wired to the team's repo + team-scoped skills/runbooks stored in-repo. Opus as default, Sonnet/Haiku by sub-step. Week-to-month build for one team; multiplies cheaply across teams because each team only adds its own skill file. Replaces the on-call triager and the "incident-write-up" engineer; the alert itself is the prompt.

### 2. Corpus-grounded roleplay agent as always-on sales training
**Source:** [Impel — Anthropic case study](https://claude.com/customers/impel) — automotive-dealer SaaS, 150+ customer-facing reps; built in ~3 weeks on a corpus of 150k+ Gong-recorded dealer calls.
**Mechanism:** Rep starts a practice session on their own schedule → agent plays a dealer persona using scenarios and rubrics distilled from the call archive → session runs by voice (speech-to-text and text-to-speech) → agent scores the rep on objection handling, rapport, product knowledge, and next steps, then DMs the scorecard to the rep in Slack. Replaces practicing with colleagues or live dealers, and the ride-along where a solutions engineer or sales leader has to sit in on early customer calls. New-product ramp dropped from 3–6 months to about 1 month, with ~20% fewer escalations in the first two months of a rollout.
**Why agentic:** Multi-turn voice conversation with a stateful persona, dynamic scoring across several dimensions, and an artifact (the scorecard) written back to the user's workflow tool. The archive isn't a dashboard; it's the agent's training ground and judge.
**Generalizable core:** curated internal conversation archive + rubric → voice-capable agent plays the counterparty on demand → scores the session → writes feedback to the practitioner's main comms tool.
**Deployability:** Claude API + a voice stack (ElevenLabs / 11Labs, Deepgram, or Vapi) + an archive of recorded conversations with transcripts + a scoring rubric agreed to by the team's leaders + Slack webhook for the scorecard. Few-week build. Replaces/augments the sales-enablement role, the ride-along practice loop, and any "shadow a senior rep for 3 months" onboarding. Needs enough recorded-call volume to make the persona plausible — small teams would need to seed with synthetic plus 30–50 real transcripts.

### 3. Conversational marketing ops agent that acts on ad platforms, not just reports
**Source:** [Supermetrics + Claude Cowork](https://claude.com/customers/supermetrics) — 200k+ businesses on Supermetrics; Claude connector reports 250% MoM active-user growth since the February launch.
**Mechanism:** Marketer asks a question or gives an instruction in a Claude conversation → Claude calls Supermetrics' MCP server tools, which return normalized live data from Google Ads, Meta, Microsoft, TikTok, LinkedIn, Snapchat (with source, timestamp, and transformation logic attached to every figure) → agent analyzes and recommends next steps → on approval, pauses/adjusts campaigns or creates new ones (new campaigns start paused by default) → writes reports into the customer's Google Sheet and daily pacing/anomaly alerts into Slack. Replaces the manual export-reconcile-report loop that previously took one Supermetrics customer (Layer) ~10 hours per client report; now ~20 minutes.
**Why agentic:** Reads live cross-platform data, decides what to change, and writes changes back to the systems of record — behind a per-account approval level that routes changes to stakeholders for approve/reject. Dashboard is replaced by a chat box plus write-permissioned tools; this is the exact "dashboard → agent" substitution A3 is interested in.
**Generalizable core:** inbound NL request → agent reads live data across N platforms via MCP → proposes action → human approves per rules → agent writes change back to source systems and files the report.
**Deployability:** Claude Cowork (or Claude API) + Supermetrics MCP (or a custom MCP server wrapping the customer's platforms) + a lightweight approval UI + a report-writing tool (Google Sheets API or similar). Week build if an MCP already exists for the data sources; month-plus if MCP has to be written. Replaces the marketing analyst who stitches dashboards together, and partially replaces the ops person who pushes campaign changes. Works at any size; the approval-level config is what keeps it safe for small shops.

### 4. Ticket-cluster detection as trigger, with self-improving skills
**Source:** [Zendesk custom agents on Claude](https://claude.com/customers/zendesk) — 1 million custom agent executions in the first 7 weeks of early access; up to 80% reduction in human handle times; one customer handling 14M service requests/year hit 99% duplicate-merge accuracy in its pilot.
**Mechanism:** Agent watches the ticket stream → when a cluster of similar tickets appears, it fires: files a Jira issue, posts in the engineering Slack channel, and tells affected customers in Zendesk that the problem is being worked → when the fix ships, it closes the related tickets and attaches a note explaining the cause. After each run it reviews its own work and saves what it learned as a reusable skill, which it then loads into prior-run context for next time. Replaces manual exception handling (returns, warranty claims, detailed billing questions) and the operations work of spotting that "a lot of people are reporting the same thing."
**Why agentic:** The trigger isn't a single event — it's a pattern across a stream. The agent plans multi-step actions across Jira + Slack + Zendesk, then does a retrospective and writes itself an updated playbook. That retro-as-skill loop is the piece a workflow builder couldn't replicate without someone hand-tuning rules every week.
**Generalizable core:** stream of inbound events → agent detects a cluster/threshold → coordinated action across engineering, comms, and the customer-facing system of record → post-run self-review saved as context for the next invocation.
**Deployability:** Zendesk custom agents (hosted path), or Claude API + a queue poller + MCP connectors to Jira/Slack/Zendesk (custom path). Zendesk reports a 5-person team built theirs in 4 months from POC to early access. Any team with a shared inbox or ticket queue can adapt the cluster-trigger pattern — support, HR, IT, bug intake. Replaces the "swivel-chair" tier-2 who notices patterns and coordinates the response.

### 5. Non-engineer-initiated code change, including by phone
**Source:** [Mid-Ohio Food Collective — FreshTrak](https://claude.com/customers/mid-ohio-food-collective) — software used by ~2,500 pantries and 35,000 families/day; idea-to-production fell from 2–3 months to 24–36 hours.
**Mechanism:** Anyone in the org, including non-engineers, briefs Claude Tag in Slack (one example: a support-team member worked through her first task by phone). Agent reads the FreshTrak codebase, works through the change, opens a pull request, and runs the team through review rounds. Nothing merges without an engineer's approval and passing automated tests. A sibling workflow handles new-state onboarding: when a state adopts FreshTrak, Claude Code reads the full codebase plus the state's regulations and produces a working, tested implementation of that state's eligibility logic, reporting formats, and consent language. A third workflow runs on a recurring schedule, reads news/publications about crop conditions and regulatory changes, and keeps leadership informed.
**Why agentic:** The trigger is a natural-language intent from a non-engineer in whatever channel they already use — including voice. The agent takes it the rest of the way to a merged production change, gated by engineering review. This is the pattern that collapses the "file a ticket, wait for a sprint, QA next week" loop.
**Generalizable core:** anyone-in-org request (via chat or phone) → agent reads the relevant codebase + rules → opens a reviewable change → engineer approves → ships.
**Deployability:** Claude Tag + Claude Code + CI/CD gates + a strict "humans must merge" policy. Plus optional voice transcription for phone-in requests. Realistic for any org that already has engineering ownership of its own tooling; too permissive for teams without CI and tests. The recurring research agent is its own weekend build on the Claude Developer Platform with scheduled triggers and a leadership-briefing destination. Replaces the "please file a Jira" friction tax on internal tooling requests.
