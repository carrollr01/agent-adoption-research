# 2026-11-11 — Agent Pattern Scan

## TL;DR
Strongest pattern today is the "agents-as-code" delivery model from ABC Legal / Docketly: 50+ production agents authored by finance, marketing, and ops staff through the same Git+PR workflow engineers use, with Slack emoji reactions feeding a weekly tuner that opens config PRs. It's a delivery pattern, not a single workflow — the thing you sell is the convention, not the agent.

## Patterns

### 1. Agents-as-code platform — non-engineers ship their own automations through PRs
**Source:** https://claude.com/blog/how-abc-legal-turned-every-employee-into-a-builder-with-claude-managed-agents — ABC Legal (1,100-person legal document delivery firm, sister company Docketly), 50+ Managed Agents in production as of August 2026, ~310 daily users, built by a cross-functional 15-person committee.
**Mechanism:** Every agent is a Git-tracked bundle of JSON config + Markdown system prompt + YAML routing ruleset. Bitbucket Pipelines runs cron schedules; merging to `main` deploys. Changes (including those authored by finance/marketing/ops staff) go through a PR with optimistic-locked versioning. Agents post results to Slack where humans react with emoji, which is the training signal. A weekly "Harvester" scrapes reactions into structured labels, a "Tuner" agent reads the labels and opens a PR editing one of ~145 YAML rulesets, a human reviews, merges, and a config-push agent writes the merged config into the production routing DB.
**Why agentic:** The output is production config changes, not a chart. The whole chain — harvester → tuner → PR → push — is a self-improvement loop closing without rewriting any dashboard.
**Generalizable core:** Git repo as source of truth + CI as deployer + chat as interaction surface + emoji as feedback → scheduled tuner that drafts config PRs. Works anywhere routing logic (dispatch, lead scoring, triage, pricing tiers) is in versioned config.
**Deployability:** Claude Managed Agents + Claude Code to author; model tier by job. Git host + scheduler + Slack. Medium complexity; real cost is the committee + the convention. Six-week install for a mid-size shop: scaffold the repo, wire cron/Slack glue, train 3–5 citizen builders. Augments ops/finance/marketing staff rather than replacing them.

### 2. Legacy-ERP procurement agent that operates SAP GUI like a human
**Source:** https://claude.com/customers/duvo — Duvo, enterprise procurement agent running at large retail/CPG firms. One retailer reports €2.8M+ annualized savings.
**Mechanism:** Continuous commodity-price watch + inbound supplier emails + PO events trigger the agent. It reads SAP GUI screens, supplier portals, email threads, spreadsheets, and contract text. It acts by driving the SAP GUI via computer use (and MCP where APIs exist), writing back contracts and purchase orders, drafting supplier follow-up emails, and auto-correcting or escalating discrepancies. One session has been reported processing 50 POs end-to-end. High-risk actions require human approval, which is persisted so the same approval type is remembered next time.
**Why agentic:** It's pixel-level operation of a 20-year-old ERP screen that has no API. One agent holds the goal across a dozen GUI steps and a human approval; a dashboard can't fill in SAP fields, parse a half-confirmation email, and route three follow-ups.
**Generalizable core:** Buyer-of-record agent → monitors market signal → reads legacy system of record via GUI → executes routine transactions against a long tail of counterparties → escalates only exceptions. Applies anywhere a critical system of record has no API: AS/400, mainframe green-screen, legacy EHR, dealer DMS.
**Deployability:** Claude Agent SDK (Opus for computer-use, Sonnet default) + MCP where available + computer-use VMs where not. Medium-high complexity; per-customer system mapping is the long pole. Augments buyers / category managers — team claims ~40% capacity reclaimed on the long tail.

### 3. Six-axis change-review arbiter that auto-merges the low-risk tail
**Sources:** https://vercel.com/blog/58-percent-of-prs-in-our-largest-monorepo-merge-without-human-review and https://www.lennysnewsletter.com/p/how-i-ai-build-an-ai-code-review (Claire Vo's "Merge Mommy" build on the same pattern). Intercom runs the same mechanism internally with an engineer spot-check for drift.
**Mechanism:** GitHub webhook fires after CI passes. Vercel Eve runs the PR through a sandbox, scores the diff on six explicit axes — blast radius, reversibility, data security, ops impact, verification gap, change surface — and compares to a threshold. Low-risk PRs auto-approve and merge. Anything above threshold is held and a Slack ping goes to the right reviewer with the risk summary attached. 58–61% of PRs in Vercel's largest monorepo now merge without human review.
**Why agentic:** The agent reads the full diff, runs the repo in a sandbox, scores on domain-specific axes, and takes the action (merge) that was the reviewer's. Dashboards don't merge code. Also noteworthy: the PR flood only exists because other agents are generating PRs, so this is an agent whose job is triaging other agents' output.
**Generalizable core:** Any pipeline generating lots of candidate changes (PRs, marketing-copy variants, contract redlines, inventory-reorder proposals, generated-ad creatives) → arbiter agent scores the change on explicit risk axes → auto-executes the low-risk tail → routes exceptions with the risk summary. The axes list is the configuration surface clients will care about.
**Deployability:** Low-medium complexity. Reference stack is Vercel Eve + Codex in a sandbox; rebuildable on Claude Code + GitHub Actions in a day or two. Vercel also ships a productized version (vercel.com/kb/guide/vercel-agent-code-review). Replaces 55–60% of senior-reviewer minutes; augments the rest.

### 4. Action + verifier-classifier loop that catches silent failures
**Source:** https://claude.com/customers/rocket-money-qa — Rocket Money's Rowan consumer-finance agent, Q&A with VP Product Aaron Dignan and VP AI Chase Adams (Rowan launched late Aug 2026, https://fintech.global/2026/09/03/rocket-money-launches-ai-agent-to-manage-finances/).
**Mechanism:** A background subagent watches the user's Gmail (OAuth consent) for free-trial confirmation emails, extracts the trial end date, and schedules an SMS the day before renewal. For any action the agent takes on the user's behalf — cancel subscription, negotiate a bill — a separate Claude classifier reads the post-action state (confirmation page, response email, website DOM) and decides whether the action actually succeeded. If not, it labels the failure reason and escalates to a human. Model tier: Haiku 4.5 intent classifier, Sonnet 5 for most subagents, Opus for financial reasoning. When a target website changes and a cancellation script breaks, a repair agent fixes the script and commits it back to the codebase.
**Why agentic:** The trigger isn't a user click. The agent proactively finds forgotten trial emails buried in Gmail and intercepts renewal. The verifier is the key — any external action with an ambiguous outcome gets a second model reading the response.
**Generalizable core:** Background inbox/data scan → identify dated commitment → schedule outbound action → execute action → second-model verifier reads the result → escalate on failure. Pair every external write with a classifier that reads the response. Applies anywhere you take an action on a third-party surface: refunds, submissions, cancellations, scrapes, form fills.
**Deployability:** Gmail OAuth + cheap classifier tier + SMS gateway + a "Skills"-style store of brittle website flows. Medium complexity; the self-healing-script loop is the interesting A3 reusable primitive. Augments a personal-finance assistant; replaces low-stakes human intervention.

### 5. Two-agent exception recovery — one gathers, one decides, both write back
**Source:** https://www.chrobinson.com/es-us/about-us/newsroom/press-releases/2026/chrobinson-lean-ai-agents-for-ltl-pickup-efficiency/ and https://www.freightwaves.com/news/c-h-robinson-deploys-a-suite-of-ai-agents-into-navisphere — C.H. Robinson's Navisphere rollout, LTL pickup recovery.
**Mechanism:** Trigger is a failed LTL pickup (no scan at expected time). Agent A reaches out to the carrier (email, portal, or SMS) and runs a multi-turn conversation to gather why — equipment issue, driver, location — producing a structured record. Agent B reads that record plus appointment and route state, picks the next-best action from rebook / reroute / notify-shipper, and writes it back into Navisphere. A third appointment-change agent updates the appointment and notifies the carrier automatically once a load is accepted and its appointment has to shift.
**Why agentic:** Detection is trivial; the work is multi-turn outbound conversations plus a judgment call across appointment, route, and customer impact. Each decision needs fresh information gathered from the outside world, which a dashboard can only show after a human has gathered it.
**Generalizable core:** Exception event in an ops system → gathering agent that has a real conversation with the external party → decider agent that reads the gathered facts + current state and writes a corrective action back to the system of record. Applies to missed deliveries, failed appointments, no-show contractors, failed data syncs, bounced invoices, denied authorizations.
**Deployability:** Two LLM agents with tool access to the system of record + email/SMS/voice channel for the gathering agent + guarded write path. Medium-high complexity because the write path has to be safe. Augments an ops coordinator; the real win is covering the long tail of counterparties a small team can't reach fast enough.

### 6. Physical-mail orchestrator that closes the digital-to-paper-to-digital loop
**Source:** https://zapier.com/customer-stories/arden-insurance and https://zapier.com/blog/how-arden-insurance-automates-34000-hours-of-work-per-year/ — Arden Insurance (growing US brokerage, ops manager Tyler Diogo).
**Mechanism:** Trigger is a client event in the carrier system requiring a mailed legal/compliance notice. A 12-Zap chain reads the client record, formats the letter template with the correct variables, hands the formatted file to a print-mail vendor via API, waits on a proof-of-delivery webhook, then writes the POD back to the client file. One human checkpoint remains in the middle.
**Why agentic:** It crosses the digital/physical boundary. Compose → print → mail → captured delivery evidence → back into system of record is a chain of actions, not a view. Dashboards don't hand off to print vendors or close the loop on a POD webhook.
**Generalizable core:** Event in system of record → compose structured physical artifact (letter, form, manifest) → dispatch to a physical-world vendor API → poll/wait for return signal → write that signal back to the originating record. Fits regulated workflows requiring paper: lender notices, patient letters, HOA compliance notices, legal demand letters, government filings needing signed hard copy.
**Deployability:** Zapier or n8n for glue + Lob/PostGrid for physical dispatch + any system of record with an API. Week-to-month depending on how dirty the inbound client data is. Replaces an admin role doing manual mail-merge → print → stuff → track.
