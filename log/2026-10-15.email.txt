# 2026-10-15 — Agent Pattern Scan

## TL;DR
Stripe's internal "Kai" platform shows a reusable blueprint for scaling a company-wide agent: employees package work as shareable "skills," and a two-pass selector loads only the skills (and then only the tools) each task actually needs, dodging the 500+ tool bloat trap. Three more concrete patterns on calendar-driven pre-meeting briefing with policy filters, browser-operating agents for API-less SaaS, and status-meeting replacement via per-person Slack digests.

## Patterns

### 1. Skill-gated internal action platform (Stripe's Kai)
**Source:** How I AI — "Build your own company brain" with Sharadh Krishnamurthy, Stripe (Sept 7, 2026) — https://www.chatprd.ai/how-i-ai/how-stripe-built-kai-data-dashboards-reusable-skills-and-enterprise-ai-governance ; LangChain case study — https://langchain.com/blog/how-stripe-built-their-knowledge-ai-platform-on-deep-agents — Stripe's internal AI platform, reported at 10K+ weekly active employees.
**Mechanism:** Any team can package a workflow (a sequence of prompts + the tools it needs) as a shared "skill" and publish it to the Kai catalog. On an employee prompt, the agent first does an LLM pass to pick relevant skills, then each selected skill gates which tools get loaded into the context for the task. "Projects" wrap all of this with per-use-case policy: which tools are allowed, which model to route to, where a human-in-the-loop checkpoint is required. Writes land back in the originating tool (Slack, internal ticketing, data warehouse, etc.).
**Why agentic:** It executes multi-step work (query a system, transform, post a result) against production tools with policy-governed autonomy, not a read-only report surface.
**Generalizable core:** Shared skill library + two-tier selection (skills → tools) + per-project policy wrapper = scalable company agent that stays usable as the tool catalog grows past 500.
**Deployability:** LangChain Deep Agents or similar harness, a config layer per team, an auth-aware tool proxy. Month-plus build for an org with real data isolation needs; a scrappy version with a Claude Agents SDK + MCP server catalog + per-team YAML can be stood up in a week. Replaces/augments the "ask the data team" ticket queue and ad-hoc internal dashboards.

### 2. Calendar-polled pre-meeting brief with sensitive-title suppression
**Source:** Gamut Meeting Briefer agent template — https://www.gamut.so/agent-templates/productivity-internal-ops/meeting-briefer ; Lindy calendar-prep template — https://docs.lindy.ai/use-cases/popular-workflows/calendar-prep ; Rox pre-meeting briefs docs — https://docs.rox.com/development/how-to-use-rox/plan/pre-meeting-briefs — three vendors shipping the same shape in Q3–Q4 2026.
**Mechanism:** Agent polls the user's calendar hourly (Gamut) or fires a timer ~10 min before each event (Lindy) for upcoming meetings. Filter 1: external meetings only — compares attendee email domains against the company domain, skips if all internal. Filter 2 (Gamut): the meeting title is matched against a sensitive-keyword list (board, legal, review, etc.); if it hits, the agent posts attendees-only skeleton and skips all enrichment. Otherwise, it pulls CRM record, recent email threads with these attendees, LinkedIn profile data, and public web/news on the account, drafts a brief with attendee context + account research + open risks + suggested discovery questions, and posts it to Slack/Notion + optional CRM note.
**Why agentic:** Multi-source retrieval, a classification decision on each meeting (external? sensitive?), and a proactive write — not a prompt the rep has to remember to run.
**Generalizable core:** Scheduled or event-triggered pre-work agent → attendee/entity enrichment across internal + external sources → brief written to the channel the human already lives in, with a privacy/sensitivity filter on which meetings get enriched at all.
**Deployability:** Zapier/n8n/Lindy + Google-Calendar or Outlook trigger + a CRM lookup + enrichment APIs (Apollo/Clearbit) + Claude/GPT for the brief. Weekend build for a solo rep, week-ish for a sales org including the sensitive-keyword policy. Replaces the 20–40 min of manual pre-call research most reps don't actually do.

### 3. Browser-operating agent for login-walled operational systems
**Source:** dev.to — "The five primitives I run a whole company on" (solo_operator) — https://dev.to/solo_operator/the-five-primitives-i-run-a-whole-company-on-21cl — solo-operator post arguing roughly 90% of small-business operations live behind a login wall with no usable API.
**Mechanism:** A headless-Chromium agent (Playwright or similar) logs into seller dashboards (Amazon Seller Central, Shopify admin), bank portals, state tax portals, and payroll back-ends on a schedule or on-demand. It takes a screenshot, extracts the fields the task needs via a vision/model pass, decides the next click (filter, export, pay, approve), executes it, and writes the extracted data back into the operator's own store (Airtable/Postgres/Google Sheets). Credentials and 2FA are kept in a vault layer; sensitive actions (payouts, filings) require a human approval in Slack before the agent clicks confirm.
**Why agentic:** It takes autonomous action inside a UI meant for humans — not just scraping, but actually clicking through flows and submitting forms, with a policy-defined human gate on irreversible steps.
**Generalizable core:** Any system with no API → browser-operating agent → read-and-act loop with a human-approval checkpoint on reversibility-risky actions → clean structured record in the operator's own data layer.
**Deployability:** Playwright + Claude/GPT with vision + a credential vault + Slack approval relay. Realistic as a week-ish build per workflow once you've built the harness. Replaces the data-entry / portal-babysitter role; works at a solo-operator scale without any ML headcount. Scale caveat: fragile against UI changes — needs retry logic and a reviewer when the model loses the DOM.

### 4. Weekly status-meeting replacement via per-person Slack digest
**Source:** Vellum "Cross team status updates" template (updated Jan 10, 2026) — https://www.vellum.ai/template/cross-team-status-updates ; Viktor blog — "Replace meetings with async reports" (May 2026) — https://viktor.com/blog/replace-meetings-with-async-reports ; Notion weekly-status-reporter agent template — https://www.notion.com/custom-agent-templates/weekly-status-reporter-es-es .
**Mechanism:** Cron trigger each Friday mid-afternoon. Agent iterates each team member, pulls their closed/moved Linear issues for the week, their merged/open PR activity from GitHub, release notes from the deploy tool, and recent Slack mentions. For each person it produces a three-section summary — what moved, what is blocked, what needs a human decision — and posts a per-person thread into #team-status plus a merged roll-up to a Notion page. Blockers tagged "needs decision" get @-mentioned at the manager automatically. The standing status meeting is cancelled; the single remaining weekly meeting is reserved for the decisions the digest surfaces.
**Why agentic:** It aggregates across tools, writes a judgment-shaped summary (not a tool-level dump), and triggers downstream human attention on the specific items that need it — the meeting itself is the replaced artifact, not the data display.
**Generalizable core:** Scheduled trigger → multi-tool aggregation per person → structured summary with a "needs decision" field → posted into the collaboration channel the team already uses → recurring meeting removed, with the one escape-hatch meeting kept for the escalations the digest surfaces.
**Deployability:** Zapier/n8n/Vellum + Linear/GitHub/Slack/Notion APIs + a Claude or GPT summarizer. Weekend build for a 10-person team; the harder work is upstream — getting people to actually close their tickets. Replaces/augments the engineering or product status meeting; honest scale caveat is cultural, not technical.
