# 2026-07-25 — Agent Pattern Scan

## TL;DR
Five qualifying patterns today. The standout is a distinct class emerging in the wild: agents that periodically re-read the entire book of business to originate net-new work items, rather than reacting to incoming events. Eve Legal running a nightly sweep across a plaintiff firm's whole active caseload to surface missed treatment, unfollowed MRIs, and clients newly eligible for active mass torts is the clearest example — the work it produces did not exist as a ticket before the agent ran.

## Patterns

### 1. Nightly book-of-business re-scan that originates new work
**Source:** [Eve Legal AI Auditor](https://www.eve.legal/use-cases/ai-auditor-for-plaintiff-law) and [Anthropic customer page](https://claude.com/customers) — Eve reports 900–1,200 plaintiff firms on EveOS; the AI Auditor was featured July 2026.
**Mechanism:** Nightly schedule fires across the firm's entire active caseload in the CMS/DMS. The agent reads case files, medical records, treatment histories, and intake questionnaires, then writes flagged findings back into the case management system as new attorney/paralegal tasks. Findings include clients whose doctors ordered an MRI they never followed through on, treatment patterns suggesting undiagnosed TBIs, and existing clients newly eligible for active mass torts (Depo-Provera, PowerPort, talc, asbestos).
**Why agentic:** The output is new work items the firm did not know it had, not summaries of existing work. Nobody asked the agent a question. It re-reads the whole book, decides what merits action, and creates the record.
**Generalizable core:** Scheduled re-scan of the whole system-of-record → surface state changes and missed opportunities against a policy → write new tasks into the primary work queue.
**Deployability:** Anthropic MCP or a Claude Agent SDK harness with CMS/DMS + medical records connectors; week-to-month build for a single firm, longer for the connector library. Replaces or augments a legal ops manager doing periodic case-audit reviews. Scale caveat: needs a real system-of-record with structured enough records to reason across; not a starting point for a firm still on Google Drive.

### 2. Kanban column as agent control plane
**Source:** [How I AI with Alessio Fanelli, Kernel Labs](https://www.lennysnewsletter.com/p/how-i-run-autonomous-coding-agents) and [MindStudio writeup](https://www.mindstudio.ai/blog/openai-symphony-spec-linear-agent-control-plane-500-percent-pr-increase) — solo founder shipping production code from a phone, cites 500% PR volume increase.
**Mechanism:** Linear ticket state transitions are the trigger. Assigning a ticket spawns an agent that reads the ticket, its attached spec, and repo state, then opens a PR. Moving a PR-linked ticket to a "Rework" column re-triggers the agent, which reads the human's line-comments on the PR, writes a rework checklist, addresses each comment, and submits a new PR. On merge, the ticket auto-moves to Done. Per-task token spend is logged as a spec-quality signal.
**Why agentic:** The human's only surface area is dragging cards and writing PR comments. There is no chat thread to re-engage, no shell to run, no orchestrator to configure — the ticket board is the interface. This is materially different from the already-logged "overnight coding agent" pattern; the mechanism worth stealing is the ticket-column-as-state-machine, not the fact that code gets written unattended.
**Generalizable core:** Kanban column transition → agent reads ticket context and current artifact → produces next artifact → moves ticket to next column. Human directs work by dragging cards, not by prompting.
**Deployability:** Linear + GitHub + Claude Agent SDK or Symphony spec; weekend-to-week build for a single-repo setup. Replaces async project management overhead for the person driving the agent. Works cleanly for any queue-shaped work where each item passes through discrete review states, not just code — legal drafts, marketing copy, procurement PRs.

### 3. Outbound voice with live warm-transfer on intent detection
**Source:** [OpenAI Cars24 case study](https://openai.com/index/cars24/) and [ElevenLabs blog](https://elevenlabs.io/blog/cars24) — 3M+ voice-minutes/month across 13 Indian languages, 45% assisted-sales rate.
**Mechanism:** CRM state events fire the agent: missed inspection appointment, cooling seller lead, dropped web lead. The agent places an outbound call, reads the CRM record for prior context (vehicle interest, drop-off point, previous quote), negotiates in the customer's local language, and detects purchase-intent signals mid-conversation. When intent trips, the agent live-transfers the call to a human sales rep with the conversation context already loaded, so the human picks up mid-dialogue rather than starting from a callback.
**Why agentic:** Different from the already-logged inbound voice-receptionist pattern in two ways worth logging separately: it is outbound-initiated from CRM state changes, and the handoff preserves conversation state so the human never restarts the conversation. The agent decides which calls become human calls.
**Generalizable core:** CRM state event → outbound voice conversation → mid-call classifier decides "handle" or "escalate with context" → human joins live, not asynchronously.
**Deployability:** ElevenLabs or Retell for voice + OpenAI/Claude for the reasoning layer + Twilio warm-transfer + CRM webhooks; month-plus build for the language and transfer plumbing. Replaces outbound tele-sales rep doing lead re-warming. Scale caveat: warm transfer requires a staffed rep queue during operating hours to catch the transfers, or the pattern breaks.

### 4. Multi-PDF contract-vs-invoice variance agent with line-pinned findings
**Source:** [FlowManual (YC S26)](https://flowmanual.com/) — construction/MEP contractors, launched Summer 2026 batch.
**Mechanism:** New PDF upload fires the agent — a signed contract, a bid, a spec set, or a vendor invoice. The agent reads across the prior bid, the signed contract, and the arriving invoice, comparing bid-vs-contract for scope adds/deletes and buyout-vs-invoice for price changes. It writes a ranked list of variances by dollar impact into the PM's queue, with each finding pinned to the exact PDF line for one-click approval or dispute.
**Why agentic:** Reasoning across three heterogeneous documents to produce prioritized, actionable variances is not a diff view. The output is decisions the PM would otherwise spend hours reconstructing, not a display of raw differences.
**Generalizable core:** Document arrival → cross-reference against prior contractually related documents → rank variances by materiality → write findings pinned to source location.
**Deployability:** Claude or GPT with vision + a PDF parser (Unstructured, LlamaParse) + storage; week-to-month build depending on document heterogeneity. Replaces the estimator's or PM's manual red-line ritual. Works for any workflow where a "signed spec" and a "delivered artifact" diverge over time — insurance claims vs coverage docs, SOWs vs consultant timesheets, PO vs receiving.

### 5. Single-order post-purchase ops agent (decides and executes end-to-end)
**Source:** [Pango (YC S26)](https://www.ycombinator.com/companies/pango) — 30 DTC brands live, claims 99% self-serve resolution on returns.
**Mechanism:** Trigger is a customer-initiated return/exchange in the brand's portal or a carrier tracking event (delayed, lost). The agent reads a single order record — line items, warehouse pick/pack detail, carrier tracking, prior contacts — plus the brand's plain-English return policy set at onboarding. It decides refund vs exchange vs reship, generates the shipping label, routes the parcel through one of 100+ carrier connectors, updates the TMS and the customer, and issues the refund in the payment processor. All against one order record.
**Why agentic:** The same system that decides also executes the decision across warehouse, carrier, refund, and customer comms. It is not a rules engine handing decisions to humans, and it is not a routing layer with humans deciding.
**Generalizable core:** Customer or system event on a single record → agent reads full record + plain-English policy → executes multi-system resolution → closes the loop with the customer.
**Deployability:** Custom stack (Pango is bespoke), but reproducible with n8n or Gumloop + Shopify/WooCommerce + a shipping API (ShipStation, EasyPost) + Stripe/Klarna + Postmark; month-plus build for full multi-system coverage. Replaces the CX rep working returns tickets in Gorgias/Zendesk plus the ops person coordinating warehouse and carrier. Scale caveat: needs enough return volume to justify the integration surface; a brand doing 20 returns/month is better off with a template response.
