# 2026-09-25 — Agent Pattern Scan

## TL;DR
Four qualifying patterns, all pulled from Claude customer case studies with clear trigger → action → replaced-task mechanics. The most interesting is Rocket Money's "self-healing procedure": deterministic scrapers keep running until a target site changes, and only then does an agent step in to diagnose the break and rewrite the code back into a codified procedure. That flips the usual agent-first framing on its head.

## Patterns

### 1. Recorded-call corpus as live coaching partner
**Source:** [Impel AI customer story on Claude](https://claude.com/customers/impel) — Impel sells software to auto dealerships and has to train sales reps to handle dealer conversations that veteran reps have internalized over years.
**Mechanism:** Rep opens a practice session (voluntarily or as part of certification) → agent reads 150,000+ recorded dealer calls from Gong plus Salesforce account context to model veteran judgment → runs a real speech-to-text / text-to-speech roleplay in character ("I've got about 30 minutes before I need to jump into a floor meeting") → writes a scorecard to Slack rating objection handling, rapport, product knowledge, and next steps → replaces 3-6 months of solutions-engineer shadowing and post-call coaching.
**Why agentic:** The agent picks a persona, chooses objections in real time based on where the rep is weak, and grades a conversation it just held — not a static training video or checklist.
**Generalizable core:** Historical recorded-work corpus → agent role-plays as a customer/counterparty in real time → grades the conversation and writes structured feedback to a work channel.
**Deployability:** Requires call recordings (Gong, Chorus, Fireflies) + CRM context + a voice stack (Vapi, Retell, ElevenLabs) + a scoring rubric in a system prompt. Week to month build depending on rubric complexity. Replaces or augments a sales enablement manager or SE. Doesn't need enterprise headcount — any team with a call library and a coach they can't clone.

### 2. Primary-source-fed regulated calculation with expert-in-the-loop on edge cases
**Source:** [DXC Technology customer story on Claude](https://claude.com/customers/dxc) — DXC processes workers' comp claims and had claims experts computing pre-injury average weekly earnings (PAWE) by hand against state legislation.
**Mechanism:** Workers' comp claim gets filed → agent reads the relevant state legislation, DXC's documented calc rules, and the existing calculator algorithms → produces a PAWE determination for the claim → routes the 20% of edge cases the agent flags as uncertain to a claims expert, whose correction becomes training data → replaces the manual regulated calc that used to sit entirely with the expert. Stood up in eight hours, 80% correct on first pass.
**Why agentic:** The agent isn't fetching a value from a table — it interprets legislation against a specific claim's facts, and the human reviewer only sees the cases the agent isn't sure about. That's a judgment loop, not a lookup.
**Generalizable core:** Regulated event happens → agent reads the source-of-truth statute/rulebook plus the record → produces the regulated determination + a confidence flag → uncertain ones queue to a human, whose correction feeds back into the loop.
**Deployability:** Claude API + MCP against the primary-source doc set + your existing calc engine as a tool. Week build for the first calc type; the pattern scales to any regulated determination (payroll tax, workers' comp, unemployment, benefits eligibility, permit fee schedules). Replaces mid-level analyst work; doesn't remove the expert, just concentrates them on the edge cases. Legal/compliance sign-off is the real timeline, not the code.

### 3. Deterministic procedure + agent self-repair when the target breaks
**Source:** [Rocket Money customer story on Claude](https://claude.com/customers/rocket-money) — Rocket Money's Rowan agent handles subscription cancellations and bill negotiations. Their engineering position is that recurring automations shouldn't rerun a full agent every time.
**Mechanism:** First execution of a task (e.g., cancel a specific subscription vendor) runs as an agent → once it works, the flow gets codified into deterministic scraper/API code that runs cheaply on every future request → when that code breaks (usually because the vendor's website changed), an agent picks up the failure, diagnoses what changed, rewrites the code, and hands it back to the deterministic runner. The agent's job is repair, not repeat.
**Why agentic:** The agent isn't in the hot path — it's the maintenance layer. But the maintenance is real agentic work: read the broken step, load the target page, figure out which selector or endpoint moved, patch and redeploy. Replaces the engineering ticket that would otherwise sit in a backlog until a customer complained.
**Generalizable core:** Automated procedure runs deterministically → failure event triggers an agent to diagnose the specific break and edit the code → procedure resumes.
**Deployability:** Claude API + your existing scraper/API automation code + a failure queue (any dead-letter queue works) + write access to the automation code repo. Month build for the diagnose-and-repair loop. Replaces the on-call engineer maintaining brittle integrations. Real for any small business running a fleet of scrapers, RPA scripts, or API integrations against third parties they don't control.

### 4. Multi-channel document intake → work is already done when a human opens it
**Source:** [Spellbook customer story on Claude](https://claude.com/customers/spellbook) — Spellbook does contract review for legal teams and reports ~530,000 contract reviews per month across roughly 15 agent configurations.
**Mechanism:** Contract lands via email attachment, Slack DM to a legal bot, or Salesforce record → agent pulls it in, reads the full document, flags problematic clauses against the org's playbook, drafts redlines in Word, and benchmarks the terms against market standards → by the time the lawyer opens the file in Spellbook, the risk map and suggested edits are already sitting on the page → replaces the "open the PDF, read it cold, start marking it up" step that used to be the whole job.
**Why agentic:** The trigger is the arrival of a document in any of three channels, not a human clicking review. The agent decides which playbook rules apply and drafts specific redlines, not just risk labels. The lawyer's first action is editing the agent's proposed markup, not producing it from scratch.
**Generalizable core:** Inbound document in any channel (email/chat/CRM) → agent pre-processes against the org's playbook → the human's first view is already-marked-up work, not a blank page.
**Deployability:** Claude API + MCP for the source channels (Gmail/Outlook, Slack, CRM) + a Word add-in or Google Docs plugin for the delivery surface + a playbook as a prompt or config file. Week build for a scoped version (one contract type, one playbook), month build for multi-type. Replaces the first 60-80% of a review specialist's time on any repetitive-document workflow — vendor contracts, insurance policies, lease riders, RFP responses, permit applications.
