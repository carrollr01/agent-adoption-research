# 2026-11-09 — Agent Pattern Scan

## TL;DR
The most interesting pattern today is Sentry Seer's agent-to-agent handoff: a monitored error that clears a fixability threshold triggers a root-cause analysis agent, which then hands the structured context to a separate coding agent (Cursor Cloud Agent or Claude Code) via webhook, which opens the PR. It is one of the first production patterns where one agent's job is to decide another agent should take over.

## Patterns

### 1. Fixability-gated error → agent-to-agent handoff → PR
**Source:** [Sentry blog — Seer can now trigger Cursor agents](https://blog.sentry.io/seer-can-now-trigger-cursor-agents-to-fix-your-bugs) + [Sentry cookbook — self-healing workflow](https://sentry.io/cookbook/self-healing-workflow-seer/) — Sentry's Seer + Cursor/Claude Code integration, generally available in late 2026, used across Sentry's own customer base including deployments described in the Claude Managed Agents customer case page.
**Mechanism:** New error event in Sentry → background task scores the issue for fixability (eligibility bar is roughly 10+ events seen in the last 14 days and a fixability score at "high medium or above") → if it clears the bar, Seer runs root cause analysis against the stack trace plus linked repo context → at the configured stopping point, Seer either opens a draft PR itself or sends a structured RCA prompt via webhook to a Cursor Cloud Agent or Claude Code → that second agent writes the patch, runs tests, and opens the PR → human reviews on the normal GitHub PR surface. Replaces the on-call engineer's first-pass triage and patch-drafting shift.
**Why agentic:** Two separate judgment calls, not one. Agent A decides *whether this issue is worth fixing at all* (gating). Agent B decides *how to fix it* (code changes). The handoff is a webhook with structured context, not a human relay, which lets the two be optimized independently and swapped without rewiring the trigger.
**Generalizable core:** Monitored event stream → gating agent scores + enriches → handoff to a specialist agent → artifact lands in the normal human review queue.
**Deployability:** Sentry + GitHub + Cursor/Claude Code API keys. A couple-day wiring job for a team that already runs Sentry; mostly settings and integration keys, not custom code. Replaces first-pass SRE/on-call triage. Scale caveat: the fixability gate matters more than the fix agent — teams that remove the gate and auto-dispatch every error burn tokens on noise and get PR spam. Starts paying off at ~10+ production incidents/week.

### 2. Proactive background inbox + calendar agent with action-type approval gate
**Source:** [Anthropic — Claude Duet product page](https://claude.com/product/claude-duet) + [Zapier — What Is Claude Duet](https://zapier.com/blog/claude-duet/) — Anthropic's Claude Duet, research preview announced 2026-10-21, waitlisted to US Pro/Max subscribers.
**Mechanism:** Scheduled trigger (polling every few hours plus a morning slot) → Duet runs on Anthropic's cloud compute, independent of the user's device → reads connected Gmail, Google Calendar, and other MCP-connected apps → produces a prioritized morning brief, drafts replies, prepares calendar moves and invoices → surfaces an approval card before any action in a "write" category (send a message, make a payment, sign, delete) → certain classes (securities trading, inter-account money movement) are blocked even with approval → on approval, writes back to the connected app. Replaces the executive-assistant morning routine of triaging inbox, calendar, and task queues.
**Why agentic:** It isn't just filtering mail. The scheduler polls on its own, the agent decides which items to surface at all, drafts the response, and chooses which require explicit approval versus which it can shelve, all on a cloud computer the user is not watching. The approval gate is action-class-based rather than per-message, which is the design shift from older "summary + unread list" agents.
**Generalizable core:** Scheduled poll of inbound channels → agent composes queued actions → tiered approval gate (auto / ask / blocked by class) → write back to source system.
**Deployability:** For an SMB, either use Claude Duet directly (once off waitlist), or rebuild the mechanism on n8n/Make with a cron trigger, MCP connectors for Gmail/Calendar/Slack, Claude API for drafting, and a Slack approve/deny button layer. ~1-2 week build to get the approval-tier design right. Replaces part of an EA or chief-of-staff role. Scale caveat: the harder it is to classify an action into the right approval tier, the more the agent needs a per-tenant policy file — not plug-and-play across tenants without that.

### 3. Any-event-to-agent runtime for operational automations
**Source:** [InfoQ — Azure Functions ships Serverless Agents Runtime at Build 2026](https://www.infoq.com/news/2026/06/azure-functions-serverless-agent/) + [Microsoft TechCommunity blog](https://techcommunity.microsoft.com/blog/appsonazureblog/introducing-the-azure-functions-serverless-agents-runtime-preview/4523804) — Microsoft Azure Functions Serverless Agents Runtime, public preview (Build 2026, June), broadly used through fall 2026 per community posts.
**Mechanism:** Any Azure Functions trigger (HTTP, timer/CRON, queue, blob upload, SQL/Cosmos change feed, Service Bus, SharePoint "file created", Outlook email, Teams message) → spawns an agent defined in a markdown file with its tools and prompt → agent runs on Flex Consumption, pay-per-invocation → uses managed identity to call internal APIs and MCP servers → writes results back to the originating system or anywhere it has permissions. The published reference example is a timer-triggered agent that walks every GitHub org/repo on a schedule, audits security posture (secret scanning, branch protection, workflow permissions), and files issues for drift.
**Why agentic:** The runtime erases the difference between a "function" and an "agent" — the author writes a markdown file, and the platform binds any event source to agent reasoning with tool access. The GitHub security auditor isn't a scheduled script running a fixed checklist; it reads current org state, judges what counts as drift against policy, and decides whether to raise an issue, which is the moment the pattern stops being a cron job and becomes an agent.
**Generalizable core:** Native event source (file, row, time, message) → agent reasons against current state and a policy → writes an outcome (ticket, PR, message, record) back into the operational system.
**Deployability:** For teams already on Azure, this is the lowest-friction way to put an agent behind any real event. Weekend build for a single trigger + agent + Slack notifier. Scale caveat: timer triggers can occasionally fire twice, so the agent needs idempotency on its write step. Replaces a lightweight ops/SRE scheduled walkthrough, not a full role.

### 4. File-drop-to-classify-and-route agent for document intake
**Source:** [Box blog — Workflows that don't just do, but decide: Box Automate](https://blog.box.com/workflows-dont-just-do-decide-box-automate-redesigns-enterprise-automation-box-customers) + [AILearningGuides — Box AI Workflow Builder 2026](https://ailearningguides.com/box-ai-workflow-builder-content-agents/) + [ComputerWeekly — RWS Global deploys Box AI for contract workflow](https://www.computerweekly.com/news/366639242/RWS-Global-deploys-Boxs-AI-tools-to-streamline-contract-workflow) — Box Automate agentic workflows, deployed at RWS Global and similar mid-market customers in late 2026.
**Mechanism:** File uploaded to a watched folder (e.g. `/Contracts/Inbox`) → trigger fires → Box AI agent reads the file content via Box Extract → classifies the document (contract type, sensitivity, jurisdiction) → pulls structured fields (parties, effective date, auto-renewal clauses, dollar amount) and writes them to a metadata template on the record → scores risk against a policy (e.g. indemnity language, non-standard payment terms) → routes: standard goes to e-sign, flagged goes to a specific reviewer's queue with the flagged clauses already highlighted → assigns a human-review task with the extracted metadata pre-filled. Replaces the paralegal or ops intake person who used to open each PDF, type the key fields into a tracker, and forward the risky ones.
**Why agentic:** The classification and risk-scoring steps are per-document decisions on unstructured content, and the routing output is conditional on those decisions, not on a fixed form field. It is the content itself that drives the branch.
**Generalizable core:** Unstructured artifact lands in a watched inbox → agent classifies, extracts structured fields, and risk-scores → conditional routing + pre-filled human-review task.
**Deployability:** Box Automate turnkey if the customer is on Box; the same mechanism rebuilds on Google Drive + Claude API + n8n ("new file in folder" trigger, Claude for extraction and classification, Airtable/Notion as the metadata store, Slack DM to the right reviewer). 1-2 week build for a tight single-folder use case. Replaces 0.5-1 FTE of intake work for firms with ~100+ incoming documents/week. Scale caveat: classification accuracy depends on a stable taxonomy; teams that let it drift end up with a "misc" bucket eating all the volume.
