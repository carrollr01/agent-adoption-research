# 2026-07-13 — Agent Pattern Scan

## TL;DR
Five patterns cleared the mechanism bar today. The standout is a self-directed incident-forensics agent that walks logs across multiple systems on its own path rather than following a fixed pipeline — it's the clearest example this week of an agent doing work whose next step depends on what it just read.

## Patterns

### 1. Self-directed incident-forensics agent that traces across systems
**Source:** Australian Payments Plus on OpenAI, 2026-07-07 (https://openai.com/index/australian-payments-plus/) — the operator of AU's payments schemes (~$1T/year cleared); Codex agent used by engineering to investigate scheme reconciliation exceptions.
**Mechanism:** A reconciliation exception or member-raised ticket referencing a missing or miscounted transfer fires the agent. It reads system logs across multiple payment rails, reconciliation ledgers, scheme rulebooks, and internal runbooks — picking which log family to pull next based on what the last one showed. It produces a written root-cause narrative and a suggested fix in the ticket; an engineer confirms before any change. Replaces the "two engineers grep logs for three days" investigation any payments or ops team recognizes.
**Why agentic:** The novel move is choosing its own search path across heterogeneous systems and iterating on the trail — a fixed enrichment pipeline can't do this, and a dashboard shows telemetry rather than deciding what to look at next.
**Generalizable core:** Anomaly/exception fires → agent forages multi-system logs on a self-chosen path → writes a root-cause narrative + suggested fix into the ticket.
**Deployability:** Codex or Claude Code + read-only DB/log access + one MCP server per source system + a case-writeback tool. About a week per single system to wire up; a month for a real multi-system zoo. Replaces senior incident-investigator hours, not the on-call decision itself.

### 2. Prior-authorization appeals agent (variation on medical billing coding — new angle: outbound appeal drafted from a structured denial)
**Source:** Muni Health prior-authorization denial guide, July 2026 (https://muni.health/blog/prior-authorization-denial-complete-guide-2026); CareRoute (https://www.careroute.ai/blog/prior-authorization-denied). Context: CMS-0057-F took effect January 2026 requiring insurers to emit structured denial reason codes over an API — that's what newly makes this automatable end-to-end.
**Mechanism:** A denial webhook fires from the insurer's electronic PA API with a structured reason code. The agent pulls the patient chart, the specific denied CPT/HCPCS code, the payer's medical-policy PDF, and matching clinical guidelines. It drafts a payer-specific appeal citing policy language plus guideline evidence, submits it through the payer portal on behalf of the practice, and owns the response calendar — re-firing if the 60-day window is about to lapse. KFF data cited across sources says ~82% of Medicare Advantage PA denials that are appealed get overturned, but most are never appealed because the manual load is prohibitive.
**Why agentic:** The agent authors an original letter by joining three unstructured corpora, submits it into a portal (not just an API), and owns the deadline calendar with self-re-triggering.
**Generalizable core:** Regulator-mandated structured denial/rejection → agent assembles a bespoke rebuttal from heterogeneous corpora → submits and owns the response clock.
**Deployability:** Payer PA-API webhook + EHR FHIR read + retrieval over policy PDFs + browser-use for portal submission + a deadline scheduler. Six-to-ten week build; the browser-use step is the wild card and the maintenance surface.

### 3. On-call agent that pairs the alert with the deploy that caused it
**Source:** Elastic Security Labs, early July 2026 (https://www.elastic.co/security-labs/alert-triage-agentic-soc-elastic-workflows); Torq 2026 alert-management writeup (https://torq.io/blog/cybersecurity-alert-management-2026/); operator commentary in Show HN: Scan your AI agents for dangerous capabilities (https://news.ycombinator.com/item?id=48804182).
**Mechanism:** A PagerDuty, Sentry, or Datadog alert fires. The agent pulls the last hour of metrics for the affected service, tails logs since the most recent deploy, and reads the git diff of any deploy that landed inside the alert window. It then produces one of three outputs: auto-contain a low-risk asset within policy, propose a specific rollback or config flip to the on-call engineer with a one-click approve, or escalate SEV1 with a drafted status-page update and a drafted Slack incident message. The recommendation is posted as a threaded reply to the alert.
**Why agentic:** The novel move is joining alert → recent code change → service runbook and producing a specific proposed action plus the customer-facing comms — that's proposal-with-context, not enrichment.
**Generalizable core:** Real-time alert → agent joins telemetry + change-log + runbook → drafts a specific action and the human-facing status update → gated by approval for high blast radius.
**Deployability:** Alert webhook + read-only telemetry/logs/git + runbook RAG + Slack + PagerDuty ack API. Three-to-five week build for a single service tier. Replaces the first 30 minutes of on-call cognitive load, not the ownership.

### 4. Nonprofit RFP-to-application agent
**Source:** Granted AI (https://grantedai.com/); Grant Assistant July 2026 playbook (https://www.grantassistant.ai/resources/articles/5-innovative-ai-workflows-to-win-more-grants-in-2026); OpenGrants 2026 grant-writing analysis (https://opengrants.io/why-grant-writing-ai-will-change-the-way-you-apply-for-funding-in-2026-2/). Cadence in July posts suggests small nonprofits (roughly $1–10M budget) running this monthly.
**Mechanism:** An RFP PDF is dropped in a folder or a watched Grants.gov URL updates. The agent extracts every required section, eligibility rule, evaluation-rubric weight, and page/word limit. It matches each requirement against the org's prior-proposal library and program-outcomes database, auto-fills 40–60% of the boilerplate and org-info sections, and produces a punch list of the remaining human-required blanks — each blank paired with a targeted interview question for the program lead. Final output is a formatted PDF or DOCX in the funder's required format.
**Why agentic:** It reads an unbounded requirements document, decomposes it into a requirement graph, plans the assembly against a heterogeneous prior-work corpus, and owns the "what's still missing" ledger. Plan-execute-track, not template-fill.
**Generalizable core:** Unstructured requirements document → agent extracts a requirement graph → matches each node against a corpus of prior work → outputs a targeted human interview plus a partial draft.
**Deployability:** File-drop trigger + PDF parser + RAG over prior proposals + LLM planner + DOCX/PDF renderer. Four-to-six week build. Replaces the grant writer's first-pass drafting and requirement-extraction time.

### 5. Call-wrap agent that writes the CRM record the rep would have typed
**Source:** Deutsche Telekom on OpenAI, 2026-07-10 (https://openai.com/index/deutsche-telekom/) — European telco contact center at DT scale; the wrap-up slice is what's portable to a small shop.
**Mechanism:** On call hangup, the agent takes the streaming transcript that ran during the call, the customer's account state, and the tariff or product catalog, and writes the structured post-call summary, the disposition code, and any follow-up task straight into the CRM. The rep does not type the wrap-up. DT also runs live whisper and translation during the call, but the wrap-up leg is the standalone unit you can ship on its own.
**Why agentic:** It classifies (which disposition), summarizes free text into structured fields, decides whether a follow-up task is warranted, and writes to the system of record. Not a transcription drop-in.
**Generalizable core:** Streaming conversation ends → agent produces the structured record and next action a human would have typed → writes to the system of record.
**Deployability:** Twilio or Retell for the media pipe + any LLM + CRM write API. About a week to ship for a single CRM. Replaces the two-to-four minutes of clerical wrap-up per call and the QA sampler's spot-checks.
