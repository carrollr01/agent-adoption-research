# 2026-06-29 — Agent Pattern Scan

## TL;DR
Four patterns surfaced today. The standout is Crowdin Copilot's ambiguity-flag synthesis loop: instead of putting a 800-flag review queue in front of a localization manager, the agent clusters flags by underlying decision and asks four questions. It is a clean example of an agent that compresses a long review queue into a short human-in-the-loop dialog, applicable anywhere a pipeline emits a bulk list of "needs human" items.

## Patterns

### 1. Bulk-review-queue compression: cluster flags into minimum question set

**Source:** [Crowdin Copilot: From AI Translation to Localization Orchestration](https://crowdin.com/blog/meet-crowdin-copilot) and [Slator: Orchestration, Not Just Translation](https://slator.com/orchestration-not-just-translation-meet-crowdin-copilot/) — Crowdin shipped Copilot in March 2026 and has been iterating; the Task Agent is in production for localization teams managing multilingual SaaS strings.

**Mechanism:** Trigger is a pre-translation pipeline completing on a content batch. The agent reads every ambiguity flag the AI translator emitted (untranslatable noun, inconsistent terminology with translation memory, gendered pronoun with no source signal, etc.), plus the project glossary, translation memory, and prior manager decisions. It clusters flags whose resolution depends on the same underlying decision — e.g., 200 flags around how to translate "user" across a product all collapse into one question — and writes a synthesized question set to the localization manager (Crowdin's example: 800 flags into 4 questions). Manager answers in-app; the agent writes those answers back into the pipeline as constraints and resumes pre-translation. Replaces the manager's manual triage of every flag, which historically gated launches in new locales.

**Why agentic:** It is not surfacing the flag list as a dashboard. The agent reasons about which flags share a root cause, decides what to ask, and uses the answers to mutate the pipeline behavior. A dashboard would still leave 800 rows to triage.

**Generalizable core:** Pipeline emits N "needs human" items → agent clusters by underlying decision → asks minimum question set → writes answers back as policy that resolves the whole cluster.

**Deployability:** Claude API or any frontier model, plus a clustering pass (can be the same model). The hard part is not the model — it is having structured access to the underlying queue and a way to write decisions back as rules the pipeline obeys. Week build if the queue is already structured (Stripe disputes, Zendesk tickets with tags, content moderation queues, QA flags in software testing). Month build if "the queue" lives in PDFs or emails. Augments queue-triage roles (ops managers, QA leads, support managers).

### 2. CI-failure triage agent that opens diagnostic PRs

**Source:** [GitHub Agentic Workflows public preview, June 11 2026](https://github.blog/changelog/2026-06-11-github-agentic-workflows-is-now-in-public-preview/), with named production users at Carvana (vulnerability remediation, dependency maintenance) and Marks & Spencer (reusable security/quality/delivery workflows). GitHub itself reports a 69% merge rate (9 of 13) on PRs proposed by its own CI-triage agent against internal repos.

**Mechanism:** Trigger is a `workflow_run` failure event in GitHub Actions. The agent reads the failed job's logs, the diff in the PR or commit that caused the failure, and `git log` history of similar failures in the repo (it grep's prior issue titles and PR descriptions for matching signatures). It writes a diagnostic issue with the failure summary, the likely cause, and either a suggested fix as a code block or a draft PR with the change. Sandboxed container, read-only permissions by default, threat-detection job on outputs. Replaces the developer's first 30 minutes of "what failed and why" — they open the issue, accept or reject, merge.

**Why agentic:** The trigger is an event, not a chat. The agent decides what to read (logs vs. history vs. diff), what to write (issue vs. PR), and stops at human approval. It is not a status dashboard of red builds; it is action on each red build.

**Generalizable core:** Failure event in any system → agent reads logs + recent changes + historical context for similar failures → proposes specific remediation as a reviewable artifact → human approves or rejects.

**Deployability:** GitHub-native if the codebase lives there, otherwise the same pattern works with GitLab pipelines, Sentry incidents, Datadog alerts, or PagerDuty. Claude Code or Codex inside Actions YAML, or Claude API with a custom runner. Weekend build for a single repo; week build to make it useful across an org with reusable workflow templates. Replaces the first-line on-call triage step, not the fix itself.

### 3. Dashboard-replaced-by-MCP: experimentation by conversation

**Source:** [Optimizely Remote MCP Server announcement (April 29, 2026)](https://www.optimizely.com/insights/blog/experimentation-mcp-server/) and [CMS Wire coverage](https://www.cmswire.com/digital-experience/optimizely-launches-remote-mcp-server-to-bring-experimentation-into-ai-tools/) — hosted by Optimizely, OAuth login, works with Claude.ai, ChatGPT, Cursor, Claude Code out of the box.

**Mechanism:** Trigger is a PM or analyst asking a question in their existing AI tool — "summarize last week's homepage test results," "draft a 50/50 test for the new checkout button," "is the pricing-page test hitting significance." The agent reads experimentation data, feature flag state, audience definitions via the hosted MCP server. It can list projects, query results, flag anomalies, create draft experiments, and modify traffic splits — but cannot publish; the final go-live click stays in the Optimizely UI. Replaces opening the Optimizely dashboard, navigating to the right test, and reading the cards.

**Why agentic:** The agent assembles cross-test context the dashboard does not show on one screen (which audiences overlap, which experiments are stacked on the same users, what previous tests on the same surface concluded). It takes action — creating drafts, mutating configs — not just rendering rows. Dashboard would require the user to know what to look at.

**Generalizable core:** Any SaaS with a complex dashboard → expose a hosted MCP with OAuth → users ask questions and stage actions in their chat tool of choice → publish step remains a human click in the source-of-truth UI.

**Deployability:** Hosted MCP server is the new pattern worth mimicking — no client install, no API key management, no per-customer integration code. Frame matters: if you build a custom dashboard for a client and they have an LLM-using team, an MCP wrapper on the same data may be more valuable than the dashboard itself. Replaces the role of "the analyst who knows where to click in the SaaS tool."

### 4. Build-time agent, runtime determinism for portal integrations

**Source:** [Libretto Show HN (May 2026)](https://news.ycombinator.com/item?id=47780971) and [Libretto YC profile](https://www.ycombinator.com/companies/libretto) — open-source, came out of a healthcare startup whose team spent a year maintaining browser automations against EHRs and payer portals where no API exists.

**Mechanism:** Trigger is a developer needing to integrate with a web app that has no official API. Instead of an agent that operates the browser at runtime (slow, expensive, breaks under bot detection, fails on every DOM change), Libretto runs the agent at build time: it inspects pages, captures network traffic, records the developer's actions, and outputs deterministic TypeScript that uses Playwright plus direct in-session network calls. The generated code is reviewed, checked into the repo, and runs without an LLM in production. The agent is invoked again only when the site changes and the deterministic code starts failing — at which point it re-records.

**Why agentic:** The agent is not a passive code generator. It runs a live browser session, decides which clicks are stateful vs. cosmetic, captures the underlying API calls that fire behind the DOM, and produces code that bypasses the DOM where possible. The mechanism is agentic at build time and deterministic at runtime — the opposite of most browser-use products.

**Generalizable core:** When the long-term cost of an agent acting at runtime is unacceptable (latency, $, brittleness, observability), invert the pattern — agent at build time produces deterministic artifact, deterministic artifact runs in production, agent re-engages only on drift.

**Deployability:** This is more a meta-pattern than a stack recommendation. Apply it whenever a client wants "an agent to do X every time," where X is repetitive and lives behind a stable-ish UI: invoice extraction from a portal, expense report submission, government compliance filings, supplier-portal order placement. Week build per integration once the meta-pattern is internalized. Replaces both the human doing the task and the brittle RPA macro.
