# 2026-07-31 — Agent Pattern Scan

## TL;DR
Lance Live has a voice/SMS agent that drives a hotel's *existing* PMS through computer-use — no API, no rip-and-replace — and is live in real hotels on a $5M seed. That "agent as a legacy-UI driver" is the sharpest line between an agent and a SaaS-with-LLM-inside I've seen this month. Five other mechanism-distinct patterns below.

## Patterns

### 1. Voice/SMS → computer-use driver against a legacy PMS
**Source:** [Lance Live, YC W26](https://www.ycombinator.com/companies/lance) · [Lance Live homepage](https://www.lance.live/) — $5M seed, live in production hotels.
**Mechanism:** Inbound guest phone call / SMS / email (or staff radio message) → LLM planner reads the PNR, room status, prior notes, and hotel policies → a computer-use loop clicks through the hotel's actual PMS, housekeeping, and F&B booking UIs to modify the booking, dispatch housekeeping, open a work order, or book the restaurant → sends the confirmation back on the originating channel. Writes to the existing PMS + task platform. Replaces the front-desk role of catching every call and hand-keying updates into the PMS.
**Why agentic:** Multi-step navigation across several unrelated legacy UIs, conditioned on live guest intent — not a chat overlay, not a form. The agent chooses which of several systems to touch per request.
**Generalizable core:** Voice/email intake → LLM planner → computer-use driver against a legacy vertical SaaS UI → confirmation back to originator.
**Deployability:** Heavy build. Anthropic-style CUA loop + Twilio + per-PMS DOM reliability + a supervised-handoff queue for ambiguous requests. Month-plus. Replaces receptionist + coordinator hours. Scale caveat: brittle to PMS UI changes; the same skeleton is the unlock for any industry (title, escrow, healthcare front-office, dental) where the workflow lives in an API-less vertical SaaS.

### 2. Mutable-rubric mass-record screener
**Source:** [Kalinda AI, YC S25](https://www.ycombinator.com/companies/kalinda) · [Kalinda homepage](https://www.kalinda.ai/) — live with two of the largest US plaintiff firms, 600k pages processed.
**Mechanism:** New claimant intake packet (thousands of pages of medical, pharmacy, and product records) uploaded → agent reads the full record set plus the case's *current* eligibility criteria (product model + exposure window + injury codes) → extracts usage proof, matches against criteria, scores the claimant, and produces a per-claimant summary with citations back to specific record pages → writes to the firm's case-management system and feeds a prioritized queue for attorneys. Replaces hundreds of paralegal-hours of record review per case.
**Why agentic:** The criteria change mid-litigation. The agent re-scores the existing corpus against the new rubric without a re-ingest and cites back to page numbers, which is the piece that makes the output defensible.
**Generalizable core:** Large heterogeneous doc dump + a rubric that changes → per-entity extract → per-entity score with source citations → ranked queue with re-scoring on rubric edit.
**Deployability:** Week-scale on clean OCR, month-scale on messy scans. Vector store + a rubric-versioned scoring loop + strict citation traceability. Replaces paralegal + legal-nurse review. Same skeleton for insurance eligibility, grant screening, resume review with changing role criteria, or any triage where the definition of "qualified" moves.

### 3. Nightly matter-wide case-prep sweep
**Source:** [Eve Legal Anthropic customer story](https://claude.com/customers/eve) · [eve.legal](https://www.eve.legal/) — 800–1,700 plaintiff firms, 12.5M documents/month.
**Mechanism:** Two triggers: (a) a new document lands in a matter (records request, medical file, deposition transcript), or (b) a nightly scheduled sweep across every open matter. Agent reads all documents in the matter + prior demand letters in the firm's voice ("Blueprints") + the medical/records chronology + statute-of-limitations dates → classifies each new document, updates the chronology, cross-checks statements for inconsistencies, and drafts the next deliverable (demand letter, discovery response, motion) in the firm's tone. Writes into the firm's DMS as a queued draft in the attorney's inbox. Replaces paralegal + associate first-draft work.
**Why agentic:** Unattended nightly loop across the *entire portfolio*, cross-document consistency checking, drafting the next-best deliverable per matter — not a Q&A bot and not a per-request tool call.
**Generalizable core:** Nightly, iterate every open case / project / account; per item, ingest new artifacts, update a structured chronology, draft the next deliverable in the operator's voice for human review.
**Deployability:** Month-plus with a domain-tuned prompt library + firm-voice examples + secure DMS integration. Enterprise-grade (privilege / security). Skeleton generalizes to insurance claims, IR disclosures, tax cases, private-equity portfolio ops — any function where "state of every case" needs to advance overnight.

### 4. In-warehouse SOC triage agent (compute-to-data)
**Source:** [Snowflake + Anthropic press release, Jun 2026](https://www.snowflake.com/en/news/press-releases/snowflake-and-anthropic-accelerate-enterprise-ai-adoption-driven-by-rising-demand-for-governed-ai/) — eSentire MDR named as a production deployment at Snowflake Summit 2026.
**Mechanism:** New alert lands in a Snowflake-hosted telemetry table (EDR, log source, IDS) → agent, running via Snowflake Cortex on the alert's row-scoped context, pulls related logs, threat-intel feeds, and asset inventory *from other Snowflake tables* (no data egress) → produces a Tier-1 verdict (benign / escalate) with enrichment and suggested containment → writes to a Snowflake case table, auto-closes benign items, hands escalations to SOAR/ticketing. Replaces Tier-1 SOC analyst triage shifts.
**Why agentic:** Multi-tool investigation (SQL queries, correlation lookups, enrichments) on live inbound alerts. The mechanism differentiator here isn't the LLM — it's that the compute goes to the data, so governance and residency are structurally satisfied rather than reviewed per query.
**Generalizable core:** Alert-triggered agent that stays inside a governed warehouse, pulls multi-source context via SQL/tool calls, writes a triaged verdict + case entry back to the same warehouse, escalates above threshold.
**Deployability:** Enterprise-only. Requires a governed data plane (Snowflake or equivalent) + Cortex/Bedrock LLM binding + a data model already curated by SecOps + data-eng. Month-plus. Note this shape for any regulated buyer who says "we can't send data to your API" — the answer is now to run the agent inside their perimeter, not to shrink the agent.

### 5. Membership-aware support drafter with a second QA agent watching
**Source:** [Zapier customer story: Erewhon](https://zapier.com/customer-stories/Erewhon) · [Zapier blog: Erewhon builder](https://zapier.com/blog/erewhon-ai-automation-builder/) — grocer, 10 stores, built by one internal Business Analyst.
**Mechanism:** New Help Scout ticket → agent joins the customer's membership status and purchase history from BigQuery + a vector store of policy/product knowledge → 39-step Zap branches member vs. non-member into two different ChatGPT prompt paths (member tone is warmer) → drafts the reply in Help Scout for the agent to send, and surfaces purchase totals so store managers prioritize high-spend members. A *second* agent ("English Tutor") grades each draft against the eventual human-finalized version and logs the score to BigQuery. 70% of drafts go out unmodified; 1,500 labor hours/yr saved; $40K/yr.
**Why agentic:** Multi-path branching + tool use (warehouse lookup + RAG) + a self-evaluation loop that catches quality drift over time. The second agent is doing the QA job a human ops lead would otherwise never actually do.
**Generalizable core:** On inbound message, join customer-value data + policy KB, generate tone-matched draft, log a quality score vs. the final human reply for drift detection.
**Deployability:** Zapier + Help Scout + a vector store + a warehouse. Weekend to a week for the single-store version; the QA-grading loop and warehouse join push a full multi-store build to ~1 month for someone comfortable in Zapier. Notable that this shipped without a dedicated engineer.

### 6. Multi-channel, statute-citing consumer claims agent
**Source:** [AirKaren "How It Works"](https://www.airkaren.com/how-it-works) · [AirKaren on Product Hunt](https://www.producthunt.com/products/airkaren) — free beta, top-3 launch on PH in July.
**Mechanism:** User submits a flight grievance (delay, cancellation, lost bag, denied boarding) with itinerary + receipts → agent identifies applicable regulation (EU261, DOT rule tables) → drafts and sends the compensation letter, fills the airline's claim webforms, *places outbound phone calls* to airline hotlines to push the claim → if rejected, re-drafts citing a different regulation and escalates on non-response. Writes to airline portals, airline email, airline IVR menus, and case status back to the user. Replaces hours of consumer self-advocacy.
**Why agentic:** Chooses channel per case (form vs. email vs. voice), retries on failure with a different rule cite, and closes an escalation loop until resolution — not a template mailer.
**Generalizable core:** Entity + grievance in → rule engine matches statute → multi-channel outbound execution (form / email / voice) → escalation loop with rule-swap until resolution or dead-end.
**Deployability:** Week-to-month build. Twilio for voice, a rules DB per statute, headless-browser fleet for portals. Same skeleton is directly applicable to insurance claims, warranty disputes, medical billing errors, and property tax appeals. Scale caveat: airlines are now deflecting with their own claims-triage AI, so this is a two-agent arms race, not a one-sided win.
