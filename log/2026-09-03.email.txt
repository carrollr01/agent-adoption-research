# 2026-09-03 — Agent Pattern Scan

## TL;DR
Five real patterns today, all mechanism-level. Most interesting: Rocket Money's Rowan — an SMS-loop personal finance agent where the entire user interface is a text thread, and the agent handles the human-facing negotiation call (subscription cancellations, bill renegotiation) on behalf of the user after a one-word approve/deny. Also notable: Anthropic open-sourced a Commerce Agents blueprint the same day that collapses discovery, comparison, cart, checkout, and post-sale support into a single chat context.

## Patterns

### 1. SMS-loop personal finance action agent
**Source:** Rocket Companies press release (https://www.rocketcompanies.com/press-release/rocket-moneys-rowan-rewrites-what-ai-can-do-in-personal-finance/) and PYMNTS coverage (https://www.pymnts.com/news/artificial-intelligence/2026/this-ai-agent-ends-subscriptions-without-a-phone-call/) — Rocket Money launched Rowan on Aug 25, 2026, powered by Anthropic; rolling out to Premium Plus subscribers first.
**Mechanism:** Rowan runs continuously against a user's linked bank + card accounts. When it detects a savings opportunity (a free trial nearing charge, a bill it thinks it can renegotiate, a surplus balance it can move to savings), it sends the user a plain-English SMS. The user replies in plain language ("cancel", "yes", "hold off"). On approval, Rowan executes the action — including contacting the merchant to cancel or renegotiate, without the user placing a call. When Rowan hits an unfamiliar cancellation flow, it solves it once and reuses the solved path across the wider user base.
**Why agentic:** The user's interface is one text thread, not a dashboard. The agent detects, proposes, and executes a real-world outbound transaction against a third party; a dashboard would only surface the savings opportunity and hand the call back to the user.
**Generalizable core:** monitored data stream → threshold or event triggers agent → agent messages the human with a proposed action → one-word human approval → agent executes an outbound transaction against a third-party system.
**Deployability:** Claude API + Plaid (or an accounts aggregator) + a transactional SMS gateway (Twilio) + a voice/browser layer for the outbound cancellations. The tricky piece is the outbound merchant-side action; the SMS loop itself is a weekend build. Replaces both a static "you have subscriptions" dashboard and the user's own follow-through work. Consumer-fintech volume; small-firm equivalents (bookkeeper, ops assistant) would follow the same skeleton against different data.

### 2. Omnichannel dispatch coordinator with unified state across voice, email, SMS, and WhatsApp
**Source:** HappyRobot / DHL Supply Chain blog post (https://www.happyrobot.ai/blog/dhl-boosts-operational-efficiency-and-customer-communications-with-happyrobots-ai-workers) and FreightWaves (https://www.freightwaves.com/news/dhl-partners-with-happy-robot-for-ai-efficient-operations) — DHL Supply Chain deployed across regions; handling hundreds of thousands of emails and millions of voice minutes annually. Variation of the 2026-05-24 voice-agent entry — new angle: multi-channel with shared state, tied into the TMS.
**Mechanism:** Trigger comes from the TMS (MercuryGate, McLeod, Tai) — a shipment that needs a driver appointment scheduled, or a delivery running late. The agent picks the right channel per counterparty (voice via 8×8/RingCentral/Vonage for a broker who prefers a call, email for a warehouse contact, SMS/WhatsApp for a driver), reads the shipment context, negotiates the appointment or update, and writes the confirmed slot back into the TMS. A single conversation can cross channels — the human doesn't restart context because a driver replied by SMS after the email chain.
**Why agentic:** The novelty over a voice bot is the unified state layer across four channels feeding one TMS record. It's not "a receptionist for one call"; it's a dispatch coordinator that can hold a two-day, multi-party negotiation to a shipment record.
**Generalizable core:** operational-system event → agent picks the counterparty's preferred channel → multi-turn negotiation across possibly multiple channels sharing one conversation state → writes structured outcome back to the source system.
**Deployability:** the omnichannel state layer is the hard part — HappyRobot spent real engineering there. A one-channel version (voice + email + one CRM) is a month build with LiveKit or Vapi plus an email connector; the multi-channel unified-thread version is not yet weekend-scale. Replaces logistics coordinators handling appointment scheduling and follow-up calls at scale.

### 3. Missed-call voicemail reclamation into a structured CRM record
**Source:** Zapier blog on Autotorino (https://zapier.com/blog/autotorino-lead-intake-inbound-call-automation/) and Wade Foster on X (https://x.com/wadefoster/status/2091871916575322307) — Italy's largest car dealer group, 74 locations, ~100k inbound calls a month; estimated €150k/month in previously unanswered demand recovered.
**Mechanism:** A phone rings at a dealership; when no one picks up, the call rolls to a capture layer instead of a dead voicemail box. The recorded audio is transcribed by AssemblyAI, an OpenAI classifier runs it against Autotorino's own request taxonomy (sales inquiry, service booking, part question, complaint), and a Zap writes the structured lead — with location, brand, request type, contact number, transcript — directly into Salesforce for the correct dealership's queue. The sales team's next-morning list is what the agent produced overnight.
**Why agentic:** A dashboard would summarize "call volume trending up" and end there. This pattern actually converts audio that would otherwise vanish into a working CRM row that a rep can call back on, and it decides *which* location and *which* team owns it. The action taken is the routed record, not a display.
**Generalizable core:** dropped/unanswered channel → capture the raw signal → transcribe if needed → classify against an internal taxonomy → write a structured, routed record to the system of action, in place of the human who wasn't there to intake it.
**Deployability:** Zapier + AssemblyAI + OpenAI (or Claude) + Salesforce (or any CRM), a weekend to a week for a single site, longer to fan across 74 locations with per-brand taxonomies. Replaces the "we'll get to voicemails when we have time" queue, which is usually never. Especially useful for any business where inbound demand exceeds staffed capacity — trades, medical practices, dealerships, restaurants at peak.

### 4. Full-funnel commerce inside one chat context (discovery → cart → checkout → post-sale)
**Source:** Anthropic blog: Building Commerce Agents with Claude (https://claude.com/blog/claude-for-commerce-agents) and Explainx analysis (https://www.explainx.ai/blog/claude-commerce-agents-open-source-blueprint-september-2026) — open-sourced Sept 3, 2026; retailers reporting carts up to 35% larger, 60% higher completion.
**Mechanism:** The agent lives in a chat surface (the merchant's site chat, or a Claude-native surface reached by the shopper). Trigger is a shopper turn. The agent reads the merchant's product catalog and inventory, renders products and comparison views inline in the conversation, builds the cart in-thread, and hands off to the merchant's checkout when the shopper is ready. After purchase, the same conversation handles "where's my order," returns, exchanges, and refund-policy questions by reading the order system — no context switch to a support page. A companion merchant-side agent on the back office works catalog cleanup, restock decisions, and pricing.
**Why agentic:** The pattern eliminates the funnel entirely as a UI concept. Instead of a shopper navigating pages, an agent traverses the catalog, the pricing rules, the inventory system, and the order-status system on the shopper's behalf, and holds continuity from "I'm looking for" through "where is it now." It's a workflow that spans systems a human shopper would otherwise stitch together themselves.
**Generalizable core:** conversational surface as the only UI → agent reads across multiple internal systems (catalog, inventory, orders, policy) → executes both pre- and post-conversion actions → carries state across the whole customer relationship in one thread.
**Deployability:** Anthropic's blueprint is open source, so the shopping-agent skeleton is a weekend integration to a well-structured catalog; making it perform at conversion depends on catalog quality — Commerce Clarity's read of the code (https://commerceclarity.com/blog/claude-commerce-agents-catalog-constraint) is that the catalog is the constraint, not the agent. Realistically a week-to-month build for a mid-size merchant with a Shopify or headless commerce backend. Replaces (or drastically shrinks) faceted-search UI work, live-chat support, and cart-recovery email flows.

### 5. Spreadsheet as the policy layer for a customer-support classifier agent
**Source:** Zapier customer stories page (https://zapier.com/customer-stories) referencing Mercari's build; discussed in June 2026 Zappy Awards recap (https://zapier.com/blog/zappy-award-monthly-winners-june-2026/) — Mercari handles first replies on 97% of tickets, ~47k tickets/month fully automated.
**Mechanism:** Every inbound support ticket triggers a master Zap of roughly 90 steps. The Zap classifies the ticket by pulling its prompts, category definitions, and per-category policy rules live from a Google Sheet. If the classifier + policy layer resolves the ticket, the agent drafts and sends the first reply and takes any allowed action (issue refund, update order, etc.). If not, it hands off to a human with the classification and drafted reply attached. The reason the Sheets layer matters: support ops leads can add a new refund policy row or edit a category definition in a spreadsheet, and the agent picks it up on the next run — no engineering deploy.
**Why agentic:** The action is a sent reply plus a real state change (refund, exchange, order edit), not a dashboard row. What makes it durable is that non-technical ops staff own the behavior in a spreadsheet, so the agent stays current with policy without rebuilding the workflow.
**Generalizable core:** inbound event → agent reads its own policy from a human-editable source of truth (spreadsheet, doc, table) → classifies and drafts → takes bounded action inside allowed categories, escalates outside them.
**Deployability:** Zapier or n8n + Google Sheets (or Airtable) + an LLM node + the target system's write API. The 90-step master Zap is enterprise-scale; a same-shape build at SMB scale is a week for one queue with maybe 15 steps. The pattern is broadly reusable for any triage-then-act workflow where the policy churns faster than engineering cycles — invoice AR treatment, HR PTO requests, tenant maintenance requests, insurance claim triage.
