# 2026-11-18 — Agent Pattern Scan

## TL;DR
Five patterns today, drawn from vendor-published customer stories (Zapier, Anthropic/Claude, LaunchDarkly) where the mechanism is written in enough detail to steal. The highest-signal one is LaunchDarkly's three-stage ops triage loop: alert in, scoped-fix PR out, with a validator agent in the middle doing the thing a human would otherwise do.

## Patterns

### 1. Three-stage ops triage loop that lands a scoped-fix PR
**Source:** [LaunchDarkly — Stories from the Factory Floor: Building a self-driving ops triage loop](https://launchdarkly.com/blog/building-a-self-driving-ops-triage-loop/) — the Foundation team runs this on its own production stack; three Cursor Automations agents coordinate through Jira.
**Mechanism:** Datadog or Spinnaker alert fires → triage agent reads monitor details, logs, and recent delivery state, writes a Jira ticket with a proposed plan → validator agent reads the plan and approves, rewrites, or rejects it → implementation agent opens a scoped-fix PR in GitHub with the on-call engineer tagged. Without validation the loop wouldn't be trusted; with it, the first two steps run without human intervention.
**Why agentic:** The mid-loop validator is the key. It's an agent whose job is to adversarially read another agent's plan, which removes the usual "humans have to grade every suggestion" bottleneck that keeps most PR-bots stuck at advisory status.
**Generalizable core:** Monitored event → reader agent proposes action → validator agent approves or kills the plan → executor agent files the artifact with a human tagged as reviewer.
**Deployability:** Cursor Automations + Jira + GitHub + any alerting source. Week-to-month build depending on how tight your runbooks are. Replaces the first pass of on-call triage and fix-drafting for operations engineers. Scale caveat: assumes alerts are high-fidelity and runbooks are codified — noisy alert streams would drown the triage agent in work.

### 2. Monday-morning cross-CRM churn + expansion scan
**Source:** [Zapier — Healthie saves 60 hours per week with AI agents](https://zapier.com/blog/healthie-saves-60-hours-per-week-with-ai-agents/) — Healthie, a B2B health-tech platform; built by RevOps lead James Kase.
**Mechanism:** Every Monday morning a Zapier agent queries Salesforce, HubSpot, Vitally, and Help Scout → correlates usage signals, ticket volume, and account movement to identify churn risks and expansion opportunities → posts a ranked summary into Slack where CS and Product leads see it before the week starts. Replaces the weekly meeting-prep ritual where someone combs four tools and assembles a list.
**Why agentic:** The agent decides which accounts matter — it's not a dashboard rendering preset filters. The signals are cross-system and the ranking depends on what's actually anomalous that week, not on a static health score.
**Generalizable core:** Scheduled trigger → agent reads multiple systems-of-record → reasons about anomalies → posts a ranked, actionable digest to a human channel.
**Deployability:** Zapier Agents or any orchestration platform with connectors to the source systems. Weekend-to-week build. Replaces the Monday-morning account review that's usually one person's unpaid weekend task. Scale-agnostic — works for any B2B business with 3+ account-signal sources.

### 3. Post-call action-extraction chain into CRM + Slack + draft email
**Source:** [Zapier — How NisonCo fuels business growth with Zapier agents](https://zapier.com/blog/how-nisonco-fuels-business-growth-with-zapier-agents/) — NisonCo, a PR and marketing firm; founder Evan Nison runs it.
**Mechanism:** New call transcript lands (Fireflies or similar) → agent A reads the transcript and extracts action items like "send a proposal" or "follow up in two weeks" → agent B creates a prospect record in the CRM (Relatable), which fires a Slack alert to the team → agent C drafts a follow-up email grounded in what was actually said and parks it in the founder's Gmail drafts folder for human review before send. Three narrow agents instead of one general one.
**Why agentic:** The draft is written off the actual call content, not a template; the CRM logging depends on what the transcript surfaces, not a form submission. The mechanism replaces the ~20-minute post-call ritual rather than aiding it.
**Generalizable core:** Event producing a transcript → extractor agent → system-of-record writer → human-review draft of the outbound action.
**Deployability:** Zapier Agents, Fireflies/Granola/Gong, CRM of choice, Gmail or Outlook. Week build. Replaces the sales-ops task of post-call CRM hygiene and follow-up drafting. Works at any scale from solo operator to mid-market sales team.

### 4. Membership-tier routing before the agent even starts
**Source:** [Zapier — Erewhon AI automation builder](https://zapier.com/blog/erewhon-ai-automation-builder/) — Erewhon, a US grocery chain running customer service across 10 stores.
**Mechanism:** Inbound Help Scout ticket → Zap pulls the shopper ID, checks membership status against Erewhon's customer database → routes members to a "member agent" that pulls from a vector store of institutional knowledge and responds in a warmer, more detailed tone, and routes non-members to a standard agent with tighter scope. Both agents can escalate to BigQuery lookups for order history. One pipeline, two personalities, chosen by a lookup before the model sees anything.
**Why agentic:** The routing-before-reasoning pattern means the agents don't have to figure out tier themselves, which cuts cost and cuts "wrong tone" errors. The member agent isn't just verbose — it has access to a different knowledge base.
**Generalizable core:** Inbound event → system-of-record lookup to classify the requester → route to one of N specialized agents each with its own tone, scope, and tools.
**Deployability:** Zapier or any orchestrator with Help Scout + customer DB + vector store + LLM. Week build once the knowledge base exists. Replaces the "we need a different experience for VIPs" conversation that usually ends in a human-staffed tier. Scale note: only earns its keep when customer tiers actually mean different things.

### 5. Chat-to-workflow builder that assembles via tool calls, not JSON
**Source:** [Claude — How n8n built an AI Workflow Builder](https://claude.com/customers/n8n) — n8n, open-source workflow automation platform; first-party Anthropic case study.
**Mechanism:** User describes an automation in chat ("when I get a Stripe invoice, summarize it and post to Slack") → Claude calls discrete tools one at a time (`add_node`, `connect_nodes`, `configure_node`) rather than generating the whole workflow JSON in one shot → user sees the workflow assemble node by node, typically in about three minutes versus 10–30 minutes of manual drag-and-drop. The team found the step-wise approach "much more digestible for the model" and said errors became easier to diagnose because the builder has context about what's happening in the workflow.
**Why agentic:** The model is making real tool calls against the n8n workflow state, inspecting intermediate results, and self-correcting. It's not an LLM generating code that a separate system executes blindly.
**Generalizable core:** Natural-language spec in → agent manipulates a structured target one operation at a time via tool calls → finished artifact out, inspectable mid-build.
**Deployability:** Claude Sonnet via Anthropic API + MCP or custom tool definitions for whatever structured artifact you're building (Zapier zap, Make scenario, CI pipeline, Shopify flow, even internal admin forms). Month build for the tool-call surface area, then the model does most of the work. Replaces the human-writing-config task anywhere config is composable. Scale caveat: only pays off if the config surface has clean primitives — monolithic blobs are a bad fit.
