# 2026-09-24 — Agent Pattern Scan

## TL;DR
Google shipped an agent (CC) with its own permissioned account that acts as a family's household ops coordinator, subscribed to selectively-forwarded email streams from each member. The skeleton — agent as its own identity, opted-in per-stream data access, writing to shared systems — is a reusable pattern for any multi-stakeholder ops context, not just families. Also strong today: Stripe's internal "Kai" (skills-registry-as-agent-surface) and Understudy Labs' meta-pattern of an agent that captures production LLM traffic and auto-migrates it onto a cheaper distilled model behind an eval gate.

## Patterns

### 1. Household-ops agent with its own account and per-stream opt-in
**Source:** [TechCrunch, Google CC as household agent](https://techcrunch.com/2026/09/18/googles-new-cc-is-an-ai-agent-that-helps-families-run-their-households/); [Google Labs blog](https://blog.google/innovation-and-ai/models-and-research/google-labs/cc-expanding-to-groups/) — Google relaunched its CC assistant on Sept 18 as a family-coordination agent in Labs, up to six members per household.
**Mechanism:** CC has its own Google account with distinct identity and permissions. Trigger: each member individually forwards or shares specific email streams (school confirmations, ortho appointments, sports RSVPs, birthday-party invites) and calendar visibility. Reads the shared inbox slices, existing shared calendar, and current shared task list. Acts: parses dates/times/action items, drafts calendar events and to-dos, drafts meal plans in a shared Google Chat, fills in permission-slip-style forms. Writes to a shared Google Calendar and shared task list; drafts land in Chat for human confirm. Replaces the parent-as-household-COO role — remembering, transcribing, cross-scheduling.
**Why agentic:** No dashboard is being read. The trigger is an inbound email arriving in a stream someone opted in, not a person opening an app; the write is a state change in the family's shared system, not a chart.
**Generalizable core:** Multi-party inbound event on an opted-in channel → agent (with its own audited identity) enriches with shared context → drafts or writes an update into a shared system of record → humans see it materialize, not a report about it.
**Deployability:** The novel bit isn't the LLM — it's the ownership model. Anywhere multiple stakeholders share ops but don't want to grant blanket inbox access, you can rebuild this with a service Gmail/Outlook account per agent, a Zapier/n8n router (or Claude API + Gmail MCP + Google Calendar MCP), per-user forwarding rules, and a small approval UI. Week build for an SMB clone (family co-op, HOA board, small property manager, small nonprofit board). The role it replaces is the unpaid coordinator — the person quietly running the calendar for everyone else.

### 2. Skills-registry-as-agent-surface (internal "company brain")
**Source:** [Stripe's Kai on Deep Agents](https://www.langchain.com/blog/how-stripe-built-their-knowledge-ai-platform-on-deep-agents); [Lenny's essay with Sharadh Krishnamurthy](https://www.lennysnewsletter.com/p/build-your-own-company-brain-the); [How I AI podcast, Sept 7](https://podcasts.apple.com/us/podcast/how-i-ai/id1809663079) — Kai now runs across 83% of Stripe, 60k+ sessions/week, with 1,000+ skills contributed by 100+ teams.
**Mechanism:** Trigger: an employee asks a question in the Kai interface, or an internal team publishes a scheduled skill (e.g. weekly risk digest). Reads: any of the 1,000+ registered skills, each of which is a typed contract to an internal system (financial models, data warehouse, docs, service APIs). Acts: decomposes the question, selects and chains the relevant skills, runs them, synthesizes an answer with citations. Writes back into Kai for the user (and downstream into Slack, docs, ticketing when the skill's action is a write). Replaces the internal-analyst-ticket queue, the "find someone who knows how to run this SQL" chase, and the cross-team pull that used to eat a partner-manager's morning.
**Why agentic:** The user isn't reading a dashboard; they're expressing intent, and the agent chooses which internal tools to call. The dashboard is downstream of a skill, not the interface.
**Generalizable core:** Ambient prompt in a shared surface → agent selects from a registry of team-published skills (each a typed action) → executes the skill chain against internal systems → returns an answer or performs a write, with governance tracking who published and who called what.
**Deployability:** Stripe used Deep Agents on LangGraph, but the pattern is portable: Claude API + MCP tools registered per team, or Zapier "custom actions" per team, or n8n sub-workflows tagged as skills. The heavy lift is the governance and skills-onboarding layer, not the LLM. Month build for a 50–500-person company; weekend build for a single-team version (5–10 skills, one Slack surface). Replaces the internal ticket queue for repeatable analytical asks. Scale caveat: pays off only when you have enough repeated internal asks to justify the governance layer; a 5-person shop can just chat with Claude.

### 3. Merchant back-office agent (analysis + draft, not autonomous action)
**Source:** [Anthropic Claude Commerce Agents blueprint](https://github.com/anthropics/commerce-agents) — Apache-2.0 reference blueprint released Sept 2 with two agents; the merchant-side one is the less-covered half. [PaymentsJournal writeup](https://www.paymentsjournal.com/anthropics-merchant-blueprint-a-key-step-for-agentic-commerce/); [MarkTechPost detail](https://www.marktechpost.com/2026/09/03/anthropic-released-claude-commerce-agents-an-apache-2-0-blueprint-for-shopping-and-merchant-agents-across-retail-travel-telecom-and-entertainment/).
**Mechanism:** Trigger: a scheduled tick (daily/weekly) or a threshold event (inventory below reorder point, sales anomaly, new review posted). Reads: sales history, inventory levels, current price/promo state, catalog metadata, marketing tool state. Acts: answers "how did sales go this week," flags inventory that needs a PO, drafts pricing/promo recommendations with rationale, drafts marketing campaign copy tied to a specific SKU cohort. Writes: draft campaigns into the marketing tool for approval, inventory alerts into the merchant's ops channel, pricing suggestions into a review queue. Replaces the weekly "cat manager grinds through a spreadsheet and writes a Monday recap" ritual.
**Why agentic:** The merchant doesn't open a dashboard to see what happened; the agent decides *what happened is worth surfacing*, and drafts the response, not the chart. Dashboards can still exist downstream, but they're not where work starts.
**Generalizable core:** Scheduled or threshold event in an operational database → agent reads structured business state → drafts the action (email, PO, promo, alert) with reasoning → human approves and it goes live.
**Deployability:** The blueprint is runnable locally in an afternoon (Claude API + MCP for catalog/cart/checkout/orders). Weekend build for a Shopify/WooCommerce single-store version; week build for a multi-channel small e-commerce shop. Complements — doesn't replace — a category manager, but eats the weekly-recap task and the routine promo-drafting task. Also directly applicable outside e-commerce: any small business with a scheduled ops-review cadence (bookkeeping practice, service business monthly retros, agency weekly client updates) can lift the merchant-agent skeleton.

### 4. Auto-distilled model routing behind an eval gate
**Source:** [Understudy Labs YC S26 launch](https://www.ycombinator.com/launches/SPb-understudy-the-self-optimizing-inference-cloud) — LLM gateway that captures production traffic and auto-migrates the routine slice onto a cheaper distilled model.
**Mechanism:** Trigger: a company routes its LLM calls through Understudy's gateway (single URL swap replacing the Anthropic/OpenAI endpoint). Reads: production request/response traces from the company's own agent workloads. Acts: fine-tunes smaller open-weight models on the captured traces in the background, runs held-out eval sets against the frontier model's output on the same inputs, and only starts routing when the small model matches or beats the frontier on those evals. Writes: routing decisions in the gateway; audit trail of which requests went to which model and why. Replaces the LLM-ops engineer whose job is prompt migration, eval maintenance, and cost optimization.
**Why agentic:** The system decides, per request class, which model to serve; no one sits at a dashboard picking a model. The eval gate is the agent's own precondition for acting.
**Generalizable core:** Continuous stream of production LLM traffic → capture and label in background → train a specialist candidate → auto-gate on eval → change routing behavior in place, with no human release step.
**Deployability:** As a customer, you consume this by swapping a URL and setting up your eval harness — a day. As a pattern to build yourself, the skeleton (capture → distill → eval-gated route) is a month build with Vercel AI Gateway or LiteLLM as the router and an eval framework (Promptfoo, Braintrust) as the gate. Only worth building yourself if your LLM bill is >$50k/mo — below that, just use Understudy or an equivalent. Replaces LLM-ops cost-tuning as a role. Scale caveat: needs enough repeated production traffic to distill from — thin workloads don't distill well.

### 5. Scheduled SOC threat-hunt agent, not just reactive triage
**Source:** [Proofpoint SOC Analyst Agent, on OpenAI Daybreak](https://www.proofpoint.com/us/blog/corporate-news/proofpoint-introduces-soc-analyst-agent-powered-openai-daybreak-models-through) — introduced Sept 3, private preview, GA end of Q3 2026. [Channel Insider writeup](https://www.channelinsider.com/security/proofpoint-soc-analyst-agent-openai-daybreak/).
**Mechanism:** Two trigger classes, and the less-obvious one is the interesting one. Reactive: a natural-language investigation prompt from an analyst ("who else got hit by this campaign in the last 24h?"). Proactive: a scheduled threat hunt or scheduled data-security investigation configured to run against Proofpoint's own detection data. Reads: message metadata, URL/attachment analysis, user risk scores, threat intel context. Acts: turns the question or scheduled hunt into structured, traceable findings — pivots, entities of concern, recommended next steps — and keeps decisions human-in-loop. Writes: case notes, escalation reports routed to the on-call analyst. Replaces the L1 SOC analyst's morning triage queue and the "run the same threat-hunt notebook every Monday" ritual.
**Why agentic:** The proactive-hunt trigger means the agent starts work without a human prompt at all. Findings are traceable, not just a chart.
**Generalizable core:** Cron tick or NL question → agent runs an investigation over a domain-specific data store → produces structured, cited findings and next steps → routes to the human on the hook. Not security-specific — the same skeleton applies to scheduled fraud sweeps, scheduled churn-risk digests, scheduled compliance sweeps against internal data.
**Novelty vs. logs:** Adjacent to the 5/23 morning-scouting pattern, but the mechanism is different — scouting was public-web input, this is internal ops-data input with a case-note write-back and audit trail. Worth logging as a distinct skeleton (scheduled hunt over internal ops data → structured investigation → case-note write) rather than a variation.
**Deployability:** In the wild, ship this on Claude API or OpenAI's Daybreak models + MCP connectors to your data stores (SIEM, CRM, finance system, ticketing) + a small scheduler. Week build for a single-domain scheduled-hunt agent (fraud sweep, churn digest, exception-report hunt) at an SMB. Only Proofpoint-scale customers need the enterprise routing — a small shop can just email findings to a Slack channel.
