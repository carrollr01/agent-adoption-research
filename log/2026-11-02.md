# 2026-11-02 — Agent Pattern Scan

## TL;DR
Three patterns worth logging today, all mechanism-level. The sharpest is Ryan Carson's "Watchdog + named-playbook" dyad: a cron agent sweeps inbox/calendar/code every 15 min and pings a human in Slack, who one-clicks a named playbook (e.g. "Land PR") to fire the high-stakes action. It cleanly separates autonomous polling from human-authored execution. ## Patterns

### 1. Watchdog cron agent + human-fired named playbook

**Source:** Ryan Carson (solo founder, Untangle), described across the Behind the Craft podcast and secondary write-ups ([Creator Economy write-up](https://creatoreconomy.so/p/how-this-5x-founder-runs-his-startup-solo-with-ai-agents-ryan-carson), [How I AI tactical notes](https://www.chatprd.ai/how-i-ai/how-ryan-carson-manages-40-prs-a-day-with-devin-and-codex)). Carson runs ~15 concurrent Devin agents against a single-person SaaS; the two agents to look at are "Clawd Chief" and "Watchdog."

**Mechanism:**
- Clawd Chief runs on a 15-minute cron. Reads: Gmail inbox, Google Calendar, a markdown priorities file, open Linear tickets. Writes: a short Slack message to Carson summarising what's new and what needs a decision.
- Watchdog runs continuously against GitHub. Reads: PRs in his repos, CI status, agent transcripts. When a PR is ready to merge, it pings Slack with a "Land PR" link.
- Carson clicks "Land PR" in Slack, which invokes a Devin playbook (a saved markdown prompt) that squash-merges, closes the Linear ticket, deploys, and posts a changelog entry.
- Replaces: the "did engineering finish anything?" check-in; the morning Gmail/Calendar/Linear triage; the manual merge-and-deploy ritual.

**Why agentic:** Two distinct trigger classes compose into one workflow. The cron and the state-watcher are fully autonomous. The human remains the sole trigger for the high-stakes merge, but the merge itself is a named playbook, not a dashboard click. The dashboard-equivalent (a Linear or GitHub board the human scans) is explicitly displaced.

**Generalizable core:** Scheduled poll of a mixed context set → surfaces a specific decision in the human's primary chat → human fires a *named* playbook that executes a multi-step action. Autonomy is in the watching; the human stays on the trigger of the write.

**Deployability:** Devin ($500/mo) + Slack + a few markdown playbook files. Replaceable stack: Claude Code background agents + Slack webhooks + GitHub Actions. Complexity: ~weekend build for a single workflow; the structural work is drafting the playbooks. Replaces an ops-lite PM or a founder's own triage time, not a specialised role. Scales down to solo and up to small teams; the Devin cost is the main bar.

### 2. Label-triggered PR approval agent that fails closed

**Source:** PostHog's "Stamphog" workflow, visible in [PR #2316 on PostHog/code](https://github.com/PostHog/code/pull/2316/files). An agent that reviews and approves PRs when a specific label is applied.

**Mechanism:**
- Triggers: `pull_request:labeled` with the Stamphog label; `pull_request:ready_for_review` when the label is already present; `pull_request:synchronize` when the decision step previously flagged a re-review.
- Reads: the PR diff, metadata, and an internal "decide-delta" step that scores whether the change is in the safe-to-approve set (small, scoped, no cross-cutting edits, passes CI).
- Acts: if approved, posts a GitHub review with an approving verdict through a GitHub App token (the default `GITHUB_TOKEN` cannot approve). If the decision step errors or is uncertain, posts a comment asking a human to re-apply the label to retry. No implicit approval ever.
- Writes to: GitHub review state + PR comments.
- Replaces: the "someone from infra, can you LGTM my obvious migration?" ping; and the backlog of trivial PRs waiting on a human reviewer.

**Why agentic:** It is literally gating a merge, not reporting on PRs. The agent reads code, makes a scoped decision, and takes a durable write action (an approval review). The script runs from `main` rather than from the PR branch, so the PR being reviewed can't modify the reviewer — a small but important design detail other label-bots routinely get wrong.

**Generalizable core:** State transition on a tracked artifact (label applied) → agent re-reads the artifact against a scoped policy → either executes a privileged write (approve, merge, deploy) or posts a specific human-callable retry affordance. Fails closed by default.

**Deployability:** GitHub Actions + a dedicated GitHub App with review permissions + any model with tool-use. Complexity: ~week build if you include the policy evaluator and the fail-closed plumbing; longer if you want the policy to learn from previous rejections. Replaces a slice of a senior reviewer's attention on low-risk PRs. Caveat: only useful at team sizes where enough mechanical PRs exist to warrant the gate; a 2-person team won't see the return.

### 3. Overnight scoped-brief research agent with a question queue

**Source:** Design pattern recurring across practitioner write-ups through 2026, including the [Overnight Researcher post on DEV](https://dev.to/whoffagents/the-overnight-researcher-how-our-ai-agent-improves-itself-while-we-sleep-omp), a [self-evolving overnight agent that ran 59 rounds](https://dev.to/terryfyl/i-built-a-self-evolving-ai-agent-that-ran-59-exploration-rounds-overnight-4jcj), and the [Sendy overnight-autonomous-agent architecture doc](https://sendy-hq.pages.dev/docs/solutions/architecture-patterns/overnight-autonomous-agent). The common ground is a scheduled research/writing agent that runs 6–12 hours unattended and hands over a bounded deliverable in the morning.

**Mechanism:**
- Trigger: cron (typically 22:00 or end-of-day). Also started manually at the end of a working session with a task spec.
- Reads: a task file (markdown, with required output schema), the web, a vector index of the company's docs, optionally the user's email or Linear for context on the "why."
- Acts: produces a scoped deliverable in a required format — e.g. "one-page brief: 3 findings, 3 contradictions, 3 open questions, each sourced." Every time it hits something it can't resolve, it writes a line to a `questions.md` file alongside its best guess and keeps working, rather than blocking.
- Writes to: a filesystem path (the brief + the question queue) and a silent Slack delivery to the user before 06:00. Any action with external side effects (publish, email, deploy, spend) is deliberately gated to morning review.
- Replaces: a research hour at the start of the day; a half-day of literature combing before a client meeting; the "I need a market scan on X by tomorrow" ask.

**Why agentic:** Not a dashboard — the output is a decision-ready brief in a prescribed shape, with sourced claims and explicit open questions. The question queue is what makes it genuinely autonomous: it keeps the agent making progress without a human in the loop, while cleanly surfacing what the human still needs to resolve. The dashboard-equivalent (a research feed the user scans) is explicitly displaced.

**Generalizable core:** Scheduled run → agent executes a long task against a required output schema → when blocked, writes question + best guess to a queue and continues → silent delivery of the finished artifact + queue before the user's morning.

**Deployability:** Claude Code or Cursor background agents, or Devin, plus cron and a Slack webhook. Markdown files are both the input (task spec) and the output (brief + questions). Complexity: a weekend to get one lane working, a week to harden the question-queue discipline (the hard part is strict output-schema adherence and silent delivery, not the research itself). Replaces a slice of an analyst, researcher, or PM-doing-prep. Works at any scale, since the deliverable is per-task and the agent isn't shared.
