# 2026-10-12 — Agent Pattern Scan

## TL;DR
Three strong patterns today, all engineering-adjacent: PR auto-approval that scores each change on six risk dimensions and self-approves only the low-risk slice (Merge Mommy / Vercel Eve), on-call agents triggered by Sentry alerts posted into Slack that either draft a fix PR or classify the alert as noise (Qovery and several others converging on the same shape), and Slack-emoji-triggered unattended coding agents that now ship ~1,300 PRs/week at Stripe. Common thread worth noticing: the trigger surface is moving off of ticket systems and into the ambient chat/alert stream where humans already live.

## Patterns

### 1. PR auto-approval with multi-dimensional risk scoring
**Source:** [How I AI — Build an AI code review bot in 30 minutes with Vercel Eve](https://lennysnewsletter.com/p/how-i-ai-build-an-ai-code-review) and [Lenny's episode notes](https://lennysnewsletter.com/p/build-an-ai-code-review-bot-in-30) — Claire Vo (CTO at ChatPRD) walks through "Merge Mommy," which she says she built in one Codex session on top of [Vercel Eve](https://www.chatprd.ai/how-i-ai/merge-mommy-vercel-eve-ai-bot-for-auto-reviewing-pull-requests). Intercom cited as prior art showing AI-approved PRs ship ~5x faster with a lower revert rate ([write-up](https://radar.zurb.com/article/intercom-ai-approved-code-ships-five-times-faster-with-fewer-reverts)).
**Mechanism:** Trigger is a PR passing CI checks. The agent reads the diff, scores the change on six risk dimensions (change surface / blast radius, reversibility, data security, operational impact, verification gap, and change surface again — the author did not hand-write the rubric; Codex generated it from a loose prompt), auto-approves the PRs that fall below a threshold, and sends the rest to Slack with the risk breakdown attached so a human picks it up. Writes to GitHub (the approval) and Slack (the review request). Replaces the senior engineer's queue of mechanical "is this PR safe to merge" reads — not the design review for the harder changes, just the pile-up of small ones.
**Why agentic:** Decision autonomy over whether to approve, with per-PR reasoning, not a static CODEOWNERS routing rule. Every low-risk PR that merges never touches a human. The agent takes action in GitHub; it is not just a dashboard of risk scores.
**Generalizable core:** New record passes a quality gate → agent scores it against a learned/prompted multi-dimensional rubric → auto-acts on the low-risk slice, routes the rest to a human with the reasoning attached.
**Deployability:** Vercel Eve + Codex-authored agent definition, SOC-2 compatible per the author. Weekend build (she says one Codex session). Replaces/augments: senior-engineer review time on routine PRs. Scale caveat: works best when you can define "low-risk" concretely enough that false auto-approvals are rare — the author tolerates it because reverts are cheap in her setup.

### 2. Sentry alert → autonomous investigation → draft fix PR, posted back into the Slack thread
**Source:** [Qovery — How we use an AI agent to fix Sentry errors](https://www.qovery.com/blog/how-we-use-an-ai-agent-to-fix-sentry-errors) (Oct 8, 2026, first-person from the Qovery team). Convergent instances: [Sourcery's On Call Engineer](https://sourcery.ai/blog/production-issues-beta), [Antimetal's Slackbot](https://antimetal.com/integrations/slack), [Rootly's 2026 observability guidance](https://rootly.com/sre/ai-observability-2026-predictive-alerts-auto-remediation-577de), [Hockeystack's internal debugger](https://www.hockeystack.com/applied-ai/we-built-a-production-debugging-agent-that-finds-the-right-root-cause-92-4-of-the-time) (May 2026), and [Kortix's read-only triage agent](https://kortix.com/use-cases/oncall-triage). Qovery is the cleanest builder-post.
**Mechanism:** Sentry fires on a production error and posts the alert into a specific Slack channel. The agent (spawned per alert) reads the stack trace, pulls the relevant source files from the repo, checks the recent commits around the touched code, and cross-references prior incidents. It then does one of three things: opens a draft PR with a proposed fix, replies in the Slack thread calling the alert noise or transient (with its reasoning), or flags it as needing a human. Writes to GitHub (the draft PR), to the original Slack thread (the reply), and comments back into Sentry. Replaces the on-call engineer's first 20–30 minutes per alert — the "is this real, is it ours, what changed recently" bootstrap.
**Why agentic:** The agent decides the response class per alert (fix / noise / escalate) and takes different downstream actions accordingly. The noise-classification branch is the key agentic move — a dashboard cannot shrink the alert volume, this does.
**Generalizable core:** Alert fires in channel X → agent assembles context from the toolchain the humans would check anyway → produces one of {draft fix, classification, escalation} and writes the outcome back into the thread that triggered it.
**Deployability:** The Qovery write-up suggests a Claude/GPT model + Sentry API + GitHub API + Slack bot. ~Week build for a basic version; the trick is tuning the noise-classification branch so it does not auto-dismiss real bugs. Replaces/augments: on-call engineer triage time, which several of the vendors above pitch as "30 min → 3 min per alert." Scale caveat: the write-ups candidly note that noisy monitors generate false positives and that teams need to prune alerts in parallel.

### 3. Slack emoji reaction as the trigger surface for an unattended coding agent
**Source:** [Lenny's — How Stripe built Minions, AI coding agents that ship 1,300 PRs weekly from Slack reactions](https://www.lennysnewsletter.com/p/how-stripe-built-minionsai-coding) (How I AI episode with Steve Kaliski, Stripe engineering manager). Related mechanism now also GA as a platform primitive: [GitHub Copilot cloud agent for Linear reached GA on July 23, 2026](https://github.blog/changelog/2026-07-23-copilot-cloud-agent-for-linear-is-now-generally-available/) — assigning a Linear issue to the Copilot user triggers an isolated agent run that opens a draft PR and streams progress back to the Linear timeline.
**Mechanism:** A Stripe engineer reacts to a Slack message (bug report, feature request, thread discussion) with a specific emoji. That reaction spawns a Minion in an isolated environment with the same tooling and context as a human engineer; it orchestrates the work using "blueprints" (deterministic code wrapped around flexible agent loops) and produces a PR with code, tests, and documentation. The PR goes to a human reviewer. Writes to GitHub (the PR) and Slack (progress updates in-thread). The GA Linear variant uses ticket assignment as the trigger instead of an emoji, but the shape is identical: lightweight work-item signal → ephemeral agent run → draft PR back to the human. Replaces the engineer's "pick this up next sprint" interstitial — the work gets started immediately in a side thread rather than queued.
**Why agentic:** The agent plans the change, runs tools against the real codebase, iterates on tests, and produces a reviewable artifact without a human in the loop until review. The Slack emoji is literally the only user action required to start the run.
**Generalizable core:** Lightweight in-context signal (emoji, ticket assignment, @mention) → ephemeral agent run in an isolated workspace with full tool access → artifact posted back into the originating thread/record for human review.
**Deployability:** Stripe's Minions is custom-built on a fork of goose with internal blueprints — month+ build for the platform, but any individual Minion is cheap. The GA Linear primitive is a zero-build install for teams on GitHub + Linear (requires org-owner + workspace-admin privileges). Replaces/augments: the "small-but-not-trivial" tier of engineering work that currently sits in backlogs. Scale caveat: Stripe is at 1,300 PRs/week after a multi-year investment; a greenfield team should expect to spend time curating blueprints and keeping the review bottleneck from becoming the new ceiling.
