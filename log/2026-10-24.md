# 2026-10-24 — Agent Pattern Scan

## TL;DR
Four mechanism-level patterns surfaced in Anthropic's current customer stories, each turning on a different trigger class: batch file drop, pattern across many simultaneous records, alert in a chat channel, and a long-document intake event. The most reusable is EvenUp's cost-tiered extraction pipeline, which lets a single agent swallow a 1,000-page intake without burning the budget on pages that didn't need vision OCR, and keeps every extracted fact linked back to its source page so the drafting step can cite without re-reading.

## Patterns

### 1. Cost-tiered document extraction with citation-preserved fact base
**Source:** [claude.com/customers/evenup](https://claude.com/customers/evenup) — EvenUp drafts personal-injury demands and settlement sheets at a specific California firm scale (previously a 45-day backlog, 8–15 hours per case for one person).
**Mechanism:** New case intake (often 1,000+ pages of medical records, billing ledgers, police reports) → pipeline runs each page through the cheapest extraction method that works, starting with embedded text, then standard OCR, then Claude vision only for scanned bills and checkbox forms → classifies each document (billing statement, clinical note, intake form) so each page is only asked questions it can answer → deduplicates entries and keeps every extracted fact linked to its source page → Opus builds a case "blueprint" (applicable rules, likely counter-arguments, central narrative) once, consistency-checking across the fact base → Sonnet drafts each section from that blueprint applying state-specific rules → draft lands in a work queue for an attorney to review and sign. Costs are logged per task so spikes are traceable.
**Why agentic:** The pipeline makes model/tool-selection decisions per page (which OCR tier to escalate to, which classifier to run), then switches models mid-run (Opus for the plan, Sonnet for drafting), rather than one fixed prompt chain. The classification step narrows what each page is asked, which is the agent's job to decide.
**Generalizable core:** Long-document intake → classify-then-escalate per page → merged, source-linked fact base → cheap model drafts from a plan the expensive model built.
**Deployability:** Claude API with Opus + Sonnet in the same pipeline, a document classifier (fine-tuned or prompt-based), OCR tiering via a cheap OCR vendor fronting the vision escalation, a Postgres fact table with page refs. Month-build at the lower bound. Replaces a paralegal or junior associate's chronology-and-draft work on a backlog. Scale caveat: the citation-linked fact base is the hard part — if you skip it, your drafts hallucinate and lose the whole value.

### 2. Batch file-drop → staged bulk actions → single-point human approval
**Source:** [claude.com/customers/qonto](https://claude.com/customers/qonto) — Qonto, a European SMB bank, shipped an "operator" agent in-app for payroll and invoicing on top of Claude on Amazon Bedrock.
**Mechanism:** User drags 15–20 pay slips (or a CSV of clients) into Qonto → the operator agent routes the request to a payroll or invoicing sub-agent → for payroll, agent reads each pay slip, extracts beneficiary + amount + reference + attaches the slip, and composes one bulk transfer; for invoicing, agent reads the client list and drafts one invoice per client with correct customer + amount → everything is staged in Qonto, nothing is sent → user reviews the stack and approves (or rejects individual lines) → the bank then executes. Haiku runs the simpler sub-steps, Sonnet/Opus the harder ones; deterministic checks run alongside the model on the most sensitive flows.
**Why agentic:** The agent reads unstructured input (pay slip PDFs, CSVs with varying column names) and assembles concrete financial state (a staged bulk transfer) in the system of record. The human decision collapses from "do each one" to a single yes/no on the composed batch.
**Generalizable core:** Batch file drop → agent reads each item, assembles the full action set, stages it in-system → one human approval releases the whole batch.
**Deployability:** Claude API (model-tiered), the vertical SaaS's own write APIs (otherwise this doesn't work — you need to stage, not send), a staging UI that previews what's about to happen. Week-to-month build depending on how exotic the "stage before send" primitive is in the target SaaS. Replaces a bookkeeper, operations assistant, or AP clerk's per-item data entry. Caveat: this pattern lives or dies on the SaaS's ability to stage un-executed actions — most CRMs and ERPs have "draft" states, but not all primitives (payroll runs, inventory moves) are drafted by default.

### 3. Alert-triggered root-cause agent with version-controlled, team-scoped instructions
**Source:** [claude.com/customers/carvana](https://claude.com/customers/carvana) — Carvana runs Claude Tag against production monitoring across their retail-science, release, and wholesale channels.
**Mechanism:** A production monitoring alert posts to a Slack channel → the agent re-reads that team's runbooks, skills (release-comparison logic, log baselines), and standing prompt from the team's own git repo on every run → uses a per-team scoped identity to query the data warehouse (e.g., trace a VIN's status), work tickets, build history, and code → compares the release's errors / warnings / log volume against the pre-release baseline → posts analysis back in the team's required format with code owners tagged → optionally opens a PR adding logging if the logs couldn't explain the problem, or files a ticket, or stands down and flags a follow-up if an upstream outage is the real cause. Scheduled hourly runs do the same against data pipelines and feature flags rather than waiting for an alert.
**Why agentic:** Decisions are made at run time: whether to open a PR, file a ticket, stand down, or dig deeper. The instructions are not baked into the prompt — they live in the team's repo, so a change to the runbook is a merge, not a config push, and every team gets a different agent out of the same binary.
**Generalizable core:** Trigger (alert or cron) → agent pulls team-specific instructions + skills from version control at run time → scoped read of the operational data stores → posts analysis in-channel and conditionally takes a durable action (ticket, PR, nothing).
**Deployability:** Claude API, GitHub + per-team folder convention, Slack bot framework, scoped data-warehouse credentials, a ticket API (Jira/Linear). Week to month. Replaces or augments the on-call engineer's triage window and the "where's the runbook" scramble. Caveat: the repo-as-prompt pattern needs enough teams to be worth the convention — one team is just a system prompt.

### 4. Multi-ticket cluster detection → cross-system coordinated response
**Source:** [claude.com/customers/zendesk](https://claude.com/customers/zendesk) — Zendesk's custom agents running on Claude, reaching 1 million agent executions in seven weeks.
**Mechanism:** The agent monitors incoming support tickets in Zendesk → when the shape of inbound (many similar tickets arriving in a short window) matches an incident signature, the agent treats the cluster as the trigger rather than any one ticket → files a Jira issue summarizing the pattern → posts in Slack to alert on-call engineering → messages each affected customer that a fix is in progress → when a resolution ships, closes the related tickets and leaves a note explaining the problem. After each run, the agent reviews its own work and saves what it learned as a reusable skill for next time. Zendesk logs every tool call for audit.
**Why agentic:** The trigger is a volume/similarity pattern across many records, not a single event. The response coordinates writes to three different systems and does them in order (engineering first, customers second, auto-close last once the fix is confirmed). Self-review-plus-save-skill is the agent writing its own future context.
**Generalizable core:** Volume/pattern across inbound records (not one record) → agent fans out a coordinated multi-system response → logs the resolution and distills a reusable rule for the next occurrence.
**Deployability:** Claude API with tool-use to the customer support platform (Zendesk, Freshdesk, Intercom), the ticket system (Jira/Linear), and the chat (Slack/Teams), plus a small per-customer "skills" store. Month-build; the pattern-detection threshold is the hard tuning. Replaces the lead support rep's "wait, are we getting slammed with the same thing?" instinct and the manual broadcast-and-coordinate afterward. Caveat: needs enough ticket volume for pattern detection to be meaningful — a 20-ticket-a-day team doesn't benefit from this; a few-hundred-a-day team does.
