# 2026-07-04 — Agent Pattern Scan

## TL;DR
Three qualifying patterns today, all mechanism-level and distinct from the last 14 days of logs. Most interesting is GitHub Agentic Workflows' public-preview "safe outputs" split: the agent reads under a read-only role and hands write intents to a separate permission-gated job. That governance shape generalizes far beyond code and is the reusable idea worth stealing. Note: this is the first entry after a five-week gap; scan quality is what it would be for a fresh run rather than continuous.

## Patterns

### 1. Repo-event agentic workflows with permission-split write-back
**Source:** [GitHub Changelog, June 11 2026](https://github.blog/changelog/2026-06-11-github-agentic-workflows-is-now-in-public-preview/) — GitHub Agentic Workflows in public preview; natural-language Markdown compiles to Actions YAML, first customers are using it for issue triage, CI failure analysis, and doc updates.
**Mechanism:** A repo event fires (issue opened, PR pushed, scheduled tick, `/command` in a comment) → the agent runs read-only against the repo, issue body, PR diff, CI logs → it emits structured "safe outputs" (label X, comment Y, open PR Z) → a separate, permission-scoped job executes those outputs after a threat-detection pass for secret leakage and policy violations → the change lands as a normal GitHub event. Replaces the engineer's first pass on the issue backlog and the "why did CI fail" grep session at the start of the day.
**Why agentic:** The workflow does not surface unlabeled issues on a dashboard; it decides what each new issue is and modifies GitHub state. Every trigger fires a decision-plus-action, not a report.
**Generalizable core:** Inbound event in a versioned system → read-only agent enriches with context → structured write-intents handed off to a narrower-scoped executor → auditable state change.
**Deployability:** Native GitHub Actions plus a model provider (Anthropic/OpenAI). A weekend build for a first triage workflow, a week to design the safe-output allowlist and threat rules for a real repo. Replaces first-line eng triage; augments maintainers. No dedicated ML headcount. The reusable piece for us is the split — a proposer-executor pattern with a policy scanner in between, applicable to any client system where autonomous write-back needs auditability (CRM updates, ticket state changes, doc edits).

### 2. Production error to open PR
**Source:** [Zencoder / Zenflow + Sentry MCP, June 2026](https://zencoder.ai/blog/zenflow-sentry-integration-automated-bug-resolution) — Zenflow's "Fix a Bug" pipeline built on the Sentry MCP server; Anthropic's Code with Claude announcement lists Sentry among the launch customers of Managed Agents doing "flagged bug to open PR" end-to-end.
**Mechanism:** A Sentry exception crosses an alert threshold → the agent pulls the stack trace, breadcrumbs, release version, and affected-user count via the Sentry MCP server → correlates with code paths in the repo → writes an `investigation.md` artifact naming the suspected root cause → drafts a patch plus a regression test → opens a PR against the release branch. Replaces the on-call engineer's error-to-diagnosis-to-branch loop for P1/P2 defects; teams using it report ~60% reduction in MTTR on those tiers.
**Why agentic:** The system moves from a live production signal all the way to a merge-ready code proposal, not to an alert dashboard. The output is a PR the maintainer reviews, not a chart of errors over time.
**Generalizable core:** Production signal (error, alert, threshold breach) → agent walks the cause-chain (logs, deploys, recent changes, related records) → drafts a corrective artifact (patch, ticket, response, message) → hands to human for merge/send.
**Deployability:** Sentry (or any observability tool exposing an MCP server) + coding agent (Claude Code, Cursor SDK, Zenflow) + Git provider. Week build for a first pipeline scoped to one service. Replaces the diagnosis phase of on-call; augments senior engineers who now review PRs instead of writing them from scratch. Scale caveat: works well when the error class resembles historical cases; genuinely novel failures still route to humans and the agent should be tuned to abstain rather than confabulate a fix.

### 3. Mid-call live CRM synthesis during human sales conversations
**Source:** [Aloware launch, June 2026](https://www.leadlock.ai/blog/ai-voice-agents-and-crm-integration-automatic-call-logging-and-follow-up/) with Thoughtly production stats — Thoughtly runs ~13K outbound sales calls per month for a nationwide operation; Aloware shipped native inbound/outbound agents pulling full HubSpot context on every call.
**Mechanism:** A sales rep is on a live call (inbound or outbound) → the agent streams the transcript turn by turn → extracts entities as they surface (prospect intent, objection type, competitor named, promised follow-up date) → executes SOQL lookups and creates/updates Salesforce records **during** the call → fires HubSpot workflow triggers before hangup so the next-touch sequence is already queued → post-call summary lands on a record that is already reconciled. Replaces the rep's ~4 hours/week of manual CRM logging plus the "hold on, let me check something" mid-call context lookup.
**Why agentic:** The system takes CRM actions while a human is still speaking, based on the ongoing conversation. Not a passive recorder, not a post-call summarizer, not a dashboard; it is a decision-making listener with write access.
**Why not a duplicate of prior voice-agent patterns:** The 5/24 PollyReach entry is agent-as-the-caller (fully autonomous receptionist). This is agent-as-silent-third-party on a human-to-human call. Different trigger surface, different write cadence, different failure modes.
**Generalizable core:** Live human conversation → agent transcribes and interprets in-flight → writes to a system of record before the conversation ends → primes the next step (follow-up, escalation, routing) so the human hangs up on a completed state.
**Deployability:** Telephony (Twilio, Vapi, or Retell) + real-time STT + LLM entity extraction + CRM API. Month build for reliable schema mapping, confidence gates, and a "confirm on hangup" checkpoint for high-stakes fields (deal amount, close date). Replaces junior CRM ops role; augments AEs. Caveat: any field where a wrong write is expensive should be staged and reviewed at hangup rather than committed live. The same pattern moves cleanly to any structured system-of-record with a live conversation on top: clinical notes during telehealth, ticket updates during support calls, case notes during intake interviews.
