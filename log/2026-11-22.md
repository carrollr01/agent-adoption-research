## Patterns

### 1. Data-pipeline incident agent that sandbox-tests its own fix before PR
**Source:** [Databricks blog — Genie ZeroOps public beta](https://www.databricks.com/blog/genie-zeroops-now-public-beta-autonomous-agent-fixes-data-pipelines-lessons-80000-customer) — public beta opened ~Nov 19, 2026 after a private preview that observed 80,000+ customer pipeline issues.
**Mechanism:** Trigger is a Databricks job/pipeline failure OR a detected data-quality regression where outputs change without a hard failure (schema drift, row-count anomaly, downstream staleness). The agent reads the failing job's code from the linked Git repo, recent run history, upstream table lineage, and the actual error. It spins up a zero-copy shallow clone of the data as an isolated sandbox, attempts a fix, and runs the pipeline against the clone to verify the fix actually produces correct output. If it works, it pushes to a new branch and opens a pull request in the team's repo; the fix still flows through the team's CI/review gates. Replaces the data engineer getting paged at 2am to spelunk through job logs and DAG lineage.
**Why agentic:** Multi-step: ingest failure → read code + data lineage → form a hypothesis → execute a repair in a real runtime → verify against real (cloned) data → produce a reviewable artifact. A dashboard would show you the failed job; this closes the loop to a PR you can merge.
**Generalizable core:** State-change trigger on an operational system → agent reads code + recent history + upstream context → mutates a sandboxed clone to test a hypothesis → opens a human-reviewable change request on the real system.
**Deployability:** Databricks platform required for this exact product, but the pattern ports: GitHub Actions + Claude API + a sandbox runner for any data pipeline (Airflow, dbt, Dagster). Weekend build for a toy version, month build for anything production-grade, because the sandbox-clone step is the hard part. Replaces/augments the data-platform on-call engineer. Scale caveat: the "silent regression" variant needs real observability (lineage, data-quality metrics) already in place.

### 2. AML alert-to-case-file agent for bank compliance desks
**Source:** [FIS press release](https://www.fisglobal.com/about-us/media-room/press-release/2026/fis-aml-investigations-agent-now-commercially-available) and [Fintech Singapore coverage](https://fintechnews.sg/139104/ai/fis-aml-investigations-agent-anthropic-us-banks/) — commercially available to all US banks as of Oct 15, 2026; Amalgamated Bank and BMO are named design partners.
**Mechanism:** Trigger is an AML screening alert (sanctions hit, structuring pattern, unusual transaction behavior). The agent pulls the customer's KYC record, transaction history, counterparty data, prior SAR filings, and external watchlist context from multiple bank systems. It assembles a Level 1 or Level 2 investigation narrative with the data points cited, drafts a recommended disposition (close/escalate/file SAR), and puts it in front of a human analyst. The analyst still approves every case closure, and banks keep their own investigation rules and thresholds. Claude runs in FIS's private cloud; Anthropic never sees customer data. Projected reductions: 90%+ on L1 review time, 98% on L2 case investigation time (vendor projection, not audited results).
**Why agentic:** The agent doesn't just surface the alert, it goes and fetches everything a human would have fetched — across multiple source systems — and writes a reasoned recommendation. The analyst reads a case file, not a dashboard.
**Generalizable core:** Threshold/rule-violation alert → agent fans out to pull every piece of context a human reviewer would normally click through to collect → produces a drafted recommendation with citations → human approves. "Case file, not dashboard."
**Deployability:** The compliance-grade version requires private cloud deployment, auditability, and integration with specific bank cores. The pattern is portable to any alert-triage workflow (fraud review, insurance claims FNOL, HR policy violations, security incident triage, clinical case review). SMB version is a week build on Claude API + MCP connectors to the relevant systems. Scale caveat: regulated-industry variants need audit logging and data residency from day one.

### 3. Inbound sales replaced by a buying agent on the pricing page
**Source:** [Anthropic write-up](https://claude.com/resources/articles/how-anthropics-sales-team-rebuilt-inbound-with-claude-managed-agents) and [Inc. coverage](https://www.inc.com/robert-gillespie/anthropic-replaced-contact-form-for-ai-agent/91415246) — Anthropic's own sales team, late September 2026.
**Mechanism:** Trigger is a prospect opening the chat on the pricing or contact-sales page (also runs in-product and in email reply threads). The agent asks about team size, use case, and procurement constraints. It answers pricing, security, data-handling, and residency questions directly, without a rep in the loop. It then recommends a specific plan and seat count. Small deals route straight to self-serve checkout. Larger deals (500+ seats, BAAs, bespoke contracts) route to a human rep with the full chat history attached so the rep walks in already briefed. Reported result: leads that reach a rep convert 2.5× more often than the old contact form, deals close ~5 days faster.
**Why agentic:** It's not a chatbot answering FAQs. It conducts a real discovery conversation, makes a seat-count and plan recommendation, and decides routing (self-serve vs human). The human rep's first touch is already a qualified opportunity, not a form fill.
**Generalizable core:** Inbound interest signal → conversational discovery with memory → the agent recommends a priced package and either closes it or hands a warm, pre-briefed context package to the human who takes over.
**Deployability:** Claude Managed Agents (beta) is the ready-made stack here, but the pattern is independent of vendor. Week build on Claude API + a CRM webhook + stripe/checkout link generation. Replaces/augments the inbound SDR qualification role. Scale caveat: cost per session-hour (~$0.08 on Managed Agents plus tokens) only pays off above modest inbound volume; for a firm doing 10 inbound leads a month, a form is probably still fine.

### 4. Agent-to-agent handoff: diagnoser passes a work order to a coding agent
**Source:** [Sentry cookbook](https://sentry.io/cookbook/self-healing-workflow-seer/), [Seer → Copilot handoff changelog](https://sentry.io/changelog/gh-copilot-agent-GA/), [Seer → Cursor handoff](https://blog.sentry.io/seer-can-now-trigger-cursor-agents-to-fix-your-bugs) — Sentry Seer, GA'd this year, with explicit handoff integrations to GitHub Copilot and Cursor Cloud Agent.
**Mechanism:** Trigger is a new unhandled exception or regression Sentry flags in production. Seer reads the stack trace, request context, Git blame for the suspect files, and the runbook if one is attached. It produces a root-cause narrative plus a proposed fix plan. Then — and this is the new part — instead of writing the fix itself, it hands the context package (error, root cause, suggested change) off to Cursor Cloud Agent or GitHub Copilot, which runs in the user's own repo with the user's own coding-agent config and opens the actual PR. Sentry links the resulting PR back to the issue so the thread stays closed. The engineer sees: "here's the exception, here's why it broke, here's the PR that fixes it," without an engineer having done the handoff.
**Why agentic:** Two separate autonomous agents with different strengths (diagnosis vs. code-writing in your repo's style) collaborate over a structured work-order payload. The hand-off isn't a human copying the Seer analysis into Cursor; it's an API-level task-dispatch between agents.
**Generalizable core:** Specialist agent produces a diagnosis + work order → dispatches to a second (possibly third-party, possibly customer-controlled) agent that owns the execution environment → results link back. Useful anywhere expertise and execution live in different systems: a legal-review agent dispatching to a document-drafting agent, a diagnosis agent dispatching to a scheduling agent, a planning agent dispatching to a Zapier/n8n worker.
**Deployability:** The specific Seer→Cursor/Copilot path needs Sentry + one of those coding-agent subscriptions. The general pattern is a week build: define a shared "work order" schema and an MCP/webhook dispatch. Weekend build on Claude API + a job queue if you own both ends. Replaces the senior engineer who used to be the handoff point between "we found a bug" and "someone open a PR for it." Scale caveat: the two-agent setup only earns its keep when the diagnosis step is genuinely non-trivial — for simple refactor PRs a single agent is less complex.
