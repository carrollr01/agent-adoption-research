# 2026-08-25 — Agent Pattern Scan

## TL;DR
Risk-scored auto-approval is showing up outside code review: the same "read the artifact, score it against rules, auto-execute low-risk cases, escalate high-risk to a human" loop is running production traffic in insurance FNOL, in construction submittals, and in property-management maintenance intake. The most transferable mechanism today is the auto-triage agent, not the voice receptionist.

## Patterns

### 1. Risk-scored PR auto-approval ("Merge Mommy")
**Source:** [Lenny's Newsletter — Build an AI code review bot in 30 minutes](https://www.lennysnewsletter.com/p/build-an-ai-code-review-bot-in-30) — a Vercel Eve reference implementation the Eve team runs on its own repo and has been repackaged by early adopters.
**Mechanism:** GitHub webhook fires when CI turns green on a PR → agent pulls the diff, the CI summary, and the touched files' recent blame → scores the change across six risk dimensions (blast radius, test coverage delta, migration/schema touch, auth-adjacency, dependency change, revert cost) → posts a single review comment with the score sheet → auto-approves if every dimension is low, or pings the on-call reviewer in Slack with the specific dimensions that failed → writes the verdict back to the PR labels so branch protection can use it. Replaces the first human triage read of every PR (roughly "is this obviously safe?"), not the deep review.
**Why agentic:** It's a durable process that acts on the PR (approve, label, escalate) rather than a comment-only "here's what I noticed" bot; the six-dimension rubric is the policy, and the agent decides which branch of the workflow it takes.
**Generalizable core:** new artifact enters the queue → agent scores it against a small explicit rubric → auto-executes the low-risk branch, escalates the rest with the reasons attached.
**Deployability:** Vercel Eve or a plain Claude API + GitHub webhook + Slack API; a weekend build for a technical team. The rubric is the real work — porting the pattern means writing 6-to-10 domain-specific dimensions, not building infrastructure. The pattern generalizes cleanly to expense-report approval, vendor invoice approval, listing changes in a marketplace, and support-ticket refunds.

### 2. Law-firm inbound mail intake to matter file
**Source:** [Lyron AI — Law Firm Automation with n8n Case Study](https://www.lyron-ai.com/en/news/law-firm-automation-n8n-case-study/); a German firm running self-hosted n8n, cited as cutting manual research time ~70%.
**Mechanism:** New email (or scanned physical mail dropped into a shared inbox) triggers an n8n workflow → agent reads the message, attachments, and any prior thread → classifies as new-matter, existing-matter update, court-deadline notice, or admin → if new, it opens a matter record in the practice-management system, drafts a client intake summary, and files the source doc in the matter folder; if it's a deadline notice, it extracts the date, party, and court, adds a calendar entry with the firm's standard reminder lead-times, and pings the responsible attorney with a one-paragraph brief. Replaces the paralegal's first-pass mail sort plus the manual deadline-into-calendar step.
**Why agentic:** The agent decides which downstream workflow to run based on what the document actually is; different mail types cause different writes to different systems (case management vs. calendar vs. attorney inbox) with no fixed rule tree.
**Generalizable core:** unstructured inbound message → classify → assemble the right record set → write to the right system of record → notify the right human with a pre-summarized brief.
**Deployability:** n8n or Make + Claude API + practice-management SaaS (Clio, PracticePanther, MyCase) + Google Workspace or Outlook + Google Calendar. Week-long build for a small firm; the sensitive part is the classifier's failure modes, so most deployments keep an attorney's approval gate before the calendar write for the first month. Replaces roughly one paralegal FTE-worth of intake work at a 5-attorney firm.

### 3. Construction submittal spec-compliance agent
**Source:** [Varseno — How AI Is Transforming Construction RFI & Submittals in 2026](https://www.varseno.com/ai-transforming-construction-rfi-and-submittals/), aggregating deployments across GCs using Procore and Autodesk Construction Cloud.
**Mechanism:** A subcontractor uploads a submittal (product cut sheet, shop drawing, material data) to the project's document control tool → agent pulls the project spec section referenced in the submittal, the current approved product list, and any relevant building-code appendix → produces a line-by-line compliance check (spec-required value vs. submitted value), flags every deviation with the exact spec citation, and either routes for engineer-of-record review (if any deviation is present) or auto-approves with a comment (if clean) → writes the annotated PDF and the compliance verdict back into the submittal record. Replaces the project engineer's first-pass line check, which typically consumes 3-6 hours per submittal on a mid-size job.
**Why agentic:** The agent picks which spec sections to load based on the submittal's content, then produces a routing decision (auto-approve vs. escalate with reasons). The output is a structured verdict the document-control tool acts on, not a summary a human still has to read.
**Generalizable core:** uploaded document → agent locates the authoritative reference → compares clause-by-clause → routes for approval or human review based on the delta.
**Deployability:** Procore or Autodesk API + Claude with a strong document-parsing pass + a project-spec vector store + a comment/label write-back. Month-long build for a GC with a real IT function; the hard part is getting the spec into a form the agent can cite reliably. Ports to permit intake at municipalities (application → code cross-check → approve or route), to lab-report review at clinical trials sites (result → protocol cross-check → approve or flag), and to insurance-endorsement review at brokerages.

### 4. Property-management maintenance intake and dispatch
**Source:** [US Tech Automations — Property Management Maintenance Automation Compared, 2026](https://ustechautomations.com/resources/blog/property-management-maintenance-automation-platform-comparison-2026); the pattern is running across AppFolio, Buildium, and DoorLoop shops per the 2026 property-management benchmark that flags 44% of PMs using AI in this exact workflow.
**Mechanism:** Resident sends a message via portal, SMS, or email → agent parses the description, asks up to two follow-up questions to disambiguate ("is water actively coming out?" "which appliance?"), classifies issue type and urgency, checks the pre-negotiated vendor list for the right trade and coverage window, checks the resident's lease for who pays, opens the work order in the PMS with everything filled in, schedules the vendor via the vendor's booking API or a scheduling email, and sends the resident an SMS with the confirmed appointment window → routes to a human PM only for high-cost work, ambiguous liability, or vendor-availability gaps. Replaces the property manager's phone/email triage plus the manual vendor dispatch call.
**Why agentic:** The agent runs a real conversation to disambiguate the issue, then acts across four systems (PMS, vendor booking, resident SMS, and internal escalation) with a policy-driven decision tree rather than a fixed script.
**Generalizable core:** inbound freeform request → clarify via short back-and-forth → classify + policy-check → dispatch to the correct external actor → confirm to the requester and write to the system of record.
**Deployability:** AppFolio/Buildium/DoorLoop API + Claude or GPT + Twilio for SMS + a shared vendor roster (often a Google Sheet at SMB scale). Weekend build for the intake-and-classify half; the vendor-dispatch half is a week or two of per-vendor integration work. Replaces roughly half a PM assistant's day; the pattern ports directly to condo-association ticketing, university facilities, and small-hospital maintenance intake.

### 5. Insurance FNOL triage-and-route
**Source:** [Hesper AI — Claims Triage Automation: the 2026 Playbook](https://gethesperai.com/blog/claims-triage-automation-guide/), with quoted deployments dropping FNOL-to-triage from 4-8 hours to under 5 minutes at mid-sized carriers.
**Mechanism:** A First Notice of Loss (FNOL) hits the claims intake queue via phone transcript, portal, or broker email → agent pulls the policy record, coverage terms, historical claim frequency for the insured, and any relevant external context (weather feed for the loss date/zip, catastrophe event flags, fraud model score) → runs the carrier's triage rules to score complexity, severity, and fraud risk → assigns the claim to a specific adjuster queue (fast-track auto-settle candidate, standard, complex, or SIU), attaches a pre-drafted acknowledgement letter for the insured, and writes the routing decision and reasons back to the claims system → escalates to a supervisor only when the score sits inside an ambiguity band or the fraud model trips a hard threshold. Replaces the manual FNOL clerk's triage-and-assign step and shrinks the first-touch SLA by 50-98%.
**Why agentic:** The agent assembles context from four or five sources on demand, applies the carrier's actual triage policy, and takes the routing action itself rather than surfacing a recommendation.
**Generalizable core:** inbound event with a policy attached → assemble policy + history + external context → score against the policy's rules → route the work item, draft the human-facing message, log the decision.
**Deployability:** Guidewire/Duck Creek/Origami claims system + policy admin API + a weather/CAT data provider + Claude or a fine-tuned classifier for severity + a fraud-model call. Month-plus build for a carrier IT team; the pattern is only "SMB" in independent-agency setups, and even there it usually reaches through a claims TPA. Ports cleanly to warranty claims for appliance retailers, chargeback triage at payment processors, and refund-request triage at DTC brands.
