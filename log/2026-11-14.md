# 2026-11-14 — Agent Pattern Scan

## TL;DR
Walmart's Agent Gateway is the standout: the first production spec of a retailer letting outside agents transact under a per-agent identity with a customer-set spend cap, approval gate, and revocable attribution. Alongside it, Gopuff plugged its catalog into Grok as the delivery backend so the customer never opens the Gopuff app, Northern Trust shipped a schema-translation agent that builds its own approval memory across onboarding, and OutSystems + Honk shipped a chat FNOL that dispatches a physical tow truck in parallel with the intake. Six patterns below.

## Patterns

### 1. Per-agent shopping identity with spend ceilings (Walmart Agent Gateway + Agent Profiles)
**Source:** https://ppc.land/walmart-lets-ai-agents-buy-within-customer-set-limits-such-as-50-or-100/ and https://retaildive.com/news/walmart-welcomes-external-ai-shopping-agents-terms-boundaries/833723 — Walmart, announced 2026-10-21, beta rollout underway. Counter-move to Amazon currently blocking Perplexity/Meta agents from shopping on behalf of users.
**Mechanism:** A customer-authorized third-party agent (ChatGPT, Perplexity, etc.) attempts to transact on Walmart. The Gateway reads the customer's Agent Profile (per-agent cap of $50/$100/$200, approval-required flag, data-share scope) plus a privacy-filtered "usual items" view, and real-time catalog/price/stock. It completes the purchase under cap, or bounces a push approval to the customer. Every action is attributed to that specific agent profile so the customer can revoke one agent without revoking the rest. Replaces the customer's periodic replenishment shopping and the merchant's ad-hoc fraud triage on every unfamiliar bot session.
**Why agentic:** The outside agent initiates actions against Walmart's system of record on the shopper's behalf. A dashboard equivalent is a receipt list.
**Generalizable core:** Platform publishes per-agent capability profiles → outside agents bind to a profile → profile sets spend cap + data-share + approval rules → platform brokers every write.
**Deployability:** For a client platform (marketplace, SaaS with transactional APIs, any system outside agents will touch): month-plus for per-agent identity + scoped OAuth + rule engine + async approval push + per-agent kill switch. For a buyer-side agent: weekend to bind. Scale caveat: this is new infrastructure, not a workflow. Only Walmart has shipped it; Amazon's blocking stance is a reminder that the host-platform policy can flip in weeks.

### 2. Third-party-chat catalog as the storefront (Gopuff connector in Grok Bot)
**Source:** https://retailboss.co/gopuff-adds-in-chat-checkout-to-grok-bot/ and https://www.supermarketnews.com/grocery-technology/gopuff-is-now-connected-through-grok-bot — Gopuff (instant-delivery retailer, ~500 micro-fulfillment centers) exposing catalog + delivery + payment to xAI's Grok, announced 2026-11-11.
**Mechanism:** Trigger is a user utterance in Grok ("I'm sick, send cold meds and tissues", "weekly groceries"). The agent calls Gopuff's connector to read live inventory, pricing, user address, delivery-window availability, and promotions, plus prior-turn chat context for dietary preferences and past orders. It assembles a cart, surfaces total and ETA, asks for one approval tap, then writes the order to Gopuff's dispatch system routing to the nearest MFC. Replaces the Gopuff mobile-app shopping funnel as the entry point; the customer never opens the retailer's own app.
**Why agentic:** The user states a need in natural language, not a SKU. Mapping intent to in-stock SKUs at the right MFC with compatible delivery windows requires live calls across inventory, pricing, geo, and logistics. A catalog page can't do it.
**Generalizable core:** Natural-language intent in a third-party chat surface → agent queries inventory + pricing + logistics APIs → proposes a cart → single-tap approve → order downstream.
**Deployability:** Week to expose an existing product catalog as an MCP server over existing commerce/payment APIs. The hard part is partnership with the agent host; OpenAI business accounts also shipped Nov 10, 2026 as an alternate route for SMBs without needing Grok. Role replaced: the mobile-app shopping funnel for a slice of users. Stack: Claude API + MCP, or any agent-host-compatible connector spec + existing commerce backend.

### 3. Client-data schema translation with growing approval memory (Northern Trust + Microsoft)
**Source:** https://www.cio.com/article/4245961/northern-trust-streamlines-client-onboarding-with-ai-agent.html and https://www.morningstar.com/news/business-wire/20261109144614/northern-trust-and-microsoft-collaborate-to-transform-client-onboarding — Northern Trust, ~$1.8T AUA; onboarding institutional clients (asset managers, family offices), announced 2026-11-09.
**Mechanism:** Trigger is a new client's historical transaction/position file arriving in any format they happened to export. The agent reads the file plus a "governed knowledge layer" of previously-approved onboarding mappings, infers the mapping to Northern Trust's Front Office Solutions schema, writes a draft to Excel/SharePoint for an analyst to correct and approve, and feeds approved mappings back into the knowledge layer. The next client with a similar export shape runs cleaner. Reported 2.5 weeks of analyst data prep compressed to 3 days.
**Why agentic:** Every client's export is shaped differently, so no form or ETL template can be prebuilt. The agent iteratively infers the mapping, escalates exceptions, and the system gets smarter with each approval. A dashboard can't propose a schema.
**Generalizable core:** External file in unknown shape → agent infers mapping against internal schema + prior-approvals memory → draft to a reviewable surface → human approves → knowledge layer updated for next time.
**Deployability:** A week for a scoped pilot on Claude API + MCP (Sheets/Drive + file store + approval channel); a month for governance and audit. Stack-agnostic. Role replaced: analyst's first-week onboarding data prep. Caveat: the reusable primitive here is the growing approval memory, not "back-office automation" generally.

### 4. Chat FNOL with parallel physical-world dispatch (OutSystems + Honk)
**Source:** https://www.outsystems.com/blog/posts/introducing-outsystems-agentic-first-notice-of-loss and https://insurancenewsnet.com/oarticle/outsystems-introduces-agentic-claims-solution-to-modernize-policyholder-experiences — OutSystems Agent Workbench packaged for auto carriers, Honk as the roadside marketplace, GA announcement 2026-11-11.
**Mechanism:** Trigger is the policyholder tapping "File a claim" in the carrier's app after an accident. The Claims Conversation Agent runs a safety check first ("are you OK, is the car safe"), then fires three subagents in parallel: a dispatch agent that calls Honk's tow-network API, a coverage-check agent that validates the loss against policy terms, and an image-analysis agent that extracts damage metadata from uploaded photos. Writes an FNOL record to the carrier's claims system, a tow dispatch + ETA to Honk, and a status tile back to the policyholder's chat. Human adjuster retains coverage, fault, and payment calls.
**Why agentic:** Real-world side effects, keyed off unstructured chat + photos, dispatched in parallel. A form cannot route a tow truck or decide whether the photo shows a drivable car.
**Generalizable core:** Mobile-app event → conversational intake agent → parallel specialist agents (one of which calls a physical-world marketplace API) → writeback to system-of-record + human-approval seam for the material decisions.
**Deployability:** Carrier integration is week-to-month on OutSystems; the pattern itself ports to any "customer-reports-incident → multi-vendor dispatch + system writeback" shape (field service, equipment breakdown, travel disruption, home warranty). Scale caveat: regulated — NAIC AI model bulletin adopted in 24+ states forces documented decision gates, which is why coverage/liability stay human.

### 5. Voice roleplay simulator with scored rubric (Impel)
**Source:** https://claude.com/customers/impel — Impel, automotive AI vendor; internal training partner for their own reps on dealer conversations. Roleplay corpus built from 150K+ recorded Gong calls and the Salesforce instance.
**Mechanism:** Trigger is a rep logging in to practice a scenario, often off-hours or pre-launch. The build pipeline mined the Gong corpus + CRM for real objection patterns, personas, and deal shapes. At runtime the agent runs a speech-to-text/text-to-speech voice conversation in character as a specific dealer persona ("Derek, who has limited time"), through a full track from sales objections to support follow-ups. At the end it writes a structured scorecard against a rubric (objection handling, rapport, product knowledge, next steps) and DMs it to the rep in Slack. Replaces solutions-engineer / sales-VP time that used to sit in and roleplay, and replaces first-attempt practice happening on live dealers.
**Why agentic:** Real-time conversational turn-taking in a persona, followed by a rubric-scored evaluation. Neither piece is viewable in a report, and the persona depth depends on mining a corpus of real calls.
**Generalizable core:** Realistic voice roleplay persona + scored rubric → async self-paced practice for any customer-facing skill.
**Deployability:** Mid-to-enterprise. Needs STT/TTS, rubric design, and a corpus of real calls to seed personas. Ports cleanly to: field-service dispatcher training, medical intake practice, CS QBR rehearsal, legal client-intake roleplay. Distinct from the already-logged "voice-enabled phone number agent" pattern because the voice endpoint is a training partner, not a live caller.

### 6. Phishing-report triage with orchestrator + specialist subagents (Red Canary Managed Phishing Response)
**Source:** https://redcanary.com/blog/threat-detection/phishing-ai-agent/ with Nov 2026 cross-reference https://www.ajayk.sh/blog/ai-soc-agents-security-operations-2026/ — 21 production agents across customer SOCs, processing >30M security events.
**Mechanism:** Trigger is an end user hitting "Report Phish" in Outlook/Gmail; the mail forwards to a Red Canary collector. The orchestrator spawns specialist subagents: a header/SPF/DKIM/DMARC parser, a URL and IP enrichment agent, an attachment sandbox, and a spoofing checker. It reads the raw .eml plus prior verdicts on the same sender/domain and the org's reporter history, and produces a structured verdict (malicious / suspicious / benign) with per-step evidence. Writes three destinations: tailored feedback email to the reporting employee, a SOC case only for non-benign verdicts, and a "Previous Assessment" record so later duplicates don't get conflicting answers. Replaces the Tier-1 SOC analyst's phishing triage queue.
**Why agentic:** Every report is a free-text artifact needing branch-dependent tool orchestration (WHOIS, URL detonation, header parse, sandbox). A dashboard can only count tickets.
**Generalizable core:** Standardized user report → orchestrator + specialist sub-tools → verdict with evidence → branched writes (user-facing + ops-facing) + dedupe memory.
**Deployability:** Reproducible in LangGraph or the OpenAI SDK with VirusTotal + urlscan + mailbox API, ~month of integration work. Role replaced: Tier-1 phishing triage specifically. The "orchestrator + specialist subagents + branched writes + dedupe memory" shape is the primitive worth reusing; it generalizes to any user-reported-incident queue (abuse reports, product-safety complaints, content moderation).
