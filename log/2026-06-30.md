# 2026-06-30 — Agent Pattern Scan

## TL;DR
Three concrete mechanisms emerged after a long gap since the last scan. The standout is rejection-event recovery: an agent that watches for an inbound rejection (e-billing kickback, denied claim, returned filing) and drafts a data-informed appeal before anyone on the team notices. The other two — Lassie's portal-scraping payment reconciliation for medical practices, and Metabase's Reprobot reproducing user-reported bugs in ephemeral environments — both replace specific human triage roles rather than augmenting them.

## Patterns

### 1. Rejection-event recovery agent (Aderant Appeals Agent)
**Source:** [Aderant Agent Center, Momentum Global 2026](https://www.aderant.com/news-pr/aderant-introduces-agentic-law-firm-operations-ai-agent-center/) — Aderant shipped a three-agent Agent Center on the Stridyn platform; one of the three is the Appeals Agent, which targets e-billing rejections in law firm accounts receivable.
**Mechanism:** Client e-billing systems (LEDES vendors) reject a submitted invoice with a coded reason. The agent picks up the rejection event, reads the rejection code, the underlying matter context, the original time entries, and any history of successful appeals for similar codes, then drafts a data-informed appeal response and queues it for a billing partner to approve before resubmission. Output writes back to the firm's billing workflow.
**Why agentic:** It's not a notification or a queue. It interprets a coded rejection, assembles matter-specific context the human would have to look up by hand, and produces an artifact (the appeal draft) that resolves the event. The collections agent shipping alongside it works the same way — payment-risk signal triggers a prioritized dunning sequence rather than just surfacing a list.
**Generalizable core:** Inbound rejection event → agent reads rejection reason plus original submission context plus history of successful appeals → drafts response → human approves and resubmits.
**Deployability:** The Aderant version is a vertical product on Stridyn/MADDI for firms already on Expert Sierra. The generalizable shape is much easier — webhook from the rejecting system (claim clearinghouse, permit portal, tax filing service, content moderation API), Claude or similar for drafting against a retrieval index of past appeals, light approval UI. Week-build for a single rejection type; month-build to handle a portfolio of rejection codes well. Replaces the AR clerk or paralegal who handles rejection queues — and recovers revenue that otherwise gets written off because nobody had time to appeal.

### 2. Portal-scraping payment reconciliation agent (Lassie)
**Source:** [Lassie raises $35M Series A led by a16z, June 3 2026](https://www.businesswire.com/news/home/20260603909717/en/Lassie-Raises-$35M-Led-by-Andreessen-Horowitz-to-Build-AI-for-Small-Businesses-to-Run-Themselves) — Lassie operates in 700+ medical and dental practices across 49 states; the company describes the agent's loop in product copy and the funding coverage repeats it in detail ([Unite.AI summary](https://www.unite.ai/lassie-raises-35m-series-a-to-build-ai-agents-that-handle-medical-practice-administration/)).
**Mechanism:** On a schedule (and likely on EFT/ERA arrival webhooks where supported), the agent logs into each payer's insurance portal, retrieves explanations of benefits and remittance data, matches each payment line to the right claim and patient in the practice management system, posts payments and adjustments into the PMS, then cross-checks the deposited amount against the practice's bank feed. Claim follow-ups and appeals run from the same loop. Lassie reports up to 80 hours per practice per month eliminated, with some practices recovering 190.
**Why agentic:** It moves money on its own. It crosses systems with no shared schema (payer portals, PMS, bank), handles partial payments, denials, and adjustments without a fixed mapping, and only escalates when the reconciliation breaks. A dashboard would just show what's unreconciled.
**Generalizable core:** Scheduled poll of an external portal → agent extracts unstructured-ish payment data → matches against system-of-record → posts the reconciliation → flags exceptions for human review.
**Deployability:** The portal-scraping piece is the hard part — payer portals fight automation, and Lassie has clearly built dedicated infrastructure for it. For non-healthcare reuse (e.g., wholesale distributors reconciling supplier rebates against AP, agencies reconciling ad-platform payouts, contractors reconciling card processor deposits), the same shape works but with friendlier APIs. Stack: Playwright or browser-use under an orchestration layer, Claude or similar for the reconciliation reasoning, write-back via the system-of-record's API. Distinct from the 5/25 invoice-chase pattern, which is outbound dunning — this is inbound money the practice already earned but couldn't get into the PMS without manual effort. Replaces the AR specialist or billing coordinator role for revenue cycle management.

### 3. Bug-reproduction agent on every new GitHub issue (Metabase Reprobot)
**Source:** [Metabase: Meet Repro-Bot, our GitHub issue triage agent](https://www.metabase.com/blog/reprobot-github-issue-triage-agent) — Metabase, the OSS BI vendor, deployed Reprobot against its own metabase/metabase repo, which carries a very high volume of user-reported bugs.
**Mechanism:** A new GitHub issue is the trigger. Reprobot parses the description, extracts the purported steps to reproduce, and provisions an ephemeral Metabase instance the same way a developer would (Docker plus DB config). It uses Playwright for the browser steps and REPL access into the running instance for state inspection. It has full read access to the codebase and the existing tests, which it uses to figure out where to look. If it reproduces the bug, it writes a failing test against the codebase and attaches the test, the stack trace, and the exact environment state to the issue.
**Why agentic:** It does the same thing a human triage engineer does — read the report, set up an env that matches, try the steps, capture state — and produces an artifact (a failing test) the human engineer can drive a fix against. It either succeeds or comes back with concrete failure data; it doesn't just route or summarize.
**Generalizable core:** Inbound bug/issue/complaint with prose-described state → agent assembles a matching execution environment → runs the described steps → produces a reproducible artifact (failing test, screen capture, log bundle) → attaches to the originating record.
**Deployability:** Reuse outside of software-on-software contexts is harder, but the same pattern works for any SaaS support org with a sandboxable test environment, and for QA-heavy products in regulated industries (medical device firmware, fintech transaction flows, e-commerce checkout). Stack: webhook from GitHub or the ticketing system, Docker for the sandbox, Playwright plus the product's REPL or test harness, Claude or similar for the orchestration. Month-build at minimum — the sandbox provisioning is where teams underestimate the work. Replaces the first-pass triage engineer who spends hours reproducing user-submitted bugs before the actual fix begins.
