# 2026-09-02 — Agent Pattern Scan

## TL;DR
Four patterns worth logging. The strongest is the "alert-to-investigation" pattern: a threshold trip triggers an agent that correlates logs, traces, and deploy history and writes a root-cause hypothesis into the alert itself, replacing the on-call engineer's dashboard-hunting step. This is the clean anti-dashboard shape we've been looking for.

## Patterns

### 1. Alert-triggered investigation agent replaces dashboard hunting
**Source:** [Elastic Observability Labs — Beyond the dashboard: agentic troubleshooting](https://www.elastic.co/observability-labs/blog/beyond-the-dashboard-the-move-toward-agentic-troubleshooting) — Elastic Agent Builder + Workflows generally available; described as production usage inside SRE teams.
**Mechanism:** Standard monitoring rule fires (e.g. error rate above 5% for 10 minutes) → agent reads the alert payload, pulls related traces, logs, metrics, recent deploys, and known incident runbooks → writes a root-cause hypothesis and the supporting evidence chain into the alert or an incident channel → optionally files a Jira ticket pre-populated with the suspect commit and affected service. Replaces the on-call engineer's first 15–30 minutes of manually opening dashboards and correlating data.
**Why agentic:** The dashboard existed before; the human was doing the correlation. This inverts it: the correlation is the automated step and the dashboard becomes something the engineer only opens if the hypothesis is contested.
**Generalizable core:** Threshold crossed in any monitoring system → agent enriches with adjacent context (recent changes, related entities, historical incidents) → writes a hypothesis into the notification channel → human confirms or overrides.
**Deployability:** Elastic-native today; the same shape is buildable in a week on Claude API + MCP with connectors to Datadog/Grafana/Sentry/GitHub. Replaces the first-responder triage step, not the fix. Works for any team already routing alerts to Slack or PagerDuty; no ML headcount needed. This exact pattern also generalizes off the SRE use case to any thresholded metric with a human diagnostic loop behind it (inventory, churn signals, cash flow anomalies).

### 2. Employee lockout resolves itself through Slack-mediated manager approval
**Source:** [n8n case study: Delivery Hero](https://goodspeed.studio/blog/n8n-case-studies-automation-success-stories) and [Mooretech breakdown](https://www.mooretech.io/blog/hr-automation-delivery-hero-case-study) — 1,400 tickets/month automated, average lockout time down from 35 to 20 minutes, ~200 hours/month of employee time recovered.
**Mechanism:** Okta lockout event → Slack bot DMs the locked-out employee: "want to recover?" → on confirmation, bot DMs their direct manager for approval with a 2-minute SLA → on approval, workflow fires API calls to Okta (reset), Jira (create ticket record for audit), and Google Workspace (restore access). Replaces the IT helpdesk ticket triage step and the manual identity-verification back-and-forth.
**Why agentic:** The trigger and the routing (who the manager is, what systems need to be touched, whether the request looks legitimate) is the agent's job. The dashboard equivalent would be a helpdesk queue where someone has to pick up the ticket; this deletes the queue.
**Generalizable core:** System event on a person's record → bot pings the person → routes to their approver in the channel they already live in → executes cross-system API calls → logs the audit trail. Same shape works for any request-approval-execute loop: expense approval, access requests, PTO, refund escalations, deploy approvals.
**Deployability:** n8n or Make weekend-scale build if the underlying identity/HR systems have APIs (they usually do). Replaces first-line IT helpdesk work. Delivery Hero is enterprise scale but nothing in the mechanism requires it; a 20-person firm with Google Workspace, Slack, and any identity provider can run the same pattern.

### 3. Multi-specialist agent chain runs healthcare RCM end-to-end
**Source:** [Thoughtful AI — Revenue Cycle Automation](https://www.thoughtful.ai/platform/revenue-cycle-automation) and [Thoughtful — Breaking down silos in RCM](https://www.thoughtful.ai/blog/cross-functional-ai-agents-breaking-down-silos-in-revenue-cycle-management) — deployed at Easterseals Central Illinois and other behavioral health providers; 35-day reduction in average AR days, ABA claim denials held below 2%.
**Mechanism:** Six named agents handling sequential handoff (Eva/eligibility → Paula/prior auth → Cody/coding → Cam/claims submission → Dan/denials & appeals → Phil/payment posting). Each agent owns a discrete revenue cycle step, reads from EHR + payer portals + accounting system, writes results back into the RCM system, and hands the case to the next specialist based on state. Human staff step in only for exceptions or appeals judgments.
**Why agentic:** Not a single "billing dashboard." Each agent independently does its job, passes state forward, and fires downstream work without a human orchestrator. The generalizable insight is that the specialist pipeline pattern beats a generalist agent for compliance-heavy multi-step workflows.
**Generalizable core:** Long process with N clearly defined handoff stages → one narrow-scope agent per stage → shared state object passed forward → human handles exceptions the pipeline flags. Applicable outside healthcare: mortgage underwriting, permit applications, insurance claims, procurement approvals, immigration filings — anywhere a case moves through defined stages with clear entry/exit criteria per stage.
**Deployability:** Thoughtful ships this as a platform, and it's month-scale to build competitively (dedicated compliance and integration work per stage). Feasible for a two-person team only in narrower verticals where the stages fit in a Claude API + MCP + n8n stack. Scale caveat: works because Thoughtful has direct payer-clearinghouse integrations most SMBs don't have to replicate, but the pipeline pattern itself is copyable without them. Note: Thoughtful is [sunsetting stand-alone services post-Smarter Technologies merger](https://acuity.news/technology/thoughtful-ai-shutdown-smarter-technologies-aba-transition-2026/), so the case study is a pattern reference, not an active build-with vendor.

### 4. Autonomous long-horizon coding run on a codebase the team doesn't own
**Source:** [Anthropic 2026 Agentic Coding Trends Report](https://resources.anthropic.com/2026-agentic-coding-trends-report) — Rakuten case study, 7-hour autonomous single run.
**Mechanism:** Engineer defines a numerically verifiable specification (in Rakuten's case, extract activation vectors from vLLM, a 12.5-million-line open source library the team doesn't own) → Claude Code runs autonomously for 7 hours, reading the target codebase, writing extraction code, comparing outputs against a reference method, and iterating until it hits 99.9% numerical accuracy → returns the finished implementation. Reduced a task from 24 working days to 5. Replaces the exploratory research spike that a senior engineer would normally do.
**Why agentic:** Not just autocomplete on the engineer's screen — the agent is running loops, writing and executing verification code, and self-correcting against a numerical target inside a codebase it has to read cold. The engineer sets up the correctness oracle and comes back later.
**Generalizable core:** Numerically or otherwise machine-verifiable spec → autonomous long-running agent → produces working code against an unfamiliar codebase → engineer reviews the finished output. Works whenever "success" is testable: data pipeline rewrites, migration scripts, extraction from vendor SDKs, format conversions, backtesting harnesses.
**Deployability:** Week-scale for a small team using Claude Code today; the hard part is defining the verification oracle, not the agent itself. Replaces the "engineer spends a week understanding an unfamiliar library" work. Scale caveat: expects real infra for long-running background jobs and cost tolerance for multi-hour runs, but the mechanism is not enterprise-only — a two-person firm doing SDK integration work could use it directly.
