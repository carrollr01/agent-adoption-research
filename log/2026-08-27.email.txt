# 2026-08-27 — Agent Pattern Scan

## TL;DR
The strongest pattern this scan is AppZen's AP Inbox Service Center: eight prebuilt agents that turn a shared vendor-facing email inbox into a classified, action-taking service center, with a dedicated fraud-signal agent for bank-change requests. The generalizable skeleton is "shared inbox with predictable request classes" and it maps onto customer service, dispatch, admissions, or any queue that today gets triaged by a human reading email top-to-bottom.

## Patterns

### 1. Classified vendor-inbox agents for accounts payable
**Source:** SiliconANGLE (Apr 2026) https://siliconangle.com/2026/04/21/appzen-targets-accounts-payable-bottleneck-new-ai-agent-service-center/ and AppZen product page https://www.appzen.com/ap-inbox-service-center — AppZen shipped an AP Inbox Service Center in April 2026 with eight prebuilt agents that fully manage the vendor-facing AP mailbox for finance teams.
**Mechanism:** Vendor email arrives in the shared AP inbox. An intake agent classifies it into buckets like payment-status inquiry, bank-account change, W-9 request, duplicate-invoice claim, statement reconciliation, and remittance request. A Payment Status Responder pulls the invoice record from the ERP and replies with real-time status plus an optional CSV. A Bank Change Verification Guardian scores the request against fraud signals (domain mismatch, urgency language, unknown sender, process bypass), escalates risky ones to Vendor Management with the risk classification attached, and lets clean ones flow to the update workflow. Every reply and every escalation writes back into AppZen as a trackable, auditable ticket.
**Why agentic:** The old inbox was a human reading each message and deciding what to do; the new one is a set of agents that decide, act, and log. The dashboard here is the audit trail after the work is done, not the surface the AP clerk works on.
**Generalizable core:** Shared inbox with predictable request classes → intake classifier fans out to per-class specialist agents → each specialist reads the system of record, drafts or executes the reply, and either auto-sends or escalates on defined risk signals.
**Deployability:** Enterprise-flavored (AppZen sits on ERP integrations and is priced for mid-market and up), but the same skeleton is a week-build at SMB scale using Claude API + Gmail MCP + QuickBooks/Xero connector + a small rules layer for escalation. Replaces one or two AP clerks per shared inbox in the enterprise version; for an SMB it typically augments the bookkeeper by absorbing the "reply with invoice status" and "answer W-9 requests" work. Scale caveat: works best when the inbox actually has predictable request classes; a low-volume or highly bespoke inbox is not the target.

### 2. Incident-alert triage agent that pre-investigates before it pages a human
**Source:** PagerDuty SRE Agent product docs https://support.pagerduty.com/main/docs/sre-agent and PagerDuty blog Q1 2026 update https://www.pagerduty.com/blog/ai/new-enhancements-to-pagerdutys-sre-agent-triage-faster-without-waking-a-human/ — PagerDuty's SRE Agent is deployed inside incident workflows across their customer base; PagerDuty reports 50% faster resolution on incidents where the agent runs first.
**Mechanism:** An incident fires in PagerDuty above a severity/priority threshold. The workflow invokes the SRE Agent instead of paging a human first. The agent reads recent log windows from Datadog (or the connected observability platform), pulls the matching runbook from Confluence or GitHub, checks the state of related dependencies (queue depth, connector health, recent deploys), and produces a triage note attached to the incident. When the runbook allows, it takes safe remediation (rollback, restart, scaling) itself. If it cannot resolve, it pages the on-call with the summary and evidence already assembled, so the human starts at "here is what is broken and here is what I tried" instead of "an alert fired."
**Why agentic:** A dashboard shows an alert and lets a human hunt. This agent reads the alert, decides which logs and runbook are relevant, executes the runbook, and writes the finding back into the incident. The human enters the loop only when the agent cannot close it.
**Generalizable core:** Alert crosses a threshold → agent gathers evidence from the connected systems named in the runbook → attempts the deterministic remediation → escalates to a human with the investigation attached, not just the alert.
**Deployability:** Enterprise fit for PagerDuty customers; the same pattern is a week-build for any SMB that already runs Sentry, Datadog, or a status-page monitor: Claude API + observability MCP + a runbook markdown folder + a Slack escalation. Replaces the first 15-30 minutes of an on-call engineer's night for known-shape incidents. Scale caveat: only pays off when there are enough repeat incidents that a runbook exists, which is usually not a single-developer shop.

### 3. Pre-interview candidate briefing agent
**Source:** Zapier customer story, JBGoodwin REALTORS https://zapier.com/blog/jbgoodwin-realtors-automates-recruiting-with-zapier/ — a 900-interview-per-year real-estate brokerage in Texas replaced manual applicant research with Zapier Agents running against HubSpot, saw 20-25% less recruiter data entry, and credited the workflow with a 37% year-over-year increase in recruiting.
**Mechanism:** An applicant submits an application, which lands as a new contact in HubSpot. A Zapier Agent fires on that record, pulls the applicant's public profile from LinkedIn and enrichment sources, cross-references transaction history and licensing data available for real-estate agents, drafts a one-page briefing that summarizes background, red flags, and likely fit, and writes it back onto the HubSpot record before the recruiter opens it. Follow-up nurture messages are sent from the same agent through Mailchimp or JustCall when the applicant does not respond in a defined window.
**Why agentic:** Not a "candidate database" dashboard. The trigger is a specific record event, the read fans across multiple sources, the write is a synthesized artifact, and the follow-up cadence is executed rather than displayed. What was five to ten minutes of a recruiter's time per applicant is now zero minutes.
**Generalizable core:** New record in a CRM → agent enriches from external sources → writes a synthesized briefing back onto the record → runs a defined nurture cadence if no reply.
**Deployability:** Weekend build. Zapier Agents + HubSpot (or any CRM) + LinkedIn/Apollo/Clay + Mailchimp is the demo stack; a lighter version is Claude API + a webhook and one sheet. Augments a recruiter or a partner in a professional-services firm; also fits admissions, member intake at a gym or club, and inbound demo requests. Scale caveat: enrichment sources cost money at volume, but volumes at the SMB level are trivially cheap.

### 4. Stalled-shipment proactive-outreach agent
**Source:** eesel AI on Gorgias delay thresholds https://www.eesel.ai/blog/gorgias-chatbot-to-check-delivery-status-and-delay-thresholds and Stormy AI's 2026 Shopify support playbook https://stormy.ai/blog/shopify-support-automation-playbook-2026 — pattern is being deployed on Gorgias + Shopify in mid-to-high-volume e-commerce shops in 2026 as the "autonomous resolution" replacement for reactive shipping tickets.
**Mechanism:** The agent watches shipping status across the Shopify order file on a schedule (typical threshold is "no carrier scan for 48 hours" or "estimated delivery date passed"). When a shipment trips the threshold, the agent pulls the carrier tracking record, checks for regional carrier-service advisories, joins the order and customer record, and drafts a personalized note that acknowledges the specific delay, sets an updated expectation, and often attaches a small goodwill token (discount code, priority reship option). The note is either sent as a proactive Gorgias message before the customer has opened a ticket, or logged as a queued ticket with the reply already drafted.
**Why agentic:** The threshold is the trigger, not a dashboard row a human has to notice. Between trigger and outbound message the agent reads three separate systems and composes a customer-specific reply. The customer's first touch is the resolution attempt, not the complaint.
**Generalizable core:** Threshold crossed in an operational system → agent reads related records for context → drafts a customer-specific outbound message → sends proactively or queues with the draft attached.
**Deployability:** Weekend build in Gorgias for Shopify shops using its native automation surface; a day-to-week build outside Gorgias using Claude API + the carrier tracking API + Shopify (or WMS) + the outbound channel (Klaviyo, Postscript, or plain email). Replaces the support rep who scans the shipping report each morning. The same skeleton works for "invoice past-due but no reply", "loan application stuck at underwriter for X days", "patient no-show risk on tomorrow's schedule", any workflow where a stall in an operational system is the actual event.
