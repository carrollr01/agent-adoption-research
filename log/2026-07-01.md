# 2026-07-01 — Agent Pattern Scan

## TL;DR
The single most interesting pattern today is the autonomous carrier check-call voice agent (Tai TMS Track & Trace, HappyRobot, others), which places outbound voice calls to truckers on schedule or geofence triggers, holds a real conversation to extract location/ETA/exceptions, and writes the update directly to the TMS. It compresses a $165K/year dispatcher headcount problem into an outbound voice loop with a structured write-back, and the same skeleton — "chase status from a human via voice/SMS and write the answer to the system of record" — copies into any coordination-heavy job. Second-most interesting is Lassie's remittance-posting agent for dental and medical practices, which is notable less for the AI and more for the local Windows bridge that finally lets agents automate against the on-prem software most SMBs actually run.

## Patterns

### 1. Autonomous carrier check-call voice agent
**Source:** [Tai TMS Track & Trace Agent](https://markets.financialcontent.com/stocks/article/gnwcq-2026-4-13-tai-tms-introduces-ai-track-and-trace-agent-making-check-calls-a-thing-of-the-past), launched April 2026; [debales.ai carrier check-calls automation](https://debales.ai/blog/carrier-check-calls-automation-freight-broker-cost) — freight brokerages, small-to-mid carriers running Tai, McLeod, Turvo, or similar TMS platforms.
**Mechanism:** Trigger fires when a load's status is stale in the TMS or the truck crosses a geofence (pickup ETA, halfway point, delivery ETA). Agent looks up the driver's phone number from the TMS load record, places an outbound voice call, holds a real conversation ("Hey, this is a dispatch check-in on load 40218 to Dallas — where are you and what's your ETA?"), parses the free-form answer, retries via SMS if the driver doesn't pick up, and writes the parsed location/ETA/status back to the TMS load record. Escalates to a human dispatcher only when the driver reports an actual problem (breakdown, delay, wrong address). Replaces the dispatcher task of manually calling every active truck every few hours.
**Why agentic:** The agent has to conduct a real voice conversation with variable outcomes — drivers ramble, mishear, describe locations in landmarks not zip codes — and decide whether the answer actually resolves the check or reveals an exception. It's not a template; a rule-based system fails on the 60% of calls where the driver says something the script didn't anticipate.
**Generalizable core:** scheduled or geofence trigger → agent identifies contact via the system of record → agent runs voice/SMS conversation → parses free-form response → writes structured update to system of record → escalates only on exception.
**Deployability:** Voice stack (HappyRobot, Vapi, or Retell) + TMS webhooks/API + Twilio SMS fallback + Claude API for parsing. Week-long build for a single TMS integration; two to four weeks across multiple. Replaces roughly 0.5–1.0 FTE per medium brokerage. The same pattern copies straight to field service ("does that install need another day?"), delivery driver dispatch, wedding/tour operators tracking bus arrivals, and construction subcontractor coordination — anywhere a human's daily job is "ping X for status and update the schedule." No dedicated ML headcount required.

### 2. On-prem remittance-posting agent (Lassie)
**Source:** [Lassie $35M Series A, June 3 2026, a16z-led](https://www.unite.ai/lassie-raises-35m-series-a-to-build-ai-agents-that-handle-medical-practice-administration/); [a16z investment thesis](https://a16z.com/announcement/investing-in-lassie/) — deployed in 700+ independent dental and medical practices across 49 states.
**Mechanism:** Trigger is the arrival of an ERA (electronic remittance advice) from a payer plus the matching EFT in the practice's bank. A local Windows agent installed on the office PC bridges the practice's on-prem EHR (Dentrix, Eaglesoft, Open Dental) to Lassie's cloud. The cloud agent parses the payer remittance, matches each line to the correct patient/claim in the PMS, applies the practice's contractual adjustment logic per payer (BCBS, UHC, Delta Dental, Cigna, Aetna, MetLife, Guardian), and posts payment + adjustment + write-off directly into the PMS. Plaid/MX confirms the EFT hit the bank. When records reconcile, the agent posts silently. When they don't — underpayment, mismatched EFT, ambiguous write-off — the agent files an exception into a staff review queue instead of leaving it in a backlog. Replaces the biller's daily job of manually keying payer statements into the PMS.
**Why agentic:** The reconciliation crosses three data sources (payer ERA, bank deposit, PMS claim record) and has to apply practice-specific contract logic that differs by payer. It's not RPA — the exceptions (which are the whole point) require reasoning about whether a mismatch is a legitimate write-off, a payer error, or a keying mistake.
**Generalizable core:** multi-source inbound event (payment, invoice, delivery, record) → agent reconciles against system of record with entity-specific rules → auto-posts on clean match → routes only exceptions to a human queue.
**Deployability:** The novel piece is the local Windows bridge. Most SMBs (dental, veterinary, auto repair, small legal, small insurance, small real estate) run on-prem verticalSaaS with no public cloud API — Cornerstone/AVImark for vets, Mitchell/ShopKey for auto, TABS3 for small legal, QQCatalyst for insurance agencies, Top Producer for realtors. A lightweight bridge process on the office PC unlocks automation against systems no cloud tool can reach. Month-plus build per vertical because you have to reverse-engineer each PMS's data model. Anthropic's Agent Skills spec makes the repeat-per-payer logic easier to package once you've done it once. Replaces one back-office biller per practice; scales to a "one agent, N practices" service model.

### 3. Natural-language markdown as workflow definition (GitHub Agentic Workflows)
**Source:** [GitHub Agentic Workflows public preview, June 11 2026](https://github.blog/changelog/2026-06-11-github-agentic-workflows-is-now-in-public-preview/); Carvana using it for multi-repo engineering changes at scale.
**Mechanism:** An operator writes an `.aw.md` file — a plain-English markdown description of what should happen on a given event ("when an issue is labeled `bug`, look up related PRs, estimate severity from the stack trace, draft a repro plan, post it as a comment, and apply a `triaged` label"). GitHub Agentic Workflows compiles the markdown into standard Actions YAML at commit time. When the underlying event fires (issue labeled, PR opened, CI failed, workflow run finished), the compiled workflow spins up a coding agent inside Actions, the agent reads the relevant context via the GitHub MCP server, and it writes the action back to GitHub — comment, label, PR, merge. Replaces the human-in-the-loop triage/routing/first-response layer of a bug tracker.
**Why agentic:** The reasoning happens at run time, not at author time. The markdown says "estimate severity" — the agent decides how based on the actual stack trace in the actual issue. Unlike a hand-written Action, one workflow file handles novel inputs it was never explicitly coded for.
**Generalizable core:** platform-native webhook event → agent authored in natural language → agent reads related context via the platform's MCP server → agent writes an action back to the same platform (comment, label, message, record update). The general pattern is genuinely new — the workflow file itself is the agent, and platform MCPs make it possible to write once and reach the whole platform.
**Deployability:** Weekend build for a single workflow anywhere the platform has an MCP server, which as of mid-2026 includes HubSpot, Notion, Linear, Stripe, Slack, Intercom, Zendesk, Shopify, and more. Replaces the manual first-response/triage layer in any inbox-shaped system: HubSpot lead assignment, Linear ticket triage, Zendesk first-touch, Shopify order-flag routing. Complexity stays low precisely because the workflow is markdown, not code — this is what makes it deployable to non-engineering operators. Caveat: agents that write back to production systems need a governance layer (GitHub calls theirs "safe outputs"). Roll your own approval gate before letting an agent close tickets or update customer records at scale.

### 4. Claim-intake triage agent with immutable audit trail (Allianz + Anthropic)
**Source:** [Allianz + Anthropic partnership](https://www.allianz.com/en/mediacenter/news/media-releases/260109-allianz-and-anthropic-forge-global-partnership.html); [Anthropic financial services agent templates, May 2026](https://www.anthropic.com/news/finance-agents) — Anthropic claims 88% human-expert accuracy on insurance claims out of the box.
**Mechanism:** New FNOL (first notice of loss) arrives via email, portal upload, or claim intake form. Agent classifies the claim type, pulls the customer's policy from the underlying system, extracts incident facts from unstructured attachments (photos, PDFs of police reports, medical bills), runs the coverage check against policy terms, and drafts a first-pass decision — pay, deny, or request more information — with the payment amount if payable. Every decision, rationale, data source, and prompt version is logged to an immutable audit trail. Sensitive or complex cases (fatalities, disputes, large loss) route straight to a human adjuster; routine sub-limit claims can auto-approve first payment. Replaces the adjuster's intake-and-first-decision workflow, which is the highest-volume, lowest-judgment stage of the claims funnel.
**Why agentic:** The agent reads unstructured inputs — a phone photo of a crumpled bumper, a scanned police report, a doctor's handwritten note — that no fixed schema handles, applies policy rules to what it extracts, and produces an actionable first-pass decision. That's reasoning across unstructured input plus structured business logic, not RPA.
**Generalizable core:** inbound claim/case/request in any format → agent normalizes to structured intake → agent runs entitlement/eligibility check against policy or rules → produces first-pass action + immutable audit trail → routes ambiguous cases to a human.
**Deployability:** Allianz is enterprise, but the skeleton copies down to SMB scale in any regulated-decision domain: small insurance brokerages doing sub-limit claim first-pass, PT clinics filing prior-auth appeals, benefits administrators processing FSA/HSA reimbursement requests, warranty admins triaging appliance claims, HOA management companies handling maintenance requests against covenant rules. Complexity: month-plus build. The real gate is not the agent — it's the audit trail. For SMB deployments a Postgres append-only table plus an immutable object-store bucket for the source docs is enough to defend the decision if it comes up later. This pattern only works if you're willing to build that audit layer up front; skip it and you can't defend the automated decisions when a customer, regulator, or opposing counsel asks how the agent decided.
