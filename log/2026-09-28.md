# 2026-09-28 — Agent Pattern Scan

## TL;DR
Four concrete patterns today, all mechanism-level: an alert-triggered SRE agent that traces incidents from Slack to a merged pull request (Carvana on Claude Agent SDK), an inbound-contract triage agent that redlines against a firm's standards before a lawyer opens the file (Spellbook ACM), an agent-native cloud provisioning protocol that lets a coding agent buy a domain and ship a Worker with tokenized payment (Cloudflare + Stripe), and Amazon's Seller Assistant "workflows" that react to marketplace threshold events instead of returning a dashboard row. The most interesting angle for A3 is Spellbook: the trigger isn't a user request, it's the arrival of a document in any of three channels, and the agent's output is a routed, diagnosed work item rather than a summary.

## Patterns

### 1. Alert-in-Slack becomes root-caused pull request
*(variation of 2026-04-22 entry — new angle: trigger is an automated production alert, not a human @mention; agent investigates across logs, warehouse and code before drafting the change)*

**Source:** [Carvana Claude Tag case study](https://claude.com/customers/carvana) — Carvana's SRE and platform teams route production monitoring alerts into Slack channels where a Claude Agent SDK app is a listening member; reported outcomes are a 56% reduction in retail-science alert volume and 65% faster answers for the wholesale platform team.

**Mechanism:** A production monitoring alert lands in a Slack channel → the agent reads the alert payload, pulls the last hour of pre-deploy baseline logs and compares them, queries the team-scoped cloud data warehouse for the affected slice, checks code ownership and recent commits/tickets, then posts a team-formatted root-cause analysis back to the thread with owner tags. When the fix is straightforward (log line missing, obvious null-check, misconfigured threshold) it opens a pull request directly from the investigation thread; human review still gates the deploy. Replaces the on-call engineer's first 20–40 minutes of triage — grepping logs, chasing ownership, hunting the offending commit — before any code change.

**Why agentic:** The alert never renders as a dashboard row waiting for someone to look; the agent fans out across four data sources (logs, warehouse, git, tickets), reasons about which team owns the affected code, and produces a mergeable artifact. A rule engine cannot pick the right warehouse slice for a novel alert or write a targeted PR.

**Generalizable core:** automated system event in any channel → agent fans out across logs + code + ownership metadata → produces a diagnosed work item (PR, ticket, or draft change) with the responsible owner tagged.

**Deployability:** Claude Agent SDK + Slack app + read-only warehouse credentials scoped per team + GitHub App with PR-open scope. Week to two-week build for a first channel if the observability stack is already normalized; longer if log/warehouse conventions vary by team. Replaces the on-call engineer's first-pass triage; augments (does not replace) the fix-and-review loop. Scale caveat: works best where alerts already carry structured metadata and code ownership is already recorded — a shop with drift in either will get lower-quality RCAs.

### 2. Inbound contract triage across email, Slack and Salesforce
*(tags: `in-house-legal`, `procurement`, `sales-ops`, `agencies-with-MSAs`)*

**Source:** [Spellbook ACM launch (June 30 2026)](https://spellbook.com/blog/introducing-acm) — [Artificial Lawyer coverage](https://www.artificiallawyer.com/2026/06/30/spellbook-launches-clm-killer-acm/). Serves 4,500+ legal teams including Dropbox in-house and Kennedys.

**Mechanism:** A new contract arrives in one of three channels: an email inbox, a Slack channel, or a Salesforce opportunity attachment → the agent pulls the file, classifies contract type (MSA, DPA, NDA, order form, vendor T&Cs), diffs each clause against the firm's playbook of preferred positions and hard redlines, generates a diagnostic (which clauses drift, where the risk sits, which fallback to propose), redlines the document, and routes it to the correct pipeline and owning attorney based on contract type and counterparty. Signed versions land in a renewal-aware repository that reads dates and re-surfaces the contract before auto-renewal windows. Replaces the paralegal or contract manager's intake queue — the 30–90 minutes per contract spent classifying, checking against playbook, and assigning.

**Why agentic:** A rule engine can route by sender domain but cannot read a novel clause and decide whether it drifts from a playbook, and it cannot generate the diagnostic that a lawyer opens first. The trigger is arrival across three different channels, so the entry point is polymorphic — a fixed workflow would need three near-identical branches with hardcoded handoffs.

**Generalizable core:** inbound document in any channel → agent classifies, reads it against a stored standard, produces a diagnosed + partially-actioned artifact + routes it to the right human, with a downstream repository that re-triggers on time-based conditions.

**Deployability:** Reachable at two levels — buy Spellbook ACM directly (weekend integration for a firm already on Word), or rebuild the skeleton on Claude API + MCP file/email/Salesforce connectors + a playbook stored as a versioned JSON/Markdown spec + a vector store for prior versions. Custom build is a month for a real playbook; the playbook itself is the moat, not the agent. Replaces or augments a paralegal / contract manager. Scale caveat: only pays back if the firm actually has a written playbook — most SMB legal work has playbooks in someone's head, which is a discovery moment, not a blocker.

### 3. Agent-native cloud provisioning with tokenized payment
*(tags: `dev-agencies`, `internal-tools-teams`, `agent-builders`, `SMB-solopreneurs`)*

**Source:** [Cloudflare + Stripe Projects launch (Agents Week 2026)](https://developers.cloudflare.com/agents/tools/payments/) — [Registrar API docs](https://developers.cloudflare.com/registrar/registrar-api/). The user logs in to Stripe once; from then on an agent can create a Cloudflare account, register a domain, subscribe to a paid tier, obtain an API token, and deploy a Worker end-to-end.

**Mechanism:** A user tells a coding agent (Claude Code, Cursor Agent, Devin, or a homegrown SDK app) "spin up a new project for X and register a domain" → the agent runs a three-step protocol: (1) discovery — it asks Stripe which providers accept agent-initiated purchases, (2) identity attestation — it presents a signed identity for the user, (3) payment tokenization — Stripe hands a short-lived token to Cloudflare so the card number never touches the agent. With that token the agent calls the Cloudflare Registrar API to check availability and buy a `.dev`, provisions an account, subscribes to Workers Paid, mints a scoped API token, and pushes the initial Worker. A $100/month per-provider cap on the token is the guardrail. Replaces the "sign up → payment method → domain search → DNS → API token → first deploy" chain a developer or ops person walks through the first day of every new project.

**Why agentic:** The trigger is a natural-language project request; the agent has to select a domain name (judgment), decide which plan tier is needed (judgment), and route around failures (name taken, plan constraint). None of this is expressible as a fixed workflow — and critically, it opens a class of workflows where the agent itself is the buyer, not a user pressing a button on a page.

**Generalizable core:** user request for a new capability → agent authenticates as the user through a tokenized identity → performs a chain of purchases + provisioning across third-party services → returns a live, connected artifact instead of a checklist.

**Deployability:** Claude Agent SDK or any OpenAI/Anthropic-compatible tool-use agent + Stripe Projects account + Cloudflare account. Weekend build to wire the protocol; the interesting complexity is spend controls, audit logs, and the boundary of what the agent is allowed to buy — which is where an A3-style custom firm can add value on top. Complexity is low technically, medium organizationally (finance and IT want spend caps and receipts). Replaces the DevOps / IT provisioning task; augments the developer. Scale caveat: only Cloudflare + Stripe today, but the discovery step is designed to expand, so this is the pattern to watch even for shops not on Cloudflare — the same shape will show up in AWS Marketplace and GCP within 12 months.

### 4. Marketplace-metric-threshold workflow instead of a seller dashboard
*(tags: `e-commerce-operators`, `amazon-3P-sellers`, `retail-brands`, `distributor-ops`)*

**Source:** [Amazon Seller Assistant workflows expansion (Sept 23 2026)](https://smallbiztrends.com/amazon-seller-assistant-adds-24-7-automation-and-claude-integration/) — [Distribution Strategy Group coverage](http://distributionstrategy.com/2026/09/amazon-expands-agentic-ai-to-automate-seller-pricing-inventory-tasks/). Runs on Amazon Bedrock with Claude models; every primary seller account gets a 12-month Quick Plus subscription through Dec 2026, meaning the mechanism is about to touch the entire 3P long tail.

**Mechanism:** The seller writes a natural-language rule that becomes a persistent workflow: "if my Buy Box share on ASIN X drops below 80%, or a competitor drops price by more than 5%, adjust my price within my margin floor and update the listing copy to emphasize free shipping." The workflow runs 24/7 as a background subscriber to Amazon's own event stream (pricing changes, ratings changes, listing status, inventory position) → when a condition crosses the threshold, the agent reads the surrounding context (current margin, replenishment ETA, competing listings), takes the pre-authorized action (price change, listing edit, replenishment order draft), and posts a note to the seller. Replaces the seller's morning routine of pulling five reports and manually adjusting price/inventory — the classic "we have a dashboard for that" workflow.

**Why agentic:** The rule is expressed in natural language, the context assembly is dynamic (pull margin AND ETA AND competing listings, only the ones relevant to this ASIN), and the action is a real API write, not a chart. A traditional Amazon repricer tool does one dimension (price); this pattern chains price + listing + replenishment on a single trigger.

**Generalizable core:** persistent natural-language rule + platform event stream → agent reads context on threshold crossing → executes an authorized action across multiple sub-systems → posts a note instead of a dashboard row.

**Deployability:** Amazon's built-in Seller Assistant is the fast path for 3P sellers (free with account, no build). For other marketplaces (Shopify, Etsy, Faire, Walmart Marketplace) the same pattern rebuilds on Claude API + the marketplace's webhook stream + Zapier/Make for the pre-authorized writes, or n8n for full custom. Week-long build for a single channel; a month for a multi-marketplace generalized version. Replaces a merchandising / pricing analyst; augments a small-business owner running their own store. Scale caveat: pattern requires the marketplace to expose a webhook stream, which excludes some older platforms; also raises real questions about who's liable when the agent auto-lowers price into a loss, so most real deployments cap actions with hard floors.
