Agent Pattern Scan — 2026-08-25 — 5 patterns | Risk-scored auto-triage is porting out of code review

Repo: https://github.com/carrollr01/agent-adoption-research/blob/main/log/2026-08-25.md

TL;DR
Risk-scored auto-approval is showing up outside code review: the same "read the artifact, score it against rules, auto-execute low-risk cases, escalate high-risk to a human" loop is running production traffic in insurance FNOL, in construction submittals, and in property-management maintenance intake. The most transferable mechanism today is the auto-triage agent, not the voice receptionist.

1) Risk-scored PR auto-approval ("Merge Mommy")
Source: Lenny's Newsletter — Build an AI code review bot in 30 minutes (https://www.lennysnewsletter.com/p/build-an-ai-code-review-bot-in-30). A Vercel Eve reference agent the Eve team runs on its own repo.
Mechanism: GitHub webhook fires when CI turns green on a PR. The agent pulls the diff, the CI summary, and the touched files' recent blame, scores the change across six risk dimensions (blast radius, test coverage delta, migration/schema touch, auth-adjacency, dependency change, revert cost), and posts a review comment with the score sheet. If every dimension is low it auto-approves; otherwise it pings the on-call reviewer in Slack with the specific dimensions that failed. It writes the verdict back to the PR labels so branch protection can act on it. Replaces the first human triage read of every PR, not the deep review.
Why agentic: durable process that acts on the PR (approve, label, escalate) rather than a comment-only bot; the rubric is the policy, and the agent picks which branch of the workflow to run.
Generalizable core: new artifact enters the queue -> agent scores it against a small explicit rubric -> auto-executes the low-risk branch, escalates the rest with reasons attached.
Deployability: Vercel Eve or a plain Claude API + GitHub webhook + Slack API. Weekend build for a technical team. The rubric is the work; the infra is not. Ports cleanly to expense-report approval, vendor invoice approval, marketplace listing changes, and support-ticket refunds.

2) Law-firm inbound mail intake to matter file
Source: Lyron AI — Law Firm Automation with n8n Case Study (https://www.lyron-ai.com/en/news/law-firm-automation-n8n-case-study/). German firm on self-hosted n8n, ~70% cut in manual research time.
Mechanism: New email or scanned mail dropped into a shared inbox triggers an n8n workflow. The agent reads the message, attachments, and any prior thread, then classifies as new-matter, existing-matter update, court-deadline notice, or admin. New-matter: opens a matter record in the practice-management system, drafts an intake summary, files the source doc in the matter folder. Deadline notice: extracts date/party/court, adds a calendar entry with the firm's standard reminder lead-times, pings the responsible attorney with a one-paragraph brief. Replaces the paralegal's first-pass mail sort plus the manual deadline-into-calendar step.
Why agentic: the agent picks which downstream workflow runs based on what the document actually is; different mail types write to different systems.
Generalizable core: unstructured inbound message -> classify -> assemble the right record set -> write to the right system of record -> notify the right human with a pre-summarized brief.
Deployability: n8n or Make + Claude API + practice-management SaaS (Clio, PracticePanther, MyCase) + Google Workspace/Outlook + Google Calendar. Week-long build for a small firm. Most deployments keep an attorney approval gate on calendar writes for the first month. Replaces about one paralegal FTE-worth of intake at a 5-attorney firm.

3) Construction submittal spec-compliance agent
Source: Varseno — How AI Is Transforming Construction RFI & Submittals in 2026 (https://www.varseno.com/ai-transforming-construction-rfi-and-submittals/). Deployments across GCs using Procore and Autodesk Construction Cloud.
Mechanism: A subcontractor uploads a submittal (product cut sheet, shop drawing, material data) to document control. The agent pulls the project spec section referenced in the submittal, the approved product list, and any relevant building-code appendix, then produces a line-by-line compliance check with the exact spec citation for every deviation. Clean submittals get an auto-approve comment; anything with a deviation is routed to the engineer-of-record with the annotated PDF attached. Replaces the project engineer's first-pass line check, typically 3-6 hours per submittal on a mid-size job.
Why agentic: agent picks which spec sections to load based on the submittal's content, then produces a routing decision the document-control tool acts on.
Generalizable core: uploaded document -> locate the authoritative reference -> compare clause-by-clause -> route based on the delta.
Deployability: Procore or Autodesk API + Claude with a strong doc-parsing pass + a project-spec vector store + a comment/label write-back. Month-long build for a GC with an IT function; the hard part is getting the spec into a form the agent cites reliably. Ports to municipal permit intake (application -> code cross-check -> approve or route), clinical-trial lab-report review, and insurance-endorsement review at brokerages.

4) Property-management maintenance intake and dispatch
Source: US Tech Automations — Property Management Maintenance Automation Compared, 2026 (https://ustechautomations.com/resources/blog/property-management-maintenance-automation-platform-comparison-2026). Running across AppFolio, Buildium, DoorLoop shops; 2026 benchmark cites 44% of PMs using AI in this exact workflow.
Mechanism: Resident sends a message via portal, SMS, or email. Agent parses the description, asks up to two follow-up questions to disambiguate ("is water actively coming out?" "which appliance?"), classifies issue type and urgency, checks the pre-negotiated vendor list for the right trade and coverage window, checks the resident's lease for who pays, opens the work order in the PMS with everything filled in, schedules the vendor via the vendor's booking API or a scheduling email, and sends the resident an SMS with the confirmed appointment window. Escalates to a human PM only for high-cost work, ambiguous liability, or vendor-availability gaps. Replaces the PM's phone/email triage plus the manual vendor dispatch call.
Why agentic: agent runs a real short conversation, then acts across four systems (PMS, vendor booking, resident SMS, escalation) with a policy-driven decision tree.
Generalizable core: inbound freeform request -> clarify via short back-and-forth -> classify + policy-check -> dispatch to the correct external actor -> confirm to the requester and write to the system of record.
Deployability: AppFolio/Buildium/DoorLoop API + Claude or GPT + Twilio for SMS + a shared vendor roster (often a Google Sheet at SMB scale). Weekend build for intake-and-classify; a week or two per vendor for auto-dispatch. Replaces about half a PM assistant's day. Ports to condo-association ticketing, university facilities, and small-hospital maintenance intake.

5) Insurance FNOL triage-and-route
Source: Hesper AI — Claims Triage Automation: the 2026 Playbook (https://gethesperai.com/blog/claims-triage-automation-guide/). Mid-sized carrier deployments dropping FNOL-to-triage from 4-8 hours to under 5 minutes.
Mechanism: A First Notice of Loss hits the intake queue via phone transcript, portal, or broker email. The agent pulls the policy record, coverage terms, historical claim frequency for the insured, weather feed for the loss date/zip, catastrophe flags, and a fraud model score. It runs the carrier's triage rules to score complexity, severity, and fraud risk, assigns the claim to a specific adjuster queue (fast-track auto-settle, standard, complex, or SIU), attaches a pre-drafted acknowledgement letter, and writes the routing decision and reasons back to the claims system. Escalates only when the score sits in an ambiguity band or the fraud model trips a hard threshold. Replaces the FNOL clerk's triage-and-assign step; cuts first-touch SLA 50-98%.
Why agentic: assembles context from four or five sources on demand, applies the carrier's actual triage policy, and takes the routing action itself.
Generalizable core: inbound event with a policy attached -> assemble policy + history + external context -> score against the policy's rules -> route the work item, draft the human-facing message, log the decision.
Deployability: Guidewire/Duck Creek/Origami claims system + policy admin API + weather/CAT provider + Claude or a fine-tuned severity classifier + a fraud-model call. Month-plus build for a carrier IT team. Only "SMB" in independent-agency setups. Ports to warranty claims for appliance retailers, chargeback triage at payment processors, and refund-request triage at DTC brands.
