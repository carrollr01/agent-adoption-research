# 2026-07-30 — Agent Pattern Scan

## TL;DR
Sentry's Autofix (GA this month) is the cleanest live example of confidence-gated autonomous action: the error-monitoring service decides per-issue whether it's confident enough to hand off to Claude, and only then does an agent write and push a PR. That gating pattern — "act autonomously above threshold, defer to human below it" — is the reusable idea, applicable well beyond bug fixes.

## Patterns

### 1. Confidence-gated event-triggered autofix (Sentry Seer → Claude)
**Source:** [Sentry changelog + Anthropic customer story](https://claude.com/customers/sentry) — Sentry ships error monitoring to ~100k orgs; Seer's Claude integration moved to GA in July 2026.
**Mechanism:** A new production error hits Sentry → Seer generates a root-cause analysis and scores whether the issue is "likely fixable via code change" → if the score clears a per-project threshold, Sentry invokes a Claude Managed Agent with the stack trace, event metadata, Seer's analysis, and repo context → agent writes the patch, opens a PR against the repo, and links back to the Sentry issue. If the score is below threshold, the issue just sits with Seer's analysis attached for a human. Sentry's own blog reports one internal team going from 57 open bugs to 1 by leaving Autofix running.
**Why agentic:** No human queues the work, picks the tool, or writes the diff. The trigger is data (an error event), the decision to act is model-based (Seer's confidence), and the output is a real artifact in a real system (a GitHub PR), not a chart of open bugs.
**Generalizable core:** Event arrives → model scores actionability → if above threshold, agent gathers context and takes the action; if below, agent files evidence for a human. Works for support tickets, alerts, security findings, ops incidents, sales inbound — any queue where most items are routine and a minority need judgment.
**Deployability:** Two versions. Vendor stack (Sentry Autofix + Claude Managed Agents) is on-off toggle, no build. DIY version is a week-to-month build: webhook → LLM scoring pass → conditional branch to a coding agent (Claude Agent SDK is the closest off-the-shelf) → PR opener. Replaces first-pass triage engineer time. Requires a monitored system with reliable event webhooks and a bounded action space.

### 2. Task-board-as-invocation surface (Notion + Claude Managed Agents)
**Source:** [Notion customer story on Claude.com](https://claude.com/customers/notion) — rolled out with Claude Managed Agents in Notion workspaces (millions of users), scale claim: 30–40 concurrent agent tasks per user session.
**Mechanism:** A Notion task board is set up with columns like `Backlog` → `Ready to start` → `In review`. When a user drags a card into `Ready to start`, that column transition fires a Claude Managed Agent session, seeded with the card's description, linked docs, and any acceptance criteria in the card body. The agent runs (can be minutes to hours), writes its output back to the card (draft doc, slides, code, spreadsheet), and moves the card to `In review`. Approvals then route to whichever human owns that column. Reported ~90% cost reduction and ~85% latency reduction via prompt caching across the shared workspace.
**Why agentic:** The kanban column IS the trigger; there's no chat interface, no "run this prompt" button. Cards are work items, not just labels. The board becomes a batch queue where a single person can push 30+ agent tasks into flight without a human touching each one to kick it off.
**Generalizable core:** State transition in a workflow tool (kanban move, form status change, folder drop) → agent picks up the item's structured payload → produces the artifact type that column expects → advances the state and pings the owner. Works for any team already using a board or checklist as a queue: sales ops handoffs, legal intake, editorial pipelines, brief-to-deck production.
**Deployability:** Week-to-month build. If the workflow tool exposes webhooks or Zapier/Make/n8n triggers on status changes, this is straightforwardly wireable. Harder part is the per-column output contract — you have to know exactly what a card in `Ready to start` should become. Replaces the coordinator role that watches boards and manually re-assigns / kicks things off. Scale caveat: only worth it when the board sees dozens+ items per week and the "kick it off" work has real overhead (context gathering, formatting, drafting).

### 3. Scheduled proactive-review agent that ships fixes (Sentry cookbook: weekly perf triage)
**Source:** [Sentry cookbook — Automate weekly performance triage with Claude Code + Sentry MCP](https://sentry.io/cookbook/performance-bot-sentry-claude) — published as a recipe, not a product; adoption pattern is any team already running Claude Code with cron support.
**Mechanism:** Claude Code scheduled task fires every Monday 9am → connects to Sentry via MCP with read scopes on issues/traces/spans → queries the previous week's slowest N endpoints → groups events by fingerprint to collapse duplicates → ranks clusters by event count × affected-users → for each top cluster, pulls the trace, reads the relevant repo files, drafts a fix, opens a GitHub PR with the diff, the Sentry link, and a one-paragraph explanation of the root cause. No custom bot server, no queue infra — just a cron entry and a system prompt.
**Why agentic:** No human writes "look at endpoint X"; the agent picks its own targets from data every week. It doesn't summarize into a dashboard for someone else to read — it opens PRs that a human then merges or rejects. The reject signal is the training loop; the merge is the deliverable.
**Generalizable core:** Cron fires → agent queries a system for "worst offenders this period" via MCP or API → ranks them → produces the fix artifact (PR, ticket, doc, refund, follow-up) → hands to a human only for the accept/reject decision. Same pattern works for stale support tickets, dormant leads, expiring contracts, deprecated dependencies, cost-anomalous cloud resources — anywhere a weekly "someone should look at this" habit exists.
**Deployability:** Weekend-to-week build if Claude Code is already in your stack. The interesting part isn't the cron — it's the MCP server on the source-of-truth system (Sentry ships one; HubSpot, Linear, Notion, and Slack all have official MCP servers as of mid-2026; anything else is a small custom MCP shim). Replaces the recurring "let's look at the numbers" meeting and the engineer who spends Monday morning on triage.

### 4. 24/7 external-world monitor with contextualized alert (Operand Scout)
**Source:** [Operand — Scout agent release, Aug 2025 press release, expanded 2026](https://www.retaildive.com/press-release/20250828-operand-releases-agent-to-perform-competitor-price-scraping-product-match-1) — targeted at retail merchandising teams; adopted by mid-market e-comm brands.
**Mechanism:** Agent runs continuously (not on a schedule — it re-crawls competitor product pages on rolling intervals based on how often each page tends to change). For each fetched page: extract price, availability, promo copy → match to the internal catalog via a fuzzy product-matching pass → diff against last-known state → if a competitor's price for a matched SKU drops below your price by a configurable margin, post a Slack/Teams message to the merchandising channel with product name, both prices, screenshot, competitor URL, and a "match confidence" score. Silent when nothing crossed the threshold.
**Why agentic:** The matching step is non-trivial — competitor SKUs don't have your catalog IDs, product titles vary, images vary. That's where the LLM earns its keep. A "dashboard" version would either dump every price change (noise) or require a human to maintain a matching table (never happens). The agent absorbs the ambiguity and only surfaces the ones a merchandiser can act on.
**Generalizable core:** Continuous external polling → LLM-mediated matching to your internal entities → change detection against last state → contextualized alert only when a threshold is crossed. Works for jobs boards (competitor hiring signals), news mentions (customer PR events), regulatory filings (compliance-relevant changes), review sites, social. The reusable insight is that the LLM's job is matching + relevance filtering; the alert plumbing is off-the-shelf.
**Deployability:** Vendor version is buy (Operand, Prisync, and similar); DIY is a week-to-month build with Firecrawl / ScrapingBee for fetch, Claude for matching + summarization, and a Slack webhook for output. Replaces the merchandiser or analyst who spot-checks competitor sites weekly. Scale caveat: without decent catalog data (SKU list, current prices, product attributes), the matching step is unreliable and alerts get noisy — this is the failure mode to watch.
