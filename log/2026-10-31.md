# 2026-10-31 — Agent Pattern Scan

## TL;DR
Three mechanism-level patterns worth logging. The headline is the Toyota of Orlando setup: an upstream 38-step Zap that cleans messy lead email into a structured table, and a Zapier Agent sitting on top of that table that answers natural-language lead-trend questions in Slack. It's a working example of operational data getting a conversational layer instead of a dashboard. Also logging Double's Autoclose (continuous month-end close, a materially different angle on the 05-05 close pattern) and Kortix's per-email sandbox triage architecture.

## Patterns

### 1. Natural-language query agent on top of operational Zapier Tables
**Source:** [Zapier customer story — Toyota of Orlando](https://zapier.com/customer-stories/toyota-orlando) — a mid-size car dealership managing 30k+ lead records, built by their Director of Operations after a CRM outage.
**Mechanism:** Inbound lead email in Gmail → a 38-step Zap uses an AI step to extract, clean, and normalize lead data from inconsistent vendor formats (DealerOn, third-party portals) → routes by Paths (new vs. used vehicle, lead source) → writes a structured row into Zapier Tables → a separate Zap mirrors the table to a view-only Google Sheet for the BDC team. A Zapier Agent (nicknamed "Timmy the Table Bot") sits on top of the Zapier Table and answers natural-language questions from staff ("how many Camry leads came in from AutoTrader last week?") by querying the table directly and returning a plain-English summary with totals grouped by source and dealership.
**Why agentic:** The upstream Zap is traditional automation, but the query layer is the agentic piece: no one has to click into a dashboard, pick a filter, or ask the ops person. The agent interprets the question, picks the right columns and groupings on the fly, and answers in the channel the person is already in. It also flags anomalies when a lead source drops or spikes outside normal ranges, which replaces a weekly scheduled report.
**Generalizable core:** Messy inbound events get parsed into a structured table once; after that, a natural-language agent on top of the table replaces the dashboard-plus-filters that the team would otherwise rely on, and surfaces anomalies without being asked.
**Deployability:** Pure Zapier stack (Gmail trigger, AI by Zapier for parsing, Paths, Zapier Tables, Zapier Agents) — no custom code, built and maintained by a non-engineer. Week to a few weeks to stand up for a specific intake flow if the source data is reasonably consistent. Replaces the "ops person who runs the weekly lead report" and the dashboard-reader habit. Caveat: question quality degrades fast if the underlying table schema is dirty; the 38-step cleaning Zap is what makes the agent usable.

### 2. Continuous month-end close agent — variation on 2026-05-05 entry, new angle: trigger moves off the calendar
*(Variation of 2026-05-05's "month-end close agent that works on calendar triggers" — new angle: event-driven continuous reconciliation during the month, with the human review window at month-end, instead of a batch run fired by a date.)*
**Source:** [Double launches Autoclose](https://www.financialcontent.com/article/bizwire-2026-10-26-double-launches-autoclose-ai-that-runs-the-month-end-close) (press release, 2026-10-26); vendor detail at [doublehq.com](https://doublehq.com/). Early adopter is Attivo Partners, which supports 500+ venture-backed companies on Double.
**Mechanism:** New bank statement available / new transaction posted in client banks and payment platforms → agent fetches the statement, codes bank feed entries against each client's rules, reconciles accounts, and writes journal entries into the client's ledger (QuickBooks Online, Xero, Sage Intacct, or NetSuite). Variances get flagged as exceptions inline, not stockpiled for the end of the month. The human close window shrinks to: open review-ready books, resolve flagged exceptions, sign off.
**Why agentic:** The trigger isn't a calendar — it's whatever new transaction or statement shows up during the month. The agent decides which categorization rule applies, when something is a variance vs. a routine entry, and when to escalate. The accountant's role shifts from producer to reviewer; the dashboard of "what's still open" largely goes away because exceptions are the queue.
**Generalizable core:** A process that used to batch at a deadline (daily close, weekly reconciliation, monthly report) gets rebuilt as event-driven: each inbound record is handled when it arrives, exceptions become the only human queue, and the "deadline" becomes a review gate on an already-finished pile.
**Deployability:** Platform play — this specific instance only works because Double already brokers connections to banks, payment platforms, and the ledger. For an SMB build, the pattern applies anywhere there's a batch close process over records that could be processed as they arrive (payroll pre-close, inventory reconciliation, commission statements). Stack: event webhooks + ledger/system-of-record API + rule store per customer + an exception queue (Linear, Asana, email). Month-to-quarter build for a single-vertical SMB adaptation. Replaces the "crunch week before the deadline" and much of the recurring status-check meeting.

### 3. Per-email isolated sandbox agent for shared-inbox triage
**Source:** [Kortix — How we triage a shared inbox with an AI agent](https://kortix.com/use-cases/inbox-triage) — Kortix running the agent on their own support inbox; architecture is reusable via their open-source agent OS. The vendor is self-reporting the mechanism, which the pattern turns on, so treat results as directional.
**Mechanism:** New inbound email on the shared mailbox → the trigger spawns a fresh isolated cloud sandbox session, with scoped access only to that message, the company's help doc, and the Linear workspace. The sandboxed agent reads the message, labels it (billing, bug, how-to, lead, etc.), and takes one of two actions: draft a Gmail reply (approval gate — nothing sends until a human clicks send) or file a Linear ticket on the right team with context pulled from the help doc. Credentials are brokered server-side so the model never sees raw tokens.
**Why agentic:** The isolation per message is the interesting part. Each email gets its own context-scoped session rather than a long-lived agent that holds state across all inbound mail — so a prompt-injection attempt in one email can't bleed into another thread, and credentials are compartmentalized. The agent still makes a classification decision and chooses between drafting vs. ticketing, with a mandatory human gate on anything customer-facing.
**Generalizable core:** Inbound event in a shared channel → spin up an isolated session scoped to that one event plus a small reference set → agent classifies, drafts a response, or files work in a system of record → human approves anything that leaves the building.
**Deployability:** The sandbox-per-event idea works with any orchestration that supports ephemeral runs (Temporal workers, Modal functions, Cloudflare Workers Durable Objects, or an off-the-shelf agent OS). Weekend-to-week build for a single team's inbox if you accept a simpler isolation model (fresh conversation per email rather than full sandbox); couple of weeks if you want true credential compartmentalization. Replaces the "first-level support reader who tags and routes" role, and tightens the security story against prompt-injection in incoming email — a real concern once an agent has write access to Linear, a CRM, or a payment system.
