# 2026-09-12 — Agent Pattern Scan

## TL;DR
GitHub's own "Copilot Agent PR Analysis" workflow is a working example of an agent replacing a dashboard: it runs on cron, orchestrates a 16-tool toolbox over pre-fetched PR data, and posts a narrative operations report as a GitHub Discussion for $1.53/day. Three other patterns from this week: EDI-denial-triggered appeal packet generation in healthcare RCM, Slack-approval-chained identity restore at Delivery Hero, and field-ops agents that listen on the crew's existing radio/chat channel.

## Patterns

### 1. The daily operations narrative that posts to Discussions instead of a dashboard
**Source:** https://github.github.com/gh-aw/blog/2026-05-26-agent-of-the-day/ — GitHub's own Copilot Agent PR Analysis workflow, published as the featured example in their agentic-workflows blog and run in production on the gh-aw repo.
**Mechanism:** Cron-triggered at 6pm UTC. A prep step fetches all `copilot-swe-agent`-authored PRs into `/tmp/gh-aw/agent/pr-data/copilot-prs.json`. Claude Opus 4.7 is then invoked with 16 tool types (PR list, search, file content retrieval, `push_repo_memory` for trend storage) and decides on its own how to work the batch: merge rates, review turnaround, file change distributions, and week-over-week trends. Output is a full GitHub Discussion post in the team's repo. Runs at ~950K tokens with a 63% cache hit rate for $1.53 per execution.
**Why agentic:** The prep step is a plain fetch. The agent decides which tools to call, in what order, how deep to go on any given PR, what counts as a pattern worth surfacing, and how the narrative should read. Output is prose, not a chart; the human reads it once and moves on. Previously required "manual spelunking through dashboards, cross-referencing merged PRs with author names, and guessing at patterns."
**Generalizable core:** Scheduled trigger → agent orchestrates a toolbox over a pre-fetched batch → writes a narrative report to the team's discussion surface → replaces the "who reads the dashboard every morning" job.
**Deployability:** Weekend build on any agent framework with tool use plus a memory store (Claude Agent SDK, LangGraph, GitHub Actions + gh-aw, or Zapier Agents with a scheduled action). ~$1.50/run makes it cheap enough for daily. Direct replacement for a recurring "look at the dashboard, spot the pattern, write the Slack update" chore. No enterprise scale needed — this is a two-person team's workflow.

### 2. The EDI denial that triggers its own appeal packet
**Source:** https://medium.com/@harish.vadada/agentic-ai-for-insurance-denial-management-appeals-455b91b9a99f — pattern in 2026 healthcare RCM deployments. One health system reported reducing appeal turnaround from 15–16 days of manual nurse review to 1–2 days; the broader denial-processing time across adopters has moved from ~40 days to single digits.
**Mechanism:** The clearinghouse posts an EDI 835 denial to the provider's RCM system. The agent parses it (OCR when it's a scanned paper letter, structured parse when it's EDI) and extracts payer, member ID, date of service, denial reason, and filing deadline. It cross-references the original 837 claim file, the 270/271 eligibility record, and the patient chart for the encounter. It assembles an appeal packet citing specific clinical documentation from the chart, drops it into the document store, and either queues it for a nurse's one-click review or submits directly to the payer's appeal endpoint.
**Why agentic:** Denial reason (medical necessity vs. eligibility vs. bundling vs. missing authorization) drives which sources the agent pulls, which chart sections it cites, and whether the case has a strong enough evidence chain to auto-submit or must escalate. Not a fixed pipeline.
**Generalizable core:** Inbound structured refusal event → agent parses the reason → gathers evidence from several source systems → assembles a counter-argument grounded in that evidence → files or escalates based on confidence. Applies well beyond healthcare: chargebacks, insurance claims denials in any vertical, benefits eligibility appeals.
**Deployability:** Month build. Needs clearinghouse feeds (835/837), EHR API (FHIR or vendor-specific), and a payer submission channel per contract. Replaces a large part of a denial-management nurse's review workload. Scale caveat: worthwhile above ~500 denials/month; below that the integration cost dominates.

### 3. The Slack-button lockout that chains its own identity restore
**Source:** https://goodspeed.studio/blog/n8n-case-studies-automation-success-stories — Delivery Hero (53,000 employees, 70+ countries) production n8n workflow. Roughly 800 lockout requests per month at ~35 minutes each before automation; ~200 hours/month saved.
**Mechanism:** Okta emits a lockout event. A Slack bot DMs the affected employee: "You're locked out — request recovery?" A yes-click routes an approval to the employee's direct manager, in Slack, with a 2-minute SLA countdown. On approval, the agent workflow calls Okta to verify identity, opens a Jira ticket for the audit trail, and hits Google Workspace to restore access. Employee is notified in the same DM thread.
**Why agentic:** Sits at the workflow-to-agent boundary — the multi-system chain is deterministic, but the pattern's value is that three distinct systems of record are chained under a single manager-approval token, with the human standing in only at the yes/no. In earlier iterations, help-desk staff manually operated each of those consoles.
**Generalizable core:** Detected exception on system A → user-facing prompt in the tool the user already lives in → manager approval as the single human step → agent chains N system-of-record APIs under that approval → replaces a help-desk seat. Applies to any request-then-approve internal service: license grants, vendor onboarding, expense-limit overrides.
**Deployability:** Weekend build on n8n, Zapier, or Make once the API access is granted. The engineering cost is trivial; the political cost is getting IT/security comfortable with a manager-approval-as-auth token in place of a help-desk agent.

### 4. The ops agent that listens on the crew's radio channel
**Source:** https://opsima.com/blog/operational-insights/agentic-workflows-field-operations/ — pattern documented across 2026 field-ops deployments in ports, mining, and airport ground-support-equipment (GSE) operations, where "informal communication hides critical operational data."
**Mechanism:** The agent subscribes to the crew's existing informal comms channel — dispatch radio (transcribed live via Whisper/Deepgram), a WhatsApp group, or a Slack ops channel. It classifies chatter into operational events: "gate change," "truck breakdown," "crew running late," "equipment freed up," "shipment delayed at customs." When it recognizes a real state change, it writes it into the structured ops system (TOS, dispatch board, GSE tracker) and — depending on rule — either re-runs the routing/dispatch optimizer or pings the affected crews with a revised plan. Concurrently it monitors flight data, equipment availability, and crew certification status.
**Why agentic:** Signal is unstructured speech or free-form text. The agent decides what counts as a real operational event vs. banter, and what downstream systems to touch for each event type. Legacy setups either ignored the informal channel entirely or required a dispatcher to manually re-key each update — meaning the system of record was always minutes-to-hours stale.
**Generalizable core:** Agent subscribes to an unstructured comm channel a team already uses → extracts structured operational events → writes them into the system of record → triggers a re-plan. Applies wherever the real state of the operation lives in chat/voice, not in the software of record (kitchens, warehouses, event production, hospital wards).
**Deployability:** Week build for a bounded domain with a small event vocabulary (a single dispatch radio, ~10 event types); month build for a broad ops floor. Stack: Deepgram or Whisper for transcription, a Claude/GPT classifier with structured output, MCP or direct API into the ops system. Replaces the "runner" role (the person translating chatter into ticket updates) more than the dispatcher. Scale caveat: classification accuracy floor is high — a missed event is a real operational incident, not just a stale dashboard.
