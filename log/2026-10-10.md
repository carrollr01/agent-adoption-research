# 2026-10-10 — Agent Pattern Scan

## TL;DR
Four concrete patterns today. The headliner is a product manager's edit-watching skill loop: the agent watches his edits to its own drafts, diffs them, and writes new skills for itself when it sees recurring friction. That is a different genus of agentic workflow from anything in the prior log — the agent's job is to improve its own future output, not to produce a single artifact. The other three are production-error → open PR (Sentry Seer), specialist cross-functional agents answering ad-hoc Slack asks (Rakuten on Claude Managed Agents), and transaction-time bookkeeping with flag-the-weird-ones review (Ramp Accounting Agent).

## Patterns

### 1. Edit-watching self-improving skill loop
**Source:** [Lenny's Newsletter "How I AI" write-up on Daniel Blum (PM, Melio)](https://www.lennysnewsletter.com/p/how-i-ai-how-this-pm-uses-claude), also covered at [ChatPRD](https://www.chatprd.ai/how-i-ai/claude-cowork-for-pms-my-self-improving-productivity-system) — individual builder, PM at a mid-size fintech, running Claude Code + Cowork as his daily shell; routinely 70–80% of his work hours sit inside the agent surface.
**Mechanism:** On a weekly cron the agent diffs Claude's drafted outputs against the versions Blum actually sent (Slack messages, PR comments, Notion updates, prep docs). A reviewer skill scans those diffs for recurring edit patterns — tone changes he keeps making, structure he keeps imposing, facts he keeps correcting. When a pattern repeats, the agent writes a new skill (plain-text instructions in a skills folder the agent reads on every run) and proposes it to Blum for approval. Approved skills get loaded on next invocation; declined ones are logged with a reason. Also a Sunday prep run fills next week's Notion board from calendar + Slack + email context.
**Why agentic:** The trigger is the user's own silence (edits made without being asked for feedback), the output is a modification to the agent's own instructions, and the thing being replaced is a human retrospective — the moment where someone would sit down to write a style guide for an assistant. No dashboard displays this; the agent authors its own successor.
**Generalizable core:** passive observation of human corrections → diff against prior agent output → extract recurring deltas → author or amend the agent's own rules → gated by human approval.
**Deployability:** Claude Code + Cowork (or any agent framework with a persistent instruction/skills surface and tool access to the user's chat and doc tools) + a cron. Week build if the destination surfaces (Slack, Notion, Gmail) have good APIs; the hard part is the comparison heuristic, not the tool wiring. Augments any role where someone edits agent output every day — PM, founder, lawyer, salesperson. Works at single-user scale; multi-user versions would need per-person skill namespaces.

### 2. Production error → autonomous pull request
**Source:** [Sentry Seer Autofix and Bug Prediction](https://blog.sentry.io/sentry-ai-code-review-now-in-beta-break-production-less/), [Sentry on agents needing production context](https://blog.sentry.io/agents-need-production-context/) — in beta during 2026, deployed across Sentry's own customer base of developer teams (hundreds of thousands of orgs).
**Mechanism:** Two trigger types feed one agent. Trigger A: a new high-severity exception event lands on a Sentry project. The agent assembles stack trace, prior similar issues, the suspect commit range, and the surrounding source. Seer Autofix diagnoses the root cause (reported ~2 min) and then opens a GitHub pull request against the repo with the proposed patch and a test (end-to-end ~6 min). Trigger B: a PR opens on a repo Sentry monitors. Seer Bug Prediction correlates the diff with historical runtime issues on those lines and comments on the PR with a bug header, severity/confidence, analysis, suggested fix, and a prompt a human (or follow-on skill) can use to apply it.
**Why agentic:** The input is a runtime event and the output is a code change in a different system — the loop crosses from observability into source control without a person framing the task between them. The agent decides which stack frame to inspect, which test to write, and which branch to open; a dashboard would just list the error.
**Generalizable core:** inbound anomaly event → agent reads two sides (symptom data + source of truth) → drafts the change in the system of record → human (or policy gate) approves merge → observability loop closes.
**Deployability:** This specific stack is Sentry + their Seer agent + GitHub, but the pattern reproduces anywhere you have an inbound signal and a code or config repository it points at: Datadog monitor → Terraform PR, failing dbt test → model PR, failing lint on main → auto-revert PR. Month build for a custom version; weekend build if you adopt Sentry/Seer directly. Replaces the first 30 minutes of an on-call engineer's shift (gathering context, finding the file, writing a reproducer).

### 3. Specialist cross-functional agents answering ad-hoc Slack asks
**Source:** [Anthropic Rakuten case study](https://claude.com/resources/articles/working-at-the-frontier-rakuten), [Rakuten Q&A on Claude Managed Agents](https://claude.com/customers/rakuten-qa) — Rakuten rolled out specialist agents for product, sales, marketing, and finance in roughly a week each on Claude Managed Agents (public beta, April 2026).
**Mechanism:** Each specialist agent sits in Slack/Teams with a scoped identity (e.g. "the sales ops agent"). An employee @-mentions it with a question — "pull Q3 win rate by segment for the exec review deck." The agent authenticates to that specialty's tools (Salesforce, Looker, QuickBooks, product analytics), gathers context, writes the answer directly as a spreadsheet or slide deck, and drops the file back in the channel. In the multi-agent preview, a lead agent can decompose a cross-functional ask (e.g. "model the pricing change impact") and dispatch parallel work to the finance, product, and marketing specialists, then assemble their outputs. The underlying Managed Agents architecture separates session (memory), harness (orchestration), and sandbox (execution), so a crashed sandbox doesn't lose the thread — the lead can resume.
**Why agentic:** The ask is open-ended natural language, the toolset per specialist is heterogeneous, and the final artifact (a spreadsheet, a deck) is produced on the fly. A dashboard-replacement would be a BI tool; what this replaces is the Slack DM to a BizOps analyst that returns a one-off spreadsheet four hours later.
**Generalizable core:** @-mention a scoped specialist in team chat → specialist authenticates to its functional stack → produces a bespoke artifact (deck, sheet, memo) → delivers in-channel → optional orchestrator fans out to peers for multi-function asks.
**Deployability:** Claude Managed Agents or any agent framework with persistent sessions + MCP connectors to the functional tools (Salesforce, Looker, QuickBooks, HubSpot, Mixpanel). Managed Agents charges $0.08/session-hour on top of API tokens, so a hundred ad-hoc asks a day costs real money but less than an analyst's salary. Month build at enterprise scope; a weekend build gets you one specialist. Replaces the "quick request" layer under senior analysts in product/sales/marketing/finance — it does not replace the analyst, it replaces the "can you pull…" queue they clear every morning.

### 4. Transaction-time bookkeeping with flag-what's-weird review
**Source:** [Ramp Accounting Agent (Feb 2026 launch, CPA Practice Advisor)](https://www.cpapracticeadvisor.com/2026/02/19/ramp-unveils-accounting-agent-to-streamline-bookkeeping/177952/), [CFOtech coverage](https://cfotech.asia/story/ramp-unveils-ai-accounting-agent-to-speed-month-end-close) — shipping across Ramp's customer base of mid-market and SMB finance teams; Ramp claims 3.5x more auto-coding than rule-based tools at >90% accuracy (vendor-reported).
**Mechanism:** Each card swipe, bill, or reimbursement event triggers the agent in real time. It reads the merchant, memo, attached receipt text, the customer's prior coding decisions on similar transactions, department/project/class dimensions, and the active chart of accounts. It assigns GL account, dimensions, and tax treatment, posts to the connected general ledger (NetSuite, QuickBooks, Sage Intacct) within the posting rules the customer configured, and queues only the uncertain or policy-breaching ones for human review. During close, it runs the same loop over accruals and reconciliation entries. Critically: no "if merchant = X then account = Y" rules — the model infers coding from the shape of prior decisions.
**Why agentic:** The trigger is a continuous stream of events, not a batch; the context the agent reads is the customer's accumulated coding history, not a static mapping; and the action lands directly in the system of record (the GL) rather than in a review queue by default. The queue is the exception path, not the main path.
**Generalizable core:** continuous event stream → agent reads customer-specific decision history → acts in system of record by default → routes only low-confidence or policy-flagged events to human queue → human corrections feed back into the decision history.
**Deployability:** Ramp's version is deeply integrated into the card and bill platform, which is why it works out of the box. For a custom build you need an event-sourced ledger of past decisions, an LLM with tool access to the GL's API, and a confidence threshold worth calibrating. Month build minimum, because the risk of a wrong GL posting is real. Augments the staff accountant or controller role — the agent does the first 80% of coding, humans spend their time on the 20% the agent flagged plus the exceptions it would never have thought to flag.
