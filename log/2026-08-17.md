# 2026-08-17 — Agent Pattern Scan

## TL;DR
Four patterns worth logging. The most novel is DoorDash's `dd-cli`: a company publishing its own checkout as an agent-callable command line so any external agent can order and pay. The inverse of "install an agent inside your business" — you become the tool other people's agents call. Also fresh: Claire Vo's Sentry triage harness, OpenAI Symphony turning Linear into a coding-agent control plane, and an emerging DTC returns-fraud triage loop that runs multi-signal checks per return.

## Patterns

### 1. Agent-callable ordering CLI (`dd-cli`)
**Source:** [DoorDash `dd-cli` on GitHub](https://github.com/doordash-oss/doordash-cli) and [TechCrunch coverage](https://techcrunch.com/2026/07/16/yes-you-can-now-order-doordash-from-the-command-line/) — invite-only beta for US/Canada macOS devs, launched July 15, 2026, real payments, real orders. Anthropic demoed Claude placing an end-to-end order via the CLI.
**Mechanism:** External agent (a household assistant, a corporate meals bot, a scheduling agent that sees a lunch window on the calendar) → decides food is needed → invokes `dd-cli` subcommands to search restaurants, compare deals, customize items, check out → real payment charges, real order flows into DoorDash's normal fulfillment. The user isn't in the app at any point.
**Why agentic:** `dd-cli` is deliberately not a human UX. It exists so that AI agents can be first-class buyers on DoorDash. The trigger is another agent's decision, not a human tap.
**Generalizable core:** Wrap your business's transactions (bookings, orders, quotes, deposits) in a stable agent-callable interface — CLI or MCP server — so third-party agents can call you as a tool.
**Deployability:** Thin wrapper over an existing checkout/booking API — Node or Python CLI plus an MCP server manifest, week-scale build for a shop that already has a clean API. The hard part isn't code; it's the policy surface: spend caps, per-agent allowlists, refund flows, and how you attribute liability when an agent misorders. Fits any business whose "buy" or "book" step is already API-driven (restaurants, salons, tradesmen with online booking, print-on-demand, ticketing).

### 2. Sentry-triggered bug triage harness
**Source:** [How I AI — How I Built a Custom AI Harness with the Claude Agent SDK for Bug Triage](https://www.chatprd.ai/how-i-ai/how-i-built-a-custom-ai-harness), Claire Vo, July 2026.
**Mechanism:** New or regressed Sentry issue fires → harness spins up a Claude Agent SDK run with task-specific inputs and permissions → agent pulls the Sentry event, walks the related Linear tickets and recent GitHub commits, checks the last Vercel deploys, correlates timelines → produces a structured triage brief (probable cause, suspected commit, reproduction hint, next action) → posts it as a Linear ticket update instead of a raw chat transcript.
**Why agentic:** Multi-step, tool-using, cross-source evidence gathering that decides its own next tool call. Ends in a written artifact per issue, not a dashboard.
**Generalizable core:** New event in an observability or monitoring system → agent runs a cross-source investigation → writes a structured triage brief to the ticketing system.
**Deployability:** Claude Agent SDK + custom Ink terminal UI + MCP or in-repo adapters for the specific tools (here: Sentry, Linear, GitHub, Vercel). Week-scale build for one technical operator; the leverage comes from tightening the prompt + toolset to the exact investigation ritual you'd do by hand. Replaces the engineer's morning "read the Sentry inbox and hand-write context into tickets" ritual. Works for any monitoring surface, not just errors — uptime alerts, cost anomalies, revenue drops, security signals.

### 3. Project board as autonomous coding-agent control plane (OpenAI Symphony)
**Source:** [OpenAI's Symphony announcement](https://openai.com/index/open-source-codex-orchestration-symphony/) (April 27, 2026, Apache 2.0); [InfoQ writeup](https://www.infoq.com/news/2026/05/code-with-claude/); [MindStudio analysis](https://www.mindstudio.ai/blog/openai-symphony-spec-linear-agent-control-plane-500-percent-pr-increase).
**Mechanism:** Symphony polls Linear for unassigned issues matching a filter (label, priority, project) → each match gets a dedicated Codex agent workspace → workspace runs a five-stage pipeline: analyze → plan → implement → write tests → open PR → PR is posted back to the referenced repo and the Linear ticket flips to review. Engineers only see the PR, not the intermediate steps.
**Why agentic:** The trigger is a work-tracking record, not a human handoff. Each ticket gets its own long-running agent that decides internally how to sequence tools. Reported ~500% more landed PRs at teams that adopted it and 30–50 hours/week of reclaimed triage time.
**Generalizable core:** Any existing work-tracking board (Linear, Jira, Asana, HubSpot pipeline, a Notion table) → poll for records that match a criteria filter → spin up a dedicated agent workspace per record → run a full staged pipeline → write the result back to the source of truth.
**Deployability:** Symphony itself is OSS. Realistic on any dev-heavy shop that already lives in Linear-style tooling — one week to wire and shake down. Caveat: works best where tickets are well-scoped; on vague ones you get a lot of not-quite-right PRs. Pattern transfers off engineering: same skeleton for "unassigned HubSpot lead matching ICP" → outreach agent, "new brief in Notion" → deck-drafting agent, "new invoice draft" → AR-chasing agent.

### 4. DTC returns-fraud triage agent
**Source:** [Forthroute comparison of Signifyd vs Riskified vs Loop](https://forthroute.io/blog/ultimate-guide-ai-return-fraud-detection); [Shopify's 2026 fraud guide](https://www.shopify.com/enterprise/blog/ecommerce-fraud-management); [Sage Advent — Automate Shopify Returns](https://www.sageadvent.com/blog/how-to-automate-shopify-returns/). One reported DTC brand cut manual fraud review from 4 hours/day to under 30 minutes.
**Mechanism:** Shopper submits a return in the store's returns portal (Loop, Returnly, native) → agent enriches the request with the customer's order history, prior return rate and reasons, device/IP signals, item value, and the free-text reason → runs multi-stage checks in ~2 seconds (wardrobing, bracketing, counterfeit-swap, shallow-fake claim patterns) → applies policy: auto-approve refund, require a photo, block, or route to a human queue with a written justification → writes the decision back to the returns platform and stamps an audit line on the customer record.
**Why agentic:** It's decisioning across unstructured evidence (free-text reasons, prior-claim narratives) and a policy tree, not a static rules engine. The output is an action taken plus an audit artifact, not a chart.
**Generalizable core:** Inbound customer request that carries refund/fraud/comp risk → agent pulls history and external signals → applies policy → writes decision + audit trail back into the workflow system.
**Deployability:** Zapier / Make / n8n or Lindy sitting between Shopify and the returns platform, plus an LLM call for the reason-classification and prior-claim summarization steps. Week-to-month build depending on how many signals you want to blend. Same skeleton generalizes to warranty claims, chargeback response, insurance FNOL triage, and B2B service credits.
