# 2026-10-22 — Agent Pattern Scan

## TL;DR
Four patterns today, drawn from fresh Anthropic customer write-ups. The strongest is Carvana's Claude-Tag agent that watches production-alert Slack channels, pulls together code ownership + logs + runbooks + warehouse data, and opens a PR in the thread — a reusable blueprint for any inbound-signal-in-a-chat-channel workflow. Rocket Money's "self-healing deterministic script" pattern is the most structurally novel: agents aren't the runtime, they're the repair layer that gets called in when a cheap deterministic flow breaks.

## Patterns

### 1. Slack-channel alert triage agent that opens its own PRs

**Source:** [Carvana on Claude Tag](https://claude.com/customers/carvana) — Carvana rolled this across retail science, wholesale platform, and customer verification teams; cites 56% fewer alerts in retail science and 65% faster answers on the wholesale platform.

**Mechanism:** Triggered by production monitoring alerts posted to specific Slack channels, by new software releases/errors landing in a verification channel, by hourly cron for pipeline + feature-flag checks, and by inbound wholesale intake tickets. The agent reads: code ownership (so it can @ the right engineer), logs compared against a baseline hour from before the release, team-maintained runbooks + per-alert notes + a comparison "skill" stored in the repo, build history, and the data warehouse through its own scoped identity (e.g., trace a VIN end-to-end). It writes: a root-cause analysis in the Slack thread in the team's preferred format, optionally a PR opened from that analysis (human review required before merge), occasionally a ticket or an "I stopped — this looks like infra, needs human" note.

**Why agentic:** It's not a bot that pastes a dashboard link in the channel. The trigger is an unstructured operational signal; the agent chooses which tools to call (logs vs. warehouse vs. tickets vs. code), decides whether to answer, open a PR, file a ticket, or stand down, and loops in the right human by code ownership.

**Generalizable core:** Operational signal arrives in a chat channel → agent assembles context from codebase, runbooks, and system of record → posts analysis in-thread + proposes a next action (PR, ticket, escalation) → replaces the on-call "look at four tabs and tag someone" step.

**Deployability:** Claude Tag in Slack (or Claude Agent SDK + Slack bolt + MCP servers for GitHub, your log store, and your warehouse). Weekend build for the single-channel version; week-plus to add scoped warehouse identity, PR opening, and skill-storage. Replaces the first 15 minutes of an on-call rotation. Needs a repo for runbooks and a service account with scoped read access to logs and the warehouse — any team with those is in scope regardless of scale.

### 2. Agent as the repair layer for deterministic automation

**Source:** [Rocket Money on Claude](https://claude.com/customers/rocket-money) — Rocket Money built "agents that fix their own code" alongside Rowan, their consumer financial agent.

**Mechanism:** The actual automation (e.g., a subscription-cancellation flow) runs as cheap deterministic code against a given website. The agent is dormant. When the deterministic procedure breaks — usually because a target site changed its DOM, auth flow, or form — the agent is woken, given the failing procedure and the point where it broke, finds the correct new path by acting against the site, and emits a patched version of the script. Agent Skills are used to package the executable fix with its instructions, so the next run is deterministic again.

**Why agentic:** The pattern treats agent inference as a scarce, expensive resource used only when the deterministic path fails. The agent exercises judgment (where did this flow actually break, what's the new element path, is this a real UI change or a transient error) and emits code that replaces itself as the runtime.

**Generalizable core:** Deterministic procedure fails → agent inspects the failure context → agent executes the task once by reasoning + tool use → agent emits a patched deterministic script → system returns to cheap autopilot.

**Deployability:** Claude API + a browser-automation tool (Playwright/Browserbase) + a script store (git or a key-value store). Weekend build for a single procedure; week build for a pool of procedures with failure detection and automatic re-deploy. Replaces the ops/engineer who babysits scraper breakage. Scale caveat: works best when the deterministic task is well-defined and the breakage surface is visible to the agent (web UIs, API responses). Not for anything where "which action to take" varies by request.

### 3. Upload-triggered bulk payment agent with a single approval gate

**Source:** [Qonto on Claude via Amazon Bedrock](https://claude.com/customers/qonto) — Qonto's SMB banking customers now run payroll (15–20 pay slips at a time) and invoicing through an "operator" agent.

**Mechanism:** User drops pay slips or a CSV of clients into Qonto. A router sends the request to a task-specific subagent. The agent reads the uploaded documents plus existing account data (beneficiaries, prior invoices). It assembles the entire batch — all pay slips consolidated into one bulk SEPA transfer, or every invoice drafted with the right client and amount — and holds the batch for one final review. Nothing executes until the customer confirms. Model routing is explicit: Opus 4.5 and Sonnet for complex missions, Haiku for simpler steps; deterministic checks run alongside the model for financial impact.

**Why agentic:** Document-arrival is the trigger, not a form submission; the agent decides which account to pull beneficiaries from, which clients from the CSV match prior invoices, and bundles the full workload into one human-approvable action instead of a one-by-one entry flow.

**Generalizable core:** User uploads a batch of structured-but-messy source documents → agent routes to a task specialist, enriches each item from the system of record, and prepares a single approvable action → one human click executes the whole batch.

**Deployability:** Claude API (or Bedrock) + Haiku classifier + a file-upload entry point + whatever ERP/accounting/payroll system of record holds the beneficiaries. Weekend build for a single-document-type demo (upload CSV → draft N invoices); month build for production with deterministic financial checks and audit logging. Replaces the admin who manually re-keys each line from a spreadsheet. Scale caveat: the "one approval for a batch" UX only works if the agent is reliably correct across the batch — needs real test corpora before shipping.

### 4. Cross-ticket pattern detection that cascades a response across tools

**Source:** [Zendesk on Claude](https://claude.com/customers/zendesk) — Zendesk cites one customer running 14M+ requests/year, with 1M agent executions in 7 weeks and automated duplicate merging at 99% accuracy.

**Mechanism:** The trigger isn't a single ticket. It's a burst of similar tickets arriving in a short window — the agent detects the cluster. On detection it: files a Jira issue describing the pattern, posts in Slack to alert engineers, replies to each affected customer saying the issue is known and being worked on, and later (when the fix ships) closes the related tickets and notes the cause on each. A self-review step saves what was learned as a reusable skill.

**Why agentic:** The trigger is an emergent cross-ticket signal, not a per-ticket event. The agent fans out across three systems (ticketing, Jira, Slack) and closes a cross-system loop later when the fix lands.

**Generalizable core:** Pattern across many inbound items (not any single item) → agent files an upstream issue + notifies owners + batch-updates all affected items + closes them with a note once resolved → replaces the support manager who manually spots the surge, pings engineering, and sends the "we know" blast.

**Deployability:** Any ticketing system with a webhook + Claude API + Jira/Linear MCP + Slack. Weekend build for the "detect cluster + draft the Slack + draft the mass-reply" version; week-plus for the auto-close-on-fix feedback loop. Replaces the support-lead manual "incident declared" workflow. Scale caveat: cluster detection needs enough ticket volume to be real signal, not noise — low-volume teams get fewer, less distinct clusters.
