# 2026-09-18 — Agent Pattern Scan

## TL;DR
Andon Labs opened Pion this week, a persistent supervisor-plus-subagent stack that already runs a real cafe, a retail store, and vending machines end to end with its own bank account, phone line and terminal. Cognition also shipped Devin Auto-Triage into general availability, where an alert in Datadog, Sentry or PagerDuty pulls the agent into a full investigation and, when it can, a pull request without a human kicking it off. Apollo Research's Watcher, a sidecar monitor that blocks or escalates other agents' tool calls in real time, quietly crossed billions of tokens a month.

## Patterns

### 1. Persistent multi-tool operator running a real P&L
**Source:** [Pion, an agent designed to run any company autonomously — HN 2026-09-15](https://news.ycombinator.com/item?id=49700477) plus the [Andon Labs launch tweet](https://x.com/andonlabs/status/2099547565759062090). Andon Labs is the outfit that put a Claude-run vending machine inside Anthropic's office in early 2025; they now operate Andon Market (SF retail) and Andon Cafe (Stockholm) with the same lineage of agents. Pion opened as a research-preview waitlist on 2026-09-14.
**Mechanism:** A supervisor agent (Andonos) receives high-level directives ("run this cafe," "run this store"), decomposes them into sub-tasks, and dispatches sub-agents that each hold real-world credentials — corporate bank access, an email inbox, an outbound phone number, a browser session, and a shell on a persistent VM. Sub-agents read the current business state (bank balance, inventory, unread mail, inbound calls, prior decision log stored in the supervisor's long-term memory), then act on it: place a wholesale order, wire a supplier, reply to a customer complaint, take a call, execute a shell command against the store's POS. All state changes land in the real systems (bank ledger, inventory SaaS, email thread), not a sandbox. What it replaces is the operator layer of a small business — front office, purchasing, cash management, customer comms — collapsed into one continuously running agent.
**Why agentic:** It runs indefinitely, decides what to do next based on state it discovers, and executes irreversible actions against real money and real customers rather than proposing them.
**Generalizable core:** high-level directive + persistent credentials on real systems (bank, mail, phone, terminal) → agent inspects state on a loop → executes multi-step operational actions → state lands back in the same real systems.
**Deployability:** Pion itself is waitlisted and hard to self-host; the mechanism is not weekend work. A narrower version — one persistent agent with Claude API + MCP servers for Gmail, Twilio, a bank API (Mercury/Brex) and a POS or shop-management SaaS — is a month build and squarely inside what a two-person firm can ship. Replaces or augments an owner-operator running a single-location business; scale caveat is that even Andon's own cafe and store are not yet profitable, so treat this pattern as "agent runs specific ops loops" rather than "agent runs the whole company."

### 2. Alert-triggered code investigation with a PR at the end
**Source:** [Cognition — Introducing Auto-Triage](https://cognition.com/blog/auto-triage), rolled forward through the [Devin 2026 release notes](https://docs.devin.ai/release-notes/2026). Auto-Triage first shipped in May and expanded across September to cover PagerDuty incident-lifecycle events, weekly dependency sweeps, and CI-failure loops.
**Mechanism:** Devin subscribes to webhooks from Datadog, Sentry, PagerDuty, Linear, GitHub, Slack, plus scheduled cron. When an alert fires — a new Sentry error, a PagerDuty incident triggered, a Linear ticket labelled "bug" — Devin starts a session unprompted. It reads the codebase, the alert payload, related past investigations from its long-term memory, and any linked observability data; it can spawn parallel sub-Devins to explore branches. Output is written back into the source system: a PR on GitHub with the proposed fix, incident notes on the PagerDuty timeline, a de-duplication comment linking a new alert to a prior thread, or a daily DataDog health digest in Slack. What it replaces is the first hour of every on-call rotation — the "what's this alert, where does it come from, is it a duplicate, do we already know how to fix it" work.
**Why agentic:** The trigger is external and unattended; the agent picks its own investigation path and produces an artifact (PR, postmortem, dedup link) that lands in the same tools the team was already using.
**Generalizable core:** external event in a system-of-record → agent reads the system state and its own memory of prior events → drafts a concrete remediation artifact → writes it back into the same system for humans to approve.
**Deployability:** Devin itself is a paid SaaS; a hand-rolled equivalent for one ops team runs on Claude API + MCP for the tracker + a persistent vector store for prior investigations, roughly a week for the first tracker and days per additional integration. Replaces the L1 triage rotation and Monday-morning "what happened over the weekend" review. Not SMB-scale in the enterprise-observability version, but the shape (webhook → agent investigates → PR/comment) is trivially copyable to a plumbing-ticketing tool, a Shopify merchant's returns queue, or a nonprofit's donor-CRM alert stream.

### 3. Sidecar oversight agent that blocks other agents mid-tool-call
**Source:** [Apollo Research — Watcher](https://watcher.apolloresearch.ai/) and their September post [Monitor Your Coding Agents Without Slowing Them Down](https://watcher.apolloresearch.ai/blog/monitor-coding-agents.html). Apollo says Watcher is monitoring "billions of agent tokens a month" across production engineering teams at agent-building scale-ups and multinationals.
**Mechanism:** Watcher hooks into another agent's tool-call boundary. A **blocking monitor** intercepts each tool call in real time and decides allow / deny / escalate against a policy trained on the ~40 recurring failure modes Apollo has catalogued (deception, dangerous exec, instruction violation, exfiltration attempts, etc.). A **trailing monitor** re-scans windows of the session transcript on a delay and scores nine dimensions 1–10. Blocked calls are surfaced to a human review queue with the reasoning attached; scored sessions feed an audit trail. Published metrics: 93% recall on high-severity cases, <1% false positives, <0.1% escalation rate to humans, 3–5% latency overhead. What it replaces is the human "watching the agent's shoulder" that today caps how autonomously any agent can be trusted to run.
**Why agentic:** It's an agent acting on another agent's actions, in real time, with real veto power — not a passive log viewer.
**Generalizable core:** every tool call from another agent → policy monitor with memory of failure modes → block / allow / escalate → writes to an audit log and, when needed, a human review queue.
**Deployability:** Watcher is a hosted product with a self-hostable monitoring backend. The DIY shape is MCP middleware: wrap the actual tool servers in a proxy that calls Claude with the tool-call args plus a small policy, returns a verdict, and either forwards or 4xx's. That is a weekend build for a narrow policy ("never let this agent send Slack DMs to anyone outside the company"), a month for a real catalog of failure modes. Replaces the manual review cost that keeps most SMB agent deployments in "recommend, don't execute" mode.

### 4. Shared-inbox document ingestion, gated by an allowlist of known senders
**Source:** [Microsoft Payables Agent — Setup, Dynamics 365 Business Central](https://learn.microsoft.com/en-us/dynamics365/business-central/payables-agent-setup) plus the [August 2026 release note on Known Senders](https://learn.microsoft.com/en-us/dynamics365/release-plan/2026wave1/smb/dynamics365-business-central/speed-up-processing-known-senders-payables-agent). Payables Agent went GA in April 2026's Wave 1 release and rolled the Known Senders feature in August across all BC regions and Microsoft-supported languages.
**Mechanism:** The agent is bound to a specific Microsoft 365 shared mailbox (typically ap@company). On a poll, it pulls unread messages with PDF attachments and checks the sender against a Known Senders allowlist configured in BC. Known-sender mail runs the whole path unattended: the agent parses the PDF, extracts header and line items, opens an inbound electronic document in BC, and attempts a match against open purchase orders. Mail from senders not on the list is held for a human to promote (or reject) — a one-click way to expand the autonomous surface without ever inviting an unknown vendor into the ERP. What it replaces is the AP clerk who opens the inbox, saves the PDF, keys line items into the ERP, and eyeballs the PO match.
**Why agentic:** It's continuously polling an inbox, making entity-resolution and matching decisions per invoice, and writing structured records into a system of record — not a report of what came in.
**Generalizable core:** poll a shared inbox → for messages from allowlisted senders, extract structured data from the attachment and write to a system of record → for everyone else, queue for a human to promote or block.
**Deployability:** Native for anyone already on Business Central. The rebuild for teams on QuickBooks/Xero/NetSuite is well-worn: Gmail or Graph API for the inbox, Claude for parsing and PO matching, the accounting system's inbound-doc endpoint for the write, a small Postgres table for the allowlist. Week-long build, then days per additional document type (POs, statements, remittances). Replaces a part-time AP clerk. Scale caveat: works on structured invoice PDFs; edge cases (multi-page attachments, embedded spreadsheets) still need human touch, which is precisely what the "unknown senders queue" is for.

### 5. First-notice-of-loss voice agent that opens the claim itself
**Source:** Aviva's half-year 2026 disclosure and CEO commentary, reported in [Life Insurance International](https://www.lifeinsuranceinternational.com/analyst-comment/aviva-ai-virtual-agent-claims/) and [Insurance Times](https://www.insurancetimes.co.uk/news/aviva-to-introduce-virtual-agent-that-can-handle-claims-phone-calls/1457955.article). Aviva is one of the UK's largest insurers; the AI-enabled claims agent and a broader "virtual assistant" are both flagged for launch inside 2026. McKinsey separately reports Aviva has now deployed 80+ AI models across claims, cutting complex liability-assessment time by 23 days and reducing customer complaints 65%.
**Mechanism:** Trigger is an inbound phone call to the claims number. The voice agent authenticates the caller against the policy record, pulls their claims history and coverage details, and walks the customer through the first-notice-of-loss capture in natural conversation: what happened, when, where, injuries, third parties, photos. It structures the answers as it goes and writes a full FNOL record into the claims system. For simple, low-severity claims it can take the call end-to-end and trigger downstream payment or repair workflows; for anything complex it hands off to a human handler with the record already open on their screen. What it replaces is the FNOL contact-center rep — the person whose job is to convert a phone conversation into a structured claim.
**Why agentic:** It's holding a real conversation, deciding at each step what to ask next, and producing a system-of-record artifact — plus a routing decision (auto-resolve vs. escalate) — rather than just recording audio.
**Generalizable core:** inbound phone call about a specific event → voice agent reads the caller's account state → captures structured intake in dialogue → writes to the source-of-truth system → routes simple cases to auto-resolution and complex ones to a human with full context pre-loaded.
**Deployability:** Aviva-scale is enterprise. The SMB rebuild uses Retell or Vapi for telephony + LLM orchestration, a vertical SaaS API for the record (Simple Practice for therapy intake, Housecall Pro for HVAC service dispatch, DentalIntel for dental new-patient calls), and Twilio numbers. Two-to-four-week build for one call type. Replaces the front-desk/call-center intake seat; scale caveat is that voice quality and escalation policy need real weekly transcript review for the first months, which is now the standard-of-care pattern for production voice agents.
