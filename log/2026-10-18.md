# 2026-10-18 — Agent Pattern Scan

## TL;DR
Five mechanism-level patterns surfaced today, all distinct from the May 2026 backlog. The standout is Rocket Money's self-healing code loop: automations run as plain code until they break, and only then is a Claude agent woken up to diagnose the break, rewrite the code, and hand execution back to deterministic code. It is the clearest answer we have seen to "when do you actually need an agent in the loop and when is code enough."

## Patterns

### 1. Alert-driven root-cause + PR agent sitting on the Slack channel
**Source:** [Carvana customer story (claude.com)](https://claude.com/customers/carvana) — Carvana runs Claude Tag against production monitoring Slack channels and a scheduled hourly sweep of pipelines and feature flags.
**Mechanism:** Production alert posts in a Slack channel → Claude Tag identifies which team owns the affected code → reads that team's work tickets, build history, and codebase (read-only, scoped per-team identities) → compares the current release against the hour before it shipped → posts a root-cause analysis in the thread and tags the owner → on request, opens a pull request from the analysis (one real example: it opened a PR to add logging when existing logs couldn't explain a deploy) → human review merges the PR. Scheduled hourly checks replace continuous monitoring for issues that don't need real-time attention. Alert volume in the retail-science channel fell 56%; wholesale team time-to-answer dropped 65%.
**Why agentic:** The agent decides which team owns an alert, which sources to read, and whether a fix is warranted — it files a ticket, opens a PR, or decides to do neither. It also replaces two homegrown Slackbots. A dashboard here would just show more red; the agent moves the alert toward resolution.
**Generalizable core:** Monitoring event in channel X → agent resolves ownership and reads the owner's own tickets/history/code → publishes RCA in the thread → optionally drafts a reversible remediation (ticket or PR) → human approves.
**Deployability:** Claude Tag + per-team Slack channels + read-only tool scopes to each team's repo, ticketing, and build system. Weekend build for a toy version against one service; week-plus build to get ownership resolution and tool scoping right at a real org. Replaces first-pass on-call triage and homegrown Slackbots. Not SMB-easy — the pattern needs scoped read access to multiple systems and some discipline about team-owned "skills" (runbooks and release-comparison logic kept in each team's repo).

### 2. Self-healing automation: code until it breaks, then an agent rewrites the code
**Source:** [Rocket Money customer story (claude.com)](https://claude.com/customers/rocket-money) — Rowan, Rocket Money's personal finance agent.
**Mechanism:** User asks Rowan in plain language (e.g. "cancel my gym membership") → a Haiku 4.5 classifier routes to a task-specific subagent → routine tasks like cancellations are packaged as deterministic code (Agent Skills). The code runs until it breaks, usually because a vendor site changed. On break, a Claude agent is called in → diagnoses where the code failed → repairs the process → turns the repair back into code → the deterministic path takes over again until the next break. After each action, Claude also checks whether the cancellation actually completed and tells the user what happened.
**Why agentic:** Agents are only invoked at the break edge; everything else is cheap, deterministic code. The agent's job is to repair the code and hand control back, not to run every request. That inversion is the pattern — most "AI agent" writeups put the LLM in the hot path.
**Generalizable core:** Deterministic code runs a repetitive task → runs break (vendor change, schema drift, API 4xx) → agent is invoked only on failure → diagnoses + rewrites the code → deterministic path resumes.
**Deployability:** Claude API with Agent Skills + a code store the agent can read and rewrite + a break detector (test failure, non-200 response, output schema mismatch). Weekend build for a prototype against one brittle vendor; month build to get a safe code-write-back loop and regressions coverage. Replaces the SRE/support engineer who had to log in and manually fix a broken scraper or automation every time a website changed. Scale caveat: works best when the task is high-frequency enough to be worth rewriting as code rather than agentic-every-time.

### 3. Pile-of-stuff bulk operator agent with hard human approval gate
**Source:** [Qonto customer story (claude.com)](https://claude.com/customers/qonto) — Qonto's operator agent and analyst agent, exposed inside the Qonto app and via MCP.
**Mechanism:** Trigger is an unstructured pile landing in the app — e.g. 15–20 PDF pay slips dragged into bulk transfer, a CSV of clients dropped for invoicing, or a meeting transcript piped in via MCP that implies a quote. The operator agent routes the pile to a specialized sub-agent scoped to that task → sub-agent reads each item + relevant account context (balances, labels, past invoices) → prepares the full batch of transactions, invoices, or quotes inside Qonto → customer sees everything in a prepared state and approves (nothing with financial or customer impact ships without confirmation; deterministic checks run alongside the model for sensitive cases) → on approval, Qonto executes.
**Why agentic:** The input is unstructured and heterogeneous (PDFs, CSVs, free text), the agent has to pick which specialist to invoke, and the output is a batch of real transactions. It replaces the human loop of "open each pay slip, type each beneficiary, re-key amount, build the transfer." A dashboard here is useless; the work was never visibility, it was re-keying.
**Generalizable core:** Heterogeneous batch lands in app/channel → router agent picks a specialist → specialist reads each item + account context → prepares full batch of writes in the target system in draft state → human bulk-approves.
**Deployability:** Claude API + MCP server over the system of record + a draft-state model in the target app so the human can approve or reject at the batch level. Week build for a single input type (e.g. CSV of invoices → draft invoices in QuickBooks); month build for a true router with multiple sub-specialists and MCP. Replaces operations/finance admin at the batch-entry layer, which is where SMB bookkeepers and ops managers spend a lot of their time.

### 4. Status-change-triggered autonomous worker with a shared skills library that gets better
**Source:** [Notion customer story (claude.com)](https://claude.com/customers/notion) — Notion's internal use of Claude Managed Agents against its own task boards.
**Mechanism:** Trigger is a status change on a Notion task board (team member moves card to "ready to start") → Notion kicks off a Claude Managed Agents session for that task → agent reads context from connected pages: linked design docs, API docs, PRDs, design-system pages → does the actual work (prototype code, slides, PDFs, spreadsheets, websites) with no one watching, since the session runs long-form in Anthropic-managed infrastructure → routes the result to the right humans for review in Notion. Novel part: after each finished task, the agent identifies what it learned and writes it into a shared "skills" database that future sessions draw on. Agent quality compounds over time with no manual curation. Notion internally kicked off 30 prototype tasks at once and came back to find them done.
**Why agentic:** The trigger is a Kanban status change, not a chat prompt. The work is long-running and unattended. And the skills library is a feedback loop — the agent is literally improving its own future runs by writing to a shared store that teammates and future agent sessions both read. That is not a dashboard, and it is not a Zap.
**Generalizable core:** Record state change in system of record → long-running managed agent session starts → reads connected context → produces artifact → writes artifact back + writes a short reusable "learned this" note into a shared skills store that future sessions read.
**Deployability:** Claude Managed Agents (so the long-running session doesn't need babysitting) + the system of record emits status-change webhooks + a shared skills store the agent is allowed to append to. Week-plus build for an internal-only version; month for a safe production version with the skills store. Replaces the junior-engineer or coordinator step of "pick up the ticket, go find the context, do the work." Scale caveat: the learning loop only pays off if you're running enough similar tasks that the skills store sees reuse.

### 5. Cross-ticket pattern detection as the trigger, not a single ticket
**Source:** [Zendesk customer story (claude.com)](https://claude.com/customers/zendesk) — Zendesk custom agents, 1M executions in seven weeks.
**Mechanism:** Instead of firing per inbound ticket, the agent watches the ticket stream and notices when many similar tickets arrive in a short window → recognizes "this is one incident, not N tickets" → takes the configured actions in one shot: files one Jira issue, posts in Slack to engineering, notifies all affected customers with the same explanatory note, closes the related tickets as duplicates → after the run, reviews its own work and saves the handling as a reusable skill the next similar incident can use. Routing is cost-aware: simple one-off requests get a single Sonnet call; harder/incident-shaped ones get the full plan step. Each tool call is logged.
**Why agentic:** The trigger is a pattern across many records, not a single event. The agent is deciding "this is an incident" and acting across Jira + Slack + the ticketing system in one pass, then writing a skill for next time. A dashboard would show a spike; this takes the spike as a signal to act and ties off the long tail of duplicate tickets.
**Generalizable core:** Many similar records arrive in a window → agent detects the cluster as a single underlying event → takes the one-time response across adjacent systems → closes/dedupes the long tail → saves the response as a skill.
**Deployability:** Claude Agent SDK (Zendesk did it with a 5-person team in 4 months, PoC to early access) + plain-English customer instructions + a few tool connections (Jira, Slack, ticketing) + skills store. Week-plus build for a single-channel version at a smaller shop (support inbox with a repeated-complaint detector); month+ for multi-channel with safety rails. Replaces the support manager/escalation engineer step of noticing "wait, this is the same issue" and the manual follow-up spray. Zendesk reports up to 80% reduction in human handle time on complex ticket types.
