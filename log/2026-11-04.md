# 2026-11-04 — Agent Pattern Scan

## TL;DR
Rocket Money's Rowan assistant runs its routine actions (like cancelling a subscription) as plain deterministic code, and when the target website changes and breaks it, an agent reads the error, fixes the code, and merges it back — turning a one-shot fix into a durable task. The pattern collapses the "it worked once, then broke" failure mode that kills most SMB automation.

## Patterns

### 1. Self-healing deterministic task layer
**Source:** [Claude customer story — Rocket Money / Rowan](https://claude.com/customers/rocket-money) — the Rowan conversational finance agent, 2026 rollout, reported by Anthropic.
**Mechanism:** A user texts Rowan in plain English (e.g. "cancel my gym membership"). A Haiku 4.5 classifier routes the request to a purpose-built subagent. Routine, well-worn actions are not executed by the LLM at all — they run as deterministic code (browser scripts and API calls). When the code fails because a target site changed its DOM or flow, an agent is invoked on the error, reproduces the task, patches the deterministic code, and promotes the fix back to the task library. After every action, Claude verifies it actually happened (e.g. that the cancellation confirmation landed) and reports why if not.
**Why agentic:** The trigger is an unstructured user request and the system chooses an execution path (deterministic code vs. agent). The repair loop is the agentic part — the agent reads a stack trace or broken selector, re-plans, and writes new code without a human in the loop.
**Generalizable core:** Natural-language request → router → prefer deterministic code for repeat tasks → agent repairs the code when it breaks → verifier confirms the real-world side effect.
**Deployability:** Claude Code + Bedrock for the model layer; Playwright or Browserbase for the deterministic script layer; any Git host for the repair-then-commit loop; Postgres or Airtable for the task library. Week build for a single-domain version (e.g. "cancel/pause/change" against three target websites) against a month-plus build for the general case. Replaces the "support ops person who keeps the scripts alive." Caveat: this is a B2C app with scale, but the self-healing idea works for a one-person ops team running three or four brittle vendor integrations.

### 2. Slack-alert triage agent that writes the RCA and opens the fix
**Source:** [Claude customer story — Carvana](https://claude.com/customers/carvana) — Claude Tag deployed across production monitoring and release verification. Carvana reports 56% fewer alerts in one channel and a 65% reduction in time-to-answer for the wholesale platform team.
**Mechanism:** A monitoring alert hits a Slack channel. Claude Tag picks it up on arrival, reads the team's runbooks and per-alert notes stored in the repo, pulls build history, ticket history and the hour of logs before the release, and identifies the owning team. It writes a root-cause analysis in the team's preferred format, opens a pull request if the fix is in code (e.g. a logging change for observability), and files a ticket. If it concludes the alert is downstream of a broader outage, it stands down and says so in the thread rather than piling on. Each team has its own scoped identity; the wholesale platform team's identity had read-only access to the cloud warehouse.
**Why agentic:** Trigger is an inbound event, the context is reassembled per-incident from heterogeneous sources, and the output is a decision plus artifacts in multiple systems (Slack thread, PR, ticket). The stand-down branch is the giveaway — the agent exercises judgment on whether to act, not just on how.
**Generalizable core:** Inbound event in any channel → agent gathers runbook + history + fresh telemetry → writes diagnosis + opens fix artifact → or explicitly declines to act with a reason.
**Deployability:** Claude Tag (or Claude Code + Slack) + GitHub/GitLab + Linear/Jira + whichever observability stack the shop runs (Datadog, Grafana, Sentry). Weekend build for a single alert type with a single runbook; month build for a fleet-of-teams version with scoped identities. Replaces the on-call engineer's first 20 minutes on every alert. Caveat: the runbook-in-repo habit is the real prerequisite; shops without written runbooks will not get this benefit until they write some.

### 3. Playbook-driven document redlining in place
**Source:** [Claude customer story — Spellbook](https://claude.com/customers/spellbook) — Spellbook for contract review in Microsoft Word, reports ~10 hours of lawyer time per agreement reduced to ~1.
**Mechanism:** Contracts arrive via email, Slack or Salesforce and are opened in Word. The agent reads the inbound document, the legal team's codified playbook (its standards for review and negotiation), and the firm's contract library of prior deals. It flags risks, drafts redlines, compares terms against market norms, and makes edits in place — scoped to specific paragraphs rather than rewriting the whole file. Negotiated versions are indexed back into the library for later re-evaluation. The newer autonomous flow starts the loop when a salesperson requests an agreement.
**Why agentic:** The playbook is the agent's source of truth, not the specific document — it is reasoning against a codified standard on each incoming artifact and writing scoped changes back into the artifact itself.
**Generalizable core:** Document arrives → agent compares against a codified house standard → writes scoped edits directly into the document → indexes the result for the next comparison.
**Deployability:** Claude API + a Word add-in (Office JS) or Google Docs API; the house standard lives as a markdown or JSON playbook in Git; Salesforce / HubSpot / Dropbox for inbound triggers. Week build for a single document type with a small playbook (e.g. an MSA checklist). Replaces the senior reviewer's first pass. Works outside law: any trade RFP response, insurance underwriting narrative, or grant application that has to conform to a codified house style has the same shape.

### 4. Training roleplay agent built from historical call transcripts
**Source:** [Claude customer story — Impel](https://claude.com/customers/impel) — automotive dealer software company, reports ramp time for a rep down from 3–6 months to roughly 1 month after rolling out the practice agent.
**Mechanism:** Claude was run over 150,000 recorded dealer calls plus Impel's full Salesforce instance to extract realistic personas, common objections, and the rubrics by which a good conversation is judged. In production, a rep opens a practice session on their own time; the agent plays a dealer persona using speech-to-text and text-to-speech, stays in character across turns, and at the end scores the rep on objection handling, rapport, product knowledge and next-steps. The scorecard is posted as a DM in Slack. About 25% of the go-to-market org logged in for practice in the past month.
**Why agentic:** The agent is both a stateful conversational counterparty (multi-turn, in-character) and an evaluator producing a structured artifact. The input corpus trained the scenarios; the live session is the pattern.
**Generalizable core:** Historical corpus of real customer interactions → extract personas and rubrics → spoken-or-text roleplay partner → scored artifact routed to the manager's channel.
**Deployability:** Claude API for reasoning and scoring; Vapi, Retell or ElevenLabs Conversational for voice; Gong, Fathom, Fireflies or a call recording export as the input corpus; Slack or email for the scorecard. Week build if the rubric is already written; month build if you have to mine it. Replaces manager-led roleplay sessions and shadow-ride-alongs. Scale caveat: the 150K-call corpus is overkill. A few hundred recorded calls is enough to extract 5–10 usable personas and a rubric — fits any SMB sales team, home-services call center, dental front desk or client-facing legal practice that already records calls for QA.

### 5. Escalating-cost OCR plus plan-then-draft pipeline for document-heavy intake
**Source:** [Claude customer story — EvenUp](https://claude.com/customers/evenup) — personal injury law firm software, reports 8–15 hours of paralegal work per case down to ~30 minutes.
**Mechanism:** A case file (often 1,000+ pages — medical records from several providers, billing ledgers, police reports, intake forms) arrives. Each page is read with the cheapest extraction method that works: existing embedded text first, then standard OCR, then Claude vision for scanned bills and checkbox forms. Documents are sorted by type (billing statement, clinical note, intake form). Facts are extracted with citations back to specific source pages, and duplicates across providers are merged. Opus builds a blueprint (applicable rules, likely opposing arguments, the case's central theme) and checks it for internal consistency. Sonnet drafts each section from that blueprint using state-specific drafting rules written in plain English. A separate Opus pass totals damages from the validated records for smaller cases. An attorney does a single review on the finished draft and signs.
**Why agentic:** The pipeline is multi-stage with branching extraction strategies and a plan-then-execute loop (blueprint by the big model, drafting by the cheap one). The consistency check and the citation-to-source-page requirement are the pieces that make it trustworthy enough to put in front of a licensed signatory.
**Generalizable core:** Document-heavy intake → escalating-cost extraction (text → OCR → vision) → sort and dedupe → plan with the expensive model → draft with the cheap one → single human sign-off at the end.
**Deployability:** Claude API with mixed Opus/Sonnet routing; Tesseract or AWS Textract for the middle extraction tier; a document DB (Postgres + pgvector, or SharePoint for law firms) for the sorted corpus; the firm's existing case management system (Clio, Filevine, PracticePanther) as the write target. Month-plus build end-to-end; week build for just the extraction-and-sort stage. Replaces the paralegal's records-review phase. Works outside PI law for any file-heavy intake: insurance claims, loan underwriting packets, M&A diligence binders, a construction company's permit submission, a benefits broker's enrollment packets.
