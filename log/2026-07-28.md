# 2026-07-28 — Agent Pattern Scan

## TL;DR
Five distinct patterns cleared the filter today. The most useful shape recurring across three of them: **a record-, event-, or state-change in a system of record triggers an agent that investigates via MCP/tool adapters and writes a structured or prose artifact back to that same system** — no chat interface, no dashboard, agent as a scoped service account. Cleanest new example is OpenStatus's incident-timeline writer that drafts and updates status-page prose during a live outage.

## Patterns

### 1. Monitor-webhook-triggered status-page report writer
**Source:** [OpenStatus engineering blog + open-source repo `openstatusHQ/agent-webhook`](https://www.openstatus.dev/blog/agent-webhook) — OpenStatus is an open-source uptime/monitoring + status-page vendor, dogfooding this internally and shipping it as a template for users. Mid-July 2026.
**Mechanism:** OpenStatus monitor flips state (`error` / `degraded` / `recovered`) → HTTPS POST to `/webhook` → agent uses the OpenStatus MCP server to investigate the failing monitor (recent probe results, historical baselines, related monitors), optionally cross-references Sentry/PagerDuty/Grafana via additional MCPs → decides whether to open a new incident, extend an existing one, or wait for more signal → drafts prose describing what's broken → writes report to public/private status page → posts follow-up updates as new signal arrives → marks resolved when monitor recovers. Replaces the "someone has to update the status page" tax that usually loses out to firefighting during real incidents.
**Why agentic:** The output is written text produced from investigation, not a rendered field. Deterministic scripts get "flap vs. real outage in the same minute" wrong every time; the agent's job is to make that judgment and keep the artifact accurate as facts change. A related but broader framework worth flagging: [Sourcegraph Amp's Event-Driven Orbs](https://ampcode.com/news/event-driven-orbs) (shipped July 23) generalizes this shape — any HTTPS event wakes a fresh agent thread with repo/context access; Amp separates trusted metadata from untrusted content bodies to blunt prompt injection from external issue text.
**Generalizable core:** External state-change event → agent investigates via MCP/tool adapters → writes/updates a prose artifact in a system of record → keeps updating until a stop condition fires.
**Deployability:** Weekend build. Stack: OpenStatus MCP + any LLM + a webhook handler (Node); ships with `DRY_RUN=on`. Replaces the "incident-commander writes updates" chunk of on-call. Scale caveat: needs monitor-to-component mapping and a week of dry-run before write access.

### 2. CRM-record-triggered public-document enrichment
**Source:** [Ignite Reading × HubSpot Agent Builder](https://ppc.land/hubspot-agent-cuts-350-hours-a-year-for-ignite-reading-across-25-states/) — Ignite Reading is a virtual literacy tutoring provider working across 25+ US states with ~1,000-1,400 school-district records/year. Named flagship customer for HubSpot's [Agent Hub / Agent Builder public beta](https://www.hubspot.com/company-news/meet-agent-hub-and-agent-builder), launched July 23, 2026.
**Mechanism:** New (or renewal) deal record enters HubSpot with `domain` and `school_year` fields populated → agent hits the open web, locates the district's academic-calendar page (different URL and format per district — HTML table, PDF, image, interactive widget) → parses first/last day of school, holidays, breaks, PD days, end-of-year date → writes normalized start/end/holiday dates to structured properties on the deal → downstream scheduling and tutor-assignment workflows key off those fields. Replaces the ops-person routine of Googling "[district] academic calendar 2026-27," opening a PDF, and transcribing into HubSpot. HubSpot claim: 350+ hours/year recovered.
**Why agentic:** Each district publishes differently. A scripted scraper breaks on every other district. The agent adapts per-page: locates the right URL, chooses PDF vs. HTML extraction, decides what counts as an in-service day vs. a holiday.
**Generalizable core:** New CRM record with an external identifier (domain, address, license number) → agent locates a public artifact scoped by that identifier → extracts structured fields → writes back to the CRM.
**Deployability:** Weekend build in HubSpot Agent Builder's no-code canvas (Pro/Enterprise); a week to roll your own with a headless browser + LLM parser + record write-back. Replaces the boring "look this up per new customer" ops task most SMBs just skip. Scale caveats: per-execution credit meter; needs an eval set of source pages to catch parse regressions. Ports to any B2B relationship where the customer publishes something structured about themselves — restaurant menus, dispensary hours, physician-panel rosters, retail SKU lists, permit records.

### 3. CVE-to-merged-PR remediation with a CI-failure repair loop
**Source:** [GitLab 19.2 release, July 16, 2026](https://about.gitlab.com/press/releases/2026-07-16-gitlab-19-2-brings-governed-agentic-automation/); [InfoWorld coverage of the auto-remediation loop](https://www.infoworld.com/article/4200083/gitlab-previews-auto-remediation-of-vulnerable-dependencies.html). Shipped in public beta across GitLab Ultimate customers.
**Mechanism:** Dependency-scanning job flags a CVE in a project's lockfile (or a scheduled sweep finds one) → Duo agent opens an MR that bumps the dependency to a safe version → CI pipeline runs on the MR → on failure, agent reads the failing job logs plus every callsite in the repo that touches the package's API, rewrites the offending callsites, commits the fix to the same MR, re-runs the pipeline → loops until green → MR sits for human review. Writes: Git branches/MRs/commits, CI pipelines, vulnerability report. Replaces the developer's 1-4 hour "bump dep, run tests, fix the three imports that moved, run tests, ship" cycle per vulnerability, times a backlog.
**Why agentic:** Pipeline failure branches the plan. A dashboard would list vulnerable packages; this observes CI output and decides what code to change next.
**Generalizable core:** Failing automated check → agent reads failure context + related code/data → commits a patch → re-runs the check → loops until pass (or iteration cap fires).
**Deployability:** Same-day if you're already on GitLab Ultimate; ~1 week to build outside GitLab with any CI + LLM harness (needs log ingestion, sandboxed commit permission, retry budget). Replaces junior-dev dependency-hygiene rotations. Caveat: unbounded loops burn tokens fast — needs a hard iteration cap and human review before merge on high-blast-radius packages. The pattern is applicable well beyond dep bumps: schema migrations, failing lints, broken test fixtures.

### 4. Voice-locked drafting with an interview + adversarial-critic loop
**Source:** [How I AI podcast, July 20, 2026 — Alex Lieberman (Tenex Labs / ex-Morning Brew) walks through his six-step "Content Machine"](https://www.lennysnewsletter.com/p/how-the-founder-of-morning-brew-built). Tenex Labs reports "tens of millions in pipeline" attributed to the machine.
**Mechanism:** Scheduled (rolling 7-day window) or on-demand → an "Oracle" agent scans internal systems (meetings, project updates, Slack) and the open web for "content spikes" — anecdotes, contrarian moments, story hooks — and scores them → an "Interview Panel" agent converts each surviving spike into structured questions and captures the operator's real, live answers (this step is where slop is prevented) → voice/style files enforce tone in drafting → an "Editorial Council" of critic agents scores the draft against learned rubrics, rejects or rewrites → a "Lessons Loop" fine-tunes the critics on the operator's actual accept/reject edits → drafts land in the content queue. Replaces the writer + editor + junior content strategist doing weekly ideation and drafting; keeps the operator on the hook only for their own tacit knowledge in the interview step.
**Why agentic:** The Oracle *decides* what's worth interviewing about. The Editorial Council *rejects and rewrites* drafts against rubrics that update over time. It's a chain of judgment calls, not a fixed template pipeline.
**Generalizable core:** Trawl-for-signal → interview the owner for substance → draft in owner's voice → adversarial critic loop against learned rubrics → learn from operator edits. Applies to any recurring artifact produced from an operator's tacit knowledge: sales enablement decks, RFP responses, partner briefings, technical whitepapers, expert-witness reports.
**Deployability:** ~1-month build for a real voice-locked version; Claude + orchestrator + a small store of voice samples and prior accepted drafts. Replaces the drafting/editing bench, not the expert. Scale caveat: the interview step still requires the human's live answers — this pattern reduces the operator's time from days to ~15 minutes per artifact but doesn't remove them.

### 5. Pre-partner client-inquiry intake with parallel conflicts + scoping
**Source:** BigLaw deployments described by [Perspective AI's Kirkland & Ellis writeup](https://getperspective.ai/blog/kirkland-ellis-ai-strategy-7b-big-law-leader-client-intake-2026) and [Latham & Watkins writeup](https://getperspective.ai/blog/latham-watkins-ai-adoption-how-biglaw-is-deploying-generative-ai). Vendor blog is the primary public source, so treat the specific efficiency numbers with skepticism, but the mechanism recurs across multiple named firms.
**Mechanism:** New client inquiry lands (email, web form, referral doc, PDF) → agent digests the messy inbound into structured facts (parties, jurisdictions, matter type, deadlines, likely staffing) → runs a preliminary conflicts check across the firm's client history in parallel with a scope-note draft and fee-arrangement suggestion → produces a partner-ready briefing → writes a structured record to the matter management system, flags conflicts to New Business Intake, sits upstream of drafting tools like Harvey so the drafters work on cleaner inputs. Replaces the multi-day email/Word-doc shuffle between BD, the originating partner, conflicts team, and NBI. Firms report intake-to-engagement-letter compressed from days to under an hour.
**Why agentic:** The agent chooses which parties to conflict-check, classifies the matter type, and generates a novel scope note per matter — not a form fill.
**Generalizable core:** Unstructured inbound inquiry → structured facts extraction → parallel checks (conflicts / eligibility / pricing / capacity) → decision-ready briefing → write to system of record + flag to reviewers. Fits underwriting, grant intake, procurement RFQs, hospital admissions, VC deal-intake, agency new-business qualification.
**Deployability:** Month-plus for a defensible version given the security and conflicts audit surface. Stack: Claude + retrieval over the firm's client corpus, or a vendor like Perspective AI. Replaces the intake/BD-coordinator layer. Big caveat: false-negative conflicts checks and hallucinated citations are the real risk, not model quality — needs airtight retrieval and clear escalation gates.
