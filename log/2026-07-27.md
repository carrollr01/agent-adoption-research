# 2026-07-27 — Agent Pattern Scan

## TL;DR
The most interesting pattern today is Amp's event-driven orbs: coding agents that expose a durable webhook URL and wake themselves whenever any external service — CI, Linear, a monitor, a GitHub release feed — sends an HTTP event. The agent has no session open, no human present; it reads the event context, does the work, and posts back. This is the cleanest example so far of an agent behaving as a subscribable service rather than a chat session, and the trigger class (arbitrary webhook + signed event payload) is reusable in any business that has a system emitting events.

## Patterns

### 1. Webhook-triggered coding orbs that self-schedule against any external event
**Source:** [Amp event-driven orbs release, July 23 2026](https://ampcode.com/news/event-driven-orbs) — Sourcegraph shipped this as the fifth release in a seven-day run; also written up at [Digital Applied](https://www.digitalapplied.com/blog/amp-event-driven-orbs-self-scheduling-agents-2026).
**Mechanism:** A developer starts a thread in an orb for a repository and tells Amp which events to watch and what to do with them. Amp turns that request into a project-specific plugin: it scopes a listener to the repo and event types, verifies GitHub's signature, deduplicates deliveries, and exposes a durable webhook URL. When CI fails on main, a Linear issue opens, a monitor fires, or any HTTP request hits that URL, the orb wakes into a read-only thread with the trusted event metadata as context. It reads the failing job logs, the linked commit, or the dependency changelog, then acts — posts the failure investigation to Slack, opens an upgrade PR against the repo, or writes a reply back to the issue. The prior state was: a human noticed the CI email, opened the log, investigated, then opened a PR.
**Why agentic:** The orb has no session open. The wake event supplies the "why act now" signal, and the agent chooses the next step — read this log, run this command, open this PR — without any dashboard rendering the state for a person to click through.
**Generalizable core:** External system emits event → signed webhook lands on a durable URL → agent wakes with event metadata as context → reads relevant history → takes bounded action → writes result back to the same or a paired system.
**Deployability:** Amp orbs handle the webhook plumbing directly; the equivalent from scratch is a Cloudflare Worker or Next.js API route verifying HMAC signatures, dropping the payload onto a queue, and spawning a Claude Agent SDK run per event. Weekend build for a single event type, week for a small catalog. Replaces the "on-call engineer notices, reads the log, does the thing" motion. Scale caveat: this only pays off when the event stream carries most of what the agent needs — event → action loops with sparse payloads still need retrieval, which is where the cost creeps in.

### 2. Nightly review-every-matter agents at plaintiff law firms
**Source:** [Eve is now EveOS](https://www.eve.legal/blogs/eve-is-now-eveos) — the June 2026 platform launch covered by [LawSites](https://www.lawnext.com/2026/06/eve-builds-on-ai-workforce-launch-with-eveos-an-ai-native-operational-platform-for-plaintiff-firms.html); firms have built 20,000+ casework agents on Eve in the last three months per the company's own summary.
**Mechanism:** Intake runs 24/7 through an inbound-call agent (Jenny) that screens leads and books qualified callers. The core operational loop is a nightly sweep across every open matter in the firm's case management system: the agent reads the current status, the medical records that arrived that day, deadlines, discovery obligations, and prior correspondence, then advances the file. That means producing a structured medical chronology from newly ingested records, drafting a demand letter calibrated to the firm's existing voice for cases that hit the demand threshold, and drafting discovery requests and responses due within a window. Attorneys start the morning with a queue of drafts to review rather than a queue of files to open. Reported outcomes: 3x attorney capacity, 30% higher settlement values, 20+ hours saved per attorney per week.
**Why agentic:** The trigger is "another day passed"; the action is variable per matter (draft a demand letter here, extract a chronology there, flag a deadline elsewhere), decided by the agent reading each file's state. A dashboard would surface the same information but leave the drafting to the attorney.
**Generalizable core:** Nightly cron over every open work item → agent reads current state and any new inputs → decides which of N template actions applies → drafts the artifact and queues it for morning human review.
**Deployability:** The horizontal version is a Claude Agent SDK loop over records pulled from a practice management, CRM, or project system, with retrieval over any documents attached to the record since the last run. Week to a month depending on how many action templates you support. Replaces the paralegal or junior associate nightly sweep. Scale caveat: quality depends on whether the case management system already holds structured status fields — firms still working from email threads and Word docs need a normalization pass first.

### 3. Vision-in, agent-out back-of-house at restaurants
**Source:** [Truffle](https://www.usetruffle.ai/) — YC S26, launched publicly in July; company page at [YC](https://www.ycombinator.com/companies/truffle).
**Mechanism:** Cameras and voice capture in the kitchen and stockroom register real-time inventory levels — the company claims 90% faster than manual counts and 97% forecast accuracy on item-level demand. Those signals become the trigger surface: when case counts drop against forecasted demand, a procurement agent drafts POs against the restaurant's supplier list and sends them. When invoices arrive by email or paper, a reconciliation agent matches line items against the PO and the receiving count and flags discrepancies. Scheduling agents build shift plans against forecasted covers; food prep agents translate the forecast into a prep list per station; menu engineering agents recommend removing low-margin items whose ingredients are driving waste. The whole back-of-house — normally a manager with clipboards and spreadsheets stitched between Toast, a supplier portal, and QuickBooks — collapses into agents that read the sensor stream and act.
**Why agentic:** The trigger isn't a human opening the app; it's a case count dropping past a forecast-adjusted threshold, or an invoice arriving in the ops inbox. Each of those fires a specific workflow, and the workflows communicate (waste flagged by menu engineering feeds back into prep quantities).
**Generalizable core:** Physical sensor or scan → structured inventory/state event → forecast layer adjusts the trigger threshold dynamically → agent selects the workflow that matches the event class → executes against the supplier, accounting, or scheduling system.
**Deployability:** Full stack (CV + voice + forecast + N agents) is a founding-team-months build, but the pattern in isolation is a week: a scheduled agent that reads a POS or accounting inventory snapshot, applies a demand forecast (even a simple exponential smoothing), and drafts POs when projected stock-out crosses the reorder-lead-time window. Replaces the general manager's Monday morning ordering session. Scale caveat: the CV/voice input layer only pays off at multi-location operators; single locations get most of the value from the software-only version.

### 4. Post-purchase ops as a rules-fed agent instead of a ticket queue
**Source:** [Pango](https://pango.ai/) — YC S26 agentic OS for e-commerce, [YC profile](https://www.ycombinator.com/companies/pango); customer-facing writeup at [narracomm](https://www.narracomm.com/pango-pango-ai-the-agentic-os-automating-post-purchase-operations-yc-s26/).
**Mechanism:** The merchant connects Shopify, their carrier accounts, and their support inbox, then writes the rules for how they want post-purchase to work — return window, refund policy, RMA eligibility, exchange defaults, claim thresholds. The trigger surface is every post-purchase event that carriers, storefronts, and customers generate: tracking update, delivery exception, return initiated, refund requested, claim filed. Each event wakes an agent that reads the order history, the customer's prior interactions, the carrier state, and the merchant's rules, then executes: books the return label, routes to the nearest drop-off, issues the refund via the payment processor, sends the customer a branded update, escalates to a human only if the event doesn't cleanly fit the rules. Pango's own numbers: 99% of returns and shipping ops running autonomously across 30 brands.
**Why agentic:** The alternative is a support agent opening a ticket, opening the order, opening the carrier portal, deciding, then writing five replies. Here the event is the trigger and the "reply" is the outcome of the rule-check plus the tool calls.
**Generalizable core:** Domain event (delivery, return, refund, claim) → agent reads full transaction and customer history → applies operator's declarative policy → executes tool calls across payments, carrier, and comms → escalates the residual to a human.
**Deployability:** Rebuilding this is a month-plus for a full post-purchase stack, but the pattern — event-listener + policy layer + tool-calling agent — ports to any ops function that today runs as a ticket queue with rules the humans hold in their heads. Zapier or Make can carry the event routing; Claude with tool use runs the decide-and-execute layer. Replaces post-purchase support headcount at ecommerce brands; the generalized pattern replaces any "review the ticket, apply the policy, take three actions in three systems" role.
