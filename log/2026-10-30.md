# 2026-10-30 — Agent Pattern Scan

## TL;DR
The sharpest pattern this run is a self-tuning multi-agent fleet at Anthropic Japan where a "Coordinator" agent edits the other agents' instructions and shared memory whenever a human corrects a draft. Three other patterns, all with before-and-after numbers from named teams: Sentry handing error diagnoses off to Claude for autonomous PR authoring, risk-scored auto-approval of low-risk PRs at Ona and Customer.io, and engineering standups replaced by an agent that reads 24h of Linear/GitHub/Slack and posts a per-person status thread.

## Patterns

### 1. Self-tuning multi-agent fleet with a coordinator that rewrites its peers' prompts
**Source:** [How an Anthropic Japan BDR runs his day with a fleet of Claude agents](https://claude.com/it/resources/articles/how-an-anthropic-japan-business-development-representative-runs-his-day) — a BDR runs six Claude Managed Agents, collectively named "Nakama," on scheduled runs.
**Mechanism:** Five domain agents each have a scheduled trigger (Furiwake triages the inbound lead queue each morning; Sabaki qualifies and drafts outreach; Henji drafts email replies hourly; Shoudan posts Salesforce opportunity updates; Nokori wraps the day from the calendar and meeting transcripts). All five read and write one shared memory store; after each run they compare their draft against what the human actually sent and save the diff as a note. A sixth agent, the Coordinator, polls Slack every ~15 minutes for human comments in a dedicated channel, and translates those into edits to the other agents' instructions and the shared knowledge base. Credentials sit in per-agent managed vaults the agents never see directly, and instructions are version-numbered so a bad edit can be rolled back. Model routing is explicit — rule-following agents on Sonnet, judgment-heavy ones on Opus, and Henji escalates to Opus through an advisor pattern when it hits a decision it can't make alone.
**Why agentic:** The Coordinator isn't a dashboard summarizing what the fleet did — it rewrites the fleet. One human correction propagates across all six agents on the next run without a prompt-engineering pass.
**Generalizable core:** Human correction in a shared channel → meta-agent diffs intended vs. actual output → updates sibling agents' instructions and shared memory → fleet behaves differently on the next scheduled run.
**Deployability:** Claude Managed Agents (beta) with built-in schedules, vaults, versioning, and Claude Tag for the Slack side; the heavy lift is designing the memory schema and the Coordinator's editing policy, not plumbing. Reported ~60 hours/week saved for a single BDR, so this is a weekend-to-week build on top of Managed Agents, not a month-long infra project. Replaces or augments the human prompt-engineer role an SMB usually can't afford to keep paying — the fleet maintains itself.

### 2. Error monitor hands diagnosis to a coding agent that opens the PR
**Source:** [Sentry case study with Claude Managed Agents](https://claude.com/customers/sentry) — Sentry processes over 1M root cause analyses per year on this workflow.
**Mechanism:** A new issue in Sentry's monitoring platform is the trigger. Sentry's in-house diagnostic agent, Seer, selects the most actionable bugs, pulls source code plus telemetry (errors, logs, spans, metrics, stack traces, profiles, trace connections), and produces a root cause analysis. The RCA is handed to a Claude agent running on Managed Agents, which plans the fix, writes the code change, and opens a pull request. The developer's job collapses to reviewing a specific proposed diff. A single engineer integrated this in weeks, not months, because sandboxing, agent runtime, and lifecycle management are the managed platform's problem, not Sentry's.
**Why agentic:** The chain crosses two systems and produces a code change rather than a report. The dashboard would have ended at "here is the stack trace"; this ends at "here is the fix, click merge."
**Generalizable core:** Monitoring event → specialist agent assembles cross-system context into a diagnosis → handoff to an action agent → the action agent writes to the system of record (code, record, document, ticket) and asks a human to approve.
**Deployability:** Claude Managed Agents gives the sandboxed runtime; the custom work is the diagnostic agent (Seer's role) and the handoff shape. For an SMB, the same pattern works for Datadog/Honeycomb → GitHub, support-ticket spike → Linear bug, CRM anomaly → draft outreach. Week to month of work depending on how much telemetry has to be joined.

### 3. Risk-scored auto-approval of low-risk PRs with human escalation on the rest
**Source:** [Ona — "How auto-approving low-risk PRs with AI cut our lead time by 74%"](https://ona.com/stories/auto-approving-low-risk-prs) (April 2026). Converging accounts: [Customer.io — "How we taught AI to approve pull requests"](https://customer.io/learn/how-we-work/how-we-taught-ai-to-approve-pull-requests), [Intercom — "AI is approving our pull requests"](https://intercom.com/blog/ai-is-approving-our-pull-requests-heres-how-we-made-it-safe), and Claire Vo's "Merge Mommy" on Vercel Eve ([How I AI episode writeup](https://www.chatprd.ai/how-i-ai/merge-mommy-vercel-eve-ai-bot-for-auto-reviewing-pull-requests)).
**Mechanism:** PR opens → CI finishes → agent reads the diff plus repo context (ownership files, recent incidents, surface area touched) → scores the change on multiple risk dimensions (Merge Mommy uses six; others use similar axes like blast radius, test coverage, data-schema touch, auth touch). A score under a configured threshold triggers auto-approval; above it, the agent posts to Slack with the risk breakdown and leaves the review to a human. A human still clicks merge. Ona reports median first-approval wait fell from 2h 49m to 3.8 minutes four weeks after turning the agent on, with deploy frequency 3x on the same team. Customer.io reports merge time from 3.5h to 33 minutes across 500+ AI-approved PRs with zero resulting production incidents. Intercom reports 19% of PRs fully auto-approved.
**Why agentic:** The agent takes a reviewable action (approve) under its own authority inside a defined envelope. A dashboard would have ranked the PRs by estimated risk; this one commits a review.
**Generalizable core:** Inbound work item + machine-checkable context → multi-dimensional risk score → below threshold, take the action; above threshold, hand to a human with the score as the briefing.
**Deployability:** GitHub Actions / GitHub App + Claude or any frontier model + a short Slack notifier. Weekend build at the toy level; the engineering is in the risk-dimension taxonomy and the threshold calibration, not the plumbing. Replaces the "someone has to look at this doc change" review bottleneck. Works outside code: expense approvals, vendor contract redlines, policy exceptions, refund decisions — anything with a reviewable action and a measurable blast-radius proxy.

### 4. Standup replaced by an agent that reads 24h of repo and chat activity
**Source:** [Cotera — "Jira standup automation"](https://cotera.co/articles/jira-standup-automation) (an engineering manager of a distributed 11-person team describes their build after trying Geekbot and Standuply) and [getviktor.com — "The Async Playbook"](https://getviktor.com/blog/replace-meetings-with-async-reports). Also [DEV Community — "The meeting-free week"](https://dev.to/kineticgoods/the-meeting-free-week-what-happened-when-our-team-stopped-having-daily-standups-3mhb), reporting 8h/week back per person after dropping the live meeting.
**Mechanism:** Scheduled trigger each morning at team start-of-day. Agent reads the last 24 hours from Linear/Jira (status changes, assignments), GitHub (PRs opened, merged, blocked), and Slack (channel messages mentioning blockers or decisions). It composes a per-person update that separates work shipped from in-progress from blocked from dependencies, then posts the full digest as one Slack thread in the engineering channel. Blockers that mention another person's name are pinged to that person. The agent writes the status back to Linear/Jira where fields were out of date.
**Why agentic:** The agent assembles a cross-system picture that no individual engineer had before the meeting, and it writes updates back to the ticket system. The live standup produced a conversation that disappeared; this produces a searchable record and triggers follow-ups.
**Generalizable core:** Scheduled sweep across the systems where work actually happens → per-person synthesis of state and blockers → single post that replaces a meeting and nudges the specific people who are blocking others.
**Deployability:** n8n or Zapier for the scheduled trigger and the Slack post; Linear/Jira + GitHub + Slack APIs for context; Claude or any mid-tier model for the synthesis. A weekend build. Replaces the daily standup facilitator and the manager's status roll-up. The 8h/week/person figure is one team's self-report, so treat it as directional — but the same pattern generalizes to any team doing daily status in a meeting (operations teams reading Monday.com, support leads reading Zendesk, sales ops reading Salesforce activity).
