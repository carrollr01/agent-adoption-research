# 2026-07-02 — Agent Pattern Scan

## TL;DR
The sharpest pattern today is Danfoss + Go Autonomous: inbound B2B order emails get parsed against SAP, validated, and turned into ERP records without a human touching the queue except on exceptions. Per-interaction handling dropped from ~9 minutes to ~1. Same shape (inbound message → reconcile against system of record → write structured transaction) generalizes to any business drowning in email-driven order or quote intake.

## Patterns

### 1. The inbound-email order agent that writes straight to the ERP
**Source:** [Go Autonomous / Danfoss case](https://goautonomous.io/news/articles/danfoss-streamlines-order-intake-with-ai/), corroborated by [Google Cloud customer story](https://cloud.google.com/customers/danfoss) — Danfoss, global industrial manufacturer, using Go Autonomous's agent layer on Google Cloud (GKE) to process B2B orders arriving as email.
**Mechanism:** New customer email lands in a shared inbox → agent parses the email body and any attachments (POs, spec sheets, PDFs) → cross-checks part numbers, quantities, and contract terms against SAP → drafts a structured order in SAP, or flags a specific mismatch back to a human. B2B interaction time dropped from ~9 minutes to ~1 (roughly 90%), and the share of orders needing full manual processing has kept trending down.
**Why agentic:** The trigger is real inbound work (not a schedule or a button), the agent has to reconcile a semi-structured email against a live system of record, and the write is a transactional record inside SAP, not a summary in a dashboard.
**Generalizable core:** Inbound unstructured message in any channel → agent parses intent + entities → reconciles against system of record → writes a structured transaction (or asks a targeted human question).
**Deployability:** Enterprise scale here (SAP + GKE), but the skeleton fits any SMB with a shared inbox and a real system of record (QuickBooks, Jobber, ServiceTitan, Shopify). Realistic SMB build: n8n or Make watching an inbox + Claude for extraction + a small validator step. Weekend build for a rough version; week to production. Replaces the order-entry/CS person who mostly retypes emails into a system.

### 2. The bug-to-PR agent triggered by production error monitoring
**Source:** [Sentry × Claude Managed Agents](https://claude.com/blog/building-with-claude-managed-agents) — Sentry paired their Seer debugging agent with a Claude-powered agent that writes patches and opens PRs; integration shipped in weeks on Managed Agents.
**Mechanism:** Production error fires in Sentry → Seer localizes the fault (stack trace, repro context, likely file) → hands off to the Claude agent → Claude reads the repo, writes a patch, opens a PR against the affected service → developer reviews the PR instead of triaging the bug from scratch. The trigger is monitoring, not a human filing a ticket.
**Why agentic:** The event is a production signal, not a human ask. The agent assembles cross-repo context on its own and produces a reviewable code artifact, not a diagnosis document.
**Generalizable core:** Threshold/anomaly signal from a monitoring system → agent assembles code + context relevant to the signal → produces a reviewable proposed change in the system that would fix it → human approves.
**Deployability:** Requires a real error-monitoring feed and a versioned system-of-truth (git, config repo, CMS). Any team with Sentry/Datadog/Rollbar + GitHub can build a rough version with Claude API + GitHub Actions in a week. Replaces the on-call triage-and-first-attempt-fix cycle; augments (doesn't replace) code review.

### 3. The task-board-as-agent-queue for knowledge work delegation
**Source:** [Anthropic Managed Agents customer stories](https://claude.com/blog/claude-managed-agents), covered [here](https://linas.substack.com/p/claude-managed-agents-guide) — Notion's Custom Agents run on Managed Agents; teams assign work to Claude directly from a Notion task board, and dozens of tasks run in parallel.
**Mechanism:** A human assigns a task to Claude on a Notion project board → the agent walks the workspace graph around that task (linked docs, meeting notes, connected data, previous decisions) → produces the deliverable (code, deck, spreadsheet, doc) → the finished artifact lands back on the same task card for review. Task board is the queue; each card is a scoped agent session.
**Why agentic:** The trigger is a project management event (assignment), not a chat prompt. Context isn't pasted — it's assembled by walking connected documents. The output is a real work product on the same card, not a summary of what should be done.
**Generalizable core:** Work-item created/assigned on a project board → agent gathers surrounding context from linked artifacts → produces the deliverable → attaches it to the same work item for human review.
**Deployability:** Notion + Managed Agents is the marquee version, but the pattern replicates on Linear, Asana, Jira, ClickUp, Trello via their APIs + Claude API. Week build if you already have documents structured; longer if the "connected data" graph needs building. Replaces the "gather-inputs-then-draft" front half of knowledge work; augments the reviewer/finisher role. Fair caveat: value tracks how well-organized the source workspace already is — messy workspaces produce mediocre agent outputs.

### 4. The inbound-PDF construction quote agent
**Source:** Aggregated across [RTS Labs 2026 construction agent guide](https://rtslabs.com/ai-agents-for-construction) and [PRL International's 2026 deployment review](https://www.prlinternational.com/post/what-real-ai-agent-deployment-looks-like-in-2026), with vendor implementations at [Kreo](https://www.kreo.net/), [Beam AI](https://www.ibeam.ai/), and [CountBricks](https://www.countbricks.com/). One case: a mid-size general contractor's estimator, previously producing ~200 quotes/year at ~3 days each, moved to roughly 15 minutes per quote after deploying an agent to read incoming project PDFs and structure quotes.
**Mechanism:** New project PDF (drawings + spec) arrives via email or upload → agent identifies quantities from drawings (takeoff), pulls historical pricing and current material rates → produces a structured quote deliverable in Excel/PDF → estimator reviews and adjusts before sending. In Kreo's Caddie, the agent operates inside the takeoff software as an operator, running measurements and returning quantities.
**Why agentic:** The trigger is a real inbound bid opportunity, the agent does the multi-step measurement + pricing work on its own, and the output is a reviewable quote artifact, not a "here's what to consider" summary.
**Generalizable core:** Inbound spec document arrives → agent extracts structured measurements/entities → looks up pricing/context from historical data → produces a customer-facing deliverable → human approves before sending.
**Deployability:** Category-specific tools (Kreo, Beam, CountBricks) are the fastest path for construction. Weekend-to-week build for a rough version on Claude + vision + a spreadsheet. Realistic for SMB contractors. Same skeleton fits any RFQ-driven business (industrial parts, print shops, custom fabrication, insurance quoting, freight quoting). Scale caveat: quality of the pricing/materials database drives quote accuracy more than the model does.
