# 2026-10-29 — Agent Pattern Scan

## TL;DR
Five concrete patterns today, all from Anthropic's recently expanded customer page. The standout is Impel's dealer-roleplay agent: it reads 150,000 recorded sales calls and plays the dealer in character so reps can practice before a product launch, cutting ramp from 3–6 months to about 1. Also novel: Zendesk's incident-triage agent that triggers on *patterns of similar tickets* rather than per-ticket, and Supermetrics' proactive pacing agent that posts anomalies to Slack before the client notices.

## Patterns

### 1. Slack-alert triage agent that produces a root cause and a PR
**Source:** Carvana + Claude Tag case study (https://claude.com/customers/carvana) — Carvana (used-car retailer, thousands of engineers) runs Claude Tag inside the Slack channels where production monitoring alerts land.
**Mechanism:** Trigger is any alert posted to a monitored Slack channel (also scheduled hourly checks of pipelines and feature flags, and software-release channels where every release is compared against the hour before). The agent reads the alert and thread, scoped build history and work tickets, the cloud data warehouse through team-scoped identities (e.g. tracing a VIN through its lifecycle), and recent code. It identifies the owning team, writes a root-cause analysis in that team's preferred format in the Slack thread, files a ticket, and when the fix is obvious opens a PR (one example: adding missing logging because an alert couldn't be explained from existing logs). Replaces the engineer who used to start manual triage when an alert hit — and retired two homegrown Slackbots.
**Why agentic:** The agent chooses which systems to query based on the alert, revises its conclusions when evidence contradicts them, and takes different write actions (comment, ticket, PR) depending on what it finds. It's not a static dashboard summarizing alerts; it's doing the investigation an on-call engineer would do.
**Generalizable core:** monitoring event in a chat channel → agent queries scoped data sources (warehouse, repos, tickets) → posts root cause in a team-defined format → opens the correct downstream artifact (ticket or PR).
**Deployability:** Claude + MCP connectors to Slack, GitHub, data warehouse, and ticketing (Jira/Linear). Standing prompts per team let each team define its own output format. Carvana reports retail-science alert volume down 56% and wholesale answers 65% faster. Not weekend-scale — team-week minimum because you need scoped data access and per-team output formats — but the pattern transplants cleanly to any team with pager-duty culture (DevOps, SRE, finance ops, data engineering, e-commerce ops). Flag: requires read access to the warehouse and repos, which SMB IT often won't have cleanly separated.

### 2. Agent that plays the counterparty, trained on your own recorded calls
**Source:** Impel case study (https://claude.com/customers/impel) — Impel (AI for automotive dealers and OEMs, ~500 employees) built a roleplay agent for its 150+ customer-facing reps.
**Mechanism:** Trigger is either a scheduled rollout of a new product/feature or a rep deciding to practice. The agent reads 150,000+ recorded dealer calls from Gong plus the full Salesforce instance, speaks through STT and TTS, and plays a dealer in character — including the objections, cadence, and vocabulary dealers actually use. It scores each session on objection handling, rapport, product knowledge, and next steps, then DMs the scorecard to the rep in Slack. Replaces peer roleplay sessions and the practice of pulling solutions engineers or sales VPs into live calls to hand-hold new reps. Ramp time fell from 3–6 months to about 1 month; first-two-months escalations dropped up to 20%.
**Why agentic:** The agent isn't a scripted drill — it generates its side of the conversation from the distribution of real recorded calls, chooses what objection to raise based on where the rep's pitch is weak, and scores along multiple rubric dimensions. Nothing a dashboard can do.
**Generalizable core:** library of recorded real conversations → agent plays the counterparty in a live voice session → scores against a rubric → delivers coaching to the practitioner. Trigger can be a scheduled training event, a hiring milestone, or a self-serve request.
**Deployability:** Claude + a voice stack (Vapi/Retell for STT/TTS), access to a call-recording system (Gong, Chorus, Fathom, or Twilio recordings), a CRM for product context, Slack for scorecard delivery. Week-to-month build. Transplants anywhere there's a repetitive high-stakes conversation and historical recordings: inside sales, SDR cold-calling, customer-success QBR, insurance claims, bedside manner for medical residents, 911 dispatch training. Flag: needs ~1,000+ recorded calls to generate convincing character; small teams would need to buy an archive or run the practice phase as data collection first.

### 3. Proactive pacing agent that flags anomalies in Slack before the client sees them
**Source:** Supermetrics case study (https://claude.com/customers/supermetrics) — Supermetrics (marketing data platform, 200,000+ businesses) runs Claude agents over its own MCP server.
**Mechanism:** Two triggers coexist. One is conversational: a marketer asks a question in Claude, which calls Supermetrics tools over MCP to pull normalized data from hundreds of ad and analytics sources (each figure carrying its source, timestamp, and transformation logic). The other is scheduled and proactive: daily pacing checks and anomaly detection run on their own and post into Slack — e.g. "click-through on campaign X dropped 30% overnight" — before the client notices on their end-of-month report. Campaign-level actions (create, edit, pause) can be triggered on Google Ads, Meta, Microsoft, TikTok, LinkedIn, and Snapchat, with new campaigns created in a paused state and an approval page listing every proposed change. Agency Layer took its weekly client reports from 10 hours to 20 minutes, 17 of those remaining 20 minutes being pure Google Sheets formatting.
**Why agentic:** The proactive loop is the agentic part. The agent decides what counts as an anomaly from the current context, assembles a cross-channel diagnosis, and posts it unprompted. The chat side is a conversational interface over the same tool surface; the Slack-posting side is a scheduled autonomous worker.
**Generalizable core:** schedule tick → agent queries normalized data across sources → compares against baseline → posts narrative anomaly to a chat channel with a proposed action requiring human approval. The MCP + Slack layer is the generic skeleton.
**Deployability:** Claude + MCP server over whatever analytics stack the business runs (Google Analytics, Shopify, Stripe, Mixpanel) + Slack webhook. Week build if the data is already in one warehouse; longer if sources are scattered. Replaces the "pulling Monday-morning numbers" analyst role and the end-of-month reporting scramble. Scale caveat: Supermetrics has the luxury of its own normalized data layer — small businesses without that need Fivetran-equivalent plumbing first, which is the real cost.

### 4. Document-pile pipeline for personal injury demand letters
**Source:** EvenUp case study (https://claude.com/customers/evenup) — EvenUp (legal technology for personal injury firms), replaces 8–15 hours of paralegal work per case.
**Mechanism:** Trigger is a new case file arriving — often 1,000+ pages of medical records from a dozen providers, plus billing ledgers and police reports, scanned, out of order, inconsistent. Four-stage pipeline: (1) sort — each page is classified (billing statement, clinical note, intake form) so each page is only asked the questions it can answer; (2) extract with escalation — machine-readable text first, then standard OCR, then Claude's vision for scans and checkbox forms that OCR can't handle; (3) settle the facts — each fact keeps a citation to its source page, duplicates merge, and the record is reconciled once before drafting (because one contradiction can tank the whole demand); (4) blueprint and draft — Opus identifies applicable legal rules, likely opposing arguments, and the case theme; Sonnet drafts each section following state-specific rules written in plain English. A separate step totals damages from the validated records. Replaces the paralegal's 8–15 hours of chronology-building, bill-totaling, and drafting. The attorney still reads and signs every output.
**Why agentic:** Different models and tools are routed per page based on what each page is; evidence is reconciled before drafting rather than during; the pipeline chooses what to escalate to vision based on whether cheaper OCR succeeded. The classification-first-then-escalation pattern is the agentic core.
**Generalizable core:** large unstructured document pile arrives → classify each page → extract with per-class cheapest-method escalation → reconcile across pages with citations → blueprint before draft → render in a state/firm/jurisdiction-specific template.
**Deployability:** Claude Opus + Sonnet + a classification pass + an OCR fallback (Tesseract, AWS Textract) + a vision pass + a reconciliation step. Month-plus build to get the per-page classifier and reconciliation step right. Transplants: insurance claims (homeowner's, auto), M&A due diligence binders, immigration applications, loan underwriting packets, grant application piles for non-profits, estate planning document review. Flag: the reconciliation step is where this earns its money; without it you get hallucinated damage totals.

### 5. Incident-triage agent triggered by a pattern across tickets, not a single ticket
**Source:** Zendesk Agents case study (https://claude.com/customers/zendesk) — Zendesk shipped custom agents that hit 1 million executions in the first seven weeks of early access.
**Mechanism:** The novel trigger isn't a single ticket arriving. It's the system detecting that many similar tickets are arriving at once — e.g. "forty tickets in the last ten minutes all mention the checkout page is down." On that detection, the agent (a) replies to each affected customer that a problem is being worked on, (b) files one Jira issue describing the pattern and posts it in Slack so engineers know, and (c) once the fix ships, closes the related tickets with a note explaining what went wrong. Separately, one customer (14M+ requests/year) automated duplicate-ticket merging at 99% accuracy. Four or five customers plan to run 20M tickets/year through these agents; human handle times down up to 80%.
**Why agentic:** The trigger is a derived pattern across the ticket stream, not a per-record event. The agent decides what "similar" means, when the cluster is big enough to escalate, what message to send to the affected customers, and when to close. A dashboard would show you the spike; this acts on it.
**Generalizable core:** stream of inbound events → agent detects pattern (volume + similarity above threshold) → fan-out acknowledgment + single-escalation + batched close-on-resolve.
**Deployability:** Zendesk + Claude + Jira + Slack. Zendesk's own custom-agent builder (plain-English instructions, per-agent action permissions) hides most of the plumbing. For non-Zendesk shops: any ticket system with webhook events + a pattern-detection pass + an action layer. Transplants to any high-volume support surface: hospitality guest complaints (sudden spike in "cold shower" tickets across one floor → ping maintenance once, reply to all guests), fleet-management ("brake warning on 12 trucks" → single service bulletin, reply to all drivers), gym/club member complaints ("water fountain broken" → batch), SaaS status ("login failing in region X" → one incident channel instead of forty duplicates). Flag: the pattern-detection threshold is tunable and gets this wrong at low volumes — too many fan-out messages for noise, too few for real incidents.
