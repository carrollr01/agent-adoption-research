# 2026-11-01 — Agent Pattern Scan

## TL;DR
The strongest signal this run is Claude Duet (Oct 21) — a proactive agent that polls your work apps on a schedule, surfaces a short "what needs you" brief, and runs cleared tasks on its own cloud computer, approval-gated for writes. It's the explicit inverse of a dashboard: the agent initiates, the user doesn't. Three other concrete mechanisms also qualified: NVIDIA/Honeywell's per-alarm industrial triage agent, Zendesk's duplicate-ticket-merge agent, and Covera's draft-but-never-send client message agent for insurance.

## Patterns

### 1. Per-alarm industrial triage agent
**Source:** [NVIDIA Developer Blog — Analysis AI Agent for Industrial Alarm Management with Nemotron](https://developer.nvidia.com/blog/building-an-analysis-ai-agent-for-industrial-alarm-management-with-nvidia-nemotron); [Honeywell "True Alarm" via Manufacturing Digital](https://manufacturingdigital.com/news/how-honeywell-technologies-cut-nuisance-alarms-by-up-to-90) — NVIDIA published the reference blueprint; Honeywell has it in building pilots cutting nuisance alarms up to 90% and is extending to factory floors.
**Mechanism:** A single plant alarm fires (SCADA/MES/BMS event, HTTP push) → agent is called at one HTTP endpoint with the alarm payload → it reads the sensor frame around the alarm (minutes of leading/trailing telemetry), asset metadata, and the plant's own playbook/runbook for that error code and location → runs specialist sub-steps ("is this an anomaly or part of a trend?", "what does the playbook say for this error code at this location?") → writes back a classification (real/nuisance), a diagnosis, and a recommended action, posted into the existing operator console as a button or chat panel. Replaces the control-room operator's manual triage of hundreds of pop-up alarms per shift, which is normally handled by scrolling, phone calls, and tribal knowledge.
**Why agentic:** Multi-step: pulls specific context around the fired alarm, runs playbook lookup, decides whether to escalate, drafts the fix. Not a static anomaly-score column.
**Generalizable core:** Noisy event stream → agent fetches context window + the human playbook for this event class → produces real/false verdict plus recommended action → writes decision back to the operator's existing interface.
**Deployability:** Nemotron NIM containers at plant edge or cloud; exposed as one HTTP endpoint behind the operator console. Month-scale build (historian/MES connectors, playbook ingestion, review loop) but the architecture itself is one endpoint. Replaces/augments the control-room operator. Scale caveat: works at any scale, but ROI tracks the current volume of nuisance alarms — small shops don't get the same payoff.

### 2. Duplicate-ticket-merge agent on inbound support
**Source:** [Anthropic customer story — Zendesk](https://claude.com/customers/zendesk) — Zendesk built custom agents on the Claude Agent SDK; 1M agent executions in 7 weeks of early access. One pilot customer handles 14M+ service requests a year and automated duplicate-ticket merging at 99% accuracy; four or five customers expected to run 20M tickets/year through these agents at GA.
**Mechanism:** New support ticket created in Zendesk → agent reads subject/body, requester history, and recent tickets in the same org or product area → searches for semantically similar open tickets using Zendesk search plus SDK tools → if a duplicate is found above a confidence bar, merges the new ticket into the existing one (Zendesk `merge` API), posts a note to the requester, and tags the parent → otherwise routes normally. Also calls out to Jira or Google Drive when the ticket references an engineering bug or a known-issue doc. Replaces the tier-1 agent's "do we already have a ticket for this?" judgment call, which is slow, inconsistent, and silently doubles engineering work.
**Why agentic:** Reads cross-ticket context, decides merge-or-not against a threshold, writes the merge, and comments on the user thread. A dashboard would just show "N likely duplicates this week" — this one closes them.
**Generalizable core:** New record arrives → agent searches recent related records → if match above threshold, merges and notifies, else routes → writes resolution back to the system of record.
**Deployability:** Zendesk Agent SDK + Claude; the "describe your agent in plain English" surface is customer-facing with no code for the simple variant. Week-scale internal build for a direct Claude-API implementation. Replaces/compresses tier-1 queue triage. Scale caveat: duplicate detection depends on enough semantic signal in subject/body — terse tickets ("it's broken again") won't cluster cleanly.

### 3. Proactive "comes to you" agent that polls your work apps
**Source:** [Claude on X — Duet research preview, Oct 21 2026](https://x.com/claudeai/status/2112984664256241837); [MacRumors coverage](https://www.macrumors.com/2026/10/21/anthropic-claude-duet/); mechanism confirmed by [Claire Vo's hands-on review](https://www.chatprd.ai/how-i-ai/claude-duet-review) ~6 days ago. It's a product-launch pattern, not a single customer deployment, but the mechanism is explicit and quickly becoming a template others will copy (Google's Gemini universal agent and Meta's Muse have the same shape).
**Mechanism:** Scheduled polling (every few hours) across connected work apps — email, calendar, CRM, Drive, docs — plus explicit tasks the user hands it → agent reads new inbound signal, resolves it against user-stated priorities and prior context (persistent memory) → runs any delegated tasks on its own cloud computer in the background → surfaces a short morning brief and intra-day action cards to the user's phone/desktop → asks approval before any "write" action (sending a message, making a payment, signing a document, deleting a file) → logs decisions back as memory. Replaces the morning "triage my inbox and calendar and tell me what matters" ritual, plus the chief-of-staff role of "chase this for me while I'm in meetings."
**Why agentic:** It's the inverse of a dashboard — the agent initiates, not the user. State persists across sessions, work continues while the user is away, and the gate is "ask before writing," not "wait to be asked."
**Generalizable core:** Scheduled sweep of connected apps plus user priorities → agent assembles "what needs you" summary → runs cleared tasks autonomously, drafts the rest for approval → writes back to source apps on confirm.
**Deployability:** For custom builds: Claude Agent SDK + MCP connectors to Gmail/Calendar/CRM/Drive, a scheduler (cron, Temporal), approval UI (SMS or a thin web app), persistent memory (Postgres + vector store). Week-to-month build. Replaces an EA or chief of staff for a solo operator; augments one for a team. Scale caveat: the hard problem is user-specific priority inference, not the plumbing — garbage priorities, garbage brief.

### 4. Draft-but-never-send client message agent (human-in-the-last-mile)
**Source:** [Covera (YC F26) — "AI workflows for P&C insurance agencies"](https://www.covera-agents.com/blog/covera-joins-y-combinator). F26 batch (Sept–Nov 2026). Explicit design rule: client messages are prepared for a person to send, never sent automatically. Small agencies and brokers at mid-market scale.
**Mechanism:** Trigger is any inbound client event in the agency management system (AMS360, Applied Epic, HawkSoft) — a renewal date approaching, a certificate request, a claim notice, a policy change email — or an inbound email in the agency inbox → agent reads the client's full policy history and the carrier portal's current data → drafts the exact outbound message the broker would send (certificate attached, carrier-specific wording, correct named insured, renewal options framed) → parks the draft in the broker's outbox with context notes → broker reviews, edits, sends. Replaces the account manager's 60-70% of the day spent assembling and typing routine client correspondence, while keeping the broker-of-record on the hook for every outgoing word (the regulatory concern that blocks fully-autonomous messaging in insurance).
**Why agentic:** Not a template picker — reads the policy, the carrier portal, and prior correspondence, then produces a specific message. The explicit "never auto-send" gate is the design feature, not a limitation; it unlocks adoption in regulated verticals.
**Generalizable core:** Inbound event in system of record → agent assembles full account context plus external data → drafts a specific outbound action in the human's own outbox → human one-click sends.
**Deployability:** Any agent SDK + connectors to the AMS + carrier portals (often scraped or via emerging MCP) + tight Gmail/Outlook drafts integration. Week-scale for a single-firm pilot; the hard part is carrier portal integrations. Replaces/augments CSRs and account managers in insurance, mortgage brokerage, wealth management, benefits — any licensed-advisor vertical where the broker must sign the outgoing message. Scale caveat: best for mid-sized agencies with repetitive correspondence; smaller shops may not have enough volume to justify carrier integrations.
