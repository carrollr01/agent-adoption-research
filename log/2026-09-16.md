# 2026-09-16 — Agent Pattern Scan

## TL;DR
Sharpest pattern today: Mercari's ~90-step "master Zap" that reads its prompts, refund ceilings, and hand-off rules from a Google Sheet CX ops edits directly — ~47K support tickets/month resolved with no engineering deploy per policy change. Interesting because it fixes the usual reason agent projects stall: ops-ownership. The pattern is a two-person shop's weekend build.

## Patterns

### 1. Spreadsheet-as-policy-DB behind a support orchestrator
**Source:** https://zapier.com/blog/zappy-award-monthly-winners-june-2026/ — Mercari US (marketplace), CX platform team; in production at ~120K tickets/month, ~47K auto-resolved.
**Mechanism:** New support ticket webhook fires a single ~90-step Zap. Step 1 classifies the ticket. Steps 2–90 don't hard-code logic — they look up a Google Sheet where each row is a category with its prompt, its policy text, its help-center URLs, its allowed refund ceiling, its confidence threshold, and its escalation path. The Zap reads the row, injects it into the LLM call, executes the action (refund via Stripe, reissue via internal payments service, canned reply into Zendesk), closes the ticket. If confidence drops below the row's threshold, it hands to a human queue. CX ops (not engineering) edit the sheet; the next run picks up the change. A Google Apps Script UI sits over the sheet so non-technical staff operate the whole thing without opening Zapier.
**Why agentic:** Prompts, allowed dollar amounts, and hand-off rules are read at runtime from a live policy store that its business owners edit. The same graph handles ~120K decisions/month across totally different case types with no engineering deploy per policy change.
**Generalizable core:** Inbound record → LLM classify → row-lookup for prompt+policy+ceiling → parametric action against tool APIs → confidence-gated hand-off.
**Deployability:** Zapier + Google Sheets + Zendesk + Stripe/whatever moves money. Weekend build for a first vertical; ~two weeks to reach ops-editable maturity with the Apps Script UI. Replaces the tier-1 support seat and, more importantly, the CX-ops ↔ engineering back-and-forth every time a refund cap or wording rule changes. Scale caveat: 90 steps in one Zap is at Zapier's upper edge; break into sub-Zaps past that.

### 2. Missed inbound-call rescue: transcription → classify → structured lead into CRM
**Source:** https://zapier.com/blog/autotorino-lead-intake-inbound-call-automation/ — Autotorino (Italy, 74 dealerships, 23 brands); built in-house; ~1,500 previously unanswered inbound requests/month now routed.
**Mechanism:** PBX drops every missed / after-hours call recording into an S3-like bucket. Zapier watches the bucket → AssemblyAI transcribes → OpenAI classifies the transcript against Autotorino's internal taxonomy (new-car / used-car / service booking / trade-in / parts / complaint), extracts caller intent, brand, location, callback preference. Zapier normalizes to their Salesforce lead schema, dedupes by phone, picks the right dealership/brand queue via routing rules, creates a Salesforce Lead with a summary note and the audio URL attached. Same "capture → normalize → write" shape now sits behind 109 sibling Zaps covering web forms, WhatsApp, Facebook lead ads — all funnel into the same canonical Salesforce Lead record.
**Why agentic:** Not a rule-based IVR — the agent reads unstructured natural speech, decides which of ~10 intents it is, extracts entities per-intent, picks the CRM queue. And the pattern is templated: one shape behind 109 different sources.
**Generalizable core:** Voice/text capture in unknown format → LLM classify + extract → normalize to one canonical record → write to system-of-record with routing.
**Deployability:** Zapier or n8n + AssemblyAI/Whisper + OpenAI + any CRM. One source in a weekend; the "one canonical record, many sources" schema work is a week or two. Replaces after-hours reception + the data-entry clerk who typed Facebook leads into the CRM. Scale caveat: the taxonomy is the moat — expect one FTE-week of ops effort to nail categories before it stops mis-routing.

### 3. Warranty-photo classifier that routes to refund OR supplier-chargeback packet
**Source:** https://www.claimlane.com/resources/case-studies/davidsen-warranty-claims-case — Davidsen Tømmerhandel (Danish DIY chain, 23 stores + e-com); warranty team went from ~5 agents to 1–2 in production.
**Mechanism:** Customer submits a return/warranty via portal or email; agent parses the message, prompts (via guided form) for specific photos: "show the crack, show the model sticker, show the receipt." Vision step identifies product SKU from the sticker/photo, classifies defect type (manufacturing / transit damage / user misuse / missing part / wrong item) and severity. Decision-branches on a per-supplier ruleset: within-warranty + verified defect + under $X → auto-approve refund/replacement in the OMS and email customer; over threshold or ambiguous → queue for the 1–2 remaining humans; classified as supplier defect → assemble a supplier chargeback packet (photos, order data, warranty terms, classification) and email it to the supplier's warranty contact so Davidsen recovers the cost. Every case's status and evidence live in a shared workspace.
**Why agentic:** The interesting move is the split routing. The same intake produces two different downstream artifacts depending on classification: a customer-facing refund action, AND a B2B supplier chargeback packet. Human doesn't see it unless confidence or dollar threshold demand.
**Generalizable core:** Photo/doc submission → CV+LLM classify → per-counterparty policy match → branch into customer action OR upstream recovery packet → write to both OMS and supplier email/portal.
**Deployability:** Claimlane if packaged; DIY on Claude/GPT vision + Shopify/OMS webhook + SendGrid is a week or two per merchant. Replaces most of the warranty desk AND the AP/vendor-management workflow that chased suppliers for chargebacks (usually neglected because nobody had bandwidth). Scale caveat: supplier-rules table has to be current — same maintenance risk as pattern #1.

### 4. One workflow spec, many government portals — visual browser agent for permit filing
**Source:** https://www.skyvern.com/blog/automate-construction-permit-applications-inspection-forms/ — Skyvern (open-source browser agent); GC/subcontractor and multi-family developer customers filing across the ~30,000 US local jurisdictions.
**Mechanism:** New project row in customer's PM tool (Procore / Buildertrend / Airtable) crosses a state ("permit ready to file"). Skyvern receives a JSON payload — jurisdiction, project data, uploaded PDFs (site plans, insurance certificate, contractor license). Spins a headless Chromium, uses an LLM + vision loop to read the jurisdiction's portal like a person: navigate, log in (handles TOTP/SMS 2FA and reCAPTCHA), find the right permit type, map JSON fields onto whatever fields the current page shows (they change per jurisdiction and even per session), upload each PDF to the correct upload slot, pay the fee, screenshot the receipt. Writes the resulting permit number + status + receipt back to the source PM tool. Same workflow definition runs against Phoenix, Chicago, Atlanta, and a county office it has never seen before, because the agent reads the rendered DOM/pixels — no per-portal script.
**Why agentic:** Zero APIs on the target side. The reasoning is inside the loop: "which of these 40 fields on this page is 'square footage'?" is answered per page-load. Same job with a scraper needs ~30K brittle configs.
**Generalizable core:** External state change → JSON payload + docs → visual-browser agent operates a counterparty UI as a human would → write result back to system-of-record.
**Deployability:** Skyvern (open-source and hosted), or Browserbase + Playwright + Claude computer-use for a DIY. One-portal proof in a few days; production multi-jurisdiction rollout is roughly a month with test coverage. Replaces the permit expediter ($75–150k/yr at mid-size builders) or, more commonly, the estimator/PM who moonlights as one. Same skeleton works for state business filings, DMV title/reg, DOT filings, ACORD-style insurance carrier portals, healthcare payer portals. Scale caveat: browser-visible portals only; some use client-mTLS/pinning this can't touch.

### 5. Calendar-aware feed monitor that pushes alerts into the channel you're already in
**Source:** https://www.fintrx.com/blog/fintrx-launches-new-ai-agent-named-fin-that-monitors-and-integrates-private-wealth-data-and-intelligence-into-email-slack-microsoft-teams-and-calendars — FINTRX (private-wealth data provider); "Fin" launched September 2026 to existing RIA/family-office prospector customer base.
**Mechanism:** Ingests each user's tracked-firms list, calendar, and Slack/Teams presence at signup. Continuous poll over FINTRX's data + external filings (advisor moves, ADV updates, new allocations across 45K RIA/BD firms, 4,600 family offices). On each new event, matches against the user's tracked list AND upcoming calendar attendees (matches attendee email/company to firm records), scores relevance, then pushes into whichever channel the user is on: Slack DM / Teams / Outlook / Gmail — as a "prep note" 24–48h ahead of a meeting, or as a running-list alert. Not a chatbot; no prompt required to fire.
**Why agentic:** Two coupled sensors (external market signals + the user's personal calendar) drive both delivery timing and content, and delivery goes to whatever tool the user is currently in — different push channel per event. The user never queried anything; the agent picked a moment and a channel.
**Generalizable core:** Continuous external feed × user context (calendar + explicit watchlist) → relevance score → push into current work surface at the right moment.
**Deployability:** Weekend build for a single-domain version: any pollable feed + Google Calendar API + Slack bot + a scoring prompt. Roughly a week to add multi-channel routing and dedupe. Replaces the "prep for this meeting" 20-min block admins/EAs did before customer/prospect meetings, plus the daily manual "did anything happen with my accounts?" sweep. Scale caveat: relevance tuning matters more than the LLM — bad matching turns this into notification spam and gets muted in a week.
