# 2026-11-26 — Agent Pattern Scan

## TL;DR
AT&T's "promote-on-accuracy" gate is the most useful pattern today: autonomy is a privilege each workflow earns by shipping in shadow mode until live-traffic accuracy hits a pre-declared threshold, after which the human is removed from the loop. It flips how we scope agent deployments; the trust budget is the deliverable, not the prompt.

## Patterns

### 1. Shadow-mode-to-autonomy accuracy gate
**Source:** https://siliconangle.com/?p=854245 and https://www.beri.net/article/att-500-agentic-workflows-business-agent-foundry-human-oversight-high-90s-accuracy-threshold-45-billion-tokens-ai-gateway-open-models — AT&T Business, ~500 production agentic workflows, >1M transactions/month, 45B tokens/day; disclosed at re:Invent Nov 2026.
**Mechanism:** every new workflow launches with an in-line human reviewer → an eval harness scores agent output against reviewer decisions on live traffic → once accuracy reaches the mid-to-high 90s on a rolling window AND a compliance/privacy review clears the risk tier, the human gate is removed and the agent runs autonomously → a central AI gateway routes the autonomous workflow through the cheapest model that still clears the threshold (open models for easy steps, frontier models for hard ones) → replaces the ad-hoc "pilot that never promotes to prod" problem that kills most enterprise agent projects.
**Why agentic:** the agent takes the business action end-to-end (billing adjustment, order orchestration, support resolution) once it has earned the promotion; the eval harness and the router themselves are agents choosing per-call behavior from measured history, not a static dashboard.
**Generalizable core:** treat autonomy as a privilege granted per-workflow by a measured accuracy threshold, not a design-time decision. Every agent ships into shadow first, is promoted on evidence, can be demoted the same way.
**Deployability:** for a 2-person firm, the minimum viable version is a shadow-mode harness that logs agent output next to the human decision on the same input, plus a one-line rule that promotes when agreement on the last N items beats a threshold. n8n or a 200-line Python runner is enough; no gateway needed until you have >1 model. Complexity: weekend for the harness, week for the per-workflow eval set. Role replaced: the manual reviewer of every agent run. Scale caveats: AT&T's measurement method and the 5x ROI figure are self-reported; the pattern is only as good as your eval set, which is where real work hides.

### 2. Lineage-scoped pipeline self-heal with safe-twin validation
**Source:** https://www.databricks.com/blog/introducing-genie-zeroops (public beta Nov 19, 2026) and https://kiro.dev/blog/trust-agent-triage/ for a mirror pattern on alarm-queue triage. Databricks reported >80,000 real customer issues handled in private preview.
**Mechanism:** a job or pipeline failure fires → agent pulls the Unity Catalog lineage graph and walks upstream dependencies to the responsible table, view, or code change → authors a candidate repair (SQL or DLT) → validates the repair against a shallow clone of the affected table so prod data is never touched → emits a PR-style diff and a one-paragraph explanation for a human to approve → replaces the 2 AM tier-1 data-engineer page-and-triage cycle.
**Why agentic:** the trigger is a failure event, not a human request; the agent locates the root cause across a dependency graph, writes the fix, and proves it on a twin before the human sees anything. A dashboard only tells you the job is red.
**Generalizable core:** when an agent operates on a production system, give it (a) the dependency graph of the system and (b) a safe twin it can validate against, so the human reviews a tested diff instead of a guess.
**Deployability:** you don't need Databricks. Any system with a lineage or dependency graph and a clone/sandbox gets this: Airflow + dbt manifest + a staging schema, Supabase + branch databases, Terraform plans against a dry-run workspace. Complexity: medium — the lineage source is the gating input, the clone-and-diff plumbing is cheap. Role replaced: tier-1 on-call for data or infra. Scale caveat: Databricks still requires human approval for every repair; the pattern does not yet remove the human, it collapses their work.

### 3. Playbook-refactor SDR agent with deterministic rules plus judgment-only LLM steps
**Source:** https://www.saastr.com/vercel-took-a-10-person-sdr-team-down-to-1-the-whole-thing-costs-5000-a-year-with-vercels-coo-jeanne-dewitt-grosser/ — Vercel COO Jeanne DeWitt Grosser on SaaStr podcast ep. 885 (Nov 4, 2026). Inbound SDR team cut from 10 to 1 + agent; infra and tokens ~$5K/year, self-reported.
**Mechanism:** inbound lead arrives → agent runs the 125-line SDR playbook that Vercel's top human SDR originally wrote as prose → that prose was refactored into ~14 deterministic rules (ICP match, firmographic cutoffs, routing, meeting-slot allocation) plus two LLM calls for the judgment-only steps (fit scoring on freeform site/profile text, intent read from the inbound message) → agent drafts the reply, books the meeting, writes to CRM → the remaining human runs the exception queue → replaces 9 SDR headcount seats.
**Why agentic:** the agent finishes the task — reply written, meeting on the calendar, CRM updated — rather than handing a human a score to act on. The LLM is spent only on the two steps rules cannot do.
**Generalizable core:** before writing the prompt, extract your best operator's recipe into code, split it into rules (where rules work) plus one or two LLM-judgment steps (where they do not), and spend the model budget only on the judgment. The LLM is a specialist, not the orchestrator.
**Deployability:** any CRM + an orchestrator (n8n, Temporal, custom) + one model. Complexity: low-to-medium; the hard part is sitting with the operator for a week to extract the playbook. Role replaced: inbound SDR / lead qualifier. Scale caveats: self-reported figures; pattern pays off only where inbound volume is high enough that a bored human misses signal, and only for top-of-funnel inbound (not ABM outbound).

### 4. In-house research workflow exposed as an MCP tool for other agents to call
**Source:** https://www.startuphub.ai/ai-news/claudes-corner/2026/claudes-corner-autumn-ai-yc-w2026 and https://debriefing.io/intel/autumn-ai-yc-signal-intelligence-gtm-agents — Autumn, YC W26. GTM signal intelligence, positioned as an MCP endpoint rather than a UI.
**Mechanism:** a caller agent (Claude Code, Cursor, a customer's SDR agent) invokes an MCP tool call like `get_prospect_signals(domain)` or a research prompt → Autumn's server resolves ambiguous entities (name → founders/domains/products), runs a crawl-score-rank pipeline across GitHub activity, SEC filings, press releases, blog posts, careers pages, LinkedIn, X, event pages → returns cited JSON with a source link per fact → the caller (not Autumn) performs the next action, usually writing an outreach draft or scoring a prospect → replaces the SDR's 15-browser-tab research pass and the first 30 minutes of a VC's diligence read-in.
**Why agentic:** the consumer is itself an agent, not a human — the output is structured and immediately consumed by the next agent step, closing the loop without a human intermediate. The server does entity resolution, crawl orchestration, and ranking across heterogeneous sources, not a single API lookup.
**Generalizable core:** package your in-house research, enrichment, or lookup workflow as a named MCP tool, so any downstream agent (internal or external) can request fresh, cited evidence per entity at call time instead of reimplementing the research path.
**Deployability:** this is the lowest-effort pattern on today's list for a 2-person firm, because the caller already exists — Claude Code, Cursor, and most agent frameworks speak MCP natively. You only build the tool. Stack: MCP server (TS or Python SDK), fetch/crawl layer, entity-resolution index, LLM for synthesis, a "cite every cell" post-processor. Complexity: medium. Role replaced: entry-level analyst / researcher doing the first pass. Scale caveat: freshness vs. caching is the real cost center; LinkedIn and X rate limits and TOS force careful source selection.

### 5. Fail-closed PII-masking on inbound email before any model call
**Source:** https://community.n8n.io/t/ai-email-triage-that-masks-personal-data-before-the-model-reads-it-workflow-download/330687 (Nov 24, 2026). Builder who ships triage flows to small businesses; tested on real customer support inboxes.
**Mechanism:** Gmail trigger on new inbound → a masking step strips names, emails, phone numbers, order numbers, API-looking strings, replacing each with placeholder tags (`<EMAIL_1>`, `<ORDER_1>`) → the masked text goes to Claude or OpenAI for category, priority, and draft reply → sender address and subject are taken from the raw email, never from LLM output → the draft lands in a Slack approval row where a human presses send → if the masking step fails, the LLM call is skipped, the row is logged with a mask-failed flag, and a human is paged → replaces a human triager on a shared support inbox without exposing customer data to a third-party model provider.
**Why agentic:** the triage step classifies, drafts a reply, routes to approval, and refuses to run when its safety precondition fails. A dashboard can show the inbox but can't draft or refuse.
**Generalizable core:** sanitize inputs before the LLM ever sees them; take load-bearing fields (who to reply to, IDs) from the raw source, not from model output; fail closed when sanitation fails, never degrade to an unmasked call. Any time a regulated or sensitive channel feeds an LLM, this is the skeleton.
**Deployability:** n8n self-hosted + the community masking node + Claude or OpenAI + Slack. Weekend for the happy path, a week once mask regexes, sender-wins policy, and the fail-closed branch are tuned per inbox. Role replaced: a human reading every support email before routing. Scale caveat: masking is regex-driven, so novel PII shapes (handwritten order IDs, foreign address formats) leak unless the dictionary is kept current; worth pairing with a periodic audit sample.

### 6. Inbound remittance email parsed to ERP payment-application with Slack approval
**Source:** https://claude.com/blog/how-abc-legal-turned-every-employee-into-a-builder-with-claude-managed-agents — ABC Legal, ~1,100 employees, 50+ production agents built by non-engineers. The AR remittance agent is a self-contained example a two-person firm could clone.
**Mechanism:** an inbound remittance email arrives in the AR inbox (unstructured body + attached PDF or CSV listing invoice IDs, amounts, payer references) → agent parses each line, matches to the open invoice list in NetSuite, computes short-pays, flags unrecognized references → proposes a NetSuite payment-application file → posts the proposal to a Slack channel for a human to approve with an emoji reaction → on approval, imports the file into NetSuite → replaces the AR clerk keying each line and reconciling short-pays by hand.
**Why agentic:** remittance emails are freeform — PDF tables, email prose, carrier-specific layouts. A parser-plus-dashboard does not know what to do with short-pays or partial-match references; the agent decides match/no-match and the Slack approval is the explicit human gate on the decision.
**Generalizable core:** inbound unstructured email → LLM-parse to a structured write for a downstream system-of-record → Slack approval before commit. The same recipe works for expense reports, PO acknowledgments, shipping confirmations, insurance claims intake, any "arrives as freeform text, needs to land in a database" flow.
**Deployability:** Gmail or Outlook webhook + an LLM with JSON output + whatever write API the SoR exposes (NetSuite SuiteTalk, QuickBooks, Xero, Stripe) + a Slack approval webhook. Week-long build assuming the ERP's write API is sane. Role replaced: 0.3–1 FTE of clerical AR/AP depending on volume. Scale caveat: payoff scales with volume; below ~20 remittances/day the ERP integration cost isn't earned back. No dedicated ML headcount required — this is one prompt and one JSON schema.
