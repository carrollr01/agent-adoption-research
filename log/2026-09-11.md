# 2026-09-11 — Agent Pattern Scan

## TL;DR
Three qualifying patterns. Most interesting: Carvana feeding raw production alerts from Slack directly into a Claude agent that returns a proposed fix as a PR, closing the loop without a human triage step in the middle. Also: scheduled autonomous repo-maintenance agents that open PRs on their own timer, and the emerging bank-account-as-MCP-tool shape from Qonto's Claude integration for SMB financial admin.

## Patterns

### 1. Alert channel → Claude → PR: engineering triage as a one-hop workflow
**Source:** Anthropic customer story — "Carvana turns Slack alerts into production fixes with Claude" (published 2026-09-04). [Source page listing](https://claude.com/customers). Carvana is a large US-based used-car retailer running production systems for online purchase, financing, and delivery; the case study sits inside their engineering org, not a lab.
**Mechanism:** A production monitor emits an alert into an engineering Slack channel Claude Tag has been admitted to. Claude picks the alert up as an inbound event (not a human @-mention), pulls the linked logs/trace/dashboard, cross-reads the relevant repo and recent deploy history via its connected tools, and either drafts a proposed fix as a pull request or, when the alert is a known noisy pattern, comments back in-thread with the diagnosis and closes the loop. Real fixes go through normal PR review. Replaces the on-call engineer's first-hour work: reading the alert, correlating it to a code path, opening the repo, sketching the change.
**Why agentic:** The trigger is the alert itself, not an engineer typing a request. The agent reads across systems (Slack thread, monitoring, repo, deploy history) rather than surfacing them on a screen for a human to correlate. Output is a PR or a diagnosis comment, not a chart.
**Generalizable core:** External system event lands in a shared channel → agent enriches with cross-system context → drafts the corrective action in the system of record (PR, ticket, order, message) → human approves.
**Deployability:** Stack is Claude Tag in Slack + MCP connectors to monitoring (Datadog/Sentry/Grafana), source (GitHub/GitLab), and deploy system. Week-plus build for a first channel with real guardrails on which repos and which alert types are in scope. Replaces the first pass of an on-call rotation. Scale caveat: works best where alerts already carry structured trace/deploy context; a shop still on "server crashed, check the box" telemetry gets less leverage. The same shape works outside engineering — a Shopify low-stock webhook into #ops with an agent that drafts a PO instead of a paged human is the same pattern in a different vertical.

### 2. Scheduled autonomous repo-maintenance agents that open PRs on their own timer
**Source:** GitHub's `gh-aw` (agentic workflows) "Agent of the Day" posts, week of 2026-09-07 through 2026-09-08. Concrete examples: [dead-code removal agent, 2026-09-07](https://github.github.com/gh-aw/blog/2026-09-07-agent-of-the-day/) and [CLI version checker, 2026-09-08](https://github.github.com/gh-aw/blog/2026-09-08-agent-of-the-day/). These are agents running against GitHub's own repos, but the workflow definitions are open.
**Mechanism:** Cron trigger, no human involvement. Dead-code agent runs `deadcode` static analyzer over Go source, identifies unreachable functions, removes them and their tests, and opens a PR (recent run: 4 functions removed in ~19 minutes with a full audit trail in the PR body). Version-checker agent hits `npm view` and the GitHub Releases API for eight tracked CLIs and eight Docker images, detects drift, pulls the release notes, categorizes changes by type (Breaking/Features/Fixes/Security/Performance), and opens a PR with the update plus a summary. Both replace the "quality sprint" or "dependency Tuesday" a maintainer would otherwise queue up.
**Why agentic:** Nobody asks. The agent runs on its own clock, decides whether the codebase needs a change today, and files the change as a PR. A dashboard would show "you have 4 unreachable functions" — this deletes them and asks you to merge.
**Generalizable core:** Cron trigger → agent inspects a defined slice of state → decides whether action is warranted → files a proposed change in the system of record with a full audit trail → human reviews and merges. Applies well beyond code: think overdue receivables review, dormant-customer sweep, inventory reorder proposal.
**Deployability:** GitHub Actions + Claude Code or the `gh-aw` framework directly. Weekend build once you have the target static-analyzer or API. The mechanical part is trivial; the design work is choosing scopes tight enough that PRs are always accept-or-ignore, never "argue about." Replaces cleanup-sprint capacity and manual dependency triage. Works at any scale because the agent's throughput is metered by cron, not by team size. A shop that already treats PRs as its work medium will absorb this immediately; a shop where changes bypass PR review will not.

### 3. Bank account as an MCP tool for SMB financial admin
**Source:** Anthropic customer story — "Qonto delegates financial admin for small businesses with Claude on Amazon Bedrock" (published 2026-09-03). Qonto is a European neobank serving ~500K SMBs and freelancers. [Qonto connector page](https://claude.com/connectors/qonto).
**Mechanism:** Qonto exposes an MCP server that gives Claude read-and-write access to the exact operations a business owner sees in the Qonto app: browse transactions, statements, accounts; issue and track client invoices and credit notes; review pending supplier invoices; manage debit / virtual / flash cards; handle team expense requests. Actions run with the same permissions the operating user already has. Concrete example flows Qonto highlights: "issue client invoices and follow up on unpaid ones," and "pull the month's biggest outflows by counterparty and flag supplier invoices due but not yet marked paid." Trigger is either a scheduled Cowork task or the owner opening a thread. Reads: full ledger + invoice state. Writes: back into Qonto (creates invoices, sends reminders, marks paid). Replaces the bookkeeper's manual AR-chase + AP-review + cash-reconciliation Monday.
**Why agentic:** The bank account itself is the agent's tool surface. Not a dashboard summarizing Qonto — an agent that can *act* on Qonto: send the invoice, flag the unpaid supplier bill, move the funds. The read-and-write scope is what makes this different from a reporting overlay.
**Generalizable core:** *(variation of 2026-05-25 invoice-chase entry — new angle: system-of-record vendor ships an MCP tool surface, so the agent operates directly on the ledger instead of proxying through QuickBooks/Zapier)*. Vendor exposes read/write MCP on the core object (bank account, CRM, PMS, EHR) → agent reads current state → drafts and applies routine writes → human owner steers via prompts and approvals rather than clicks.
**Deployability:** For end users, out-of-the-box: turn on the Qonto connector in Claude and go. The pattern for A3 Dev is the shape, not the vendor: whenever a client's core system-of-record ships an MCP surface (Stripe, Shopify, HubSpot, Rippling, and Qonto all have real ones in 2026), the build shifts from "wire together five APIs in n8n" to "give the agent tools and write the SOPs." Week build for a first workflow. Replaces the fractional bookkeeper for the routine AR/AP layer; the exception cases still go to a human. Scale caveat: real usefulness requires the client's SoR to already have an MCP surface — if it doesn't, you're back to building the connector.
