# 2026-10-05 — Agent Pattern Scan

## TL;DR
Sentry's Seer→Claude integration is the cleanest "monitor fires → agent writes PR" loop in production right now: a crash hands its full context to a coding agent that patches and opens the PR before an engineer even opens the ticket. PagerDuty shipped a near-identical pattern for ops incidents (triage, not code), and Chargeflow applies the same shape to Stripe disputes — a strong signal that "signal from system of record → agent assembles context → drafts the deliverable the specialist would have made → human only approves" is the dominant 2026 skeleton across functions.

## Patterns

### 1. The error that opens its own pull request
**Source:** [Sentry changelog: Seer can now trigger Claude to fix bugs](https://sentry.io/changelog/seer-can-now-trigger-claude-to-fix-bugs/) — Sentry's Seer product now hands bug context to a Claude agent that writes the patch and opens a GitHub PR; integration configured per-project with an Anthropic API key.
**Mechanism:** A production exception is captured by Sentry → Seer isolates the issue, builds a root-cause hypothesis and gathers stack trace, breadcrumbs, affected release and relevant repo files → hands the package to a Claude Agent → Claude writes a patch, runs the repo's tests, opens a PR against the default branch and links it back on the Sentry issue. The engineer's first action on the ticket is a code review, not a reproduction.
**Why agentic:** The triggering event is machine-detected, the context assembly spans two systems the human would have to glue by hand (Sentry + repo), and the deliverable is a code change, not an alert or a summary. If no engineer looks at Sentry for two hours, the PR exists anyway.
**Generalizable core:** monitoring event → agent gathers error context + source code → produces the artifact the on-call would have produced (patch, config change, runbook step) → files it in the correct system for human approval.
**Deployability:** Weekend build if you already use Sentry + GitHub + Anthropic — it is a configured integration, not custom code. Replaces the "reproduce, diagnose, draft fix" portion of an on-call engineer's work; the human stays in the loop for review and merge. Scale caveat: works best on repos the agent can navigate quickly; large monoliths need indexing (Sourcegraph, Cody, repo-level RAG) to keep context assembly tractable.

### 2. The incident with its diagnosis already written
**Source:** [PagerDuty SRE Agent](https://www.pagerduty.com/blog/ai/meet-your-virtual-responder-pagerdutys-sre-agent-for-ai-driven-reliability/) and the [Spring '26 autonomous ops release](https://www.pagerduty.com/eng/pagerduty-for-ai-how-the-sre-agent-triages-ai-incidents/) — PagerDuty's SRE Agent fires inside the same Escalation Policies that page humans, so the agent and the responder arrive at the incident at the same time.
**Mechanism:** An incident fires via normal routing rules → the SRE Agent is attached via escalation policy or severity threshold → it pulls monitor state (Datadog, New Relic, Grafana), surfaces correlated traces, retrieves memory of similar past incidents and their resolutions → posts a diagnosis plus a ranked set of next steps as the first comment on the incident → the paged human opens the incident to that pre-filled triage instead of a blank page.
**Why agentic:** The trigger is an existing operational signal, context pull spans multiple observability systems, and the output replaces a specific human workflow (the first 15 minutes of cold-start triage). It is not a dashboard — the deliverable is a written diagnosis on the correct ticket, in the thread where the responder is already working.
**Generalizable core:** paging signal → agent correlates across the observability stack and historical cases → posts the diagnosis-and-next-steps artifact into the thread where the human is already working.
**Deployability:** Week build if integrating with existing PagerDuty + observability stack; longer if building the "memory of past incidents" layer yourself (needs incident post-mortems indexed as retrieval context). Replaces the first-responder cold-start work, not the decision authority. Scale caveat: valuable at any size, but memory of past incidents only gets useful after you have 20–30 resolved incidents to retrieve from.

### 3. The chargeback that defends itself
**Source:** [Chargeflow automation docs](https://docs.chargeflow.io/docs/chargeflow-automation) and [agentic commerce evidence playbook](https://www.chargeflow.io/blog/agentic-commerce-chargebacks-the-evidence-playbook-merchants-need) — autonomous dispute engine for Shopify and other PSPs, Official Shopify Partner, one-click install.
**Mechanism:** A chargeback is posted by the payment service provider (Stripe, Shopify Payments, Braintree) → Chargeflow ingests it via webhook → the enrichment engine pulls signals from 1,000+ data points across Shopify order history, payment processor logs, helpdesk tickets (Gorgias, Zendesk), shipping carrier tracking, subscription platform state → an agent selects the right argument given the reason code and card network rules, composes the written response, attaches the right evidence screenshots, and submits the package back to the PSP within the response window. No human needs to see most disputes.
**Why agentic:** Trigger is an inbound webhook, context assembly spans at least five systems a human specialist would normally alt-tab between, and the deliverable is the actual submitted response, not a draft or alert. The chargeback is closed (won or lost) with no human touch unless flagged.
**Generalizable core:** inbound event with a hard deadline → agent assembles supporting evidence across every system that holds a relevant trace → drafts and submits the formal response in the external system by the deadline.
**Deployability:** Week build using Chargeflow directly for merchants; month build to replicate the pattern in a different reason-code domain (insurance claims disputes, refund negotiations, warranty claims). Replaces the chargeback analyst or back-office dispute specialist. Scale caveat: the value scales with dispute volume — a shop with five chargebacks a month gets less lift than one with 500.

### 4. The Slack firehose that triages itself
**Source:** [Yash Tekriwal (Clay) on How I AI — I built a custom Slack inbox](https://www.lennysnewsletter.com/p/i-built-a-custom-slack-inbox-it-was) — head of education at Clay, built a personal Slack digest + Kanban dashboard. ~150 daily notifications collapsed to ~30 actionable items.
**Mechanism:** New Slack notification arrives (mention, thread reply, keyword hit) → agent reads the message plus a few turns of surrounding thread → classifies it into one of three buckets (action-required, need-to-read, FYI) using the user's past response patterns as training examples → writes the item to a Kanban dashboard with the thread link, suggested action and deadline → the FYI bucket never pages the user, only the action bucket does. End of day, un-actioned "need-to-read" items get summarized into a single digest.
**Why agentic:** The classification uses the user's own historical behavior as context, not static rules — it is not Slack's keyword notifications or a saved search. The dashboard is not a view of Slack; it is a different system that holds decided outcomes about Slack messages. Mechanism replaces 30–45 minutes a day of manual inbox triage.
**Generalizable core:** inbound high-volume channel → agent classifies each item against the recipient's historical response pattern → writes outcome (act / defer / ignore) into a separate decision system → the original channel's notifications are collapsed to only the "act" bucket.
**Deployability:** Weekend build with Slack API + an LLM + any Kanban (Linear, Trello, Airtable); the only hard part is the classification few-shot examples, which have to be the user's own past behavior. Augments individual contributors buried in channel noise. Scale caveat: this is personal productivity scale — one user per deployment — but the exact pattern re-skins cleanly for email, support queues or dealer leads.

### 5. The GitHub issue tracker that triages itself overnight
**Source:** [Cotera: Automate GitHub issues guide](https://cotera.co/articles/automate-github-issues-guide) and [GitHub's own agent-of-the-day post](https://github.github.com/gh-aw/blog/2026-05-29-agent-of-the-day/) — teams running scheduled triage agents on open-source and internal repos; one team cut 3 hours/week of maintainer triage to ~20 minutes.
**Mechanism:** Scheduled run (several times a day) or new-issue webhook → agent reads all unlabeled issues in the queue → for each, pulls the issue body, reactions, duplicate candidates from the last 90 days, and the diff of recent commits touching mentioned files → applies labels (area, severity, type), picks an owner from CODEOWNERS, flags duplicates for closure, and asks for repro steps when missing → posts a one-line audit comment with its confidence and rationale → humans see a pre-sorted queue with duplicates already linked.
**Why agentic:** Priority uses live signals (reaction counts, revenue-feature flag, workaround present in thread), not fixed heuristics. Duplicate detection reads the whole thread and the matching candidate thread, not just title similarity. The output is applied state in GitHub (labels, assignees, linked duplicates), not a report.
**Generalizable core:** scheduled scan of an unstructured inbound queue → agent reads each item + its historical neighbors → applies classification, routing and duplicate links as state changes in the system of record → human sees a sorted queue, not a raw inbox.
**Deployability:** Weekend build with GitHub API + GitHub Actions + any LLM; a few days extra if you want the duplicate retriever to work well on large repos (needs embeddings over existing issues). Replaces the maintainer-triage portion of the week; the human still owns actual issue closure and roadmap decisions. Scale caveat: works at any repo scale, but shows the biggest payoff where unlabeled backlog > 100 issues.
