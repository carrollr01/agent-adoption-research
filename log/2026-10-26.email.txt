# 2026-10-26 — Agent Pattern Scan

## TL;DR
Three mechanism-level patterns from live or recently-shipped deployments: Choco's multi-channel ingest agent that turns voicemails, SMS, WhatsApp, emails and handwritten notes into structured ERP orders for food distributors; GROWMARK's myFS agronomy agent that pushes per-field hybrid, nitrogen and fungicide decisions to growers off platform data; and an agentic RFP workflow where specialist drafter agents assemble sections from a 192-proposal knowledge base. The common thread: every one of them replaces a human whose job was to translate messy inbound inputs into a structured artifact in a system of record.

## Patterns

### 1. Multi-channel order ingest agent for distributors
**Source:** Choco press page (https://choco.com/uk/press), Twilio customer story (https://customers.twilio.com/en-us/choco), Food Logistics on Choco multi-language ordering (https://www.foodlogistics.com/software-technology/ai-ar/news/22931318/choco-choco-offers-multilanguage-ordering-for-food-distributors) — Choco runs OrderAgent and VoiceAgent across food distributors in the US, Germany, France, Spain, UK, Austria and Belgium.
**Mechanism:** A single inbound order arrives in whatever form the restaurant customer wants: a voicemail on a dedicated number, an SMS, a WhatsApp message, an email with an attached PDF or image, or a phone call. OrderAgent parses the input against the distributor's catalog and that customer's prior order history, resolves SKUs and quantities (including handwritten notes and multi-language text), and writes structured line items straight into the distributor's ERP within seconds. VoiceAgent, built on OpenAI's Realtime API, handles the live phone-order path with sub-second latency, including after-hours. The agent replaces the human order-entry clerk who used to listen to voicemails and type orders into the ERP by hand.
**Why agentic:** The agent decides which parsing path to take based on the medium (OCR for photos, STT for voicemail, direct for text), reconciles ambiguous SKUs against customer history, and only writes to the ERP once it has a parseable order; it doesn't surface a pile of unstructured inputs for a human to re-type.
**Generalizable core:** Inbound message on any channel → agent normalizes to a structured record in the system of record → human only reviews exceptions.
**Deployability:** The stack is public: Twilio Programmable Messaging for SMS/WhatsApp, OpenAI Realtime API for voice, custom parsers for email and image attachments, and direct ERP writes. The capability only works if the distributor has a reasonably clean product catalog and historical order data per customer; patterns using Zapier or n8n with Twilio and Claude's vision model can replicate the shape at SMB scale in roughly a week-to-month build for a single channel, longer to cover all five. Replaces or augments order-entry clerks and night-desk operators.

### 2. Platform-resident agronomy agent that writes per-field decisions
**Source:** GROWMARK deploys AI agronomy agent in myFS Platform (https://letsdatascience.com/news/growmark-deploys-ai-agronomy-agent-in-myfs-platform-eee54535) — deployed by GROWMARK (a US agricultural cooperative) in partnership with Intelinair, for the 2026 growing season, across the farmers using myFS Agronomy.
**Mechanism:** A grower or GROWMARK agronomist opens the myFS platform on a given field. The agent reads what the platform already stores about that field — soil tests, planted hybrid, historical yield, weather feeds, satellite imagery — and generates concrete recommendations: which hybrid to place on which acres next season, when to apply fungicide, and the right nitrogen timing and rate. The recommendations land as decision cards in the platform tied to the specific field, which the agronomist can accept, modify, or ignore. It replaces (or heavily augments) the routine portion of a paid agronomist's visit — the recommendation work that was previously a billable consult.
**Why agentic:** It isn't a chart or a summary; it joins across field history, weather and imagery per field, decides when a decision is ripe, and writes an actionable recommendation card. The grower reads a decision, not data.
**Generalizable core:** Record in a vertical SaaS platform → agent assembles multi-source context on that record → agent writes a specific actionable recommendation back into the platform.
**Deployability:** Not an SMB weekend build — the real work is the vertical data integration (soil tests, weather APIs, satellite imagery, SaaS platform writes). The same pattern transfers to any vertical where a specialist already uses a platform of record: dental practice management (per-patient treatment plan recs), fleet maintenance SaaS (per-vehicle service recs), fitness club CRM (per-member retention plays). At SMB scale, this is a Claude API + MCP connection to the vertical SaaS plus scheduled triggers, two-to-four weeks per vertical. Replaces or augments a specialist's routine advisory work.

### 3. Specialist-agent RFP response from a proposal knowledge base
**Source:** AI-augmented pre-sales: designing and evaluating an agentic RFP workflow in healthcare and life sciences (https://er.auk.edu.ua/handle/234907866/188) — case study at a global IT services firm's pre-sales team, published May 2026. Measured active drafting effort cut by roughly 80–85% and cycle time from 5–7 days to same-day drafts across a sample of RFPs.
**Mechanism:** A new RFP document arrives (email, procurement portal). An intake step classifies the document, extracts required sections, and assigns each one to a specialist agent (pricing, technical, legal, compliance). Each specialist retrieves relevant passages from a retrieval-augmented store of 192 past proposals plus the firm's pricing matrix and clause library, drafts its section, and hands back a draft that lists the retrieval sources it used. A coordinator agent assembles the sections into one document and surfaces it in the pre-sales engineer's drafting tool for review and sign-off. It replaces the pre-sales engineer's week-long "copy from the last three similar proposals and rewrite" cycle.
**Why agentic:** The sections are drafted by different agents against different sources with different retrieval scopes; the coordinator decides what to assemble and when to escalate (missing data, novel question not in any past proposal). It isn't one prompt against one PDF.
**Generalizable core:** Structured inbound document → router splits into sections → each section runs its own retrieval + drafting agent against its own corpus → coordinator assembles for human review.
**Deployability:** Clean fit for Claude API + MCP for retrieval into a vector store of past proposals, with a thin orchestrator (LangGraph, Mastra, or hand-rolled). A week to a month to a first working build; the quality bottleneck is the past-proposal corpus, not the orchestration. Transfers directly to grant writers, insurance underwriting narratives, security questionnaires (SIG/CAIQ), vendor due-diligence packets, and construction bid responses. Scale caveat: the study was at a global IT services firm with 192 past proposals in-hand; SMB versions need thinner corpora and tighter templates, so quality drops for firms without a historical library.
