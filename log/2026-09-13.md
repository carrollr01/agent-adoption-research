# 2026-09-13 — Agent Pattern Scan

## TL;DR
Stripe's Kai agent hit 83% weekly adoption across 10k employees on the back of two boring middleware pieces (a virtual S3 filesystem and a per-request sandbox) — an under-appreciated pattern for making one company-wide agent hold 1,000+ team-specific skills without exploding. The reviewer-throughput crisis caused by AI-generated code is now producing its own class of agents (Merge Mommy) that risk-score PRs and only route the risky ones to humans. And recruiting is moving off manual signal-hunting onto per-signal "evergreen" agents — one that watches for candidate job changes has become the highest-ROI reactivation channel for at least one agency.

## Patterns

### 1. Risk-scored PR auto-approver ("Merge Mommy")
**Source:** [LinkedIn announcement from Claire Vo](https://www.linkedin.com/posts/clairevo_introducing-merge-mommy-my-ai-pr-review-activity-7490816714016923648-Ritf), [How I AI episode breakdown](https://www.chatprd.ai/how-i-ai/merge-mommy-vercel-eve-ai-bot-for-auto-reviewing-pull-requests) — Claire Vo (CPO-turned-builder, at ChatPRD scale) built and shipped it in a single Codex session, running on Vercel Eve. Now clears her team's PR backlog daily.
**Mechanism:** Trigger is "CI checks passed on a PR." Agent reads the diff, the changed files' history, and the PR metadata; scores the change across six risk dimensions (blast radius, test coverage delta, migration/config touch, secrets/auth surface, dependency changes, reviewer-owner conflict); auto-approves anything below the risk threshold and writes an approving review; for everything above, posts a Slack DM to the PR author with the top risks and the specific lines to defend. Replaces the human first-pass reviewer for low-risk changes.
**Why agentic:** It reads context and takes an irreversible privileged action (approving code for merge) — not a dashboard telling a human "this PR looks low-risk."
**Generalizable core:** New record in queue → agent scores it on a fixed risk rubric → auto-executes the safe path, escalates the rest to a specific human with the reasoning attached.
**Deployability:** Weekend build on any managed agent runtime (Vercel Eve, Claude Code, Devin, Lindy) with GitHub + Slack + an LLM. The tricky part is the rubric, not the wiring — the value is entirely in what you count as "risky." Replaces junior reviewer time and the "who's got bandwidth" Slack thread. Scale caveat: needs enough PR volume to make the rubric worth the effort — under ~20 PRs/day it's not obviously worth it.

### 2. Company-wide agent with team-owned skills as the extension point (Stripe Kai)
**Source:** [Lenny's Newsletter interview with Sharadh Krishnamurthy](https://www.lennysnewsletter.com/p/build-your-own-company-brain-the), [LangChain blog on the build](https://www.langchain.com/blog/how-stripe-built-their-knowledge-ai-platform-on-deep-agents), [Stripe Dev blog](https://stripe.dev/blog/meet-stripes-knowledge-ai-platform) — Stripe's internal AI platform, built on LangGraph Deep Agents. 83% of the company uses it weekly across 60k+ sessions; 1,000+ skills contributed by 100+ teams.
**Mechanism:** Triggered by employee prompts in a chat surface (Slack, web). Agent selects among registered skills (each is a signed, permissioned tool bundle a team publishes) and orchestrates them. Two middleware pieces do the real work: a filesystem middleware that mounts a virtual FS on S3 with a sync-in / sync-out model so any skill can drop or read files without touching the container; and a sandbox middleware that executes untrusted code and processes arbitrary file formats. The output lands in Slack, in a doc, in a linked ticket, or as a file back in the virtual FS — depending on which skill was picked. Replaces the "which internal tool answers this / which team owns this / can someone pull this data for me" scavenger hunt.
**Why agentic:** The dispatch is a decision, not a lookup — the agent picks skills, chains them, retries with different context, and produces novel artifacts. Chat is the surface; the middleware is the platform.
**Generalizable core:** Central agent + team-owned skill registry + sandboxed execution + shared virtual filesystem → any team can extend company-wide AI without infra work, and the agent picks the right skill per request.
**Deployability:** Month-plus build even at small scale, and the tempting SMB version is usually the wrong shape — the payoff comes from the skill registry compounding across dozens of teams. A two-person firm doesn't have that surface. Worth flagging to any client already contemplating a "single internal chatbot" so they don't build a monolithic tool that can't grow; the middleware split is the interesting design lesson even if you never build it at Stripe's scale.

### 3. Per-signal "evergreen" recruiting agents (job-change alerts)
**Source:** [Mokka AI writeup on autonomous re-engagement](https://www.gomokka.com/resources/uncapped-inbound-activation-turning-your-dormant-ats-graveyard-into-an-active-talent-pipeline-via-autonomous-re-engagement.html), [Execue "Recruitment Lead Signals Playbook"](https://execue.io/blog/recruitment-lead-signals-contact-company) — Mercury Hampton (UK recruiting agency) reports £25k generated from a single job-change alert agent, time-to-fill cut from 106 days to 37.
**Mechanism:** Agent watches an ATS/CRM database of dormant candidates against public professional data (LinkedIn changes, company announcements, press releases). Trigger is "a dormant record's public role changed." Agent reads the candidate's history in the ATS, the new employer's context, and any open roles the recruiter has; drafts a hyper-personal outreach that references the specific move and one live opening that fits; writes it back into the recruiter's outreach queue for a one-click send. Replaces the recruiter's manual "check LinkedIn on my top 100 dormant candidates" ritual, which never actually happens.
**Why agentic:** The valuable move is catching the signal in the two-week window when the candidate is reachable — that requires continuous watching and per-record drafting, not a report.
**Generalizable core:** Continuously watch external public data for a defined change event on records you own → on hit, assemble context from your internal system → draft an outreach or action tied to the freshness of the signal → write to the human's queue.
**Deployability:** Week-long build with an ATS/CRM API, a data source with public profile changes (there are third-party feeds; scraping directly is fragile and TOS-hostile), an LLM, and Zapier/Make or n8n. Replaces a recruiter task that in practice never gets done. Same shape works in sales (champion changes jobs → new territory opens), in fundraising (donor gets promoted or a portfolio company gets funded), and in professional services (a lapsed client's exec moves and needs the same service at the new firm).

### 4. AI maintenance coordinator for property managers
**Source:** [Haven AI maintenance coordinator guide](https://www.usehaven.ai/post/ai-maintenance-coordinator-guide-property-management), [Conduit "best AI support tools for property management"](https://www.conduit.ai/blog/best-ai-customer-support-tools-for-property-management-in-2026) — Conduit, Haven, and Vellum are all shipping this pattern for small and mid-sized property managers; Haven cites ~45% cut in emergency response time and up to 50% lower ops cost among users.
**Mechanism:** Trigger is an inbound tenant call, text, or portal message. A voice/text agent takes the request, asks the two or three clarifying questions that separate "no hot water" from "hot water but slow," classifies severity (life-safety, same-day, routine), pulls the unit's history and warranty/vendor mapping from the PMS (Buildium, AppFolio, Yardi), creates the work order, and dispatches the correct vendor with the address, unit code, scope, and window — or, for emergencies, calls the on-call number directly. Sends the tenant a confirmation with the ETA and the vendor name. Replaces the after-hours coordinator and the daily triage backlog.
**Why agentic:** It's making a dispatch decision under a severity threshold, executing the write to the PMS, and doing an outbound call to a vendor — not a form that shows a human what to do.
**Generalizable core:** Inbound message in any channel → agent extracts structured request + severity → looks up entity in the system of record → creates a work item there → dispatches the matched external party → confirms back to the requester.
**Deployability:** Two-to-four week build for a single property manager; Vapi or Retell for voice, Twilio for SMS, a PMS API (or Zapier if the PMS is behind one), and Claude/GPT for the classification and drafting. Same shape works verbatim in HVAC ("what's leaking, where, is it urgent" → dispatch tech), fleet maintenance, IT helpdesk for small MSPs, and clinic front-desk triage — the vertical noun changes, the mechanism doesn't.
