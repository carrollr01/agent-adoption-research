# 2026-11-10 — Agent Pattern Scan

## TL;DR
A one-truck plumbing shop that scaled past $3M is running its ops on 36 Next-Gen Zaps the owner wrote by describing them in English to Claude through Zapier MCP, with ServiceTitan as the database and Zapier as the nervous system. The interesting part isn't the stack, it's that the operator is the author.

## Patterns

### 1. Operator-authored Zapier agents on top of a vertical SaaS of record
Source: Zapier case study — 3R Plumbing & Mechanical (https://zapier.com/blog/3r-plumbing-next-gen-zaps/) — veteran-owned plumbing/HVAC shop, grew from $300k (2022) to projected $3.8M (2026); Ross Hunt is the plumber building the automations himself.
Mechanism: Hunt talks workflows to Claude in plain English through Zapier MCP; Claude writes the Next-Gen Zap, Hunt reviews and publishes. ServiceTitan is the system of record. Five concrete live agents: (a) a pending booking older than 20 minutes triggers an SMS to Hunt so the lead doesn't rot; (b) a new Facebook lead creates a ServiceTitan booking and auto-sends a confirmation text and email instantly; (c) scheduled hourly zaps pull ServiceTitan jobs/estimates/invoices/memberships into role-based portals the office staff uses instead of the ServiceTitan UI; (d) a morning zap pushes real booked-job conversion data back into Google Ads as offline conversions; (e) incoming vendor invoice PDFs get parsed and their line items posted to a purchase intake table. 36 total zaps, running ~1,400 times a week. Replaces an ops manager, a part-time bookkeeper, and the Google Ads agency.
Why agentic: The author is natural-language-driven, and execution is event- and schedule-triggered across live systems, not a report someone opens. Each zap is a durable program but the authoring loop is agentic.
Generalizable core: SMB operator describes workflow → agent writes automation targeting the vertical SaaS of record → operator reviews and ships → platform runs it on event/schedule triggers.
Deployability: Zapier Agents + Zapier MCP + Claude + vertical SaaS (ServiceTitan, Dentrix, Toast, Jobber, etc.) + Google Workspace. Week build per workflow. Replaces an admin layer; does not need ML headcount. Caveat: the vertical SaaS must have a Zapier connector; ServiceTitan's is officially "as-is."

### 2. Production alert channel → investigating agent → pull request
Source: Anthropic customer story — Carvana (https://claude.com/customers/carvana) — Fortune 500 online used-car retailer; Claude Tag running inside the Slack channels engineering teams already use for monitoring.
Mechanism: Monitoring tools post production warnings into specific Slack channels. Claude Tag watches those channels, sees a new alert, pulls the stack trace, logs, and relevant repo code, writes a diagnosis, proposes a fix, opens a pull request, and tags the on-call engineer for review. Over time the agent identifies recurring root causes and ships systemic fixes rather than one-off patches. The retail science channel cut alert volume 56%. Replaces the "ack the alert, read the stack, find the file, write the fix" first hour of incident response.
Why agentic: The trigger is an inbound monitoring event the agent subscribes to, not a human question. Context assembly across Slack, logs, and the codebase happens without prompting. The output is a PR, not a summary.
Generalizable core: Inbound event in a channel the team is already watching → agent assembles cross-system context → agent proposes the fix as a reviewable artifact in the team's existing tool → human approves.
Deployability: Claude Tag (Slack) + a code host (GitHub/GitLab) + whatever observability tool already posts to Slack. Week-to-month build to plumb permissions and write the agent spec. Augments on-call engineering. Scale caveat: real leverage requires the team already live in Slack and already route alerts there; a shop without that habit should not build this.

### 3. Self-healing deterministic code: agent rewrites the script when the site changes
Source: Anthropic customer story — Rocket Money (https://claude.com/customers/rocket-money). Launch coverage of Rowan: https://www.pymnts.com/news/artificial-intelligence/2026/this-ai-agent-ends-subscriptions-without-a-phone-call/
Mechanism: Routine subscription-cancellation flows are executed as deterministic scripts (cheap, fast, auditable) — not by an agent. When a target site changes and a script breaks, a monitoring agent catches the failure, re-explores the new site, diagnoses where the old script broke, rewrites the script, re-runs it, and hands the deterministic flow back to autopilot. A separate verifier model classifies whether the cancellation actually succeeded (bank statement check, confirmation email, etc.). Replaces the engineer whose job is "the Netflix flow changed, go patch the scraper."
Why agentic: The agent only fires on breakage, assembles context by re-exploring the live site, and produces new executable code that then runs without it. The agent is the code's maintenance crew, not the runtime.
Generalizable core: Deterministic script runs normally → breakage detected → agent re-explores the external system → agent rewrites the script → verifier confirms the real-world outcome.
Deployability: Claude Agent SDK (Skills pattern) + a job queue + a code store + some verifier (second model, webhook, or email parser). Month build. Replaces on-call script maintenance. Scale caveat: valuable where the external system changes often enough that maintenance is a real cost but rarely enough that pure-LLM-every-time would be wasteful — the whole point is to collapse to deterministic code 95% of the time.

### 4. Business-event-triggered support agents, authored in plain English
Source: Anthropic customer story — Zendesk (https://claude.com/customers/zendesk); Zendesk blog — 1M executions in 7 weeks (https://www.zendesk.com/blog/ai/agentic-ai/zendesk-custom-agents-claude/) — reports 1M custom-agent executions in the first 7 weeks of early access; automated resolution up ~10%, human handle time down up to 80% for ticket classes touched.
Mechanism: Zendesk's Agent Builder lets a support ops person describe an agent in plain English, point it at Zendesk actions and connected tools (Jira, Google Drive, internal APIs), and attach triggers. Triggers can be inbound tickets, Zendesk business events (SLA breaches, status changes, priority flips), or schedules. The flagship pattern is incident management: a Jira incident created → agent gathers all open tickets referencing the system, drafts a tailored update per customer, logs the response back on each ticket, and messages the engineering channel with an affected-customer list. Replaces the "support lead manually wrangling updates during an incident" role.
Why agentic: The trigger is a business event, not a human ask. Context is assembled across Jira and the ticket store. The action writes back to both the CRM and the comms channel.
Generalizable core: Business event in the system of record (ticket, order, invoice, booking) → agent gathers the affected cohort → agent drafts and sends tailored outbound per entity → agent logs what it did back on each record.
Deployability: For Zendesk shops, native. Outside Zendesk: Claude API + MCP connectors for the CRM/PSA/PM system + a lightweight orchestrator (n8n, Make, or a FastAPI worker). Weekend-to-week build for a single trigger class. Replaces coordination overhead during cross-system events (outages, recalls, refund batches, delayed shipments).

### 5. Bot-to-provider subscription cancellation by SMS reply
Source: Rocket Money's Rowan launch coverage (https://www.pymnts.com/news/artificial-intelligence/2026/this-ai-agent-ends-subscriptions-without-a-phone-call/); Rocket Money's own description of Rowan (https://www.rocketmoney.com/learn/personal-finance/what-is-rowan) — launched Aug 25, 2026; limited rollout to a Premium Plus tier.
Mechanism: Rowan scans linked bank/card feeds for recurring charges nearing a trial cutoff or flagged as unwanted. It sends the user an SMS like "You have a $14.99 Peacock trial renewing in 2 days. Reply CANCEL to cancel it." On a one-word reply, the agent opens the provider's cancellation path (web form, chat, API where available), executes the cancellation on the user's behalf, verifies via confirmation email or next-statement check, and texts the user back when done. Edge cases found in one user's cancellation (new retention offers, new dark patterns) are learned and applied to the whole user base. Replaces the 20-minute "sit on hold with Comcast" task — and the user's own cancellation anxiety.
Why agentic: The trigger is a signal in the user's bank feed, not a form the user fills. The agent chooses the cancellation channel per provider, handles retention gauntlets, verifies real-world outcome, and generalizes a solved edge case across the population.
Generalizable core: Signal in a data feed the consumer cares about → nudge to the consumer in their preferred channel → one-tap confirmation → agent transacts with a third party on the consumer's behalf → verification → portfolio-wide learning.
Deployability: Twilio/SMS + a bank aggregator (Plaid/MX) + a browser-use agent (Claude computer-use, Browserbase, etc.) + a verification step (email parser or next-period bank scan). Month build at minimum; the real work is per-provider edge-case libraries. Replaces a lifecycle-ops or VA role at scale. Scale caveat: legally sensitive — the consumer's authorization chain has to be airtight, and anti-bot defenses on provider sites are the actual engineering problem.
