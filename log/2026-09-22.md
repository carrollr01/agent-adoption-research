# 2026-09-22 — Agent Pattern Scan

## TL;DR
The standout today is Loop's Samantha for restaurants: instead of surfacing a "your stockout risk is high" tile, it phones the operator while they're driving. Also worth noting: agents that ship reasoning artifacts (a GitHub Discussion listing every label decision + confidence) and long-horizon runtimes that persist a goal across weeks rather than a single session.

## Patterns

### 1. Multi-rail reconciliation agent that phones the operator instead of alerting a dashboard
**Source:** [Loop AI](https://www.loopai.com/) via [GrowwStacks recap](https://growwstacks.com/blog/ai-agents-restaurant-industry-2026) — Loop's "Samantha" is live at multi-location restaurant operators; the vendor's own framing is "AI co-worker for the real economy," not analytics.
**Mechanism:** Trigger is a continuous poll across POS, 15+ third-party delivery platforms (DoorDash, UberEats, GrubHub, etc.), payout files, and bank deposit feeds. Reads sales, refunds, chargebacks, promo comps and platform-level fees per order. Matches orders to payouts to bank credits, flags mismatches, computes 2–3 day stockout forecasts from sales velocity. On exception, calls the manager over the phone (voice), summarizes the issue and confirms next action. Writes back to the restaurant's back-office and to a follow-up ticket.
**Why agentic:** The output is a phone call to a specific human at a specific moment with a specific ask, not a chart to check. The agent decides what deserves interruption and how to describe it in one sentence.
**Generalizable core:** Continuous reconciliation across N financial rails → agent detects unmatched or trending-bad state → picks the right operator by context → voice-calls them with the finding and a proposed action → writes the decision back to system of record.
**Deployability:** Weeks of build if you already have API/SFTP feeds from each rail; the reconciliation logic is the boring part. Voice out via Vapi/Bland/Retell + a small router. Complexity is mostly in the connectors and the "is this worth a phone call" scoring. Replaces a bookkeeper reviewing reconciliation reports and a manager scrolling dashboards. Works at small scale (a two-location operator can justify it) — no dedicated ML headcount needed.

### 2. Blueprint-in, quantities-out takeoff agent for contractors
**Source:** [Beam AI](https://www.ibeam.ai/blueprint-takeoff-software), [Togal.AI](https://www.togal.ai/how-it-works) — both are being used by GC estimators; Beam's flow is more agentic (fully hands-off with human QA review), Togal is more copilot-y (still-attended markup).
**Mechanism:** Trigger is a PDF plan set upload plus a written scope of work. Agent reads every sheet, identifies rooms, wall segments, door/window counts, fixture symbols and finish schedules; runs measurements against the specified scale; produces a line-item takeoff (SF of paint by finish, LF of trim, door counts, etc.). Beam then routes to an internal QA team for spot-checks before returning the file. Output is a downloadable takeoff sheet + bid-ready quantities within 24–72 hours.
**Why agentic:** The agent does the reading, deciding what counts and what doesn't, and produces a work product an estimator would otherwise assemble over 2–3 days. No dashboard, no human clicking.
**Generalizable core:** Document upload as trigger → agent parses structured artifacts inside an unstructured file → produces a downstream-ready deliverable (quantities, line items, extracted fields) → optional human QA gate before release.
**Deployability:** This one is a month+ build if you're rolling your own — vision-heavy, needs symbol libraries and scale reasoning. But the *pattern* is a weekend build for any industry with recurring document types (insurance forms, medical records, T&M invoices, permit sets). Claude + PDF vision + a QA queue is the shape. Replaces junior estimator hours; augments senior estimators who move to review-only.

### 3. Payment-support ticket resolver that logs into the back-office itself
**Source:** [n8n case study: Koralplay](https://n8n.io/case-studies/koralplay/) — iGaming operator, ~2,000 payment support tickets/month, 8 human agents; 70% of payment tickets now automated end-to-end in the first market it rolled out to.
**Mechanism:** Trigger is a new ticket landing in support tagged as payment-related. Agent authenticates into the back-office (including MFA), looks up the customer and the transaction, checks regulatory/AML flags, cross-references bank statement lines, drafts a resolution in the customer's language, and posts it back to the ticket. Runs 4,000+ workflow executions/week with dead-letter handling for the ones it can't resolve, which route to humans with pre-filled context.
**Why agentic:** The agent is doing the same login-lookup-check-respond loop the human did, including through-MFA authentication. No dashboard would help — the work is the investigation, not the visibility.
**Generalizable core:** Inbound ticket → agent authenticates into gated system(s), assembles investigation context across multiple lookups → drafts customer-facing resolution → posts and closes, or routes to human with the investigation already done.
**Deployability:** Week build with n8n or Make + a browser-agent step (Browserbase, Anon, or a Playwright wrapper) for the authenticated portals. Complexity is mostly credential vaulting, MFA handling, and the escalation logic. Replaces tier-1 payment support agents; the humans move up to edge cases and disputes. Works for any support org with a gated internal tool as the source of truth.

### 4. Auto-triage agent that publishes its reasoning to a public Discussion
**Source:** [GitHub Agentic Workflows: Auto-Triage Issues](https://github.github.com/gh-aw/blog/2026-05-29-agent-of-the-day/) — packaged as an open workflow (gh-aw), running in real GitHub repos including some of GitHub's own.
**Mechanism:** Trigger is dual: on `issues` events (new issue opened/reopened) and on a schedule several times daily. Agent reads unlabeled issues, reasons about content, applies labels with a stated confidence level and rationale. Every run creates or updates a GitHub Discussion titled `[Auto-Triage Report]` with a Markdown table: issue number, labels applied, confidence, one-line reasoning. Uses `gpt-5-mini` — deliberately small since the label set is bounded.
**Why agentic:** Not just applying rules — it's producing an inspectable artifact of its decisions that maintainers can audit and correct. The Discussion becomes the audit trail; the labels are the action.
**Generalizable core:** Classification agent runs on both event + schedule → applies structured metadata to records → writes a running, human-readable audit doc of every decision with confidence + reasoning → invites correction, uses correction as training signal.
**Deployability:** Weekend build. The novel move here isn't the classifier, it's using a Discussion (or a Notion page, or a Slack thread) as the transparent reasoning log. Anywhere a support-ticket router, lead-router, or content-moderation queue exists, this same pattern replaces the black-box "the AI decided" objection. Replaces the triage-committee meeting and the "why did it get this tag" question.

### 5. Long-horizon sales agent that persists a goal across weeks
**Source:** [Salesforce Agentforce launch, Sept 11 2026](https://www.salesforce.com/news/stories/agentforce-job-ready-ai-agents/); [Unite.AI writeup](https://www.unite.ai/salesforce-debuts-job-ready-agentforce-agents-and-long-horizon-runtime/) — Hunter is Salesforce's outbound SDR agent, running on a new long-horizon runtime and currently in pilot at named enterprise customers.
**Mechanism:** Trigger is a booked goal ("book 20 discovery calls in the Series B fintech ICP by end of Q4") rather than a single message. Agent reads CRM, LinkedIn Sales Nav, intent data, prior outreach history and calendar availability. Runs a multi-week sequence: research → drafts personalized outreach across email/LinkedIn/SMS → sends → waits (days or weeks) → adapts based on responses or non-responses → hands warm replies to a human AE. State persists across sessions rather than resetting each turn.
**Why agentic:** The whole design is that the loop lives longer than a chat. It remembers what it did on day 3 when it acts on day 17. That's a workflow, not a dashboard, and not a single-shot script either.
**Generalizable core:** Persistent-state agent with a goal + deadline → reads slow-changing context, plans multi-step sequence over long timescale → executes, waits, replans → hands off to human at the right moment.
**Deployability:** Month+ build if you want the runtime yourself — the hard part is durable state, not the LLM calls. Realistic path: use Salesforce Agentforce, Lindy, or Anthropic Managed Agents rather than building the runtime. Or use Temporal + Claude for the durable-workflow spine and Claude API for the reasoning. Replaces SDR sequences and the "did we ever follow up with X" scramble. Scale caveat: needs a decent CRM already in place; not a fit for a two-person shop with contacts in a Google Sheet.
