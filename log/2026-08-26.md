# 2026-08-26 — Agent Pattern Scan

## TL;DR
Five concrete patterns today. The most portable is Notion's task-status-triggered Managed Agent, which turns any status change on any task board into an agent launcher with human approval routing. The most novel mechanism is Vega's Detection Skills, which binds triage, investigation, and tuning skills directly to a SIEM rule so an alert's own rule improves itself as the loop closes.

## Patterns

### 1. Skills-bound-to-detection-rule (Vega Detection Skills)
**Source:** [Vega Detection Skills launch, Aug 2026](https://vega.io/blog/vega-introduces-detection-skills) — Vega released Detection Skills as an open standard (detectionskills.io), built on Anthropic's Agent Skills format, demoed at Black Hat USA 2026.
**Mechanism:** Trigger is a SIEM detection firing on log/event data. Instead of paging a human, the rule carries three attached skills that run as one continuous loop: (a) a triage skill reads the event context and either dismisses noise or escalates to an incident; (b) an investigation skill assembles the full evidence chain (which entities, what happened, why) before any human touches it; (c) an optimization skill takes the analyst's approved verdict and writes it back into the rule as a proposal for new coverage. Output lands as an enriched incident in the SOC platform. Replaces tier-1 analyst triage time and the offline "tuning debt" backlog most detection teams accumulate.
**Why agentic:** The skills act, mutate the rule, and improve future firings — not just describe what happened. Human review is on the verdict, not on the triage.
**Generalizable core:** Rule-in-a-monitoring-system fires → attached skills triage, investigate, and write approved outcomes back into the rule itself → only ambiguous cases surface to humans.
**Deployability:** Stack is Claude Agent SDK + Skills API + the SIEM's alerting webhook. Weekend build for a small deployment (one detection, one skill triple); month build to reach broad coverage and safe write-back. Replaces the tier-1 analyst decision and the rule-tuning meeting. Requires a SIEM or equivalent event source; not viable for shops without structured alerting.

### 2. Long-running autonomous cyber investigator (Outtake Recon Agent)
**Source:** [How Outtake built a cyber investigator on Claude](https://claude.com/blog/how-outtake-built-a-cyber-investigator-on-claude) — Outtake's customers include leading AI labs, hedge funds, and US federal agencies.
**Mechanism:** Trigger is a flagged domain or brand-impersonation event (customer-submitted or scraper-detected). The Recon Agent, built on Claude Code + the Agent SDK, reads and writes code, interacts directly with the malicious login pages to see where stolen credentials get exfiltrated, and follows infrastructure leads — shared hosting, registration patterns, analytics IDs, linked social accounts, operator handles like "Customer Support" Telegram accounts — mapping the whole adversarial network as a graph. Output is a written report with threat-actor profile and reconstructed timeline, delivered into the customer's brand-protection console. Median session is 16 minutes; runs commonly stretch past an hour, longest recorded at two hours.
**Why agentic:** The agent chooses its own investigation path, executes code to probe live infrastructure, and produces a novel artifact each run. No dashboard delivers this; a human would need hours per incident.
**Generalizable core:** Single flagged artifact → long-running agent expands from it, executing tools and code to probe connected entities → returns a graph and a narrative that a human could not have assembled in the time budget.
**Deployability:** Stack is Claude Agent SDK, code execution sandbox, browser/computer use for interacting with target sites, plus a graph store. Month build for a serious version, and the long-session cost profile matters ($ per investigation, not per query). Replaces threat intel analyst labor. Not an SMB-scale pattern for security itself, but the shape (single anchor → autonomous expansion → graph output) copies to investigative journalism, fraud recovery, M&A diligence on private targets, and insurance claim linkage analysis.

### 3. Task-status-triggered team agent with approval routing (Notion x Claude Managed Agents)
**Source:** [Notion x Claude Managed Agents case study](https://claude.com/customers/notion) — production on Notion 3.6, launched July 2026.
**Mechanism:** Trigger is a Notion task moving to "ready to start." Notion invokes a Claude Managed Agent session that pulls context from linked pages: PRDs, design system docs, API references, meeting transcripts. The agent produces the actual deliverable — code, a prototype, a slide deck, a brand strategy doc, a sample website. Output lands back in Notion, and Notion routes it to the assigned approver, who can iterate collaboratively rather than restart a chat. Replaces the pattern of one person prompting an agent in a private chat window with no team visibility.
**Why agentic:** The agent produces the artifact rather than surfacing information about it, and the work is legible and reviewable inside the shared workspace, not stranded in a chat log.
**Generalizable core:** Status change on any shared record → cloud agent reads the record's linked context → produces the actual deliverable → workspace routes the output to the designated reviewer for approval.
**Deployability:** For SMBs, the near-copy is Airtable/ClickUp/Linear/Asana status change → n8n or Zapier webhook → Claude Agent SDK call with the record's linked docs as context → posts artifact back to the record and pings the reviewer in Slack/Teams. Weekend build for a single deliverable type; week build for a real fan-out. Replaces the assigned-DRI's first-draft work: an "in review" comes back for the human to shape, not to write from scratch. Works at any size — the shape doesn't require enterprise data volume.

### 4. AP and bank reconciliation over MCP into the accounting ledger
**Source:** [Apideck bank reconciliation agent + FreeAgent MCP server](https://www.apideck.com/mcp-server/bank-reconciliation) and [Rutter on financial agents via MCP](https://www.rutter.com/blog/financial-ai-agents-and-mcp-how-ai-workflows-connect-to-systems-of-record).
**Mechanism:** Trigger is either a bank feed transaction landing in the accounting system or an AP invoice arriving that fails an automated PO match. The agent connects over MCP to QuickBooks, Xero, NetSuite, SAP, FreeAgent, or Jack Henry, retrieves the open bills and invoices, matches transactions to source documents, pulls vendor data for missing context, and posts reconciled entries directly to the ledger. Anything it cannot resolve is routed to a human reviewer with the full evidence chain pre-attached — variance amount, candidate matches, vendor history — so the human is deciding, not gathering. Output writes into the ledger; exceptions land in an approval queue. Replaces the controller's manual matching work and compresses month-end close from days to hours.
**Why agentic:** The agent reads structured accounting state, executes matching logic, writes to the system of record, and escalates only exceptions with context — not "here's a report, go match it yourself."
**Generalizable core:** New transaction hits a system of record → agent matches it against related open records via a standard protocol → resolves the clean cases automatically → hands ambiguous cases to a human with the evidence pre-assembled.
**Deployability:** For an SMB, this is Claude Agent SDK + the FreeAgent/Xero/QuickBooks MCP server + a shared exception queue in Google Sheets or Notion. Week build for one entity, one bank feed, one AP inbox. Replaces the bookkeeper's daily reconciliation task and the controller's month-end scramble. Guard rails on write-back are required — start with propose-only, promote to auto-post per vendor as confidence proves out.

### 5. Browser-use agent completing intake work in legacy web apps
**Source:** [Anthropic browser use + computer use GA, Aug 19 2026](https://enterprisedna.co/resources/news/anthropic-browser-use-computer-use-skills-api-enterprise-ga-august-2026/) with a documented e-commerce case: product update time from 6 hours to 25 minutes, error rate from 12% to 0.5%. Backed also by [Fillify](https://fillify.tech/blog/agentic-ai-browser-automation-form-filling-2026) and [ACTGSYS](https://actgsys.com/en/blog/ai-browser-agent-operator-business-2026).
**Mechanism:** Trigger is an intake document arriving — a purchase order, a supplier price sheet, a tax filing packet, a product data CSV. The agent stores the document via the Files API, attaches a versioned skill that captures the team's SOP for the target app, then uses browser use (accessibility tree) or computer use (pixels) to open the target legacy web app — an ERP without an API, a tax portal, a supplier order system, a marketplace admin — navigate to the right screen, fill the fields across pages, and save the confirmation as a file. Output is a filed record in the third-party system plus a confirmation artifact for audit. Replaces the ops person opening a browser tab and typing the same fields for the hundredth time.
**Why agentic:** The agent is doing the actual data-entry work in the target system, not producing a report someone else has to key in. And it works against systems that don't expose an API — the exact places automation has historically stopped.
**Generalizable core:** Document arrives → agent applies a versioned SOP → completes the multi-screen web workflow in a no-API target system → saves a confirmation artifact.
**Deployability:** Stack is Claude Agent SDK + browser use toolset + Files API + a small human-in-the-loop review queue. Week build per SOP for the first version, days for each subsequent SOP once the pattern is stable. Replaces back-office data-entry roles wherever an API-less SaaS or on-prem web app is in the loop — tax portals, county records, supplier B2B portals, vertical practice-management tools, older ERPs. Failure modes matter: page redesigns break the skill, so pair with a screenshot diff and a slack-me-if-it-fails alert.
