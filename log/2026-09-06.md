# 2026-09-06 — Agent Pattern Scan

## TL;DR
The most interesting entry today is n8n × Microsoft Agent 365: agents get their own company-issued identities and appear as team members in Teams, so an @mention triggers a workflow that runs with the agent's own permissions and replies inline. The other three surface variations on the same broader shift: real deployments are burying the trigger inside a tool people already live in (Jira tickets, IT request queues, deal rooms) rather than putting up a new console.

## Patterns

### 1. Agent-as-team-member: @mention in Teams triggers a workflow with its own scoped identity
**Source:** [n8n.io on X, Nov 2026 rollout preview](https://x.com/n8n_io/status/2059182944380400059) — n8n announcing its Microsoft Agent 365 integration; agents built in n8n show up as members of the team across Microsoft 365 with their own company-issued identity and permissions, and can call any n8n workflow, integration, or MCP server as a tool. Live demo shown: @mention the agent in Teams to summarize PagerDuty incidents into Excel and share the file back.
**Mechanism:** @mention of the agent in a Teams channel or DM → agent reads the message + relevant thread context using its own Microsoft 365 identity → runs the mapped n8n workflow (in the demo: query PagerDuty for incidents in a time window, aggregate, build Excel) → posts the summary and attaches the file back into the same Teams thread → replaces the "someone please pull the last week of incidents into a spreadsheet and share it" ping.
**Why agentic:** The agent has its own tenant identity with least-privilege permissions, not a shared bot token, and it decides which workflow/tools to invoke from the natural-language mention rather than being routed by a keyword slash-command. The output lands in-thread as a peer response, not on a separate dashboard.
**Generalizable core:** @mention in a chat surface where work already happens → agent runs a workflow scoped by its own identity → replies with the artifact in that same thread.
**Deployability:** n8n (self-hosted or cloud) + Microsoft Agent 365 for identity, or the same shape with Slack + Claude Managed Agents / Slack app + MCP. Weekend build for a single workflow, week for a small suite. Replaces the "internal ops person who runs the report" role for any recurring pull-format-share task, at any size. Requires an M365 or Slack tenant admin willing to provision agent identities.

### 2. Self-service IT approval agent that cross-checks requests against policy and auto-remediates
**Source:** [Gordon Food Service reduces IT workload by 85% with Zenphi](https://wreg.com/business/press-releases/ein-presswire/814307244/gordon-food-service-reduces-it-workload-by-85-with-zenphis-no-code-automation-for-google-workspace/) — Gordon Food Service, a large North American foodservice distributor, deployed a Zenphi-orchestrated agent on Google Workspace to handle Chrome extension and OAuth access requests, plus continuous monitoring of new installations across the org.
**Mechanism:** Employee requests a Chrome extension or OAuth-scoped app (self-service form, or a background scan of Workspace audit logs detects a new install) → agent reads the request against the org's approved-apps database, the extension's declared permissions, and prior review history → if approved-list match: auto-grants; if risky: suggests a safer approved alternative and routes the exception with context; if a live install violates policy: revokes access via Workspace admin API and notifies the user in Chat → writes the decision back to the ticket/audit log → replaces the IT admin manually triaging every extension and OAuth request.
**Why agentic:** The trigger is event-driven (a new install or a submitted request), the agent enriches with policy context, and it takes a real write action (grant, suggest, or revoke) rather than surfacing a queue for a human. The auto-revoke on out-of-policy installs is the giveaway that this is not a dashboard.
**Generalizable core:** Policy-touching request or event in a controlled system → agent enriches with rules + history → allow / substitute / block-and-notify decision written back to the source system → the human queue exists only for genuine exceptions.
**Deployability:** Zenphi in the Google Workspace case; the same shape works with Okta workflows + Claude API + MCP for SaaS admin, or n8n + Slack + a rules DB for smaller shops. Week build for one flow, month for a full IT-request suite. Replaces frontline IT helpdesk triage. Works at any scale; the harder part is maintaining the approved-apps / policy rules table.

### 3. Assign-to-agent inside the PM tool: Jira ticket to draft PR without a separate agent console
**Source:** [Introducing Claude Agent for Jira](https://www.atlassian.com/blog/company-news/claude-agent-for-jira) and the [setup docs](https://support.atlassian.com/jira-software-cloud/docs/set-up-claude-agent-for-jira/) — Atlassian shipping this in Jira Cloud, built on Anthropic Managed Agents.
**Mechanism:** Assign a Jira ticket to "Claude" via the assignee dropdown, @mention it in a comment, or route via an automation rule → agent reads the ticket description, acceptance criteria, linked design docs, and target repo → clones the repo in isolated infrastructure, analyzes the codebase, implements the change on a new branch → opens a draft PR in the connected GitHub repo and streams status updates back into the Jira work item's session panel → engineers review, request changes, and merge (Claude cannot merge its own code) → replaces the first-pass dev cycle on well-scoped tickets.
**Why agentic:** Trigger is embedded in the existing PM workflow (assignee change or @mention) rather than a new interface, and the agent performs multi-step code work (clone, edit, test, PR) autonomously. The bidirectional link back into the Jira item is what makes this a workflow, not a chat.
**Generalizable core:** Structured work item in the tool your team already uses (Jira, Linear, HubSpot task, GitHub issue) becomes an agent trigger when assigned to the agent → agent executes end-to-end using item context → posts artifact and status back into the same item for human review.
**Deployability:** Off-the-shelf via Atlassian Marketplace + Anthropic Managed Agents. To build the pattern yourself: Linear/GitHub Issues webhook + Claude Agent SDK + a service account for repo access. Weekend for a narrow trigger and one repo, week for multi-repo with automation-rule triggers. Replaces the "small ticket you never get to" bucket in a dev team. Not limited to code: same shape works for "assign a marketing task to the content agent" or "assign a client-onboarding form to the ops agent."

### 4. Plan-execute-validate agent for multi-document transactional work
**Source:** [Spellbook runs 530,000 contract reviews a month with Claude](https://claude.com/customers) (Anthropic customer stories, Aug 27, 2026); [Spellbook Associate product page](https://www.spellbook.legal/associate). Deployed across law firms and in-house legal teams.
**Mechanism:** A lawyer hands the agent a term sheet, a dataroom, or a template plus reference documents, and states the goal (e.g., "assemble the financing package," "run diligence and flag red-flag clauses across the room") → agent plans the subtasks, fetches relevant precedents, drafts clauses or comparisons per subtask, validates each intermediate output before moving on → assembles a complete package or diligence report in Word for review → replaces the junior-associate weeks of copy-paste-and-cross-reference on transactional matters.
**Why agentic:** It plans and orders its own steps rather than executing a fixed pipeline, and the intermediate-output validation between subtasks is real error-propagation control, not a display of progress. The end artifact is a delivered work product, not a suggestion list.
**Generalizable core:** Unstructured multi-document task with a stated goal → agent decomposes into ordered subtasks → each subtask output is validated before the next runs → final artifact is assembled and staged for human sign-off. Applies anywhere document-heavy work has "run a checklist across many files" as the underlying shape: RFP responses, audit workpapers, insurance policy comparisons, permit filings, grant applications, M&A diligence.
**Deployability:** Spellbook Associate itself if the domain is law; the pattern is buildable with Claude Agent SDK (or LangGraph / CrewAI) plus a vector store of precedents and a document I/O layer (Word, PDF, Google Docs). Month build for a narrow domain because the validation step is where the accuracy is bought. Replaces the junior-analyst hours on cross-document assembly; requires domain expertise to define the validation rules, so a bare LLM call won't get you there.
