# 2026-06-12 — Agent Pattern Scan

## TL;DR
GitHub Agentic Workflows went into public preview yesterday, turning agent behavior into a first-class CI/CD step defined in Markdown — the cleanest example yet of "inbound record triggers agent reads context drafts response writes back" as deployable infrastructure rather than a SaaS product. Salesforce shipped Agentforce Operations with "digital blueprints" that compile process docs into structured multi-system execution plans, and Mistral Vibe's remote agents made chat-triggered long-running cloud work the default mode for coding agents.

## Patterns

### 1. Agent-as-CI-step driven by repository events
**Source:** [GitHub Agentic Workflows public preview, June 11, 2026](https://github.blog/changelog/2026-06-11-github-agentic-workflows-is-now-in-public-preview/) — GitHub Next + Microsoft Research shipped a public-preview runtime that makes Markdown-defined agent workflows compile into standard GitHub Actions YAML. The Agentics sample pack at [githubnext/agentics](https://github.com/githubnext/agentics) ships ~30 prebuilt workflows including `issue-triage` and `ci-doctor`.
**Mechanism:** A repository event fires (new issue opened, CI workflow failed, PR comment posted, scheduled cron). The compiled Action spins up a sandboxed coding agent inside an Agent Workflow Firewall, which reads the triggering record plus the codebase, similar past issues, and CI logs. It runs a defined sequence ("Gather Context → Spam & Quality Check → Triage Type/Labels → Detect Duplicates → Post Report" for issue-triage; "Read failure logs → Identify root cause → Open diagnostic issue" for ci-doctor). Outputs are constrained through a `safe-outputs` validator before being written back to the same repo as labels, comments, or new issues. Replaces the maintainer's first-pass triage of inbound issues and the on-call's CI-failure investigation.
**Why agentic:** The workflow is one Markdown file invoking reasoning ("determine if this is a bug, enhancement, or question"), not a regex/label-map rule set. The same definition can call MCP tools, search the codebase semantically, and decide whether to escalate — none of that fits a deterministic Actions YAML.
**Generalizable core:** Inbound record created in a queue → agent enriches with similar-record search and system context → classifies and drafts response → writes back to the record under output-shape constraints.
**Deployability:** Stack is GitHub Actions + a Markdown workflow file + GITHUB_TOKEN (no PAT needed as of June 11) + any model the org has configured. Complexity: weekend build for the first workflow, then copy-paste from the sample pack. Replaces or augments the human first-touch on any ticketing queue. Scale caveat: the pattern is dev-side today, but the architecture (event → sandboxed agent → constrained writeback) is the same shape any ticketing system would need.

### 2. Process-doc-to-blueprint compilation as the deployment primitive
**Source:** [Salesforce Agentforce Operations launch, May–June 2026](https://www.salesforce.com/news/stories/agentforce-operations-announcement/) — Salesforce shipped 30+ out-of-the-box blueprints for back-office processes (PO rescheduling, invoice auditing, onboarding) with Slack/Teams integration arriving in June. Targeted at mid-market operations teams running on Salesforce + ERP + email.
**Mechanism:** The operator drops an existing process document or workflow diagram into the platform. The system parses it into a "digital blueprint" — a structured set of agent instructions describing each step, the systems involved, the approval gates, and the success criteria. At runtime, an inbound event (vendor email about a delayed PO, AP queue receives an invoice, new hire record created) triggers the matching blueprint. Specialized agents then run the steps across email, ERP, and Salesforce: pulling the PO line, checking inventory and contract terms, drafting the supplier reply, routing the approval, and updating the PO record. Replaces the back-office coordinator chasing approvals and reconciling fields across disconnected systems.
**Why agentic:** The blueprint encodes intent ("reschedule this PO to minimize stockout risk while staying within contract terms"), not a fixed branching script. The agents decide which fields to read, which approver to pull in, and when to escalate based on the situation.
**Generalizable core:** Existing SOP or workflow diagram → compiler turns it into a structured agent execution plan → triggered by a system event → agent runs the plan across heterogeneous systems with human approval at defined gates.
**Deployability:** Salesforce-priced stack — enterprise list, not SMB. The transferable idea is the compilation step: Claude with MCP servers for each system plus a structured-output prompt can do the same blueprint translation for a fraction of the cost. Complexity: month build to copy the pattern with Claude + n8n + per-system MCPs. Replaces operations coordinators and AP/AR clerks who currently shuttle data between systems. Scale caveat: Salesforce's version assumes enterprise data volumes and existing process docs; the open-stack version works at SMB scale but the operator has to write the SOP first.

### 3. Chat-message-triggered cloud agents with persistent sessions
**Source:** [Mistral Vibe remote agents, June 2026](https://mistral.ai/news/vibe-remote-agents-mistral-medium-3-5/) — Mistral's coding agent moved long-running work to the cloud with Slack and other third-party triggers shipping in June. Positioned for engineering teams that want background work without keeping a laptop awake.
**Mechanism:** A user posts a task in Slack ("rewrite the auth flow on the staging branch and open a PR"). The trigger hits Vibe, which spins up a sandboxed cloud session running Mistral Medium 3.5, connects to GitHub, reads the repo plus any tool connectors the team has wired, and runs for as long as the work takes — minutes or hours. Sessions persist across user device shutdowns and can run in parallel. When the agent reaches an approval gate or finishes, it notifies the user back in Slack and surfaces the diff for review. Replaces the developer babysitting a local agent session and the manual approval-loop tedium of long-running coding tasks.
**Why agentic:** The session is goal-driven over hours, not request-response. It plans, executes across tools, hits checkpoints, and resumes — the user just posted a sentence.
**Generalizable core:** Inbound message in a chat tool → durable cloud agent session is created → agent works against the goal across connected systems → checkpoints come back to the same chat thread for approval.
**Deployability:** Stack as built is Vibe + GitHub + Slack. The reusable pattern works with Claude Code via Anthropic's Agent SDK + a Slack bolt app + a sandbox runtime (Modal, Fly, or a managed service). Complexity: week build to wire Slack triggers to a hosted agent runtime with persistent sessions. Replaces the human keeping an IDE open while an agent works. Scale caveat: this is currently a developer-tool pattern but the chat → durable session → checkpoint loop generalizes to any role that has long-running judgment work (research, drafting, planning).
