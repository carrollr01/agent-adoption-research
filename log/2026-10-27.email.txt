# 2026-10-27 — Agent Pattern Scan

## TL;DR
Five patterns worth logging today, all mechanism-level: a Slack production alert that becomes a root-cause write-up and a pull request in the same thread (Carvana), a document drag-and-drop that routes to a specialist agent for bulk financial actions (Qonto), a scheduled triage agent that writes an audit-trail Discussion alongside its labels (GitHub Agentic Workflows), a contract that arrives already risk-flagged and redlined before a lawyer opens it (Spellbook), and a chat query over live ad data that can pause or adjust the campaign in the same conversation after approval (Supermetrics for Claude). The common thread this round: specialist scoping and explicit human approval gates on action, not just on draft output.

## Patterns

### 1. Alert-as-work-order investigator
**Source:** [Carvana case study on claude.com](https://claude.com/customers/carvana) — Carvana's retail-science and wholesale-platform engineering teams, replacing two homegrown Slackbots and manual on-call triage.
**Mechanism:** A production monitoring alert posts into a Slack channel. That alert starts the agent, which reads the alert itself plus a baseline of errors, warnings, and log volume from the hour before any related release, pulls the team's standing root-cause format and runbooks from a repo, and reads tickets, build history, and code (read-only). It identifies which owner's code is implicated, tags that engineer, writes the root-cause analysis in the team's format, and depending on the diagnosis either opens a pull request, files a ticket, adds logging where existing logs can't explain the event, or deliberately stands down if the likely cause is an infra outage. Engineers can also ask for a PR in the same Slack thread. Scheduled hourly runs do the same thing against pipelines and feature flags.
**Why agentic:** The alert is both the input and the trigger. Nobody opens a dashboard to interpret it: the agent assigns ownership, writes the explanation in the shape the team expects to read, and in many cases produces the fix as a PR before anyone has acknowledged the page.
**Generalizable core:** External monitoring alert → agent reads logs + build history + code + team's own format spec → writes diagnosis in the team's language + proposes the fix as a PR → replaces manual triage and on-call RCA writing.
**Deployability:** Claude Code with scoped read access to the team's warehouse, repo, and ticket system, plus a Slack posting integration and PR-opening permission; week-build if you already have the runbooks and format spec written down, month-build if you don't. Replaces the first 20-30 minutes of on-call triage. Scale caveat: the standing format and runbooks are the real asset; without them, output is generic.

### 2. Upload-routed specialist agents with an approval gate
**Source:** [Qonto case study on claude.com](https://claude.com/customers/qonto) — European business bank's SMB owners doing payroll, invoicing, and transfers.
**Mechanism:** A customer drops 15-20 pay slips, or a CSV of clients, or a single invoice into Qonto's app. An operator agent reads the upload and routes it to a specialist agent scoped to that one task (payroll agent, invoicing agent, transfers agent). The specialist pulls beneficiary and reference details without manual lookup, prepares a single bulk transfer or drafts each invoice, and stages the action inside Qonto. Nothing is sent until the customer confirms, and sensitive cases also run deterministic checks alongside the model.
**Why agentic:** The upload replaces the entire "open a form, re-key each row, submit each transfer" sequence. The operator-plus-specialist split keeps each agent's tool surface narrow, and the approval gate is at the point of financial action, not at the drafting step.
**Generalizable core:** File upload (invoices, CSV, documents) → operator agent classifies and routes to a scoped specialist → specialist prepares the end-to-end action in the system of record → user confirms → replaces a repetitive re-keying workflow.
**Deployability:** The pattern needs a routing agent, 2-4 narrow specialist agents, deterministic validators on anything that moves money, and a staging surface in the host app. Month-build inside an existing SaaS; weekend proof-of-concept in n8n or Make if you can live with a cruder human-in-the-loop. Replaces an operations analyst's or small-business owner's monthly admin block (Qonto cites ~8 hours/month). Scale caveat: the specialist split only pays off once you have more than one repeatable financial action; a single-task agent is simpler.

### 3. Scheduled triage with an audit-trail Discussion
**Source:** [GitHub Agentic Workflows "Auto-Triage Issues" post, 2026-05-29](https://github.github.com/gh-aw/blog/2026-05-29-agent-of-the-day/) — GitHub Next's gh-aw framework, running against real public repositories.
**Mechanism:** The workflow runs on a schedule several times a day and also fires on `issues` events. On each pass it walks unlabeled issues, reasons about each one's content, and applies labels along with a confidence level and a rationale. Alongside the labels, it creates or updates a Discussion titled `[Auto-Triage Report] YYYY-MM-DD` with a Markdown table listing each classified issue, labels applied, confidence, and reasoning. The underlying workflow runs read-only by default; write actions like `add-label` or `add-assignee` have to be declared explicitly as "safe outputs" with volume limits.
**Why agentic:** The Discussion is the key move. It is not a dashboard: nobody has to open it unless they want to spot-check or correct a label. The agent produces its own paper trail as a side effect, so human review is cheap but not required.
**Generalizable core:** Schedule + inbound-record event → agent reads untagged items + policy + taxonomy → applies labels/routing with confidence + rationale → writes an append-only audit record in a thread or doc → replaces manual tagging while keeping overrides one click away.
**Deployability:** gh-aw gives this away for GitHub itself. Transplantable to any system with records, labels, and threaded comments: Jira (add-label as a safe output, create a Confluence or Jira Issue as the audit log), Linear (same idea with a weekly audit issue), Zendesk (ticket tagging with a hidden internal note trail). Weekend build if the taxonomy already exists; week build if the labels still need to be designed. Replaces a support/community manager's manual triage sweep. Scale caveat: the safe-outputs ceiling matters; set volume limits before you discover them the hard way.

### 4. Pre-arrival contract pipeline
**Source:** [Spellbook case study on claude.com](https://claude.com/customers/spellbook) — 530,000 contract reviews per month across Spellbook's law-firm and in-house customers, with claimed 10x turnaround (10 hours to one).
**Mechanism:** Contracts arrive via email, Slack, or Salesforce. Before a lawyer opens the file, agents in the background pull the contract into Spellbook, extract its terms, compare them against the market and against the firm's playbook, flag risks, and draft redlines. By the time the lawyer actually opens the file in Word, the review is partially done: risk calls out, suggested edits inline, playbook deviations marked. The agents are tool-using in Word, not just chat completions.
**Why agentic:** The trigger is the contract itself showing up in any of three inboxes, not a user clicking "review this." Work happens between arrival and the first human read, which collapses the queue a lawyer sees from "stack of unread contracts" to "stack of pre-marked drafts."
**Generalizable core:** Inbound document in any channel → agent extracts structured fields + compares against policy/benchmark → writes annotations and suggested edits in the native tool (Word, Google Docs, PDF annotator) → human opens an already-worked file → replaces blank-page review.
**Deployability:** Claude running against inbound mail/Slack webhooks + a document-markup integration (Word Add-in, Google Docs API, or a PDF annotator). The hard parts are the playbook (what counts as a risky clause for this customer) and getting write permissions into the native editing surface, not the LLM. Month build end-to-end; weekend build if you skip the native-tool annotations and just output a cover memo. Replaces the first-pass reviewer role; the second-pass human (lawyer, procurement lead, risk analyst) stays. Scale caveat: works for any field where "every incoming document gets a repeatable first pass" is already how the work gets done.

### 5. Conversational ad-platform operation with approval-gated writes
**Source:** [Supermetrics for Claude case study on claude.com](https://claude.com/customers/supermetrics) and [Supermetrics' own write-up on the Claude connector](https://supermetrics.com/blog/supermetrics-for-claude-your-new-marketing-workflow) — marketers at agencies and in-house teams.
**Mechanism:** A marketer connects their ad and analytics sources to Claude via the Supermetrics connector. In a chat, they ask something like "why did campaign X underperform last week." Claude pulls the answer live from Google Ads, Meta, LinkedIn Ads, and GA4 through the connector rather than from exported spreadsheets. When the marketer wants to act on the finding, Claude can pause the campaign, adjust budgets, create a new campaign, or generate ad copy, in the same conversation, with each write action gated by human approval.
**Why agentic:** It replaces the dashboard-plus-ticket workflow with a conversation that both diagnoses and executes. The dashboard would show that the campaign is down; the agent explains why and then changes the budget on confirmation. The approval step is at the write, not at the read.
**Generalizable core:** Natural-language question → agent queries live operational system via scoped connector → explains + proposes a write → human approves → agent executes against the live system → replaces "pull a report, interpret it, then open the admin console to act."
**Deployability:** Needs a connector layer (Supermetrics-style, or an MCP server over the vendor APIs) with scoped auth, plus a confirmation UI inside the chat. The budget-and-pause write actions are small APIs; the reasoning layer is Claude. Week build for a single platform (just Google Ads, say); month build for the full stack. Replaces the "junior analyst pulls numbers, senior marketer decides" loop. Scale caveat: works well when the write surface is bounded and reversible (pause, resume, budget change); do not generalize to irreversible actions without a stronger approval design.
