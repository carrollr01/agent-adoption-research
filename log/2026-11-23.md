# 2026-11-23 — Agent Pattern Scan

## TL;DR
Most interesting pattern today is the property-manager competitor-rent tracking agent: 12 years of manual spreadsheet work ($1K/month paid to a human) replaced by a scheduled agent that scrapes competitor listings, enriches with history, and surfaces pricing moves. The classic "we have visibility problems → let's build a dashboard" ask, answered with an agent that actually decides what to look at and summarizes the takeaway.

Also notable: Notion's public stat that 90% of Claude-in-Notion agent activity now runs on automated triggers rather than chat — status changes and new records, not prompts. The agent-as-background-worker is clearly the dominant deployment, not the agent-as-sidekick.

## Patterns

### 1. Scheduled competitor-rent tracking agent for property managers
**Source:** [Jon Matzner on X](https://x.com/MatznerJon/status/2053824192173502598) — property manager had paid someone $1K/month for 12 years to manually track competitor vacancies, rent changes, days-on-market and local supply in a spreadsheet; builder replaced it with an agent.
**Mechanism:** Scheduled trigger (daily/weekly) → agent scrapes the competing property listing pages, ILS feeds, and local supply sources → enriches each unit against its own history (so rent-change deltas and DOM trajectories are visible, not just the current snapshot) → writes a structured pricing-signal brief back to the manager → replaces a human analyst's weekly maintained spreadsheet.
**Why agentic:** The spreadsheet version was the dashboard. The job that mattered was the deltas, the interpretation, and knowing which units to pay attention to — all of which the agent decides. It also handles source drift: when a competitor's listing page changes layout, the agent adapts, which a scraper or dashboard doesn't.
**Generalizable core:** Schedule → scrape external competitor/market surface → diff against stored history → produce ranked recommendation → write to operator's inbox or doc.
**Deployability:** Weekend-to-week build on Claude API + Playwright + a small Postgres for history + a scheduled worker (n8n, Trigger.dev, or a cron Lambda). The real complexity isn't the agent — it's the scraping fallbacks and the normalization of competitor data. Replaces the task of a part-time market analyst or junior ops person; small-business scale.

### 2. Agentic autofix that loops on security alerts until it passes the checker
**Source:** [GitHub changelog, 2026-10-15](https://github.blog/changelog/2026-10-15-agentic-autofix-for-code-scanning-alerts-general-availability) — GA for GitHub Advanced Security customers, following the July public preview.
**Mechanism:** Code-scanning alert is assigned (singly, or bulk up to 25) to Copilot → agent reads the alert plus the surrounding code → proposes a remediation → reruns CodeQL on the proposed diff → if still failing, revises → opens a draft PR with the passing fix and a review packet for a human. Runs inside an ephemeral Actions environment and bills to the org's AI Credits.
**Why agentic:** It's a loop with a checker in it, not a one-shot suggestion. The agent uses CodeQL as its own feedback signal, which is the agentic step: decide, test, decide again. A Dependabot-style suggestion engine couldn't do this.
**Generalizable core:** Alert fires in a validator → agent reads alert + context → proposes change → reruns the validator → iterates until pass or give up → opens draft action for human approval.
**Deployability:** Direct consumption via GHAS. For non-GitHub stacks, the skeleton is portable: any linter/CI/analyzer that returns machine-readable findings becomes the agent's reward signal. Week-long build to replicate on top of Claude Code or the Claude Agent SDK for a non-GHAS repo. Replaces/augments the AppSec engineer's triage queue; works at enterprise scale but also fits a 5-person team whose CI already runs CodeQL or Semgrep.

### 3. Status-change-in-tool-of-record as the dominant agent trigger
**Source:** [Anthropic Notion case study](https://claude.com/customers/notion) plus Notion's own [Claude agents help page](https://www.notion.com/help/use-claude-agents-in-notion) — Notion reports 18,000 agents built in the three weeks after launching External Agents, with 90% of agent activity running on automated triggers rather than chat.
**Mechanism:** User moves a task card to "ready to start" (or creates a row in a specific database, or hits a schedule) → Notion fires the agent → agent reads the card plus any linked docs/connectors → executes the configured work (code task, research synthesis, draft doc, whatever the agent is wired for) → writes the result back as a comment or child page on the same card.
**Why agentic:** The interesting thing isn't the Notion integration, it's the data point: operators are overwhelmingly wiring agents to *state changes in their system of record*, not prompting them. "Dashboard → agent → artifact back in the same place a human would check" is the dominant shape.
**Generalizable core:** State change in a system of record (status, new row, field update) → agent reads the record and linked context → does the work → writes output back into the same record, where humans already look.
**Deployability:** For a client already on Notion, Linear, Asana, Monday, HubSpot, or any CRM, you don't even need Notion AI; webhook from the tool → Claude Agent SDK → write back via API. Weekend build per integration. Replaces the Slack ping that would otherwise say "hey can you look at this one." Works at any scale — the tool you already use is the UI.

### 4. Per-agent inbound channel identities (email, Slack, Telegram) as a trigger surface
**Source:** [Agent Inbox launch coverage, 2026-11-03](https://aitoolly.com/ai-news/article/2026-11-03-agent-inbox-launches-on-product-hunt-to-provide-dedicated-email-slack-and-telegram-channels-for-ai-a) — Novu's open-source Agent Inbox gives each agent its own email address, Slack handle, and Telegram handle behind one API; Novu Connect covers the same ground for Teams, WhatsApp, and SMS.
**Mechanism:** Human (or another agent) sends a message to the agent's email address / @-mentions it in Slack / DMs it on Telegram → unified gateway normalizes to a single webhook → agent reads the message + its own history → responds in the originating channel's native format (threaded reply, email reply, etc.).
**Why agentic:** The addressable-identity pattern inverts the common one. Instead of "agent polls or scheduler fires it," the agent is a participant anyone can reach, exactly like a Zapier email-parser but with a model reasoning over the message instead of regex. Lowers the bar for human-in-the-loop handoffs — reply to the agent's email, the agent reads the reply, keeps going.
**Generalizable core:** Agent has a stable identity on human communication channels → inbound message is the trigger → agent assembles thread context → responds on the same channel → optionally pings a human on a separate channel when stuck.
**Deployability:** For a bespoke build, this is a weekend of plumbing: a dedicated Gmail or Postmark inbound for the agent, a Slack bot token, Telegram bot API, all funnelling into one Claude Code loop. For clients, the useful framing is: "your agent gets its own email; cc it on the thread." Scales to any size — in fact more valuable for small teams where routing is informal.

### 5. Pre-test browser agent that bug-checks a feature before the human tries it
**Source:** [Ben's Bites — productiv-icky walkthrough series](https://sessions.bensbites.com/) — the author describes an agent that, when a feature is built, spins up a browser and checks for bugs or errors on the site before the owner clicks around.
**Mechanism:** Build or deploy completes (PR merged, dev server restarted, Vercel preview ready) → agent spawns a browser via Playwright/Chromium → navigates to the changed surface with the feature's intent in context → clicks through the primary flow + a few obvious edge cases → captures console errors, failed network requests, visual regressions, broken flows → reports back in Slack/inline PR comment before the human opens the preview.
**Why agentic:** It's not Cypress. The agent decides what to test from the feature description and the diff, not from a pre-written test file. It's an agent that fills the gap between "no tests" and "full test suite" — a reasoning-based smoke-test that costs pennies.
**Generalizable core:** Deliverable-complete event → agent exercises the deliverable in its real environment → reports issues via a channel the maker already watches → human sees "clean" or "look at X" before touching it themselves.
**Deployability:** Already feasible with Claude Code + Playwright in a GitHub Action, or Claude Agent SDK on a webhook from Vercel/Netlify. Weekend build. Replaces the maker's "let me poke around before I show anyone" half-hour. Especially useful for a 1–5 person dev team where there's no QA role to catch the obvious stuff; at larger scale it's a complement to, not replacement for, a real test suite.
