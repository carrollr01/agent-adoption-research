# 2026-11-20 — Agent Pattern Scan

## TL;DR
Four distinct patterns today, drawn from three Anthropic customer stories and one agent platform launch. The most interesting is Duvo at Rohlik Group: a procurement agent that logs into supplier portals through the browser (not APIs), cross-references SAP, and captures the "long tail" of supplier work humans never had bandwidth to do — automating abandoned work rather than existing work.

## Patterns

### 1. Long-Tail Procurement Agent (login-through-the-UI procurement)
**Source:** [Duvo on Claude](https://claude.com/customers/duvo) — Rohlik Group, €1.5B online grocer, 5 EU markets. Duvo (EMEA startup) built on Claude Agent SDK.
**Mechanism:** Continuous commodity-price monitoring plus event triggers (supplier emails, supplier portal state changes) → agent sessions log into supplier portals via computer use / browser-use (Opus 4.6), extract delivery status across ~50 POs, cross-reference SAP GUI screens, flag discrepancies, auto-correct or escalate via human-in-the-loop gate, send follow-up emails and generate contracts, and write corrections back to the ERP. Context persists across the whole run via long-lived Claude sessions. High-risk actions require human approval.
**Why agentic:** Browser-use plus computer use operates heterogeneous enterprise interfaces that have no clean APIs. The agent decides when to escalate, when to renegotiate, which SKUs to prioritize — no fixed workflow graph. Inbound delivery confirmations went from 52% to 90%, product availability 78% to 93% in two weeks, and ~80% of annual supplier negotiations are now automated (previously happening quarterly at best, and only for the top 20 suppliers).
**Generalizable core:** Continuous poll of external operational surfaces humans don't watch → agent logs in through the actual UI (not APIs) → cross-references a system-of-record → writes correction or chase action → captures the "abandoned work" beyond the top handful of accounts/vendors/customers.
**Deployability:** Claude Agent SDK + Anthropic computer use + MCP + Sonnet 4.6 (default) + Opus 4.6 (browser). Multi-week build (3 months to €2.8M annualized savings). Replaces/augments category managers and procurement buyers. Requires tolerance for browser-use flakiness and a human-approval tier for high-value actions. Works at any scale with messy supplier stacks — the pattern is especially useful where API coverage is thin.

### 2. Inbound Qualification Chat With Full-Context Handoff
**Source:** [Anthropic rebuilt inbound with Claude Managed Agents](https://claude.com/blog/how-anthropics-sales-team-rebuilt-inbound-with-claude-managed-agents) — built by one engineer in a few weeks, now holds "thousands of conversations a day."
**Mechanism:** Opt-in chat embedded on Pricing, Contact Sales, in-product (Claude.ai), and in email → agent asks conversational follow-ups ("what are you solving for, what's your current usage") grounded in a pricing/security/billing knowledge base → terminates in one of three outcomes: (a) route buyer to checkout with recommended plan and seat count, (b) hand off to a human rep with full transcript and escalation reason attached, or (c) answer the question directly if that's all they need. No CRM enrichment layer described — context is gathered conversationally.
**Why agentic:** The branching decision (buy / hand off / answer) is model-driven per conversation, not a routing rule. The handoff carries the full transcript as grounding, so reps don't re-qualify. Numbers: inbound-to-opportunity conversion doubled, close ~5 days faster, escalation rate roughly halved, one rep's closed-won output went 2.5x. Previous volume was "tens of thousands" inbound/month.
**Generalizable core:** Inbound chat on a high-intent page → agent qualifies and educates via KB-grounded conversation → three-way branch: self-serve path, human handoff with transcript, or direct answer → replaces the SDR/BDR qualification round-trip.
**Deployability:** Claude Managed Agents (platform handles hosting + session mgmt + tool orchestration). "A prompt, a handful of tools, Claude." Weekend-to-week build. Replaces/augments: SDR qualification, inbound rep response time, and the 10-email-per-deal clarification loop. Works for any product with repeated pre-sales questions (pricing, security, compliance, seat count). Cost gated on chat volume and model choice.

### 3. Multi-System Optimization Cycle With Human Approval Gate
**Source:** [JAKALA on Claude Agent SDK](https://claude.com/customers/jakala) — marketing consultancy, 3,000+ Claude Enterprise seats.
**Mechanism:** Recurring ad campaign-optimization cycle (previously 5–7 days human-run, now <24 hours per client account) → each Performance Agent connects via MCP to the client's ad accounts (search/shopping, programmatic, social) plus JAKALA's internal geo-intelligence engine; context windows up to 200K tokens; JHexagon pulls from 400+ external data sources → agent reasons across the combined data, flags anomalies, proposes specific actions (creative/asset diagnostics, incrementality reads, micro-territory spend reallocation with rationale) → output sent to a human pod for review, approval, and execution onto the ad platforms.
**Why agentic:** Replaces the senior planner's 40–60% weekly load of pulling data from 8–12 systems and building status docs. The agent does not just render a dashboard of the pulled data — it proposes specific actions with justification, and those proposals become the human's work surface. The human pod is a write gate, not an analyst.
**Generalizable core:** Scheduled cycle that replaces a multi-day human analysis sprint → agent consolidates data from N disparate systems via MCP → outputs specific proposed actions with rationale → human approval gate before any write happens → replaces analysts' data-assembly work while keeping their judgment on the execution step.
**Deployability:** Claude Agent SDK, deployed via Bedrock / Google Cloud Agent Platform / Claude API; Opus 4.6 for heavy analytics, Sonnet 4.6 default, Haiku 4.5 for high-volume subtasks. Month-scale build, needs MCP coverage for the specific systems. Reported 70% time reduction, 30% productivity uplift, 35–40% CSAT lift. Applies anywhere a cyclical cross-system analysis currently blocks execution — portfolio reviews, inventory re-planning, A/R aging workflows, campaign optimization.

### 4. Event-Triggered Autonomous Agents With Runtime API-Wrapper Generation
**Source:** [Tasklet on Claude](https://claude.com/customers/tasklet) — startup, 5 engineers, 450,000 agent actions/day, >$2.5M ARR 5 months after launch, 160% MoM growth.
**Mechanism:** Each agent is a long-lived Claude conversation that fires on a configured trigger — cron, inbound webhook, new email, new calendar entry, RSS feed update, form submission. On fire, the triggering payload becomes the initial context; the LLM then decides what to read via tool calls. Three capability layers: (a) 3,000+ pre-built SaaS integrations, (b) MCP connectors, (c) an "AI-powered feature that dynamically creates API connectors to new services" — Claude reads the target API's docs on the fly and builds a wrapper at runtime — plus a computer use fallback that spins up a browser VM when no API exists. Named deployed use cases: email triage, revenue reconciliation across Stripe/Ramp, deal desk pipelines, competitor monitoring, VC back-office.
**Why agentic:** There is explicitly no predefined workflow graph. CEO Andrew Lee's thesis: "what if the workflow goes away and you just let the agent reason about what to do?" The agent makes "dozens or hundreds" of tool calls per task and chooses its own branches. The runtime connector generation is the key novel mechanism — it eliminates the per-integration code that otherwise gates niche SaaS automation.
**Generalizable core:** Existing SaaS events (inbox, calendar, cron, webhook, RSS, form) trigger a long-lived model session → agent reasons across tool calls (pre-built + MCP + runtime-generated connectors + browser fallback) → completes multi-step task without a predefined branch graph → replaces both traditional trigger-action workflow builders and the prompt-and-copy-paste pattern of ad hoc chat use.
**Deployability:** Sonnet 4.6 default, Opus 4.6 for complex reasoning. For an SMB consumer, pattern is "point the agent at a Gmail label or a Calendly webhook" rather than "build nodes." Weekend-to-week build for a single workflow; the real complexity is in the dynamic-connector layer, which is the moat. Replaces: no-code workflow building for operators who don't want to map branches themselves. Scale caveat: runtime API wrapping is model-token-heavy and only cost-effective above a certain repetition count.
