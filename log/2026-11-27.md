# 2026-11-27 — Agent Pattern Scan

## TL;DR
Most interesting pattern today is Clay's "GTM CI/CD" loop: an agent reviews its own prior workflow runs every night, diffs the outcomes against intent, and opens a prompt/rule change for a human to approve — closing the self-improvement loop at the control plane instead of inside the runtime. Six patterns total, spanning self-improving control loops, autonomy graduation gates, safe-investigation sandboxes, write-with-approval guardrails, and the specific case of a part-time SMB employee who built 59 agentic workflows by pasting classic Zapier Zaps into ChatGPT.

## Patterns

### 1. Self-improving workflow review loop ("GTM CI/CD")
**Source:** https://www.clay.com/blog/gtm-self-learning-loops and Latent Space ep. with Jeff Barg (Head of AI, Clay), 2026-11-26 — Claygent runs >350M times/month across customer GTM workflows.
**Mechanism:** Nightly cron → review agent reads every run of a named workflow + its outcome logs → detects mismatch classes (e.g. 47 of 159 leads routed into a segment that didn't match company size) → drafts a prompt-or-rule diff with cited evidence → opens a PR-like change → on human approval, merges into the live workflow → replaces the RevOps engineer who'd hand-eyeball yesterday's run.
**Why agentic:** The reviewer agent is not inside the runtime — it edits the agent system itself, treating prompts and rules as code. The human reviews a diff, not output samples.
**Generalizable core:** Schedule → agent reads prior runs + outcomes → proposes a config diff → human approves → change ships into production workflow.
**Deployability:** Works on top of any workflow runtime that exposes run logs and versionable config (Zapier Tables, n8n, Make, in-house). Build is ~1–2 weeks for a single workflow; the hard part is deciding what counts as a "mismatch" per workflow. Replaces the RevOps/ops-engineer who babysits automations. No ML headcount needed — judgment lives in the prompt.

### 2. Autonomy graduation gate with drift-triggered demotion
**Source:** https://siliconangle.com coverage of Luke Corbin (AT&T), mirrored at https://www.beri.net/article/att-500-agentic-workflows-business-agent-foundry-human-oversight-high-90s-accuracy-threshold-45-billion-tokens-ai-gateway-open-models — AT&T's Business Agent Foundry runs ~500 workflows, ~45B tokens/day, >1M transactions/month.
**Mechanism:** Every new workflow ships with a human reviewer on every run → Foundry tracks agent accuracy vs reviewer decisions on a rolling window → once accuracy crosses the mid/high-90s inside the workflow's risk profile, the human gate is removed and the agent runs autonomously → continuous drift monitoring re-asserts the gate if accuracy regresses → replaces the human reviewer, not the original worker.
**Why agentic:** The promotion/demotion decision is itself automated and driven by measured outcomes rather than a one-time launch call. Lets a small team run hundreds of workflows at different autonomy levels at once.
**Generalizable core:** Human-approves-every-run → measure accuracy against the human → cross threshold → agent runs solo → monitor drift → demote back under threshold.
**Deployability:** Needs a review UI, a decision log, and a per-workflow accuracy metric — a weekend build for one workflow, a month build for an org-wide program. Fits any shop with more agent ideas than reviewer hours (ops teams, back-office, compliance). The drift-monitor is where most of the care goes.

### 3. Shallow-clone scoped sandbox for safe root-cause investigation
**Source:** https://www.databricks.com/blog/introducing-genie-zeroops (public beta, 2026-11-19; carried in weekly roundups through 11/27) — 80,000+ real customer issues observed in private preview.
**Mechanism:** Job failure, pipeline failure, or data-quality violation fires in Databricks → agent reads the failing job graph, lineage, recent runs → creates a shallow clone of the affected production table inside a scoped sandbox (network isolation + narrow permissions) → runs hypothesis queries against the clone, not prod → localizes root cause → writes a proposed fix (SQL/code diff) routed through normal review and approval → replaces the data engineer running triage at 2am.
**Why agentic:** The investigation step is open-ended — the agent decides which queries to run — but the guardrail is structural: it literally cannot touch prod. The clone-and-scope step is the pattern worth stealing.
**Generalizable core:** Live-system failure → agent clones the affected slice into a scoped sandbox → investigates inside the clone → writes a fix diff that goes through the normal review path → nothing hits prod without a human.
**Deployability:** The specific implementation is Databricks-only, but the pattern lifts to anything with cloneable state: an ERP sandbox copy, a staging database, a sandboxed Shopify store, a copy of a specific HubSpot pipeline. Build complexity depends entirely on how hard your prod system is to clone at slice-level. Replaces on-call triage work.

### 4. Write-access with "paused-by-default" + approval page
**Source:** https://claude.com/customers/supermetrics and https://www.marketscale.com/industries/marketing-tech/supermetrics-lets-claude-build-ad-campaigns-that-stay-paused-until-approved.md (2026-11-04) — 6,000+ connector customers; named example Layer (marketing agency).
**Mechanism:** Marketer asks in Claude ("push $5k into the top three creatives on Meta") or scheduled pacing check fires → agent reads 200+ normalized ad-platform sources with per-figure source/timestamp/transform → creates or edits ad campaigns in Google Ads / Meta / LinkedIn / TikTok / Microsoft / Snap, but every new campaign is created *paused* → changes surface on a dedicated approval page → human promotes → agent then un-pauses or applies the budget change → separately, pacing/anomaly alerts post to Slack and finished client reports land in the client's Google Sheet → replaces 10-hour monthly client-report rebuilds (now 20 min at Layer).
**Why agentic:** The agent has real write credentials against money-moving systems. The guardrail is not a confirmation dialog — it's that the output state is non-destructive by construction until a human promotes it.
**Generalizable core:** Agent writes to the real system in an inert state (paused/draft/queued/unpublished) → change surfaces on an approval page with provenance → human promotes → change goes live. Removes the "can I let the agent write?" question.
**Deployability:** Any system with a draft/paused state works: Shopify draft orders, HubSpot deals in a "proposed" stage, QuickBooks pending bills, Google Ads paused campaigns, a Jira epic in triage. Approval page is a small internal web app (Next.js + the target system's API). Week-build for one domain. Replaces the manager-approval email loop without removing the manager.

### 5. Work-ledger-reconciled autonomous remediation
**Source:** https://shopify.engineering/river-vulnerability-remediation (resurfaced via https://digg.com/ai/rm57pw5l this week) — Shopify Infrastructure Security team; security merges through the freshness-gated queue went from ~10% to ~80% after River was adopted. Separately, Tobi Lütke reported River handled 121,804 Slack threads in September, up 4x from March.
**Mechanism:** New dependency-upgrade PR lands OR an upstream security agent files an application-security finding → River reads its own work ledger, live repo state, open PRs, and the vulnerability tracker → reconciles ledger against live state before acting (so it doesn't re-fix something a human already patched) → opens a narrowly-scoped draft PR with the fix → spawns one Slack thread per finding for discussion → updates the vulnerability tracker on merge → replaces the security engineer's manual patch-to-closure work (verify CVE still live, scope fix, push PR, chase review).
**Why agentic:** The ledger-reconciliation step is the interesting bit. Most "autonomous fix" agents assume they're the only actor; River assumes humans and other agents are also moving and checks before each action. That's why it can run at Shopify-scale without stepping on people.
**Generalizable core:** Autonomous remediation action → before acting, agent reads its ledger of in-flight work + live state of the target system → if live state already matches desired state, log and skip; otherwise act → one discussion channel per unit of work.
**Deployability:** The ledger-reconciliation idea transfers directly to any multi-actor queue: support-ticket auto-responders, inventory-reorder agents, compliance-remediation agents. The implementation needs a persistent ledger (Postgres, Airtable, even a sheet) plus a "read live before write" step. Week build; the gain is you can run the agent alongside the humans without conflict.

### 6. Classic-workflow-to-agentic authoring loop
**Source:** https://zapier.com/blog/theatre-passe-muraille-next-gen-zaps/ (2026-11-17) — Theatre Passe Muraille (Toronto non-profit theatre); one person — John Cabanela, part-time (28 hrs/wk) finance manager; 59 production Next-Gen Zaps.
**Mechanism:** Cabanela takes an existing classic Zap (deterministic trigger-and-actions) → pastes the Zap's shareable link into ChatGPT, which is connected to Zapier → ChatGPT emits a Next-Gen Zap definition (steps + the specific places where LLM judgment belongs) → he deploys it, iterates against real invoices/payroll/sales events, keeps it deterministic where it can be and only uses an agent step where judgment is actually needed → now runs 59 workflows covering payables, sales, payroll, and reporting with step-level checks, all against QuickBooks Desktop + bank feeds → replaces paper-ledger bookkeeping and most manual data entry at a sub-10-person org.
**Why agentic:** Not every step is an agent. The pattern worth stealing is the authoring loop — the LLM is the compiler from a classic workflow (that the operator already understands) into an agentic one, and the operator reviews the output before shipping. Removes "I don't know how to build an agent" as a blocker without requiring an engineer.
**Generalizable core:** SMB operator describes an existing manual or deterministic workflow → LLM-with-platform-access compiles it into an agent-augmented workflow with judgment steps where needed → operator reviews and ships → iterate.
**Deployability:** Works today with any ChatGPT/Claude integration into Zapier, Make, or n8n. Requires zero dev headcount. The honest scale caveat: this is one operator building 59 narrow workflows for one tiny organization — it won't survive being handed to someone who can't read their own books. But as a pattern for turning operators into agent builders, it's cleaner than any "AI drag-and-drop builder" we've seen.
