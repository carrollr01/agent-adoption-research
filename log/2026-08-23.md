# 2026-08-23 — Agent Pattern Scan

## TL;DR
Vega's Detection Skills is the most interesting mechanism this week: a portable, per-detection playbook file (built on Anthropic's Skills format) that the alert itself carries, so the same trigger fires a triage → investigation → rule-tuning loop without a human writing runbooks each time. The pattern generalizes far beyond security to any domain where alerts, tickets, or exceptions have a known investigation shape.

## Patterns

### 1. Detection Skills — the alert type ships its own investigation
**Source:** [Vega Introduces Detection Skills](https://vega.io/blog/vega-introduces-detection-skills) and coverage in [The AI Journal](https://aijourn.com/vega-introduces-detection-skills-the-new-open-standard-for-ai-reasoning-in-agentic-cyber-defense/) — Vega Security launched Detection Skills as an open standard in August 2026 with an initial library of 35+ skills; the format is a direct adaptation of Anthropic's Agent Skills concept for the SOC.
**Mechanism:** A detection rule fires in the SIEM → a Skill file scoped to that detection type is loaded (declares what evidence to gather, which entities to pivot on, and what dismiss/escalate conditions apply) → a triage skill filters noise at machine speed → an investigation skill assembles the case and reaches a verdict with cited evidence → an optimization skill proposes a rule refinement or new coverage → verdict is written to the case system and the tuning proposal goes to a human for approval.
**Why agentic:** The playbook that used to live in an analyst's head is now a portable artifact that the alert itself brings along. The agent doesn't just summarize; it decides dismiss vs. escalate against declared conditions and closes the loop by rewriting the rule that generated the alert.
**Generalizable core:** typed alert/ticket/exception → load a playbook file scoped to the type → gather declared evidence → decide against declared conditions → propose refinements back to the rule that triggered it.
**Deployability:** The Skills format is open and file-based, so the same shape works with Claude Skills, MCP tool servers, and any SIEM/case tracker that can call a webhook on detection. Week-build for a first vertical: pick one alert class, write the Skill file, wire the case system to fire the agent, human-in-the-loop on the tuning proposal. Replaces or augments L1/L2 analysts and, more broadly, whoever writes runbooks for repeat exceptions. No dedicated ML headcount required, but production rollout wants a review gate on the "rewrite the rule" step.

### 2. Ramp On-Call Assistant — a Slack channel per incident that opens with the root cause already written
**Source:** [ZenML LLMOps Database write-up on Ramp's engineering agent deployment](https://www.zenml.io/llmops-database/enterprise-scale-ai-agent-deployment-across-engineering-lifecycle) — Ramp (fintech, ~2,000 employees) put this in front of every incident routed to engineering, from customer support escalations to system alerts.
**Mechanism:** An incident is opened (customer support ticket routed to eng, or PagerDuty page) → a dedicated Slack channel is created for that incident → an on-call agent, running in a container with read-only credentials, uses MCP servers to pull recent Datadog metrics, Sentry error reports, related Slack threads, and the last N deploys → posts a root-cause hypothesis with evidence links into the incident's own channel before the human even joins → engineers land in a channel where the "what's happening" question is already partly answered. Ramp reports ~80% reduction in initial triage time.
**Why agentic:** The agent doesn't wait to be prompted. Incident creation is the trigger, evidence assembly happens autonomously across three tool systems, and the output is written to a working surface (the incident channel) rather than a report.
**Generalizable core:** exception event on any monitored system → spin up a scoped workspace for that event → agent auto-assembles the evidence a first responder would pull → posts the working hypothesis into the workspace before humans arrive.
**Deployability:** Realistic small-team stack: Slack + PagerDuty/StatusHero + Sentry (or Rollbar) + a hosted log tool + Claude API with MCP servers for each. Week to a month build. Replaces the first 15–30 minutes of every on-call rotation. The read-only credentials pattern is the important safety detail — worth copying exactly. Works at SMB scale without modification because the surface (a Slack channel per incident) is already free.

### 3. DoorDash Flux — reviewing agent output as a first-class production pipeline
**Source:** [DoorDash Flux: 130k Agent Tasks in One Month](https://explainx.ai/blog/doordash-flux-cloud-agents-platform-august-2026) — DoorDash AI Research announced Flux in August 2026 as their internal cloud platform for running agents; they process 25,000+ reviews per week of agent-generated work and gave Cowork access to all 4,000 employees.
**Mechanism:** Any team dispatches a task to an agent through Flux → the agent runs to completion in an isolated cloud environment → its output (PR, spec, data extract, ticket update) lands in a queue → a review pipeline routes each item to the correct human reviewer with the diff, the agent's plan, and its citations attached → reviewer accepts, rejects, or edits → outcomes flow back into evaluations that tune which agents run which tasks next.
**Why agentic:** The workflow assumes agent output is untrusted-until-reviewed by design. The novel piece is not the agent — it's treating review-of-agent-work as a durable pipeline stage with its own throughput, staffing, and metrics, the same way a factory treats QC.
**Generalizable core:** agent produces work → work lands in a typed review queue → routed to the right human with context → accept/reject/edit signal flows back into which agent is used next time.
**Deployability:** Small-shop version doesn't need a Flux clone — a shared Notion database, Linear queue, or GitHub PR label works. Weekend build for one review type; the discipline is what matters, not the tooling. Replaces the ambient anxiety of "did the agent do this right?" with a scheduled review shift. Scale caveat: 25k/week volume requires org-wide adoption; the pattern shape works from 1 review/day up.

### 4. Spotify Xirp — a worktree per agent as the unit of isolation
**Source:** [Introducing Xirp on Spotify's engineering blog](https://portal.spotify.com/blog/introducing-xirp) and [FourWeekMBA analysis](https://fourweekmba.com/ai-spotify-xirp-meta-harness-coding-agents/) — Spotify opened Xirp to public beta on August 10, 2026 after 1,300+ internal engineers and 36,000+ agent sessions on it.
**Mechanism:** Engineer dispatches a task (or an orchestrator agent spawns sub-tasks) → Xirp allocates a fresh git worktree for that task on the same repo, so files never collide with sibling sessions → the engineer or orchestrator picks the agent (Claude Code, Codex, or Gemini CLI) per task and can hot-swap models mid-session with context preserved → completed work merges back through a PR. Fifty-plus concurrent sessions per developer are routine.
**Why agentic:** This is infrastructure for autonomy, not a chatbot. The interesting piece is that isolation-per-agent is treated as a first-class primitive — the same abstraction Docker made for services, applied one layer up to agent sessions.
**Generalizable core:** parallel agent tasks on shared state → give each its own isolated workspace on that state → merge back through an explicit gate.
**Deployability:** For a two-person shop the mechanism is a shell script wrapping `git worktree add` per dispatched task, not a platform. Weekend build. Applies far outside coding: any agent that edits shared state (a shared spreadsheet, a Notion workspace, a document set) needs an equivalent isolation trick, usually a scratch copy the human diffs before commit. Replaces the coordination overhead of "who's touching what right now."

### 5. Heartbeat-cron agent — the periodic decider, not the periodic doer
**Source:** [Webhook-Driven Agent Architecture](https://www.buildmvpfast.com/blog/webhook-driven-agent-architecture-event-based-triggers-autonomous-ai-workflows-2026) documents the pattern; it lines up with what Claude Managed Agents and OpenAI/xAI shipped for scheduled tasks between June and July 2026.
**Mechanism:** A cron fires on a schedule → hits a webhook that starts an agent session → the agent reads the current state of the systems it watches (open tickets, unread email, stale data, unresolved reviews) → decides whether anything actually warrants action right now → if yes, takes the action; if no, exits cleanly. Not "run this every hour" but "check every hour whether running is warranted."
**Why agentic:** The decision to act or not act is the agentic part. A traditional cron always runs its script; a heartbeat-cron agent runs its judgment and often decides to do nothing. Idle runs are the feature, not a bug — they're what let the pattern coexist with a human without generating noise.
**Generalizable core:** schedule → assemble current state → decide whether to act → act only if warranted.
**Deployability:** Cheapest possible stack: a cron in Zapier/Make/n8n → HTTP request to a Claude API endpoint with the agent's read tools attached. Weekend build. Replaces the recurring "I keep meaning to check X" habit — inbox triage, follow-up nudges, invoice aging, quote expiration, subscription reviews, unattended leads. Works for any SMB where a person is currently the polling loop.
