# 2026-07-12 — Agent Pattern Scan

## TL;DR
Three concrete patterns worth logging today. The most interesting is a "learning agent" layer sitting above a working incident-response agent: it watches its own resolution history and, when it sees the same incident class three times, writes a compressed runbook as a reusable skill file the base agent then loads. The other two: an inventory agent that batches low-stock signals across SKUs into one supplier email per vendor with SLA escalation to Slack, and a PR-review agent that runs its own proposed patches in a sandbox and only surfaces suggestions that actually build and test green.

## Patterns

### 1. Low-stock signal → batched supplier PO email + SLA escalation
**Source:** [US Tech Automations, "Consolidate Cin7 Reorders Into 1 Supplier Email in 2026"](https://ustechautomations.com/resources/blog/automate-inventory-reorder-cin7-shopify-supplier-email-2026) — playbook aimed at DTC/omnichannel brands running Cin7 as inventory of record and Shopify as storefront, roughly $1M–$30M revenue, 200–5,000 SKUs, handful of recurring suppliers.
**Mechanism:** A SKU crossing its reorder point in Cin7 emits a low-stock event. The agent catches events across all SKUs on a batch window (typical: overnight or on a schedule), groups by supplier, drafts one purchase order per supplier containing every SKU that needs reordering at par-minus-current quantities, and sends it as a single email to the correct vendor rep. The PO number is written back to Cin7. If a supplier does not confirm within the lead-time SLA, the agent re-sends the email and pings the purchasing owner in Slack. Sample cited: five supplier emails out by 9:14 a.m., previously a Monday-morning ritual that took the purchasing lead most of the day.
**Why agentic:** The agent isn't just a threshold alert — it does cross-SKU grouping, per-supplier PO drafting, write-back of PO numbers, and time-based escalation to a specific human. There's a decision loop (which SKUs go to which supplier, has the vendor confirmed) rather than a dashboard read.
**Generalizable core:** Threshold events across many records → agent batches by downstream counterparty → drafts an outbound action per counterparty → writes result back to system of record → time-based SLA escalation to a named human when the counterparty doesn't close the loop.
**Deployability:** Off-the-shelf n8n or Make on top of Cin7 webhooks + a Shopify inventory view + SMTP + a Slack webhook; ~1 week build for a competent operator. LLM only needed for the PO email draft and vendor-tone matching. Replaces a purchasing coordinator's inbox-and-spreadsheet Monday. Works cross-vertical: bookkeeping firms batching client documentation requests by client, service businesses batching parts orders by supplier, agencies batching client invoice line items by month.

### 2. Learning-agent layer that mines resolved incidents into reusable skill files
**Source:** [AWS Blog, "Leverage Agentic AI for Autonomous Incident Response with AWS DevOps Agent"](https://aws.amazon.com/blogs/devops/leverage-agentic-ai-for-autonomous-incident-response-with-aws-devops-agent/) plus [AWS docs on Learned Skills](https://docs.aws.amazon.com/devopsagent/latest/userguide/about-aws-devops-agent-learned-skills.html) — walked through with a serverless URL-shortener case study.
**Mechanism:** A base DevOps Agent handles incidents interactively, referencing operator-uploaded runbooks (now called "Skills") to know how the team's canary deploys, rollout gates, and remediation steps work. Sitting above it is a second agent, the Learning Agent, whose trigger is "the DevOps Agent has resolved N incidents of the same class over a rolling window." In the AWS example, three DynamoDB throttling incidents in a month cross the threshold. The Learning Agent then reads its own resolution transcripts, extracts the common investigative path (in the example: "check provisioned vs consumed capacity first"), and generates a structured skill file that becomes part of the base agent's skill library. Future incidents of that class start from the compressed path instead of re-running exploratory hypotheses.
**Why agentic:** Two loops. The base agent is doing investigation and remediation with tool use. The Learning Agent is doing pattern extraction over the base agent's history and writing new instructions that mutate future runs. It's not a dashboard of incident stats — it's an agent authoring instructions for another agent.
**Generalizable core:** Agent that has already handled N examples of the same task → second agent reads the transcripts → extracts the compressed decision path → writes it to a skills store the first agent loads on next run. The system gets faster at things it's already seen without a human writing the runbook.
**Deployability:** The full AWS-managed version is enterprise-grade. A weekend build of the same idea: any agent framework where "skills" or "system prompts" are files (Claude Code skills, custom agent frameworks, plain Markdown loaded at prompt time) plus a scheduled agent that reads its own resolved-ticket history, buckets by cause, and writes new skill files when a cause bucket passes a count threshold. Replaces the postmortem-to-runbook loop that most ops teams never actually complete. Only makes sense if the base agent is already resolving problems reliably; layering it on a shaky base agent just codifies bad behavior faster.

### 3. Sandbox-validated PR review agent that filters its own suggestions
**Source:** [Vercel docs, "Code Review"](https://vercel.com/docs/agent/pr-review) — Vercel Agent, GA on their platform, positioned against generic AI review tools.
**Mechanism:** Trigger is a PR opened or updated in a connected GitHub repo. The agent reads the diff plus surrounding files, runs multi-step reasoning to hypothesize security issues, logic errors, and likely bugs, then for each hypothesis generates a candidate patch. Each candidate patch is applied in an ephemeral sandbox that runs the repo's real build and its real test suite. Only suggestions where the patch builds green and the tests pass (or fail in the expected way) get posted as PR review comments. The rest are discarded silently.
**Why agentic:** The review isn't just prompting a model over a diff. The agent generates → simulates → filters. It has a self-check loop over its own output before anything reaches a human, and it uses the target system (build, tests) as the ground-truth judge rather than model confidence.
**Generalizable core:** Agent generates candidate outputs → runs each candidate against a cheap, deterministic simulator of the target system → only forwards the ones that pass. The simulator, not the model, decides what's real.
**Deployability:** Vercel-managed for their users; the underlying idea is a week or two for a small team on any stack where builds/tests are cheap enough to run per candidate. Same shape works well beyond code: agent-drafted marketing copy sanity-checked against a brand-voice classifier, agent-drafted SQL run against a read-replica with row-count sanity checks, agent-drafted contract redlines run through a clause-policy checker. Replaces (or amplifies) the first reviewer's low-value work of chasing suggestions that don't actually apply. Requires a reliable simulator; if the simulator is flaky, the filter is meaningless.
