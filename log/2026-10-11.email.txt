# 2026-10-11 — Agent Pattern Scan

## TL;DR
Four patterns worth logging, three of them from the engineering side where this week's signal was strongest. The most reusable idea is "risk-scored auto-approval," where an agent grades each inbound artifact against a published rubric, acts on anything cleanly below threshold, and routes the rest to a human with its evidence attached. Also notable: a template-ified incident investigator and a feedback-to-PRD agent chain, both from Rakuten's internal rollout.

Note: the log has a four-month gap (last entry 2026-05-28). The 14-day dedup window is empty in a meaningful sense; the May entries were skimmed anyway to avoid repeating property-scouting, invoice-chase, voice-receptionist and milestone-invoicing patterns.

## Patterns

### 1. Risk-scored PR auto-approver with graduated autonomy
**Source:** [How I AI — Build an AI code review bot in 30 minutes (Claire Vo)](https://www.lennysnewsletter.com/p/build-an-ai-code-review-bot-in-30), [chatprd.ai writeup](https://www.chatprd.ai/how-i-ai/merge-mommy-vercel-eve-ai-bot-for-auto-reviewing-pull-requests) — Claire Vo's "Merge Mommy," a Vercel Eve agent reviewing every PR on her team.
**Mechanism:** CI checks pass on a PR → agent pulls the diff, file list, and PR metadata from GitHub → scores the change against six risk dimensions (blast radius, reversibility, data security, ops impact, verification gap, change surface) → auto-approves anything cleanly low across all six → posts a Slack message with the score breakdown for anything else, which Vo then reviews. Replaces the "I'll glance at this when I get a sec" review that was gating merges in a small team.
**Why agentic:** The agent is doing judgment work (categorizing risk across orthogonal dimensions and deciding whether to act), not displaying a dashboard of PR activity. The score itself is explanation, not just a number, and the auto-approval closes the loop rather than paging a human for every merge.
**Generalizable core:** inbound artifact passes a gate → agent scores it against a published multi-dimension rubric → auto-accept below threshold, route to human with the full score breakdown and evidence otherwise.
**Deployability:** Weekend build. Stack is Vercel Eve + GitHub app + Slack bot; Vo wrote one Codex prompt and used Codex's Chrome browser mode to click through the GitHub App and Slack bot setup screens. Replaces a senior engineer's "review bandwidth" tax; the rubric is the real IP. Travels directly to insurance claim triage, inbound RFP qualification, contract redline review, grant application screening, PO approval — anywhere a judgment call recurs on inbound artifacts and the organization already has or can write a review rubric.

### 2. Autonomous ticket-to-PR consumer running against the real backlog
**Source:** [Anthropic customer story — Delivery Hero's Herogen](https://claude.com/customers/delivery-hero) and the [Code w/ Claude London session](https://claude.com/code-with-claude/session/ldn-building-ai-native-at-enterprise-scale-monday-com-doctolib-and-delivery-hero) — Delivery Hero's internal agent for software work.
**Mechanism:** Ticket lands in the backlog → agent pulls the ticket, reads the relevant repo context, generates the code change, runs it against existing tests, opens a PR → 85% of its tickets succeed, most needing zero or one developer interactions before merging. Produces 100+ merged PRs/day (Anthropic's number) to 170+ (Delivery Hero's own Google Cloud writeup), roughly 9% of the company's PR volume. Replaces a developer picking up ticket-shaped work from a queue.
**Why agentic:** Not a code-completion tool. The agent chooses its own tickets off the queue, reads around the codebase without a human steering it, and ships merge-ready work. The developer either approves or doesn't; the agent isn't being driven line by line.
**Generalizable core:** work item enters a queue → agent picks it up, reads surrounding context, produces a merge-ready artifact → human approves or edits before it ships, most needing no intervention.
**Deployability:** Month+ build at serious engineering scale. Needs a real codebase, a real test suite, and tight repo access — this pattern only pays off where tickets are plentiful, specifications are already written down somewhere, and there's an acceptance gate (CI + review) the agent can validate against before asking a human. Translates past code into any domain with the same shape: AR dispute responses off a disputes queue, insurance adjuster first-pass notes off a claims queue, support macro drafting off a ticket queue, legal clause response off a redline queue. The required precondition — "the artifact is cheap to validate" — is what makes this hard outside engineering, not the agent.

### 3. Hypothesis-driven, read-only incident investigator in the alert channel
**Source:** [Vercel sre agent docs](https://vercel.com/kb/guide/eve-incident-sre-agent) and the [Eve incident response template](https://vercel.com/templates/other/eve-incident-response-agent), launched August 2026 as an open-source Eve template.
**Mechanism:** Alert fires in Slack (or an external system calls `POST /v1/investigate` with a title and channel) → agent gathers context from Datadog metrics/logs, GitHub commits since the last green deploy, Vercel deployment history, and the Slack thread → generates two to four candidate root-cause hypotheses, tests each against the live signals, and posts findings back to the thread with every claim linked to its source (dashboard URL, commit SHA, log line). Read-only; it never changes production. Replaces the first 20 minutes of SRE war-room investigation where someone grep-walks logs trying to form a theory.
**Why agentic:** The pattern isn't "search these logs and render them." It's "form candidate explanations, run specific lookups against each one, discard the losers, and present the surviving ones with evidence." That's investigator behavior, not reporting behavior. The read-only constraint is deliberate — the agent's job is to compress the on-call's search space, not to touch the system.
**Generalizable core:** real-time signal of trouble → agent assembles context from the available observability sources → tests multiple candidate explanations in parallel → posts a short, evidence-linked summary into the human channel; actions remain gated.
**Deployability:** Week build if you're already on the stack (Slack + GitHub + at least one metrics/logs provider); Vercel ships a template. Translates to: inbound customer complaint ("my order's wrong") → agent pulls order record + fulfillment events + carrier scan + prior tickets, posts a hypothesis-ranked explanation to the support rep's queue. Or inbound insurance claim denial appeal → agent assembles policy terms + claim notes + prior correspondence, posts candidate denial reasons with citations. The design principle to steal is "the output is evidence, not conclusions, and the agent never acts on the subject system."

### 4. Feedback-to-PRD agent chain with a human triage checkpoint
**Source:** [Working at the frontier: How Rakuten builds agents overnight with Claude Fable 5](https://claude.com/blog/working-at-the-frontier-rakuten) and [Rakuten customer Q&A](https://claude.com/customers/rakuten-qa) — Rakuten's internal product-feedback pipeline, running on Claude Managed Agents.
**Mechanism:** A conversational agent in Slack/Teams chats with users to understand needs and pain points → it creates a ticket in Rakuten's Kanban-style task system with the structured interview captured → another agent or a human triages the ticket → accepted items are picked up by a second agent that drafts a PRD, wireframe, or working prototype, which then goes back to a PM for review. Replaces a product manager running the whole loop (user interview → notes → write-up → draft spec → first prototype), and routes raw voice-of-customer to the right person without the PM playing switchboard.
**Why agentic:** Each stage is doing judgment work (what are they actually asking for; is this ticket worth building; what should the first prototype look like) and the stages hand off through a durable artifact (the ticket) rather than through a chat context. The human sits at a decision point in the middle, not at every step.
**Generalizable core:** inbound user conversation in any channel → agent extracts structured intent and writes a durable record → human (or agent) triages → accepted items trigger a downstream agent that produces the first draft of whatever artifact the next stage needs.
**Deployability:** Week+ build; two agents and a shared task system (Linear, Jira, Trello, Notion, Asana all work). The lift is defining the handoff schema (what fields the ticket must carry so the downstream agent can act) and placing the human triage checkpoint. Rakuten's version uses Slack and Teams for the front; a small services firm could run the same thing with a web form or voicemail transcript as the front, the firm's project tool in the middle, and a Claude call producing the first-draft proposal, SOW, or scope document on the back. The real "replaced task" is the PM-shaped work of translating customer language into actionable work items.
