# 2026-09-08 — Agent Pattern Scan

## TL;DR
Four concrete patterns today, all chat- or event-triggered agents that finish a piece of work rather than surface a chart. The most interesting is Sentry's Seer → Claude autofix chain (production error triggers a diagnosis agent, which triggers a patch-writer agent, which opens a PR), paired with an hourly meta-agent that sweeps Slack for stale PRs. It's a full closed loop from a production event to a reviewable code change, with an agent watching the agents' output.

## Patterns

### 1. Production-error-triggered autofix chain
**Source:** [Sentry customer story on Claude](https://claude.com/customers/sentry), [Sentry Changelog: Seer can trigger Claude to fix bugs](https://sentry.io/changelog/seer-can-now-trigger-claude-to-fix-bugs/) — Sentry ingests billions of events daily; the fix pipeline is live for their own engineering team and shipping to customers.
**Mechanism:** A production error captured by Sentry crosses a severity/frequency threshold → Seer (their debugging agent) reads the stack, telemetry, and linked source to produce a root-cause report → that report is handed to a Claude Managed Agent as the ticket → Claude pulls the repo, writes a patch, runs tests, opens a PR against the offending file → a Slack channel is notified via a new alert trigger. Separately, an hourly Claude routine scans that Slack feed and classifies any PR opened but not actioned in the last four hours, resurfacing it so nothing sits. Replaces the on-call engineer's first-response loop (reproduce, bisect, write the trivial fix) and the manager's manual scan of the stale-PR queue.
**Why agentic:** Two chained agents plus a scheduled meta-agent watching their output. The trigger is a real production event, not a human prompt; the deliverable is a reviewable code change and a stale-PR nudge, not a dashboard entry.
**Generalizable core:** monitored system throws an event → diagnosis agent reads context and hands a structured brief to an action agent → action agent produces a reviewable artifact in the team's normal review surface → scheduled meta-agent sweeps that surface for unactioned work.
**Deployability:** Claude Managed Agents or Claude API + Sentry MCP + GitHub API + Slack webhooks, ~1–2 week build for a team already using both. Replaces or augments the on-call developer for the trivial-fix tier; the meta-agent replaces the eng manager's daily "who forgot about which PR" check. Requires a mature observability tool and code the agent is trusted to touch — smaller teams without either won't get value.

### 2. Chat-native task assignment to specialist function agents
**Source:** [Rakuten customer story on Claude](https://claude.com/customers/rakuten-qa), covered in [Claude Managed Agents guide, Aug 2026](https://linas.substack.com/p/claude-managed-agents-guide) — Rakuten deployed a set of specialist agents across product, sales, marketing, and finance, each live within about a week, plugged into Slack and Teams.
**Mechanism:** An employee assigns a task to a function-specific agent inside Slack or Teams (e.g., "@marketing-agent draft the launch brief for X, deadline Friday") → the agent reads the assignment, pulls context from that function's connected systems (docs, CRM, briefs, prior work), does the work, and returns a structured deliverable in the same thread for review. Turnaround dropped from 24 days to 5 days on the tasks these agents took over. Replaces the "please draft this and send back" hand-off round trip between a manager and a junior on that team.
**Why agentic:** The trigger is a real assignment in the channel the team already uses; the agent picks up context on its own and returns the finished artifact, not a summary or a link to a report. Each function has its own agent with its own tool bundle rather than one general chat interface.
**Generalizable core:** team member assigns a task in chat → domain-scoped agent reads that function's systems → returns finished deliverable back in the thread for review.
**Deployability:** Claude Managed Agents or Claude API + Slack/Teams bot + per-function MCP tool bundle, ~1 week per function for a team with clean source-of-truth systems. Replaces the junior analyst / coordinator layer inside a function; augments the manager who was routing work manually. Works at any scale — Rakuten is enterprise but a 10-person shop can stand up one function agent the same way.

### 3. Task-board-triggered parallel agent fan-out
**Source:** [Notion on Claude Managed Agents](https://linas.substack.com/p/claude-managed-agents-guide) — Notion runs its Custom Agents on Managed Agents in production; teams described an early prototype turning ~12 hours of work into ~20 minutes.
**Mechanism:** A task card is created or assigned on a Notion task board → Claude picks up the card as a trigger, reads the docs, meeting notes, and connected-data blocks around the task (the workspace is the context store), does the work, and drops the finished artifact — code, deck, small site, doc — back into the workspace attached to the same task for review. Dozens of tasks fan out in parallel against the same board. Replaces the "assign it, wait a day, get a first draft" cycle where a person would have to open five tabs and reconstruct the context before starting.
**Why agentic:** The task board itself is the trigger substrate — every new card is an execution request. The deliverable is a finished artifact, not a status update. Parallelism is real: many cards, many agents, one workspace.
**Generalizable core:** new/assigned row in the team's task system → agent reads the surrounding workspace context → returns the finished artifact attached to that row.
**Deployability:** Notion + Claude Managed Agents natively, or replicate with Linear/Asana + Claude API + workspace-scoped MCP tools, ~1–2 week build. Replaces the "kickoff → first draft" leg of most knowledge-work tasks; augments the reviewer, who becomes the first human touch. Cleanest fit for teams whose real source of truth already lives in one workspace tool — otherwise the context step gets messy.

### 4. Tool-call-enriched alert triage
**Source:** [How Anthropic's cybersecurity team built a threat detection platform with Claude Code](https://claude.com/blog/how-anthropic-uses-claude-cybersecurity) — Anthropic's Detection Platform Engineering team runs CLUE (Claude Looks Up Evidence) as the first-pass triage layer in front of their SOC analysts.
**Mechanism:** A security alert fires from a detection rule → CLUE Triage receives it before any human sees it, then uses Claude's tool-use to enrich it: pulls the related Slack messages, hits internal documentation, queries other systems for the identity/asset/telemetry in the alert → produces a structured verdict (real/benign/needs-human, with the evidence trail) → the analyst queue only gets what CLUE couldn't clear. Replaces the first hour or two of an analyst's day spent copy-pasting IDs across five query languages and Slack search bars to figure out if an alert is worth chasing.
**Why agentic:** Trigger is an inbound event, not a query. The agent decides on its own which tools to call to gather context, and its output changes what shows up in the human queue — it isn't a chart the analyst has to interpret.
**Generalizable core:** inbound alert/ticket/lead → agent tool-calls across the systems that hold the context needed to judge it → structured verdict with evidence → human queue receives only what the agent couldn't resolve.
**Deployability:** Claude API + MCP servers for each system the agent needs to query (chat, docs, identity, whatever the alert points at) + a queue that routes on CLUE's verdict, ~2–4 week build depending on how many source systems need MCP wrappers. Replaces the first-pass triage tier of any queue-based ops function — SOC L1, support L1, sales SDR qualification, insurance claims intake. The pattern doesn't need enterprise data volume; it needs a queue with a real first-pass workload someone is doing today.
