# 2026-07-14 — Agent Pattern Scan

## TL;DR
Four patterns today, all mechanism-level and none present in the last 14 logged files. The most useful new skeleton is the blind grader-verify loop shipped by Anthropic and used in production by Spiral: the agent that writes the artifact and the agent that scores it are deliberately separated so the grader never sees the writer's reasoning. That verification-as-a-separate-agent split is a general-purpose lever, not a writing trick, and it shows up again in DoorDash's scout-plus-deep-reviewer PR bot.

## Patterns

### 1. Blind grader-verify loop for anything the agent produces
**Source:** [Anthropic Outcomes / Spiral case study](https://claude.com/blog/new-in-claude-managed-agents) — Anthropic shipped the Outcomes feature (public beta May 6 2026); Spiral by Every runs it in production behind their writing API/CLI.
**Mechanism:** Writer agent produces artifact (draft, deck, code) → platform spins up a fresh grader agent with the rubric only, no access to the writer's reasoning or tool calls → grader returns per-criterion pass/fail plus specific fix notes → failures loop back to the writer with the grader's explanation → repeat until the rubric clears. Reported lifts of roughly ten points on task success without changing the underlying model.
**Why agentic:** The grader takes actions (inspecting artifacts, returning verdicts) that gate the next writer turn. It's a decision loop, not a display. What makes it distinct from "add a critic prompt" is the enforced isolation — the grader is a separate agent instance in a separate context, so it can't be talked into agreeing with sloppy work by the reasoning that produced it.
**Generalizable core:** artifact produced → blind grader scores against rubric → fail-notes route back to producer → loop until pass. Works for any output where "did this hit the bar?" is easier to specify than "how do I generate it?" — drafts, PRs, policy checks, procurement asks, marketing copy, RFP responses.
**Deployability:** Claude Managed Agents ships this as a primitive, so the build is defining the rubric and the loop budget rather than wiring the graders. Weekend build for a first vertical; the real work is writing rubrics that discriminate. Replaces the reviewing-QA layer (editor, senior reviewer, compliance checker) that sits between a first draft and a shippable one. Works at any scale — the grader is per-artifact, not per-tenant.

### 2. Scout + deep-reviewer split for PR review
**Source:** [DoorDash engineering blog / DashBench](https://x.com/AIatDoorDash/status/2074245508403691817) — DoorDash's production code reviewer, evaluated against their in-house DashBench of replayed real PRs.
**Mechanism:** PR opened or updated → Scout model (Claude Sonnet 4.6, high effort) reads the whole diff, discards regions that don't warrant scrutiny, and emits a short list of suspect spots with reasons → Deep Reviewer (Claude Opus 4.8, high) inspects only those spots with the rest of the diff as supporting context → posts inline PR comments tagged with confidence and severity. Weighted recall 53.6% on DashBench at $3.91 per PR, versus 30.7% for a single-pass GPT-5.5 baseline.
**Why agentic:** Two agents making decisions in sequence — the scout decides where the reviewer looks, and the reviewer decides what to say on the PR. The scout is doing narrow-before-deep triage; without it the deep model wastes tokens on the boring 80% of the diff and finds less.
**Generalizable core:** cheap scanner narrows the surface area → expensive specialist deep-inspects only the narrowed set → structured output lands on the artifact of record. Any long-document / long-log / long-transcript review job has this shape — contract diffs, transcript-of-record audits, insurance claim packets, chart reviews, security ticket queues.
**Deployability:** Model-agnostic pattern (they explicitly ran scout/reviewer permutations across labs). Straightforward with Claude Agent SDK + a webhook on the PR/document event. Week-long build for a first vertical, mostly spent on the review rubric and evaluation set. Replaces the senior-reviewer bottleneck that gates every artifact. The team-defining move here is *building a replay-based benchmark of your own historical decisions* (DashBench) so you can objectively swap models and prompts — that's the moat, not the code.

### 3. HTTP-webhook agent endpoint as the drop-off point for any tool's alerts
**Source:** [Azure SRE Agent HTTP triggers, June 2026](https://techcommunity.microsoft.com/blog/appsonazureblog/http-triggers-in-azure-sre-agent-from-jira-ticket-to-automated-investigation/4504960) — Microsoft shipped named webhook endpoints per agent; the flagship example is a Jira workflow transition firing the agent with the full ticket body.
**Mechanism:** ITSM/observability/CI tool detects something → posts JSON to a named agent endpoint (each trigger has its own URL) → the JSON body enriches a pre-configured prompt → agent pulls telemetry, logs, runbooks, and code context through its managed connectors (Jira, GitHub, Azure Monitor, Atlassian Rovo MCP) → posts findings, next steps, or a fix PR back on the ticket that fired it. No engineer in the loop for the first pass.
**Why agentic:** The trigger is upstream tooling, but the investigation is a decision loop — pick which telemetry to pull, decide whether logs contradict the alert, decide whether to write a PR or escalate. It's a first responder, not a dashboard.
**Generalizable core:** upstream detector fires → HTTP POST enriches an agent prompt → agent gathers context via connectors → writes back on the artifact of record. The pattern turns the agent into just another integration endpoint any existing workflow can call. Same skeleton works for a lead-scoring event firing an outreach agent, a compliance flag firing a documentation agent, a customer complaint firing a resolution agent.
**Deployability:** Azure SRE Agent packages this end-to-end; roll-your-own is a couple of days on n8n/Zapier plus the Claude Agent SDK for the investigation logic. Enterprise scale ready but plenty applicable to a 20-person shop that already has PagerDuty/Jira/Slack. Replaces first-line SRE triage and the "who's on call, can you look at this?" ping. Scale caveat: this is only useful if the org already has the alerting/ITSM discipline to fire clean events — the agent isn't a substitute for having any monitoring at all.

### 4. Proactive delivery-exception outreach that turns a would-be ticket into a touchpoint
**Source:** [Pango (YC S26)](https://www.ycombinator.com/companies/pango) — running on 30+ Shopify/WooCommerce/Magento brands, growing 60% MoM pre-batch.
**Mechanism:** Carrier tracking event indicates delay, lost package, or delivery failure → agent joins the event with the order, customer, and prior-contact history → drafts contextual outreach (apology, updated ETA, offer of reshipment or refund based on the customer's profile) → sends before the customer opens a support ticket, and logs the touch on the order record. Escalates to human only when the case sits outside a workflow rule.
**Why agentic:** The trigger is a real-world signal (a delivery event) rather than a customer message, and the agent is choosing what to say, when, and with what remedy based on order value, customer history, and the specific exception type. That's decision-making, not a canned "your package is delayed" email.
**Generalizable core:** external-world event on a shared record → agent enriches with customer/account history → drafts and sends outreach with a specific remedy → logs against the record. The universal shape is "get to the affected party before they get to you." Works anywhere a system knows something is going wrong before the customer does — missed appointment, subscription card decline about to expire, service call ETA slipping, contract renewal drifting past a deadline.
**Deployability:** Pango is a productized version for Shopify-stack brands (~1-hour install). Roll-your-own is n8n or Make for the carrier-webhook side, Claude Agent SDK for the enrichment/drafting, Postmark/Twilio for send. Weekend build for a first workflow if the carrier/CRM data is already flowing. Replaces the post-purchase CX rep who spends their day reacting to "where's my order" tickets and the store owner who fields exception cases after hours. Scale caveat: the pattern needs a reliable feed of the upstream event — brands using a shipping platform (ShipStation, Shippo) or a carrier API already have this; brands still forwarding tracking emails don't.
