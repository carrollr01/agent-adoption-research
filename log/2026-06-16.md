# 2026-06-16 — Agent Pattern Scan

## TL;DR
Four patterns today, all sharing a common shape: the agent sits on an existing event channel (a pager alert, a new issue, a new ATS record, a customer message) and does the first 15 minutes of human work before anyone gets pinged. The most interesting is PagerDuty's SRE Agent on the escalation policy itself — it runs the diagnostic and remediation pass before the on-call's phone buzzes, so the human is paged into a thread that already has a diagnosis attached.

## Patterns

### 1. The on-call agent that sits on the escalation policy
**Source:** [PagerDuty Spring 2026 release](https://www.pagerduty.com/blog/product/the-path-to-autonomous-operations-pagerduty-spring-26-release/) — PagerDuty's SRE Agent, generally available in the Spring 26 release; rolled out across PagerDuty's existing customer base.
**Mechanism:** Monitoring alert fires and routes to a normal PagerDuty escalation policy, but the first responder on that policy is the SRE Agent rather than a human. The agent reads the alert payload, queries connected observability tools (logs, metrics, deploy history, runbooks), runs a diagnostic pass, attempts remediation via scoped tool access, and posts findings into the Slack incident channel. Only if it can't resolve or can't confidently diagnose does it escalate up the policy to the human on-call, who arrives to a thread that already contains the investigation.
**Why agentic:** It's not a notification or a dashboard. The agent owns a slot in the on-call rotation, takes real actions (queries, restarts, rollbacks under guardrails), and decides whether to escalate. The interesting design choice is reusing the escalation policy as the orchestration layer rather than building a parallel system.
**Generalizable core:** Inbound alert routed to an existing escalation/queue → agent takes first-touch slot → assembles context from connected systems → attempts the fix → escalates to human only on uncertainty, with full context attached.
**Deployability:** PagerDuty native if you're already there; otherwise this skeleton works in any incident.io / Opsgenie / Statuspage stack by wiring an n8n or Claude API + MCP agent into the first-responder webhook. Week build for a custom version. Replaces the first 10–20 minutes of an SRE's incident triage. Works at any scale where you have a paging system; the value scales with alert volume.

### 2. The auto-triage agent that lives inside GitHub Actions
**Source:** [GitHub Agentic Workflows](https://github.github.com/gh-aw/blog/2026-01-13-meet-the-workflows/) — entered technical preview Feb 13 2026, broadly available by Q2; deployed across GitHub repos with concrete production workflows for issue triage, PR review, doc sync.
**Mechanism:** A new issue or unlabeled issue triggers a GitHub Actions workflow. The agent reads the issue body, searches the codebase, scans related/duplicate issues, and decides classification (bug, feature, question, docs, chore) and priority (critical/high/medium/low). It applies labels, leaves a comment with the research it did, and optionally assigns to a team or component owner. The "auto-triage-issues" workflow can also run on a schedule across the backlog, not just on new events.
**Why agentic:** The agent does open-ended research (reads source, related issues) rather than running a fixed classifier. It writes back to the same GitHub artifact a maintainer would (labels, comments, assignees), so it's indistinguishable from a junior triager from the outside.
**Generalizable core:** Inbound record in a queue (issue, ticket, lead, form submission) → agent reads adjacent context → classifies, labels, routes → writes back to the same system where the team already works.
**Deployability:** Trivial if you're on GitHub — described in YAML, compiled with `gh aw compile`. Same skeleton ports to Linear, Jira, Zendesk, HubSpot with n8n or a Claude API workflow listening on the webhook. Weekend build outside GitHub. Replaces the morning triage pass a tech lead or support manager runs across the backlog.

### 3. The screening agent that sits on the ATS and answers every applicant
**Source:** [GoPerfect for SMB](https://www.goperfect.com/blog/best-ai-candidate-screening-software-for-small-and-mid-size-businesses-in-2026) — autonomous recruiting agent in production across Greenhouse, Lever, Ashby, Workday, iCIMS, BambooHR via Merge integration; Korn Ferry's 2026 TA report says 52% of TA leaders are deploying agents of this shape this year.
**Mechanism:** Triggered by a new applicant record in the ATS. The agent reads the JD plus any recruiter clarifications captured during intake, reads the applicant's resume and any structured questionnaire answers, scores 1–5 with explicit reasoning, and writes the score + reasoning back to the ATS candidate record. It auto-advances candidates above 4.0, auto-declines below 3.0 with a personalized email that references something specific from their application, and flags the 3.0–4.0 band for a recruiter to look at. Status changes sync bidirectionally so the recruiter sees agent decisions in the same Greenhouse view they already use.
**Why agentic:** The agent makes a graded judgment with reasoning, writes a personalized response to the candidate (not a templated form rejection), and chooses between three actions. The "zero ghosting" output — every applicant gets a real, specific reply — is the artifact a human couldn't produce at volume.
**Generalizable core:** New inbound record in a system of record → agent scores against criteria the team defined → tiered action (auto-approve / auto-decline with personalized response / flag for human) → writes status back to the same system + sends external communication.
**Deployability:** Buy: GoPerfect-style SaaS for HR. Build: ATS webhook → n8n or Claude API + MCP → ATS write-back + transactional email. Week build for a single-role version. Replaces the first-pass resume screening that recruiting coordinators do (or that disappears under volume and creates the ghosting problem in the first place). Scale caveat: the value compounds at higher applicant volume; a 3-roles-a-year shop won't notice it.

### 4. The Shopify support agent that closes the return loop itself
**Source:** [Gorgias AI Agent + Shopify deployments](https://www.usefini.com/guides/ai-platforms-ecommerce-returns-refund-automation-2026) — Gorgias and similar AI Agents in production across Shopify merchants in 2026; reported processing time drop from ~48 hours to under 60 seconds for routine return cases.
**Mechanism:** A customer message about a return arrives in a support inbox (Gorgias, Zendesk, or chat widget). The agent reads the message, pulls the order from Shopify (line items, fulfillment status, delivery date), reads the merchant's return policy (window, eligible SKUs, conditions), and decides whether the request fits inside the policy. If yes, it issues the refund or RMA via the Shopify API, generates the return shipping label, and replies to the customer with the label and status. If the request is outside policy or ambiguous (damaged goods, partial returns, mid-shipping issues), it summarizes the case and hands it to a human agent.
**Why agentic:** The agent executes a write — refund issued, label generated, money moves — not just a reply. It also exercises judgment about policy edge cases rather than running a decision tree. The replaced task isn't "answering the email" but "the full RMA round-trip a support rep used to drive."
**Generalizable core:** Inbound customer message in any channel → agent reads transactional context (order, policy, eligibility window) → executes the transaction via API → sends the artifact (label, refund confirmation, credit) → escalates only exceptions.
**Deployability:** Buy: Gorgias AI Agent or similar if you're a Shopify merchant. Build: support inbox webhook → Claude API + Shopify MCP / Admin API → write refund + transactional email. Week build for a single-policy version. Replaces the routine portion of a support rep's queue, which is usually the majority of it. Scale caveat: requires a written return policy crisp enough that an agent can actually decide eligibility; merchants whose "policy" is vibes will need to formalize first.
