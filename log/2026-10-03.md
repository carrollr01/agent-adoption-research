# 2026-10-03 — Agent Pattern Scan

## TL;DR
Four patterns today, mostly from the operations side of the house: alert-triggered root-cause investigators that explain themselves in the channel the alert fires in, change-log correlation for cost anomalies, scheduled calendar audits that detect missing expected state in a legal docket, and meeting-end agents that write action items straight into Jira/Linear with ownership. The strongest mechanism is the one that goes from "detect anomaly" to "name the specific change in the audit log that caused it" — that's a different animal from a monitoring dashboard.

## Patterns

### 1. Alert-triggered root-cause investigator that posts to the Slack thread the alert came in on
**Source:** [Vercel Agent investigations now available in Slack](https://vercel.com/changelog/vercel-agent-investigations-now-available-in-slack) and [Vercel for Slack public beta](https://www.createwith.com/tool/vercel/updates/vercel-launches-vercel-for-slack-in-public-beta) — Vercel shipped this in late August 2026; the pattern is being copied by Datadog, Groundcover and others in Q3.
**Mechanism:** An anomaly on error rate or response time fires an alert to a Slack channel. The agent reads the alert payload (service, time window, metric), then queries the logs and metrics around the alert time, looks for correlated error spikes, deploy events, dependency changes or traffic shifts, and replies as a threaded response under the original alert message with a short root-cause write-up and the specific log lines or dashboard links it's pointing at. The engineer never leaves Slack to triage.
**Why agentic:** The trigger is an external event, not a human prompt. The agent decides which logs and metric slices to pull based on what the alert says, and the output is written into the system where the on-call is already looking.
**Generalizable core:** Alert in a channel → agent gathers evidence from logs and metrics around the alert window → posts a reasoned finding as a threaded reply in the same channel → replaces the on-call's first-pass triage.
**Deployability:** Weekend build on top of Datadog/Sentry/Honeycomb webhooks plus Claude API with log-search and metrics MCPs, posting via a Slack bot. Vercel's version is turnkey if you're already on their stack. Augments the first-responder on an on-call rotation; most teams are keeping humans on the acknowledge/escalate decision for now.

### 2. Cost-anomaly agent that correlates spend against who changed what
**Source:** [AWS FinOps Agent — automated anomaly response](https://docs.aws.amazon.com/finops-agent/latest/userguide/automated-anomaly-response.md) and [TechStrong launch coverage](https://techstrong.it/featured/aws-previews-finops-agent-to-optimize-consumption-of-cloud-resources/) — AWS public preview since June 2026, now generally used in enterprise FinOps teams; setup is a one-sentence prompt.
**Mechanism:** AWS Cost Anomaly Detection fires an event. The agent reads the anomaly's dimensions (service, account, region, amount), then queries CloudTrail for API calls in that scope in the hours around the spike — launched instances, changed storage class, new principal, modified lifecycle rule — and tries to pin the cost to a specific change event and the IAM principal who made it. It posts a summary ("spike of $4,300 on EBS in us-east-1 traces to a `ModifyVolume` call by role `terraform-apply` at 14:02 Sunday") into Slack or opens a Jira ticket, routed by threshold. Config is natural-language: "when a cost anomaly over $1,000 fires on my production monitor, investigate and post to #finops-alerts."
**Why agentic:** The crucial step is cross-referencing two different data sources (billing and audit log) to name a change and an owner, which is the human analyst's actual job. A dashboard shows the spike; this names the pull request or terraform run behind it.
**Generalizable core:** External event (threshold crossed) → agent cross-references against the change/audit log for the same time window → names the responsible change and owner → writes into the ops channel or ticket queue → replaces the "who did this and why" scavenger hunt that follows every alert.
**Deployability:** Week build if DIY — the pattern is "anomaly stream + change-log API + LLM + chat/ticket output." The AWS version is zero code if you're on AWS. Beyond cloud cost: works for any surface where you have both a metric stream and a timestamped change log (feature flags, config repos, admin consoles, deployment systems). Replaces the first hour of a FinOps or SRE investigator's day.

### 3. Scheduled docket-audit agent that detects missing deadlines, not just upcoming ones
**Source:** [LawToolBox MCP Connector for Microsoft 365 and Claude](https://lawtoolbox.com/m365-mcp/) and [LawNext coverage of the August 2026 launch](https://www.lawnext.com/2026/08/watch-lawtoolbox-mcp-for-microsoft-365-claude-connects-legal-ai-to-matter-data-containers-in-m365.html) — deployed inside law firms' M365 tenants from August 2026.
**Mechanism:** On a schedule (typically weekly), a Claude agent runs inside the firm's M365 tenant. For each open matter, it uses the LawToolBox MCP to compute what deadlines should exist given the matter's jurisdiction and procedural posture (court filing rules, response windows, discovery cutoffs), then reads each attorney's Outlook calendar and the firm's matter calendar and diffs the two sets. It flags deadlines that are legally required but not on anyone's calendar. The output is a per-attorney "missing deadlines" email or Teams message that names each gap and the rule it comes from. The agent can also run alongside iManage, NetDocuments and DocuSign MCPs to pull in the triggering documents for context.
**Why agentic:** It is not reminding you about a date on the calendar. It is re-deriving the expected state from external rules and detecting the absence of entries that should be there. That requires reasoning about procedural rules per matter, which is the paralegal's job.
**Generalizable core:** Scheduled trigger → agent re-derives expected state from external rules or SLAs → compares against current state in the system of record → flags missing items (not just upcoming ones) → replaces the periodic manual audit nobody has time to do.
**Deployability:** Week to month build depending on how codified the rules are. Easy for anything with explicit rules (court procedure, regulatory filings, contract renewal windows, SLA-based support obligations, periodic compliance tasks). Harder for domains where "what should exist" is tacit. Replaces or augments a docketing clerk, compliance analyst, or ops lead who does a periodic hygiene review.

### 4. End-of-meeting agent that writes action items into the ticket system with ownership
**Source:** [Granola vs ZoomMate comparison, Aug 2026](https://meetgeek.ai/comparison/zoommate-vs-granola), [Granola CRM/action-item automation](https://sacra.com/chat/h/bd9e6266-9843-4aa0-9280-244e84d36dbd/), and Fireflies' Jira/Linear integration — pattern is now the default for engineering and GTM teams on these tools.
**Mechanism:** The agent attaches to a Zoom/Teams/Meet call (either as a bot like Fireflies or at the desktop layer like Granola). When the call ends, it processes the transcript plus any typed notes, extracts action items, classifies each by owner, project, and issue type, and creates a Jira issue, Linear ticket, Salesforce task, or Slack handoff accordingly. Each ticket includes a deep link back to the recording timestamp where the action was agreed. The organizer gets a review draft; auto-send is opt-in per team.
**Why agentic:** The thing being replaced is the human who leaves the meeting and types up action items. The agent reads an unstructured artifact (the conversation), decides what counts as an action, assigns a specific owner from meeting participants, picks a project and ticket type, and writes to the external system — not a passive summary.
**Generalizable core:** Event concludes (meeting, call, email thread, trip report) → agent extracts structured actions from unstructured capture → writes each action into the system of record with owner, type, and context link → replaces the manual post-event cleanup.
**Deployability:** Weekend build on top of a transcription service plus the target system's API and an LLM extractor; a week if you want it to disambiguate owners from vague references ("you'll take that one"). Turnkey if you already use Fireflies, ZoomMate, Granola or Otter with their integrations enabled. Replaces or augments the person who was going to type up the notes anyway, and recovers the share of action items that never make it off the call.
