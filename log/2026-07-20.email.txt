# 2026-07-20 — Agent Pattern Scan

## TL;DR
Most interesting today: the "custom harness on top of Claude Agent SDK" pattern that Claire Vo demoed live on How I AI — a two-person shop wrapping code around Claude to turn Sentry links into RCA + Linear ticket + PR draft. Same trigger class (production error → autonomous triage → PR) is now running at Sentry-scale via Managed Agents (~1M RCAs/yr, 600k PRs/mo reviewed). Second-most interesting: the sales→CS handoff agent that treats an account transition as the trigger, not an email.

## Patterns

### 1. Sentry-link-in → RCA + Linear ticket + PR draft (custom Claude Agent SDK harness)
**Source:** https://www.chatprd.ai/how-i-ai/how-i-built-a-custom-ai-harness and https://x.com/clairevo/status/2074935469381722154 — Claire Vo built this for her 2-person company ChatPRD, demoed live on the July 8 2026 How I AI episode. Same pattern now productized at Sentry: https://claude.com/customers/sentry (Autofix: Seer RCA → Claude Managed Agent → PR, ~6 min end-to-end, 1M RCAs/yr, 600k PRs reviewed/mo).
**Mechanism:** Sentry link (or Sentry webhook on a new grouped error) → harness pulls the error frame, stack, related events; walks the GitHub repo for the offending code; checks Vercel deploy history to correlate with recent releases; searches Linear for prior related tickets → drafts a root-cause narrative → opens a Linear ticket with the RCA and a draft PR against the repo. Replaces the on-call engineer's first 30–60 min of "what is this, is it new, is it real, who owns it, is there a fix."
**Why agentic:** Every step is a decision that depends on what the previous step returned (is this a known error group? did a deploy in the last hour touch this file? is there an open ticket already?). No fixed IF/THEN chain gets you from a raw Sentry link to a PR that references the right commit range.
**Generalizable core:** Monitoring signal → agent stitches code + deploy + ticket history → drafts fix artifact + writes to issue tracker → human reviews/merges.
**Deployability:** Claude Agent SDK + Ink terminal UI + adapters for Sentry/GitHub/Vercel/Linear MCPs. Week-scale build for one engineer per Vo's live demo. Augments an on-call rotation; realistic first client is any SaaS shop with >100 Sentry issues/mo. Scale caveat: needs Sentry/GitHub/Vercel already wired; the harder version (fully-autonomous PRs like Sentry's) needs a code-execution sandbox and much heavier eval.

### 2. Account-transition-triggered sales→CS handoff agent
**Source:** https://zapier.com/blog/zappy-award-monthly-winners-june-2026/ — Amber at Tivly (insurance-lead marketplace) built this in Zapier; named a June 2026 Zappy Award winner. Documented in Zapier's June winners writeup.
**Mechanism:** Trigger is a status change on an account record (sales → account management). Agent pulls the full email + call thread from Gmail, the onboarding notes, weekly campaign performance (leads purchased, sources, conversion by channel), and outstanding questions → produces a handoff scorecard with the client story, active issues, and the "why they'll churn" signal keyed to lead-source × channel within the first 30–45 days → writes to the CS team's briefing doc and pings the new owner. Replaces the 20-minute-per-account "let me catch you up" meeting that used to happen (badly) between sales and CS.
**Why agentic:** The context to assemble is not fixed — for a fast-lapse-risk account the scorecard needs different fields than for a healthy one, and which historical emails matter depends on what surfaced in the campaign data. A Zap would just dump every field.
**Generalizable core:** Role/ownership transition on a record → agent assembles multi-system history + performance data → produces briefing artifact → written to next-owner's queue. Replaces the human "let me catch you up" meeting.
**Deployability:** Zapier Agents + Gmail + CRM + Google Sheets/Docs. Week build for a Zapier-fluent operator. Augments/replaces the sales rep's briefing time and the CS onboarding manager's first-week catchup. No scale caveats for typical SMB; larger orgs will need a real CRM (Salesforce/HubSpot) as the transition source.

### 3. Policy-PDF-as-agent-spec: transaction reviewer + employee SMS Q&A
**Source:** https://ramp.com/blog/ramp-policy-agent-ga-launch and https://support.ramp.com/hc/en-us/articles/44072387128979-Policy-Agent-Overview — Ramp's Policy Agent, GA'd 2026 to Ramp Plus customers; early customers report ~85% fewer manual reviews at 99%+ accuracy, 15x more out-of-policy catches vs non-AI baseline.
**Mechanism:** Trigger 1 = finance admin uploads the expense-policy PDF (or has Ramp draft one). Agent reads the doc and builds a "reasoning graph" — a structured decision tree of thresholds, categories, required documentation. Trigger 2 = every card transaction / reimbursement. Agent evaluates the transaction against the graph, auto-approves low-risk, flags outliers with the specific policy clause cited, escalates the 10–15% that need judgment. Trigger 3 = an employee texts / Slacks a spend question ("can I expense this?"); the same graph answers from the same source of truth. Also proactively suggests policy tweaks based on the exceptions it sees. Replaces the AP/controller's line-by-line review and the "hey Slack, is this reimbursable?" thread.
**Why agentic:** The policy is written in English, not rules. The agent has to interpret "reasonable meals during travel" against a $47 Uber Eats charge at 11pm on a Tuesday, cite the clause, and decide whether to auto-approve or flag — no static rules engine does that.
**Generalizable core:** Natural-language policy/spec doc → agent compiles to a queryable decision graph → same graph used to (a) auto-decide new events and (b) answer human questions about the policy → writes decisions + citations to the operational system. Replaces policy-interpretation labor.
**Deployability:** Ramp is the productized version, but the pattern is buildable in ~2–3 weeks with Claude + a policy-parse prompt + a persisted rule store + Twilio for SMS + whatever the underlying transaction/HR/procurement system is. Great for A3 to sell to any client with a "written policy that lives in a PDF nobody reads" — HR PTO policies, procurement thresholds, reimbursement rules, safety SOPs. Scale caveat: policy-authoring quality drives everything, and you need an audit-log destination (finance/legal will demand citations).

### 4. Structured-doc upload → automated takeoff/quote
**Source:** https://www.togal.ai/case-study/coastal-construction-case-study — Coastal Construction's Miami office, ~$1M saved in year one with Togal.AI (14.5 hrs saved per plan set, ~1,160 hrs/month). Small Business Big AI podcast (July 2026) also describes a construction estimator going from 3 days → 15 minutes per quote with a Claude-based version reading incoming project PDFs.
**Mechanism:** Trigger = new architectural PDF (or DWG/RVT) arrives — over email, Dropbox drop, or a client portal upload. Agent runs CV over the plan to detect and measure rooms, walls, doors, MEP items → normalizes against AIA measurement standards → pushes structured quantities into the estimating template → drops the pre-populated quote into the estimator's queue for review. Replaces the "estimator sits with a ruler and a PDF for 8 hours" step that used to gate every bid.
**Why agentic:** Blueprints don't have consistent legends, symbols vary by architect, and the takeoff decisions cascade (identifying a wall type changes downstream material counts). This is judgment-per-symbol at scale, not a template mapping.
**Generalizable core:** Structured/semi-structured doc arrives → vision-capable agent extracts entities into your domain schema → writes to the system-of-record for the next human step → replaces manual extraction labor. Same skeleton applies to insurance loss estimates from photos, legal contract abstraction, medical intake from scanned forms, invoice line-item extraction into ERP.
**Deployability:** Togal is the vertical productized version. Custom rebuild for a specific client trade = weekend prototype (Claude vision + Airtable), production version = month (needs schema-aware post-processing, error boundaries, per-project training data). Replaces junior-estimator work; augments the senior estimator's review time. Scale caveat: accuracy needs a per-domain eval loop — this is not a "prompt it once and ship" pattern.
