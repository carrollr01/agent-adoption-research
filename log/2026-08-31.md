# 2026-08-31 — Agent Pattern Scan

## TL;DR
Five distinct trigger classes surfaced today. The strongest is Claude's computer-use claims agent working inside legacy healthcare and insurance systems that have no API, cutting the longest workflow from 32 minutes to 13. That mechanism (UI-level agent on a system nobody can integrate with) is a real alternative to the "we can't automate this because there's no API" answer, and it generalizes past the case study.

## Patterns

### 1. Computer-use agent on a no-API back-office system
**Source:** [Anthropic — Build production agents with computer use, the Skills API, and the Files API](https://claude.com/blog/computer-use-skills-api-files-api) — Anthropic's Aug 2026 production-agents post reports an unnamed healthcare/insurance customer running claims workflows against systems with no API. Longest workflow 32 min → 13 min, cost per task down ~30%, completion 100%, no prompt changes across workflows.
**Mechanism:** New claim (or claim status change) lands in the queue → agent opens the legacy carrier/EHR/claims UI in a virtual desktop, reads the record fields on screen and any attached documents, decides the next step, clicks through the screens to update statuses, upload docs, and enter codes → writes back into the same legacy UI and the queue system. Replaces the ops person who spends the day tabbing between screens re-typing what's already in the payload.
**Why agentic:** No wrapper API is being called. The agent looks at pixels, types into fields, and clicks buttons the way a human would, so the input surface is the running application, not a schema. Nothing about this is a passive display.
**Generalizable core:** New record in queue → agent drives the legacy UI as a human would → same UI is the write target → replaces a person doing screen-to-screen data entry.
**Deployability:** Claude computer-use + a browser/VDI sandbox + a queue system to feed it work. Week-to-month build for a single workflow, longer for the sandboxing and auditing scaffolding. Replaces or augments back-office processors. Scale caveats: needs a stable UI the agent can be trained on (screen drift breaks it), and running a browser per session is heavier than an API call, so unit economics matter above a few workflows per minute.

### 2. Ticket-assignment as the agent trigger surface
**Source:** [Atlassian — From prompts to orchestration: Scale AI coding agent impact with Jira Automation](https://www.atlassian.com/blog/development/scale-agent-impact-with-jira-automation) — Rivian is cited at 750+ hours saved per developer per year using Jira Automation with Claude/Copilot/Cursor as automation steps. Claude Agent for Jira (Jun 2026) also lets any user pick "Claude" from the assignee dropdown or @mention it in a comment.
**Mechanism:** Ticket status/label change or manual assignment to Claude → automation rule packages the ticket text, linked design docs, and repo context, sends it to Claude Managed Agents → agent clones the repo into a sandbox, implements the change on a branch, opens a draft PR → status streams back onto the Jira ticket as comments. Replaces the developer picking up small, well-scoped tickets (flag cleanup, dep bumps, test-coverage fill-in, first-pass bug triage).
**Why agentic:** The trigger is a normal work-tracker event that everyone already produces, and the "worker" is a real coding agent with sandbox and repo write access, not a suggestion box. The PR that comes back is either mergeable or not; there is no dashboard step in between.
**Generalizable core:** System-of-record work item transitions to a designated state → agent reads item + linked context → performs the work in a sandbox → writes back the finished artifact and updates the record → replaces a human picking work off the queue.
**Deployability:** Jira Automation + Claude Managed Agents + GitHub is off-the-shelf; a week to wire up and set guardrails, plus ongoing effort to write ticket templates the agent can actually work from. The same trigger surface exists in Linear, ServiceNow, HubSpot workflows, Salesforce Flow. Replaces or augments a junior engineer/analyst absorbing tickets; scale caveat is the mergeability rate, which depends on ticket quality, so the pattern gets better when whoever writes tickets writes them with the agent in mind.

### 3. Failure-triggered agent that patches the automation itself
**Source:** [Buldrr — Claude Code Self-Healing Workflows 2026](https://buldrr.com/self-healing-workflows-with-claude-code/) plus [n8n community — Agents fixing n8n workflows](https://community.n8n.io/t/agents-fixing-n8n-workflows/299685); popularized on YouTube by Nate Herk. Freelance operators running multiple client n8n instances are using it in production.
**Mechanism:** An n8n workflow errors (bad expression, JSON parse, type mismatch, upstream API change) → error trigger fires an alert to Telegram with the workflow name, failing node, and an "Approve fix" button → on approval, an Execute Command node spawns a headless Claude Code session with the n8n MCP server → Claude reads the broken workflow JSON via MCP, diagnoses the failing node, writes the corrected version, saves it back → workflow re-runs from the failed node. Replaces the operator or consultant who normally gets paged to open the workflow, guess at the error, and fix it by hand.
**Why agentic:** The agent's write target is the automation stack itself. It reads a machine-readable representation of a broken system, produces a patch, applies it, and re-runs the failed step. Nothing here is showing a chart.
**Generalizable core:** Failure event from any orchestrator (workflow engine, cron, ETL) → agent reads the failing artifact via a live MCP/API → diagnoses and patches it → writes the fix back and resumes → replaces the person paged to hand-fix the pipeline.
**Deployability:** n8n + n8n MCP + Claude Code + Telegram (or Slack) approval. Weekend build for a single workflow, week for a "watch everything" version with per-client isolation and a fix history. Fits a solo consultant maintaining a portfolio of client automations, or an internal ops team that owns many low-priority jobs. Scale caveat: the agent needs write access to the workflow definitions, so an approval gate matters until the operator trusts the patch quality.

### 4. Verticalized payment-ops "super agent" scoped to one function
**Source:** [Business Standard — Cashfree rolls out AI agents for merchants to automate payment operations, 30 Aug 2026](https://www.business-standard.com/companies/news/cashfree-rolls-out-ai-agents-for-merchants-to-automate-payment-operations-126083000455_1.html); [IBS Intelligence — Cashfree's Relay brings AI agents to SMB payment operations](https://ibsintelligence.com/ibsi-news/cashfrees-relay-brings-ai-agents-to-smb-payment-operations/). Beta running since May 2026, GA end of Aug. Cashfree claims ~60 hours/week of merchant payment-ops labor collapses to ~45 minutes.
**Mechanism:** Payment platform events (failed charge, abandoned cart, COD order placed, subscription card expired, chargeback filed) → agent reads the transaction and customer history on Cashfree's infrastructure → decides the next action per merchant-defined outcome: retry the payment on a schedule, message the customer through their preferred channel to recover the cart, place a confirmation call/message on COD before dispatch, message the cardholder to update payment method, or file the dispute paperwork with the acquirer → writes back to the merchant CRM/order system and the payment ledger. Replaces the payment-ops person who spends most of the week chasing failed and pending money.
**Why agentic:** The interesting move here is scoping. The "super agent" is not a general assistant; it is a set of pre-trained action agents that only trigger on payment lifecycle events. The merchant describes the outcome (prompt or speech) and the platform composes the actions. Data never leaves Cashfree infrastructure.
**Generalizable core:** Lifecycle event in a transactional system → agent reads the record and the customer's history → composes the correct downstream action from a scoped library → writes back to the same transactional system and customer channel → replaces a person whose whole job is triaging that one class of failure.
**Deployability:** Verticalized SaaS pattern; the analog is any platform sitting on a firehose of failure/retry events (Stripe, Shopify, subscription tools, dispute providers, logistics platforms, EHR portals). Month-plus build if you're the platform; weekend build if you're wiring the same idea on top of Stripe events + a workflow engine + Claude. Replaces the "AR/payments coordinator" role at SMB scale.

### 5. Long-record synthesis agent that produces the deliverable, not a summary
**Source:** [Anthropic — EvenUp customer story](https://claude.com/customers/evenup) (highlighted in Anthropic's Aug 2026 customer roll-up). Personal-injury law firms using EvenUp on Claude Opus 4.8 report drafting-time collapse from 15 hours to 15 minutes.
**Mechanism:** New PI case intake (medical records + billing packet uploaded) → agent reads the full record set, reasons over the treatment timeline (when each treatment happened and in what order), identifies the critical facts and damages, and drafts the demand letter or case document in the specific lawyer's writing style → writes the finished draft into the firm's case management system for attorney review. Replaces the associate/paralegal who normally spends multiple days on the same drafting task.
**Why agentic:** Not a "summarize this PDF" bot. The system has to keep temporal order across a large multi-source record, pick out what matters for damages, and produce a signable-quality document in a named person's voice. The output is the deliverable, not an aid to producing the deliverable.
**Generalizable core:** New long, multi-source record set → agent reads everything, reasons over the temporal/causal structure → drafts the finished client-facing document in a specific author's style → writes it into the firm's system for human sign-off → replaces the junior professional whose main job was reading and drafting.
**Deployability:** Claude Opus 4.8 + long-context ingest + a style corpus per author + write-back into the DMS/case system. Month build for the pipeline, ongoing effort for style tuning per author. Replaces or augments junior associate/paralegal drafting work. Scale caveat: needs a real style corpus per author, and works best where the deliverable is high-volume and structurally repeatable (demand letters, medical narratives, underwriting memos, IEP drafts, insurance appeal letters).
