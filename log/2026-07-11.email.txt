# 2026-07-11 — Agent Pattern Scan

## TL;DR
Spellbook shipped end-to-end contract lifecycle agents that ingest deals from email/Slack/Salesforce, autonomously redline against your playbook, then keep watching post-signature for renewals and regulation shifts. This is the clearest "lifecycle agent replaces a lifecycle spreadsheet" pattern to date, and the intake-through-post-signature loop generalizes well beyond legal.

## Patterns

### 1. End-to-end contract lifecycle agent (intake → redline → renewal watch)
**Source:** Spellbook Autonomous Contract Management (https://spellbook.com/acm) — Spellbook launched ACM on 2026-06-30 for enterprise legal teams, general rollout mid-summer, powered by Claude + OpenAI models.
**Mechanism:** New contract lands in email/Slack/Salesforce/DocuSign → intake agent pulls it, diffs against the team's playbook, generates a diagnostic of deviations and risk locations → each active deal gets its own workspace where every incoming counter-turn is auto-reviewed as it arrives → after signature, agent watches renewals, regulation changes, and policy updates in the background and pings the owner before dates slip.
**Why agentic:** The system is triggered by inbound events across four channels, decides what to redline without a human asking, and keeps working after signature — no dashboard involved, and the "output" is a redlined draft, a workspace, or a Slack ping, not a page a lawyer opens.
**Generalizable core:** Inbound document lands in any channel → agent diffs it against a house standard → drafts response and per-item workspace → keeps watching the document's downstream lifecycle (renewals, expirations, regulation drift).
**Deployability:** Requires document parsing, a house-standards artifact (playbook, style guide, SLA template), and integrations to at least one inbox and one system-of-record. Week to weekend build on Claude API + MCP for the intake + redline. Post-signature watcher is the harder part — needs durable state and a scheduler. Replaces paralegal intake and the "contract tracker spreadsheet" role. Same skeleton applies to vendor RFPs, insurance policy renewals, procurement contracts, franchise agreements, tenant leases.

### 2. Fleet of specialized, independently-governed mini-agents for outbound prospecting
**Source:** Rakuten Advertising sales workforce case (https://www.similarweb.com/blog/sales/b2b-sales/rakuten-advertising-data-pipeline/) — $2.5M in pipeline created in 6 months with no additional headcount; account prospecting time cut from over an hour to a fraction of that.
**Mechanism:** New intent signal (web traffic behavior on their properties, firmographic threshold crossed, Salesforce record created) → account-research agent pulls history and web behavior → contact-enrichment agent fills title/tech stack/recent news → sequencing agent writes and paces multi-channel outreach → CRM-writer agent logs everything. Each agent has its own permission scope, its own failure boundary, its own approval checkpoint. Errors stay isolated to one stage.
**Why agentic:** The trigger is a data event, not a human request. Each stage acts and writes to a system. What replaces the manual BDR workflow is a chain of narrow agents, not a person clicking through Similarweb, LinkedIn, Salesforce, and Outreach in sequence.
**Generalizable core:** Data event fires → specialized mini-agent per stage (research → enrich → act → log), each with narrow scope and its own approval gate → chain writes to system-of-record without a human orchestrator in the middle.
**Deployability:** Variation-of 2026-05-23 morning real estate scouting entry — new angle: architecture of separately-governed mini-agents rather than one omnibus scouting agent. This is materially more reliable in production. Stack: n8n or Trigger.dev to orchestrate, Claude API per stage, one MCP tool per data source (LinkedIn, ZoomInfo, Salesforce). Month-scale build. Replaces the junior BDR "research the account, enrich the contact, draft the email, log the touch" chain. Scale caveat: works best when there's a real data signal upstream — no signal, no trigger, no agent.

### 3. Continuous general-ledger reconciliation agent (posting-event triggered)
**Source:** Dynamics 365 Finance Account Reconciliation Agent (https://learn.microsoft.com/en-us/dynamics365/finance/general-ledger/acct-rec-agent) — production preview as of July 2026; HighRadius reports 90% auto-match, 99% accuracy, 60% of close tasks automated in comparable deployments.
**Mechanism:** New voucher posts or a journal entry hits the ledger → agent runs its reconciliation checks continuously (not at month-end) → when it finds a mismatch — voucher amount off, subledger doesn't match GL, intercompany transfer unresolved — it evaluates the discrepancy, recommends a specific journal entry or clearing action, and queues it for approval → on approve, agent posts it and updates the reconciliation state.
**Why agentic:** The trigger is an accounting event inside the ERP, not a human running a month-end script. The agent reads the ledger, decides which mismatches merit action, proposes the fix, and can write it back on approval. What it replaces is the controller's "chase every discrepancy" queue that traditionally lived in a spreadsheet reviewed once a month.
**Generalizable core:** Transactional event in system-of-record → agent runs a rules-plus-judgment check against expected state → proposes a corrective write-back → human approves in-line → agent posts it. Same skeleton fits inventory variance, payroll reconciliation, subscription revenue recognition, marketing spend allocation.
**Deployability:** For Dynamics/NetSuite shops, this is a vendor feature toggle. Building it standalone is a month+ build — needs GL API access, rule catalog, exception queue UI, approval workflow. Claude API + MCP with a finance connector works. Replaces junior accountant and staff accountant reconciliation labor. Scale caveat: only useful past a certain transaction volume — below ~500 monthly postings the ROI is thin.

### 4. Job-change and profile-drift alert agent for a candidate database
**Source:** AIRA-style job-change recruiting agents (https://aisera.com/blog/ai-recruiting/) — Aisera / Juicebox / AIRA all shipping variants; Juicebox describes agents watching 800M+ profiles across 30+ data sources continuously per open role.
**Mechanism:** LinkedIn, Github, or third-party enrichment source flags a candidate profile change (new job, promotion, layoff, activity spike) → agent checks the change against the firm's open reqs and past-candidate history → if there's a fit, drafts a personalized outreach email referencing the change → sends (or queues for recruiter approval) and, on positive reply, auto-schedules the screening call in the recruiter's calendar → writes the whole thread back to the ATS with a "re-engaged via profile change" tag.
**Why agentic:** The trigger is a state change in an external data source. The agent is reasoning about fit against multiple open roles, personalizing the message with the specific change as context, and writing to the ATS and calendar. Replaces the pattern of a recruiter periodically re-searching their old candidate list — the database becomes reactive instead of stale.
**Generalizable core:** External data source flags a state change on a record you already have → agent checks the change against your open opportunities → drafts personalized outreach that references the change → writes result back to system-of-record. Same skeleton fits customer-account watchers (churn-signal → re-engagement), competitor-hire watchers (competitor VP leaves → sales trigger), lease-expiry watchers, and licensing-lapse watchers.
**Deployability:** Weekend build if you already have an enrichment vendor's webhook (Clay, People Data Labs, Juicebox) and an ATS with an API (Ashby, Greenhouse). Claude API for the fit-check and email draft, one small state store for "who have we already re-engaged and when." Replaces the recruiter's manual database mining and the "quarterly re-outreach" campaign. Scale caveat: enrichment API costs scale linearly with database size — a 50k-candidate DB with weekly checks is not cheap.
