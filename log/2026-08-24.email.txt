# 2026-08-24 — Agent Pattern Scan

## TL;DR
The standout is Opsima's field-ops pattern: agents that listen on the VHF radio, WhatsApp groups, and email threads crews already use, transcribe and parse them, then update the system of record and trigger downstream dispatch. It sidesteps the classic "get frontline people to type into a new UI" problem by making the existing communication channel itself the trigger.

## Patterns

### 1. Agents that parasitize existing comms channels (radio / WhatsApp / email) as their trigger surface
Source: Opsima — Agentic Workflows in Field Operations, 2026 guide (https://opsima.com/blog/operational-insights/agentic-workflows-field-operations/) — deployed at ports, mining sites, and airport ground-service operations where crews communicate over VHF radio, WhatsApp, and email rather than through a system of record.
Mechanism: Trigger is any new transmission on a monitored channel (radio call, WhatsApp message, inbound email). The agent transcribes the audio or parses the message, classifies the event ("crane 3 offline", "truck 12 requesting fuel"), extracts entities (equipment ID, status, location), updates the fleet or maintenance record in the existing ops system, and — for certain event classes — kicks off a downstream workflow like dispatching a replacement or opening a safety ticket. Replaces the dispatcher role of monitoring channels plus the crew's after-the-fact data-entry burden.
Why agentic: Not a dashboard reading a database; the agent is a continuous listener that decides which utterances are operationally meaningful, what fields to update, and when to escalate. No new UI is imposed on frontline workers.
Generalizable core: unstructured message on an existing human channel → transcribe + classify + extract → update system of record → conditionally trigger downstream action.
Deployability: Speech-to-text (Whisper / Deepgram) + Claude or GPT for classification/extraction + webhook or API into the incumbent ops system + n8n or a custom worker to route events. Week-to-month build depending on channel count and how messy the incumbent system's API is. Replaces the manual "someone hears it on the radio and types it into the CMMS" step and, downstream, cuts the dispatcher's channel-monitoring time. Scale caveat: needs enough traffic on those channels to be worth the STT cost, and legal/HR sign-off to monitor operational chatter.

### 2. Scheduled coding agents that run unattended inside the data warehouse sandbox
Source: Snowflake — CoCo automations in CLI and Snowsight, Preview, released 2026-08-21 (https://docs.snowflake.com/en/release-notes/2026/other/2026-08-21-cortex-code-automations-preview) — Snowflake's coding agent (CoCo) can now be scheduled to run in a Snowflake-managed sandbox on a cron of at least once per hour, with tool permission prompts disabled so the run is fully unattended.
Mechanism: Trigger is a schedule (hourly or slower). The agent gets a stored prompt plus tool access inside a Snowflake sandbox, so it can query tables, run SQL/Python, hit approved external tools, and write results back to Snowflake — all without a human sitting in front of a terminal. Each run spawns a Cortex thread you can inspect and continue interactively. Replaces the analyst or engineer who ran a scheduled notebook, plus a lot of the plumbing normally required to give a Lambda job "an LLM's judgment".
Why agentic: It is not a static SQL job — the agent decides which tools to call, adapts to the state of the data on each run, and each run produces a threaded transcript rather than a fixed report row. Unattended tool execution is what distinguishes it from a chat session.
Generalizable core: schedule fires → agent boots inside a sandbox with warehouse + tool access → reasons over current data → writes updates and a thread of reasoning back to the same store.
Deployability: Snowflake customers already on Cortex get this natively; the same pattern is buildable on any warehouse (BigQuery + Cloud Functions + Claude via a scheduler; DuckDB + a small Fly.io worker for smaller shops). Weekend-to-week build for a Snowflake shop, week+ elsewhere. Replaces a scheduled analyst task or a brittle scripted job. Caveat: only useful if the interesting work actually lives in the warehouse — for shops whose data is scattered across SaaS, an ETL step is still required first.

### 3. Delegate-a-goal-in-Slack, get-a-finished-deliverable-back agents
Source: Rakuten Claude Managed Agents case study, 2026 (https://claude.com/customers/rakuten-qa) via Anthropic's Aug 20 GA post on computer use, Skills API, and Files API (https://enterprisedna.co/resources/news/anthropic-browser-use-computer-use-skills-api-enterprise-ga-august-2026/). Rakuten deployed specialist agents across product, sales, marketing, and finance in about a week each, plugged into Slack, Teams, and their internal task system.
Mechanism: Trigger is an employee posting a goal (not a task list) to a Slack channel or Teams thread — e.g. "put together the Q3 category-manager one-pager for pet supplies with year-over-year unit and margin." The agent reads the request, pulls the relevant data from the department's tools (BI, CRM, finance system), runs for tens of minutes to hours in a sandbox, and returns the finished deliverable — a spreadsheet, a deck, or a small app — as a file back into the thread for review. Replaces the junior analyst or ops person whose day is spent assembling other people's requests into deliverables.
Why agentic: The unit delegated is a goal, not a step. The agent picks its own subtasks, calls tools, self-corrects mid-run, and the human only sees the finished file. That is qualitatively different from a Slack bot that answers questions or runs a fixed workflow.
Generalizable core: goal posted in the team's messaging surface → agent assembles context from the team's own tools → runs long enough to produce a real artifact → returns the artifact back into the same thread for sign-off.
Deployability: Claude Managed Agents is the shortest path today (Skills package the team-specific methodology, Files API returns the artifact, Slack/Teams surfaces it); OpenAI's ChatGPT Work covers a similar pattern; roll-your-own is possible with Claude API + a background worker + Slack Events API but the sandboxing is the hard part. Week to month per specialist agent. Replaces or shrinks a junior-analyst role per department. Caveat: needs a real long-running-agent runtime — not a request/response Zapier chain — and needs the department's data actually accessible via tools/MCP.

### 4. Self-healing CI: failure event triggers an agent that reads logs, writes a fix, and opens a PR
Source: Self-Healing CI: Using GitHub Agentic Workflows to Automatically Fix CI Failures — Tiago Pascoal (https://pascoal.net/2026/03/12/self-healing-ci-using-gh-aw/) plus a working reference implementation (https://github.com/senthilkumaranT/self-healing-ci-cd-pipeline). Pattern is showing up broadly in teams using GitHub's Agentic Workflows framework (markdown + YAML frontmatter, coding agent runs inside an Actions runner).
Mechanism: Trigger is a workflow_run conclusion of "failure" (or an issue/PR event). The agent boots inside a runner, pulls the failed job's logs and the specific broken files, asks an LLM to root-cause the failure, generates a patch, pushes it to a branch, and opens a PR against the original with the diff plus an explanation. Replaces the on-call engineer who otherwise has to context-switch, reproduce, and fix routine CI breaks (dependency drift, minor lint regressions, flaky test config).
Why agentic: The action taken depends entirely on what the logs and diff say — the agent decides which files to open, whether to change code or config, and whether to escalate. Not a retry-on-failure job.
Generalizable core: system emits a failure event → agent fetches the failure context and the code that produced it → generates a proposed fix → files that fix back into the source-of-truth workflow (PR, ticket, change request) for human sign-off.
Deployability: Native today on GitHub via GitHub Agentic Workflows (markdown workflows + Copilot CLI / Claude / Codex inside runners); portable elsewhere with any CI + a webhook + Claude API + a bot account with write access. Weekend build for a first cut, week to harden. Replaces the first-pass triage that on-call does for routine CI breaks; does not replace real debugging. Caveat: needs guardrails on what the bot can push to and clear signals for when to escalate rather than patch.
