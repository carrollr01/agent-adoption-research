# 2026-09-29 — Agent Pattern Scan

## TL;DR
The single most interesting pattern today is Rocket Money's self-healing scraper: the agent's job is not to do the task but to rewrite the deterministic code that does the task, whenever the code breaks. That inverts the usual "agent as employee" framing into "agent as maintainer of a fleet of tiny programs." Four other real deployments round out the day.

## Patterns

### 1. Self-healing scraper: agent as code-maintainer, not task-doer
**Source:** https://claude.com/customers/rocket-money — Rocket Money's subscription-cancellation and bill-negotiation flows run as deterministic scripts across millions of users; when a target site changes, a Claude agent rewrites the script.
**Mechanism:** A deterministic scraper/automation fails on a task (usually because the target website changed) → the agent reads the broken procedure and its failure context → it diagnoses where execution broke, rewrites the automation logic, and re-emits it as code → the fixed code goes back into production, benefiting every user who hits the same step. Post-action, a separate classifier verifies whether the task actually completed and surfaces the failure reason for tracing.
**Why agentic:** The agent isn't executing the workflow itself; it's authoring the code that executes it. A dashboard would flag the failure; this pattern repairs the underlying process so the next N thousand runs succeed without human touch.
**Generalizable core:** deterministic job fails → agent inspects the broken step against the changed environment → rewrites the deterministic code → hands back to deterministic execution.
**Deployability:** Claude API with a subagent architecture (Rocket Money uses a Haiku 4.5 classifier that routes to Sonnet 5 subagents, with Opus reserved for the hard financial reasoning). Roughly a month-build for a serious version, weekend-build for a single narrow scraper. Replaces the on-call engineer or ops analyst who fixes broken integrations one at a time. Applies wherever you run brittle scripts against external systems you don't control: portal logins, insurance carriers, government filings, marketplace listings, benefits systems.

### 2. Post-deploy log-diff agent that files its own observability PRs
**Source:** https://claude.com/customers/carvana — Carvana wired Claude into its production Slack channels to close the loop between alert, diagnosis, and code change.
**Mechanism:** Two triggers run in parallel. (a) Software release event → agent diffs the post-release log stream against a baseline from the hour before deploy, flags anomalies, tags code owners in-thread, opens a pull request against the offending code path. (b) Scheduled hourly check → agent inspects pipelines and feature-flag state; if the current logs are insufficient to reach a verdict, it opens a PR that adds better logging on the suspicious path.
**Why agentic:** The novel move isn't triage — it's the agent recognizing "I can't tell from the current telemetry" and modifying the observation apparatus itself. That's judgment plus a code write, not a lookup.
**Generalizable core:** scheduled or event trigger → compare current state to a historical baseline → when the comparison is inconclusive, modify the instrumentation that produced the data, not just the data itself.
**Deployability:** Claude Agent SDK wrapped in a Slack app; scoped GitHub and warehouse access per team; kill switch and human approval gate for writes. Month-build minimum for the safety scaffolding. Replaces the on-call SRE's first hour and the "why is this alert firing again" back-and-forth. The self-observability-improvement move generalizes to any monitored system with a queryable log store — quality control lines, fleet telemetry, sales pipeline hygiene.

### 3. Standing-scan reward-workflow agent
**Source:** https://claude.com/customers/notion — Ramp runs 300+ custom agents in production; "Referral Bonus Roy" is the one that hunts eligible customers and closes out the payout end to end.
**Mechanism:** Scheduled scan across customer and usage data → agent identifies customers who now meet the referral-bonus criteria → verifies eligibility against program rules, drafts the payout record, routes it through approval where required, applies the credit, and notifies the customer. All state lives in Notion and the internal systems it's connected to.
**Why agentic:** It's proactive rather than triggered by a customer request, it makes judgment calls on borderline eligibility, and it runs a multi-step workflow (identify → verify → payout → notify) instead of returning a report. A "customers eligible for referral bonuses" dashboard would still leave the ops team doing the work.
**Generalizable core:** scheduled scan of a records store → agent finds records that newly meet a program's eligibility rules → runs the multi-step reward or intervention workflow to completion, with approval gates where money moves.
**Deployability:** Notion Custom Agents (or Claude API + your CRM/ERP + an approvals channel). Week-build for a single program, longer if the eligibility logic has real edges. Replaces the ops person's monthly sweep for eligible customers plus the manual payout workflow. Applies well beyond bonuses: dormant-customer winback, tier upgrades, expiring credits, refund entitlements, compliance nudges, employee anniversary programs.

### 4. Kanban card as agent dispatcher
**Source:** https://claude.com/customers/notion-qa — Notion's own product team uses the task board itself as the trigger surface for agent work.
**Mechanism:** A person creates a task on a Notion board and moves it to the "ready to start" column → that column transition invokes a Claude session → the agent assembles context from connected pages (design system, API docs, PRDs, prior tasks), produces the deliverable (prototype code, deck, sample website, spec draft), and drops the artifact back on the task card → a reviewer thumbs-up or thumbs-down the work, and the agent's skills library updates from that feedback loop.
**Why agentic:** The column transition is a workflow signal, not a chat message; the agent has to plan multiple steps (retrieve, draft, iterate) and produce artifacts, not answers; and the review feedback rewrites the agent's own instructions over time.
**Generalizable core:** state change on a shared work surface (column move, status flip, label added) → agent assembles context from a linked knowledge graph → produces an artifact back into the same surface → human reviews → review signal rewrites the agent's playbook.
**Deployability:** Notion Custom Agents natively, or the same shape with Linear/Jira/Asana + Claude API + a webhook. Weekend-build for one task type, week-build once you generalize the skill library. Replaces the "who should I ask to make a first draft of this" queue that stalls small teams — the trigger surface is already where people track work, so no new tool to learn. Feedback-driven skills updates make this compound over months.

### 5. Paused-draft agent for revenue-affecting writes
**Source:** https://claude.com/customers/supermetrics — Marketers ask questions in Claude and end the conversation with a proposed campaign change already staged in Google Ads / Meta / LinkedIn / TikTok, in paused state.
**Mechanism:** Marketer asks a natural-language question ("why did this campaign underperform last week?") → agent calls the Supermetrics MCP server to pull live data from the connected ad platforms → reasons across sources and proposes a specific action (bid change, audience swap, creative rotation) → creates the change in the target platform in *paused* state so nothing goes live → marketer reviews the staged edit and activates it if it looks right.
**Why agentic:** The write action itself is the deliverable, not the analysis. A reporting agent stops at "here's a chart"; this pattern stops at "here's the change, one click to ship." The paused-state convention is the key safety primitive that makes real write access acceptable.
**Generalizable core:** conversational question → agent pulls live data across systems via MCP → recommends and stages a real write in the target system in an inert/paused/unpublished state → human toggles it live.
**Deployability:** Claude Desktop or the Claude API + MCP servers for the target systems. The pattern generalizes to any high-consequence write surface that has a "draft" or "paused" state: PIM updates, pricing changes, HR letters, contract redlines, outbound email sequences, CI/CD deploys behind a feature flag. Weekend-build if an MCP server exists for the target; multi-week if you have to build the connector plus the paused-write convention where none exists. Replaces the analyst → account manager → implementer handoff that adds days to every marketing change.
