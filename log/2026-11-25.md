## Patterns

### 1. Kanban-style triage PM coordinating a fleet of long-running coding agents

**Source:** [Trigger.dev customer story — Capy](https://trigger.dev/customers/capy-customer-story) and [Capy automations page](https://capy.ai/features/automations). Justin Sun (co-founder/CTO at Capy) describes shipping a "PM that never sleeps" that orchestrates dozens of concurrent coding agents running for hours at a time.

**Mechanism:** Work lands in a kanban queue (ticket, Sentry alert, Slack message, Linear issue, GitHub event, or scheduled run). A triage agent reads the item, decomposes it into subtasks, and launches a child coding agent per subtask on Trigger.dev as a durable workflow. Each child agent runs in an isolated Ubuntu VM on its own git branch, works for hours, and opens a PR. A separate Review Agent triages the PR findings before anything surfaces for a human. The board is live — the kanban UI reflects agent state in real time. Replaces: the engineering manager's job of breaking work down, assigning it, and chasing status.

**Why agentic:** The triage agent isn't reporting on work — it's doing the work of assignment, dispatch, and consolidation, and the board is a side effect of what the agents are doing, not the primary interface.

**Generalizable core:** inbound work item → decomposer agent breaks it down → fan-out to long-running workers in isolated sandboxes → review agent consolidates → human sees only the surviving output.

**Deployability:** Stack is Trigger.dev (durable workflows outside serverless timeouts) + Claude/Codex agents + VM-per-task isolation (Capy inherited VM infra from its Scrapybara acquisition). Complexity: month-build if you need the VM isolation; week-build if you accept Docker containers and shorter runs. Replaces: a project manager's dispatch-and-chase work, or a senior engineer's triage-and-delegate work. The isolated-sandbox requirement means this is heaviest for code-producing agents; the skeleton still works for non-code work (sales research, document generation) with much lighter isolation.

### 2. Conversational buying agent replacing the lead form

**Source:** [How Anthropic's sales team rebuilt inbound with Claude Managed Agents](https://claude.com/resources/articles/how-anthropics-sales-team-rebuilt-inbound-with-claude-managed-agents) and [Inc. coverage](https://www.inc.com/robert-gillespie/anthropic-replaced-contact-form-for-ai-agent/91415246). Anthropic's own sales team replaced its Contact Sales form with a chat agent sitting on the pricing and Contact Sales pages. Leads passed to a rep convert >2x more often than the old form, and close ~5 days faster, per Anthropic.

**Mechanism:** Buyer opens chat on the pricing or contact page. Agent asks about team size, use case, security and compliance needs, and reads product context to recommend a plan. Small deals route straight to self-serve checkout. Larger or more complex deals get handed to a human rep with the full conversation transcript attached. Prospect can opt into talking to a human at any point. The agent also runs inside the product and inside email replies. Replaces: the lead-form-to-SDR-first-touch loop that normally takes 24–72 hours and loses most of the context in a CRM note.

**Why agentic:** It's not a chatbot that FAQs and hands off; it reads product/pricing context, makes a plan recommendation that qualifies the buyer, and either closes autonomously or packages the qualified context for a human. The "goal, not a long rule list" prompt architecture is what makes it an agent rather than a decision tree.

**Generalizable core:** inbound buyer intent arrives via any channel → agent qualifies and recommends → self-serve path OR human handoff with full conversation context attached.

**Deployability:** Stack is Claude Managed Agents (beta) + whatever the checkout/CRM is + the website chat widget. Complexity: week-build if you have clean pricing logic and a documented plan-fit heuristic; month-build if your pricing involves bespoke negotiation. Replaces/augments: the first SDR touch and the "form → notification → wait" loop. Scale caveat: Anthropic sees tens of thousands of inbound inquiries/month, so the pattern earns its keep at volume — a 10-leads/week business should weight the human-touch tradeoff differently.

### 3. Narrow-adapter bug triage harness with an evidence artifact folder

**Source:** [How I Built a Custom AI Harness with the Claude Agent SDK for Bug Triage](https://www.chatprd.ai/how-i-ai/how-i-built-a-custom-ai-harness) — Claire Vo at ChatPRD. Also discussed on How I AI with a live build.

**Mechanism:** Sentry alert fires → harness (terminal app on the Claude Agent SDK) runs → narrow, hand-written adapters pull exactly what's needed from Sentry (one trace), Linear (related tickets), GitHub (recent commits), and Vercel (deploy state). Each run writes an artifact folder containing the raw evidence pulled, the agent's reasoning trace, and the final triage decision. Output: a Linear ticket with structured classification (bug / dupe / noise), severity, suspected commit, and the evidence folder linked. Replaces: a PM/engineer's 20–40 minutes of context-gathering per Sentry alert before deciding what to do with it.

**Why agentic:** Reads live data from four systems, makes a judgment call that routes the alert, and produces a ticket with structured fields. Dashboards don't make routing decisions — this does.

**Generalizable core:** incoming incident/alert → narrow-scope adapters pull only what's needed from each source system → evidence artifact preserved per run → agent produces a classified, structured ticket for human follow-up.

**Deployability:** Stack is Claude Agent SDK + custom TypeScript adapters per external system + a scratch folder on disk. Complexity: week-build. Replaces/augments: the triage portion of an on-call rotation or a QA lead's inbox. Notable design choice: Vo deliberately avoided Sentry's broad MCP server in favor of narrow adapters that pull only what matters — the lesson is that agent reliability often comes from constraining tool scope, not expanding it. Codex generated the scaffold; Claude Agent SDK runs it. Portable to any alert-triggered triage problem (support tickets, lead qualification, compliance flags).

### 4. Reviewer-selection agent for agent-opened PRs

**Source:** [How we built an automated debugging workflow at Sentry](https://blog.sentry.io/automated-debugging-workflow-sentry/). Sentry's own engineering team describes running Seer (their autofix agent) across many projects, then using a scheduled Claude routine to pick a human reviewer for each PR Seer opens.

**Mechanism:** Seer opens a PR autonomously. Slack notification fires in the channel. A scheduled Claude routine runs, reads the PR diff, the team's recent commit history in that area, current OOO/availability, and who last touched the affected files. It picks a reviewer and @-mentions them in the PR. Replaces: the "who should review this?" tax that normally lands on an engineering manager or a rotating CODEOWNERS dartboard.

**Why agentic:** The routine reads live context (diff + ownership + availability) and takes an action (assignment + notification). A static CODEOWNERS file does the first part statically and none of the rest.

**Generalizable core:** autonomous work product lands (PR, draft contract, generated report) → reviewer-selection agent reads work + routing context (expertise, availability, prior ownership) → assigns to the right human with a one-click entry point.

**Deployability:** Stack is Claude + GitHub API + Slack + whatever has availability data (calendar, PTO tracker). Complexity: weekend-build. Replaces/augments: the implicit engineering-manager work of routing reviews. Portable to any domain where autonomous output needs the right human reviewer: AI-drafted legal memos to the right partner, AI-triaged support escalations to the right CSM, AI-generated proposals to the right AE.
