# 2026-07-19 — Agent Pattern Scan

## TL;DR
Four patterns qualified today, all with new mechanism vs. the last 14-day log. The most interesting is Mozilla's Firefox vuln pipeline, where the agent doesn't just read code — it writes and runs reproducible test cases in a sandbox to prove each hypothesis before filing, which cleaned up the false-positive problem that killed earlier read-only attempts. That "hypothesize → build a probe → run it → keep only what survives" loop is the reusable core, and it generalizes to any domain where an agent's suggestion is worthless until something executable confirms it.

Note on gap: the log was last updated 2026-05-28. This is the first run in ~7 weeks, so the patterns below draw from May–July source material rather than the last 24 hours.

## Patterns

### 1. Monitoring-webhook incident triage that drafts a PR
**Source:** [Sentry × Claude Code Routines cookbook](https://sentry.io/cookbook/performance-bot-sentry-claude/) and [Claude Code Routines launch](https://apito.ai/en/blog/dev-guides/claude-code-routines-cloud-automation-2026/) — Anthropic shipped scheduled/webhook-triggered Claude Code sessions April 14, 2026, and Sentry published a recipe for wiring them together.
**Mechanism:** Sentry error spike crosses a configured threshold → Sentry webhook POSTs a bearer-authenticated payload to the routine's `/fire` endpoint with the alert ID and stack trace → the routine pulls fresh events from Sentry MCP, groups them by fingerprint to collapse dupes, ranks clusters by event count and affected-user count → files one Linear ticket per cluster with stack snippet, affected release, and link back to Sentry → for the top-ranked cluster, correlates the stack trace with recent commits in the touched paths and opens a draft PR with a proposed fix, linking back to the Linear ticket and the Sentry issue. Replaces the on-call engineer's first 30 minutes of triage — the "which of these 40 errors are actually the same bug, which release introduced it, and what does the fix probably look like" grunt work.
**Why agentic:** It's a trigger-driven loop that reads live monitoring state, decides how to cluster, and writes to both an issue tracker and the source repo. A dashboard would show the errors sorted; this drafts the ticket and the PR.
**Generalizable core:** External-system alert crosses threshold → agent dedupes and clusters the noise → writes one work item per real problem → optionally attempts the fix and hands a human the diff to approve.
**Deployability:** Stack is Claude Code Routines + Sentry MCP + Linear MCP + GitHub. Weekend build for the alert-to-Linear path; a week for the draft-PR variant with a repo-specific system prompt. Replaces the first-pass work of an on-call engineer or SRE. Works for any team already on Sentry/Datadog/PagerDuty with a modern issue tracker; not for teams where "monitoring" is a shared email inbox.

### 2. Agent-authored reproducible test cases for security vulnerability discovery
**Source:** [Mozilla Hacks — Behind the scenes hardening Firefox with Claude Mythos Preview](https://hacks.mozilla.org/2026/05/behind-the-scenes-hardening-firefox/), reported in [The Decoder](https://the-decoder.com/mozillas-agentic-ai-pipeline-turns-claude-mythos-preview-loose-and-finds-271-unknown-firefox-vulnerabilities/) — Mozilla and Anthropic used the pipeline to find 271 previously unknown vulns across Firefox 150, contributing to 423 total resolved in April, including a 15-year-old HTML label bug and a 20-year XSLT bug.
**Mechanism:** Scheduled sweep (moving toward per-commit) → agent reads a slice of the Firefox source plus prior CVE and fuzz-corpus knowledge → generates a hypothesis about a possible vulnerability → writes a reproducible test case (fuzz input, DOM sequence, XSLT payload) and runs it in a Firefox sandbox → if the test triggers the failure mode, files a bug with the repro attached; if not, discards silently. The read-and-run loop is the whole trick — earlier read-only versions with GPT-4 and Sonnet 3.5 drowned in false positives. Mozilla is moving to gate every new commit through the pipeline.
**Why agentic:** The agent isn't summarizing code; it's iteratively proposing experiments, executing them, keeping the survivors, and only then producing an output. A dashboard couldn't do this — the signal only exists after the agent runs its own probe.
**Generalizable core:** Any domain where claims are cheap and verification is executable — write the probe, run it, only report what the probe confirmed.
**Deployability:** Non-trivial. Needs a sandbox that can execute whatever the agent generates (Firefox instance, container, database, etc.), an artifact store per run, and a strong harness. Month-plus build. Replaces a portion of a security researcher or QA engineer's exploratory work. Requires a domain where "run the test" is possible and cheap — code, SQL, config, CAD, financial models, not "review this contract." The generalized version (agent writes and runs a probe before filing a finding) is what to steal even without Mozilla's scale.

### 3. Nightly case-file audit that chains into next-best-action agents
**Source:** [Eve Auditor](https://www.eve.legal/use-cases/ai-auditor-for-plaintiff-law) and [EveOS launch, June 2026](https://www.lawnext.com/2026/06/eve-builds-on-ai-workforce-launch-with-eveos-an-ai-native-operational-platform-for-plaintiff-firms.html) — 1,200+ plaintiff firms, reporting ~30% higher settlement values and 20+ hours per attorney per week.
**Mechanism:** Nightly cron → Auditor connects to the firm's DMS (Filevine, Litify, SmartAdvocate) → reads every active matter's documents that arrived that day, plus the matter's running state → surfaces undiagnosed TBIs, missed MRIs, treatment gaps, missing records, mass-tort eligibility, and other valuation drivers → produces one prioritized queue per case manager with a recommended next action for each matter → hands the findings to downstream EveOS agents that then execute routine outbound work: treatment check-ins to providers, records-request follow-ups, claim openings with carriers, client status updates. Attorney sees only exceptions and finished work products.
**Why agentic:** It's not a report. Each finding is a typed instruction that triggers a specific downstream agent action; the human sees the case queue and the drafted outreach, not a dashboard of "cases with issues."
**Generalizable core:** Overnight scheduled sweep over a system-of-record → agent finds items needing attention → each finding routes to a specialized doer-agent whose default output is a completed piece of work waiting for approval. Variation on 5/23's Kim Howard overnight scouting, with a materially different angle: internal case files rather than external listings, and the finding *triggers action* instead of *producing a list*.
**Deployability:** Off-the-shelf if you're a plaintiff firm on Filevine/Litify. The generalizable version for other verticals is a Claude Managed Agents build with a DMS/CRM connector, a domain-specific "what should we flag" prompt library, and typed handoffs to 3–5 specialized action agents. Two-to-four week build per vertical. Replaces the paralegal file-audit and the "ping the client / chase the records" clerical loop. Works for any records-heavy vertical with a defined valuation model (insurance claims, medical billing, tax prep, M&A diligence, healthcare RCM).

### 4. Par-level threshold triggers a draft PO that a chef one-taps in Slack
**Source:** [Meuze Core](https://www.meuze.ai/platform) — AI back-office agents for multi-location restaurant groups, currently deployed across mid-sized restaurant groups per company materials.
**Mechanism:** Continuous read of POS sales, current inventory counts, prep schedule, and vendor lead times → when a SKU's projected coverage crosses reorder threshold, agent drafts a purchase order with the quantity that gets the location back to par without overshooting → posts the draft PO to the location's Slack channel as a message the chef can approve with a single tap → on approval, agent sends the PO to the vendor via email or portal and logs it back into inventory. In parallel: end-of-day, agent generates and queues tomorrow's prep brief for each GM — what to prep, in what quantity, based on forecast.
**Why agentic:** The output isn't a "you're low on onions" alert; it's a specific pre-computed order waiting for a yes. The chef never opens the inventory system. The agent is the buyer; the human is the approver.
**Generalizable core:** Threshold crossed on a rolling metric → agent assembles the specific corrective action pre-filled → posts it to the responsible human's default channel as a one-tap decision → executes and logs on approval. Approve-in-Slack replaces "click into the system to see the alert."
**Deployability:** Off-the-shelf for restaurant groups on Toast/Square + a modern inventory system. The generalizable pattern is straightforward on n8n or Zapier Agents for any SMB with a threshold-driven purchase or reorder decision: coffee roasters, dental supplies, salon retail, HVAC parts, print shops. Weekend build for a single-SKU version, week for the multi-vendor variant. Replaces a purchasing manager or the "owner does it Sunday night" ritual.
